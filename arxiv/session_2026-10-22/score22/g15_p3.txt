Abstract.
Diffusion transformers are widely used in image-editing services.
To preserve both efficiency and privacy, existing systems commonly rely on cloud–device collaboration.
Keeping request-specific inference on the device avoids sending personal images and prompts to the cloud.
These workloads often use common templates, such as in face swapping and virtual try-on, enabling KV state to be precomputed and reused across requests.
However, this reusable state is large and scales with the number of templates, making it impractical to store all of them on mobile devices.
Storing them in the cloud addresses this capacity issue, but cache transfer is placed onto the inference path and can even be slower than on-device computation, especially under fluctuating mobile networks.
We introduce SAKURA, a cloud–edge architecture that delivers reusable attention state to mobile devices under a bandwidth budget.
It first uses a fine-grained token-importance-aware compression method to preserve image quality under limited transfer budgets.
At runtime, SAKURA adaptively selects the cache representation for each upcoming shard based on network bandwidth.
To enable efficient execution, we develop a pipelined runtime that overlaps cache transfer and reconstruction with on-device execution.
We evaluate SAKURA using three editing tasks and two diffusion models, using a Snapdragon 8 Elite Gen 5 phone.
SAKURA reduces latency by 1.82 $\times$ and 3.27 $\times$ over CacheGen adapted to DiT and on-device generation, respectively.
It also reduces cache storage by 3.06 $\times$ over uncompressed cache, while preserving image quality.
## 1. Introduction
Diffusion transformers (DiTs) have become a leading architecture for
high-fidelity image generation and editing
(Peebles and Xie, 2023; Esser et al., 2024; Chen et al., 2024b; Black Forest Labs, 2026). A widely deployed class of editing
applications personalizes only part of a provider-supplied image
while preserving the surrounding content. Virtual try-on (Kim et al., 2024; Wan et al., 2026; Zhao and Peng, 2026), face swapping
(Baliah et al., 2025; Yu et al., 2025; He et al., 2026), and localized image editing
(Jiang et al., 2026; Mao et al., 2024; Simsar et al., 2024) are representative examples.
Personalized editing is already offered by cloud services,
such as Google Shopping’s photo-conditioned virtual try-on and Amazon Nova
Canvas’s managed virtual try-on API
(Google, 2025; Amazon Web Services, 2025; Alibaba Group, 2026; Alibaba Cloud, 2026). These applications take
two kinds of different inputs: provider-owned templates can be
public and reused across users, whereas each request contains
privacy-sensitive user data such as personal photographs, reference images,
and editing instructions. Keeping request-specific inference on the device is
therefore attractive because these inputs and the intermediate states derived
from them need not be sent to a remote execution service. Recent advances in model compression, architecture optimization, and
heterogeneous mobile execution have made on-device diffusion inference
increasingly practical
(Li et al., 2023; Zhao et al., 2024; Chen et al., 2025).
When requests share a template and a fixed mask defining the
editable region, computation associated with the unchanged region can be
reused across requests. In a DiT,
the key/value (KV) state of these reusable tokens can
be precomputed for each template
and reused while the device computes only
the request-dependent state for the edited region
(Jiang et al., 2026; Li et al., 2026; Yu et al., 2024; Qin et al., 2025). Cross-request reuse can therefore substantially
reduce repeated on-device computation. Every template has a different reusable state and the aggregate footprint grows with the number of templates.
This creates a mobile-specific scalability gap between execution capacity and reuse capacity: a device may have enough compute and working memory to run each edit, yet lack the storage to retain caches across a large template catalog.
In our FLUX.2-klein-4B deployment (Black Forest Labs, 2026) at $512\times 512$ resolution, the reusable FP16 KV state occupies up to 1.46 GiB for a single template. A catalog with hundreds of templates would therefore require hundreds of gigabytes of persistent storage, far beyond what is practical to replicate on individual mobile devices.
Cloud-only execution avoids this storage constraint but requires sending private user requests to the
server.
We instead consider a different cloud–edge split: request-specific
inference remains on the device, while the cloud stores the much larger,
provider-owned reusable templates and supplies the required cache on demand.
Unlike conventional cloud–edge inference, which
offloads all or part of a request to remote compute (Han et al., 2016; Kang et al., 2017; Yan et al., 2024), this scheme uses the cloud for template storage.
The network carries reusable template state,
while user inputs and request-specific activations remain on the device.
Moving reusable state to the cloud resolves the device-side capacity problem,
but places cache transfer on the inference path. At the 545 Mbps median
bandwidth of the 5G trace used in our evaluation (Narayanan et al., 2020), transferring
the full FP16 cache takes approximately 23 s, even without device-side cache
reconstruction. In comparison, executing the complete model locally without
cache reuse takes about 13 s on our mobile platform. Naively fetching
the full cache is therefore slower than running the complete model locally.
Remote reuse must both reduce the transmitted bytes and hide cache transfer
behind local computation.
These requirements translate into two challenges. First, the cache must be
compressed aggressively enough to arrive before use while preserving editing
quality. At an approximately 10% mask ratio, only 2.3 s of local computation
is available in total to hide cache transfer; even uniform 2-bit quantization
requires at least 650 Mbps, above the median 5G bandwidth.
Moreover, reusable cache compression must be constructed offline, before
future edit requests are known. This is challenging because the importance of cached tokens depends on the request-specific query generated by the edited region.
Therefore, compression must determine which tokens to preserve without knowing the future request.
Second, cache transfer must adapt as mobile bandwidth changes during an edit.
A representation chosen early in execution may become too large when bandwidth
drops or unnecessarily compressed when bandwidth improves, requiring transfer
decisions to be revised as later cache state is consumed.
Token-importance-aware cache compression.
Our first key idea is to make request-dependent token importance usable for offline reusable cache compression.
Although the exact attention scores depend on the specific request, We observe that, for a fixed template and mask, the reusable tokens that matter most remain largely consistent across different edit requests at the same transformer block and denoising
step.
This consistency allows importance measured from representative requests offline (i.e., through profiling) to guide compression for future requests.
Accordingly, compression can preseve cached tokens that are consistently important with higher accuracy.
Bandwidth-adaptive streaming.
Our second key idea is to make cache transfer
decisions at fine granularity based on the network conditions.
Each shard contains the reusable state for a group of consecutive transformer blocks at one denoising step.
SAKURA can adjust its transfer decision before each shard is needed.
It combines recent network measurements with device execution progress to determine how much cache data can arrive in time, then selects the highest-quality available representation that fits this budget.
If an earlier transfer finishes ahead of use, the resulting lead time is carried forward to later shards.
This allows cache transfer to track bandwidth changes within an edit instead of turning them into execution
stalls.
We present SAKURA, a cloud–edge cache streaming system
that realizes these ideas through complementary offline and online
decisions. Offline, SAKURA uses transferable token importance to construct
an importance-weighted low-rank factorization, preserving high-impact tokens’
KV state more accurately under aggressive compression. The compressed cache can vary along two dimensions: how much low-dimensional
structure is retained and how precisely it is encoded. These choices are
organized into a nested representation, allowing multiple compression levels
to share the same offline-constructed cache and enabling runtime adaptation
without repeating compression.
Online, SAKURA adaptively selects the representation of each upcoming cache shard based on current network conditions and device execution progress, ensuring that the shard can be transferred before it is needed for computation.
To enable efficient mobile execution, we develop a heterogeneous mobile runtime that pipelines cache
reception on the CPU, reconstruction on the GPU, and model execution on the NPU, overlapping the communication and reconstruction behind on-device computation.
This paper makes the following contributions:
• 
To the best of our knowledge, we present the first cloud–edge system that enables DiT cache reuse for mobile image editing, where reusable template cache states are stored in the cloud and streamed to the device upon request.
• 
We design a token-importance-aware cache compression scheme that exploits the stability of importance of the cache state across requests.
We also design a cache representation that supports fine-grained adaptation across precision levels without storing a separate version for each level.
• 
We develop an adaptive runtime that adjusts cache transfer to bandwidth fluctuations and overlaps cache transfer and reconstruction with on-device diffusion computation.
• 
We evaluate SAKURA on three editing tasks and two diffusion models using both 5G traces and WiFi.
On a Snapdragon 8 Elite Gen 5 phone, SAKURA reduces generation latency by 1.82 $\times$ and 3.27 $\times$ compared with CacheGen (Liu et al., 2024a) adapted to DiT and on-device generation, respectively.
It also reduces cache storage by 3.06 $\times$ compared with uncompressed caching while preserving image quality.
## 2. Background and Motivation
## 2.1. Cross-Request KV Reuse for Image Editing
Diffusion transformers (DiTs) generate images through multiple denoising steps, each executing the same stack of transformer blocks. Within each block, token-wise operators process tokens independently, while self-attention aggregates global context through Query (Q), Key (K), and Value (V) representations (Sun et al., 2026; Vaswani et al., 2023).
Masked image editing modifies only a target region while leaving the rest of a
template unchanged, creating substantial cross-request reuse opportunities
(Jiang et al., 2026; Li et al., 2026; Yu et al., 2024; Qin et al., 2025). As illustrated in
Figure 1, token-wise operators only need to process
tokens inside the editable mask. For self-attention, the model computes Q, K,
and V for these masked-region tokens, combines their K and V with cached K and
V from the unchanged template tokens, and evaluates attention only for queries
from the masked region.
Such localized editing is common in applications including virtual try-on (Kim et al., 2024; Wan et al., 2026; Zhao and Peng, 2026), face swapping (Version Systems Private Limited, 2026; Canva, nd), and inpainting (Xie et al., 2025a; Manukyan et al., 2024).
This reuse enables sparse request-time execution, but requires a large reusable cache. Because the hidden states of unchanged tokens differ across denoising steps and DiT blocks, skipping their computation requires preserving the corresponding K and V tensors for every step and every block. Thus, each template effectively maintains reusable KV state indexed by (denoising step, DiT block). For example, caching this state for a single $512\times 512$ template in a lightweight 4B FLUX2 model (Black Forest Labs, 2026) requires 1.46 GiB, and the footprint grows with the template library.
Recent mobile diffusion systems demonstrate that modern mobile devices have
sufficient compute capability for on-device diffusion inference
(Feng et al., 2026; Li et al., 2023; Zhao et al., 2024).
However, this improvement in compute capability does not eliminate the storage
cost of maintaining a large library of per-template KV caches locally.
At the same time, keeping request-time inference local avoids transmitting privacy-sensitive user inputs and request-derived intermediate states to the cloud (Sun et al., 2021; Nayan et al., 2024). This creates a mismatch between compute capacity and reuse-state capacity: the device can execute the sparse request-specific computation, but cannot retain all reusable state needed to enable it. Supporting cross-request reuse at scale therefore requires separating request-time computation from reusable-state storage.

## 2.2. Cloud–Edge Placement of Reusable State
The mismatch motivates a cloud–edge separation of computation and reusable state. As shown in Figure 1, the edge performs all request-specific inference, while the cloud stores the reusable per-template KV library and supplies the required entries on demand. This organization exploits the different roles of the two components: request-specific computation remains local, while reusable state, whose aggregate footprint grows with the template library, is placed in a remote tier with large capacity.
This setup differs from conventional cloud–edge inference, where the cloud primarily serves as an execution resource. Prior systems either offload an entire request or partition model execution across the device and server (Han et al., 2016; Kang et al., 2017), with intermediate activations or generation stages crossing the network (Kang et al., 2017; Yan et al., 2024; Xie et al., 2025b; Wei et al., 2025). In contrast, the cloud in our system acts as a remote storage for state: computation does not migrate across the network; only reusable KV state is transferred to the device.
This separation solves the device-side storage problem, but shifts the bottleneck to cache transfer. On our mobile platform, full-model execution without reuse takes 13 s, whereas transferring the full FP16 cache over the 545 Mb/s median throughput of our 5G trace (Narayanan et al., 2020) takes approximately 23 s. Naively fetching the full cache is therefore slower than local recomputation. Making remote reuse practical requires both reducing this transfer overhead and ensuring that the required cache state reaches the device in time for execution. We next examine the system challenges behind these requirements.
## 3. Challenges and High-Level Ideas
In this section, we describe two key challenges in enabling streaming KV acache for on-device diffusion editing and then introduce our high-level ideas.
## 3.1. Quality-Efficient Cache Representation
Due to limited mobile network bandwidth, only a limited cache size can be transferred before the reusable cache is consumed in the diffusion edit process.
As such, the cache compression must be quality-efficient: for a given cache size, it should preserve the reusable information that contributes most to output quality.
Using the same FLUX2 example in §2, execution with cache reuse has a median aggregate transfer window of only 2.3 s at a 10% mask ratio.
Even an aggressive 2-bit quantization still requires 650 Mbps of bandwidth, while leaving the quality non-ideal (results in §6.3).
This motivates selectively preserving the cached information with high image quality impact under a fixed transfer budget.
Cross-request DiT reuse introduces a new token importance problem.
Prior work has shown that token importance can reduce KV or computation.
LLM systems exploit this for request-time retention, eviction, or fetching (Zhang et al., 2023b; Li et al., 2024b; Lee et al., 2024), while DiT serving systems use such signals for token routing, merging, pruning, or reuse within a denoising process (You et al., 2025; Wu et al., 2025; Gupta et al., 2025).
These approaches determine important tokens based on the ongoing request.
Cross-request DiT reuse is a new challenge: a reusable cache is constructed once for a template and must serve future unknown edit requests. 
Consequently, token-importance-aware compression cannot simply reuse important tokens measured
from the current request. Instead, it requires a template-level signal that remains
valid across future edit requests.
This raises two questions: (1) whether some reusable cache tokens matter more than others to the final edit,
and (2) whether the same tokens remain important across different edit requests.

High-level idea.
These observations suggest that reusable DiT KV caches should not be compressed
uniformly. Because token importance is both highly skewed and predictable
before future requests arrive, offline cache construction can use this
importance to preferentially preserve the information carried by high-impact
tokens while allowing larger approximation error on less influential ones.
The key is to incorporate token importance into the cache representation,
while storing the cache representation in a way that can be efficiently transferred and reconstructed later online. §4.2
develops this idea using low-rank compression as an additional compression dimension beyond numerical precision.

## 3.2. Bandwidth-Adaptive DiT Cache Transfer
Even with an efficient cache representation, the cache transfer process still needs to be aware of mobile network bandwidth.
Network conditions can change as a reusable DiT cache is consumed gradually throughout execution.
Therefore, compression and transfer decisions must adapt to the granularity of DiT execution.
Mobile bandwidth changes within the DiT execution window.
For requests with a 10% mask ratio, on-device DiT execution takes 2.26 s.
To quantify the resulting transfer pressure, we examine the same duration windows
from a 5G trace (Narayanan et al., 2020) and compute the compression ratio
required to transfer the uncompressed FP16 cache within each window.
Figure 3(a) shows that the median window requires
 $9.3\times$ compression, while the slowest 10% requires $53.8\times$ .
Figure 3(b) shows the corresponding throughput
variation over time.
Importantly, these variations occur on the same time scale as local DiT
execution. As a result, the bandwidth when an early cache shard is
transferred can differ substantially from that for later shards in
the same request.
Consequently, cache compression and transfer must be adjustable throughout execution, rather than determined once.
Token-level KV transfer does not match DiT cache consumption.
Existing KV-transfer systems primarily target LLM context reuse or server-side
KV movement (Liu et al., 2024a; Mi et al., 2026; Liu et al., 2026; Cheng et al., 2025). For example, CacheGen (Liu et al., 2024a) partitions the cached context along the token dimension and
selects a transfer configuration for each token chunk. Each decision
covers the KV associated with that token chunk across multiple transformer
layers.
DiT consumes reusable KV differently. During an edit, the model advances
through transformer blocks and denoising steps, and the KV for each block is
needed only when execution reaches that block.
Hence, token-level transfer granularity used by LLM systems does not align with DiT execution, as KV associated with the same token chunk is consumed at different transformer blocks and denoising steps.
For example, a cache shard needed by an early block must be transferred immediately, while one used by a later block can continue to adapt to subsequent bandwidth changes.
Using the same token-level granularity couples cache data needed at different times, which can either over-compress some shards or delay others.
We instead use block-grained cache shards as the unit of transfer adaptation.
This aligns transfer decisions with cache consumption, allowing successive shards to exploit additional transfer time and adapt to subsequent bandwidth changes.
High-level idea.
Cache transfer adaptation should follow the consumption granularity of DiT execution.
Rather than fixing a transfer configuration for an entire request, the system can adjust cache transfer as successive shards are consumed by the on-device diffusion process.
This allows later shards to respond to changing mobile bandwidth while avoiding unnecessary quality degradation or transfer stalls.
## 3.3. Summary of High-Level Ideas
These challenges suggest two complementary mechanisms: construct a quality-efficient reusable cache offline, and adapt its transfer online as
network and execution conditions change. We next describe how SAKURA realizes these mechanisms in a cloud–edge system.

## 4.1. Overview
Figure 4 gives an overview of SAKURA.
The design separates reusable cache construction from request-time transfer
and execution. Offline, SAKURA builds two server-side artifacts for each template.
First, it uses profiled token importance to construct a compact low-rank KV
cache and stores its coefficient and basis matrices in a progressive layout,
so the same cache can serve multiple compression levels. Second, it profiles
a set of rank–precision trade-off points so later the runtime can select
the best configuration for image quality. Online, request-specific inference remains on the mobile device.
For each upcoming cache shard, the runtime monitor tracks recent network
bandwidth and device execution progress. The transfer-window controller uses
this information to determine how much cache can be transferred before the
shard is consumed, carrying forward unused transfer time from earlier shards.
The configuration allocator then selects the best-quality configuration from the
progressive cache pack and streams it to the device.
On the mobile device, cache reception, KV reconstruction, and shard execution
are pipelined across the CPU, GPU, and NPU, respectively, allowing cache
transfer and reconstruction to overlap model execution.

## 4.2. Offline Token-Importance-Aware Cache Construction
Even aggressive quantization of the full KV tensor can exceed the transfer
budgets as shown in Figure 3(a). We therefore first use low-rank
factorization to reduce the number of values that must be stored and
transmitted, and then quantize the resulting factors.
For each transformer block and denoising step, we treat its reusable K or V
matrix $X_{c}\in\mathbb{R}^{N\times D}$ as one cache unit, with one row
per reusable token. We compress each cache unit with a rank- $r$ approximation,
representing all token rows using $r$ shared components. Specifically, we use
truncated singular value decomposition (SVD)
 (Eckart and Young, 1936; Golub and Reinsch, 1970), which minimizes squared
reconstruction error for a given rank:
(1)
 $X_{c}\approx A_{c}B_{c}+\mathbf{1}\mu_{c}^{\top},$ 
where $\mu_{c}$ is the row mean,
 $A_{c}\in\mathbb{R}^{N\times r}$ contains the coefficients for each token, and
 $B_{c}\in\mathbb{R}^{r\times D}$ contains the shared basis vectors.
When $r\ll D$ , storing and transmitting $A_{c}$ and $B_{c}$ requires substantially
fewer values than the original $N\times D$ cache.
Low-rank factorization also makes the cache naturally progressive. SVD orders
components from larger to smaller contribution to cache reconstruction, so
transmitting additional components incrementally improves the approximation.
A smaller cache can therefore be obtained simply by stopping after fewer
components, without constructing a separate encoding for each rank.
Quantizing $A_{c}$ and $B_{c}$ provides a second way to vary the transmitted size.
Plain SVD, however, minimizes reconstruction error over all cache rows
uniformly. §3.1 shows that reusable DiT tokens do not
contribute equally to the final edit, and that their relative importance can
be estimated offline. We therefore incorporate these importance scores when
constructing the low-rank factors. Rather than assigning a different rank to
each token—which would create variable-length coefficients and irregular
reconstruction—SAKURA keeps one shared low-rank representation for the
entire cache unit and biases its construction toward accurately reconstructing
high-impact rows. This preserves a regular dense representation while making
the limited rank more useful for downstream editing.
## 4.2.1. From masked queries to cache-row weights.
The top half of Figure 5 shows how SAKURA turns the
importance signal from §3.1 into construction-time
row weights. For each cache unit, SAKURA measures how strongly masked-region
queries attend to each reusable template token. Following attention-aware KV
distortion metrics (Li et al., 2024b; Zhang et al., 2024; Laus et al., 2026), it squares and aggregates
attention across queries and heads, so tokens that consistently receive
stronger attention obtain larger importance scores. In
Figure 5, for example, the second reusable token receives
the largest score because both masked queries attend strongly to it.
SAKURA normalizes the token-importance scores and uses an exponent $q$ to
control how strongly they influence the factorization. With $q=0$ , all rows
are treated equally and the method reduces to ordinary SVD; increasing $q$ 
places progressively more emphasis on high-importance tokens. The resulting
weights are used only during offline construction and are not stored or
transmitted with the cache. We evaluate the effect of different $q$ values in §6.5.
## 4.2.2. Weighted low-rank factorization.
The bottom half of Figure 5 shows how these weights affect
the low-rank representation. SAKURA first subtracts the cache mean and
scales each row by the square root of its importance weight before applying
truncated SVD. This is equivalent to minimizing a weighted reconstruction
error in which errors on high-importance rows contribute more strongly
 (Srebro and Jaakkola, 2003; Manton et al., 2003). The leading components
therefore devote more of the limited rank to preserving information carried
by important tokens.
After factorization, SAKURA folds the inverse row scaling into the
coefficient matrix $A_{c}$ . The resulting representation has the same regular
form as ordinary low-rank factorization: a coefficient matrix $A_{c}$ , a shared
basis $B_{c}$ , and a mean vector $\mu_{c}$ . Thus, $q$ and the token weights affect
how the factors are constructed, but do not change the stored cache format.
The mobile device receives no importance weights and performs no
token-specific reconstruction; every cache unit is reconstructed using the
same dense matrix multiplication.
## 4.2.3. Progressive rank and bit-plane packing.
Finally, as Figure 5 shows, SAKURA quantizes $A_{c}$ and
 $B_{c}$ independently, using $b_{A}$ and $b_{B}$ bits. Their rank components remain
ordered by weighted singular contribution. This layout is what enables the
progressive representation in Figure 6: instead
of storing a separately encoded cache for every $(r,b_{A},b_{B})$ configuration, SAKURA stores the ordered factors once and later selects rank and
precision prefixes to match the available cache transfer budget.

## 4.3. Online Adaptive Cache Streaming
The offline phase leaves the server with the progressive cache pack described
above. At runtime, SAKURA determines how much of this pack to transmit for
each cache shard as network and device conditions change.
SAKURA operates at shard granularity. A shard groups consecutive
transformer blocks executed together on the NPU, and the reusable KV state
consumed by one shard at one denoising step forms a cache shard. Because
shards are consumed sequentially, later decisions can incorporate
measurements from earlier transfers in the same edit.
Figure 7 summarizes the online path. A runtime monitor
tracks network and device progress, a transfer-window controller determines
how long each upcoming shard can be transferred before use, and a
configuration allocator selects the corresponding prefix from the progressive
cache pack.
## 4.3.1. Runtime monitor.
The runtime monitor tracks the recent cache transfer rate and the arrival of
each cache shard. The device reports the bytes received and active receive
time, from which SAKURA estimates the effective transfer rate $\hat{R}$ .
The monitor also records when each shard cache arrives relative to when it
is needed. If a shard arrives early, the remaining time is recorded as
carry-over $H_{p}$ and exposed to the transfer-window controller for the next
shard. Measurements are refreshed after every shard so that later decisions
reflect both recent network conditions and accumulated transfer lead.
## 4.3.2. Transfer-window controller.
SAKURA adapts cache transfer to bandwidth: when bandwidth is high, it sends a
higher-quality cache representation, while under lower bandwidth it sends less
cache so that the transfer still completes before the shard is needed.
For an upcoming cache shard $p$ , let $T_{p}^{\mathrm{ovlp}}$ denote the
remaining device-execution time over which its transfer can be hidden, and let
 $H_{p-1}$ denote the carry-over time from the previous shard. The
controller sets the transmission window for shard $p$ to
 $\gamma\left(T_{p}^{\mathrm{ovlp}}+H_{p-1}\right)$ , where $\gamma<1$ provides
a safety margin against short-term bandwidth drops. Rather than predicting
future bandwidth, SAKURA uses the recently observed transfer rate together
with this conservatively sized window.
## 4.3.3. Configuration allocator.
A byte budget alone does not determine how it should be divided between rank
and numerical precision. Figure 8 illustrates this
tradeoff. Under tight budgets, lower-precision factors can leave room for more
rank, whereas larger budgets increasingly favor higher precision. As a result,
no single rank–precision configuration dominates across all transfer budgets.

bitwidths $(b_{A},b_{B})$ and retain only their nondominated configurations,
forming a small frontier $\mathcal{P}$ . Given the current transfer rate and
transmission window, the allocator selects the configuration with the highest
profiled masked PSNR whose encoded shard fits:

or re-encoding onto the request’s critical path.

## 4.4. Online Pipelined Mobile Execution
As shown in Figure 9, SAKURA overlaps cache transfer,
reconstruction, and DiT execution across the CPU, GPU, and NPU.
After a short start-up phase, while the NPU executes shard $j$ , the CPU
receives cache data for shard $j+1$ and the GPU reconstructs its KV tensors.
The reconstructed cache is buffered until the NPU reaches the next shard,
allowing the three stages to proceed concurrently instead of serializing on
each shard.
This pipeline hides most communication and reconstruction behind NPU
computation and avoids the NPU stalls incurred by the naïve
prepare-then-execute design.
## 5. Implementation
SAKURA’s implementation focuses on Qualcomm platforms, which are widely used in smartphones. However, the design is generally applicable to other mobile platforms.
The server uses PyTorch and ExecuTorch (PyTorch Team, 2024) Qualcomm backend with an HTP v81 libso to compile the diffusion models for the mobile platform.
It first downloads the model from Huggingface then uses their diffusers pipelines, quantizes it to W8A16, and shards it by transformer block count so that each shard is one compiled graph; the
same block groups define the cache units in §4.3. Cache
capture follows FlashPS (Jiang et al., 2026): we reuse its mask-aware
formulation of which KV state a template contributes, and store the result as
the per-unit packs in §4.2.3.
The mobile device runtime implements the heterogeneous pipeline of
§4.4 across all three engines in C++.
The CPU maintains the network transfer and the cache state machine: it requests the next shard cache, parses arriving
packets, and tracks which units are received, reconstructed, and released. The
GPU dequantizes and reconstructs those units with OpenCL kernels. The NPU
executes the compiled shards through the ExecuTorch
runtime (PyTorch Team, 2024). The three stages execute concurrently on separate shards, allowing each segment
to be received, reconstructed, and consumed in a pipeline without serializing
device execution on any single stage.

Figure 11. An example showing FLUX2 latency under VTON workload during a 60-second network trace.
Example trace.
We first demonstrate the latency under a time-varying mobile network.
Figure 11 shows FLUX2 + VTON serving under a 60-second 5G trace.
The network bandwidth changes substantially over
the trace, causing the fixed-compression baselines to exhibit large latency
variation. In particular, INTQ and CacheGen slow down
noticeably around at 30 s and 50 s, when their fixed cache representations
are too large for the available bandwidth.
In contrast, SAKURA adapts the transmitted cache representation as bandwidth

Figure 12. Generation latency under 5G trace.
Figure 13. Per-template cache storage on server.
Generation latency.
Figure 12 shows that SAKURA achieves the lowest median and tail latency on all four workloads, reducing p90 latency by 44% on average over INTQ and by 42% on average over CacheGen.
INTQ remains competitive at the median, but its tail degrades sharply because its larger cache transfers make it more sensitive to bandwidth fluctuations.
CacheGen also exhibits substantially higher tail latency on the FLUX workloads because its coarse-grained transfer delays cache reconstruction and limits communication–computation overlap.
SAKURA mitigates both issues through fine-grained, execution-aware cache transfer.
We also compare with local generation without cache reuse. The median latency of SAKURA is 2.1–4.1 $\times$ lower.
Compared to FLUX2 workloads, MB-SD has a relatively lower speedup of 2.1 $\times$ because SD3.5 is a lightweight model that has lower cost when running locally even without cache reuse.
Storage overhead.
Figure 13 compares the per-template cache size, where SAKURA has the lowest footprint for both models. The reduction comes from combining low-rank factorization with quantization, so a single compact representation supports multiple cache transfer budgets.
INTQ only reduces precision and has larger footprints.
CacheGen incurs the largest overhead, requiring 1.93 $\times$ and 2.81 $\times$ more storage than SAKURA for FLUX2 and SD3.5, respectively, because each quality level stores an independent quantized cache with no sharing across levels.
With quality levels, this overhead grows nearly linearly, whereas SAKURA reuses the same factorized representation across levels.

## 6.4. Sensitivity Studies
We evaluate the primary model, FLUX2, for sensitivity.

(1) Sensitivity to mask ratio.
Figure 16 shows that larger masks increase
latency for all methods, as more tokens are involved in DiT computation.
At the same time, larger masks reduce the cache size to be transferred and increase the
per-step compute window, increasing the fraction of cache that can be transferred.
As a result, compression becomes less aggressive and the quality gap between
systems narrows as the mask grows.
In contrast, smaller mask sizes combine the largest reusable cache with the shortest transfer window.
In such cases, SAKURA provides the highest quality improvements over INTQ and
CacheGen as its token-importance-aware representation makes better use of the
transfer budget.
Figure 17. Generation latency under different network traces.
(2) Sensitivity to bandwidth.
We evaluate two additional scenarios: a 4G+5G mixed trace that reflects lower network bandwidth and a WiFi scenario for a high-bandwidth connection.
Figure 17 presents these scenarios.
Under the 4G+5G mixed trace, SAKURA reduces p90 latency by 55–76% over INTQ and 47–62% over CacheGen across the four workloads.
Under WiFi, where network is not a bottleneck, the gap narrows: on the three FLUX workloads, SAKURA reduces p90 latency by up to 15% over INTQ and 38–44% over CacheGen.
These results show that SAKURA provides the largest benefit when bandwidth is scarce, while its fine-grained transfer still benefits faster networks.

(3) Sensitivity to multi-image-resolutions.
This experiment includes two other resolutions: $384\times 384$ and $768\times 768$ , in addition to the default $512\times 512$ .
Figure 18 shows that SAKURA scales robustly across resolutions, consistently achieving the lowest latency and the highest PSNR/SSIM.

Overall, SAKURA preserves its latency–quality advantage across all tested resolutions, demonstrating that its compression and streaming design scales effectively with larger DiT workloads.

## 7. Related Work
Diffusion cache reuse.
Prior work exploits substantial redundancy across diffusion denoising steps.
DeepCache and Faster Diffusion reuse intermediate U-Net features across nearby
steps, while Block Caching performs reuse at the granularity of individual
network blocks
(Ma et al., 2024; Li et al., 2024a; Wimbauer et al., 2024).
For diffusion transformers, FORA caches attention and MLP outputs,
 $\Delta$ -DiT reuses block residuals, ToCa selectively reuses features for less
important tokens, and TeaCache adapts reuse intervals based on timestep-dependent
changes
(Selvaraju et al., 2024; Chen et al., 2024a; Zou et al., 2025; Liu et al., 2025).
These methods primarily reduce computation within a single request by
exploiting temporal redundancy along the denoising trajectory.
Some prior work has considered reuse across requests.
For example, NIRVANA reuses
intermediate noise states from similar prompts (Agarwal et al., 2024), while FlashPS caches
template-dependent activations that can be shared across edits
(Jiang et al., 2026).
These systems assume server-side inference that directly reuses cached states on the server.
In contrast, SAKURA keeps request-specific processing on the mobile device while
streaming reusable template caches from the cloud.
KV cache compression and memory optimization.
KIVI and KVQuant compress KV caches through quantization
(Liu et al., 2024b; Hooper et al., 2024), while Palu stores low-dimensional
representations through factorized KV projections (Chang et al., 2025).
StreamingLLM, H2O, and SnapKV instead reduce the number of retained tokens
using recent-token, attention-importance, or observation-window-based
selection (Xiao et al., 2024; Zhang et al., 2023b; Li et al., 2024b). InfiniGen selectively
prefetches important KV entries when caches are offloaded to host memory
(Lee et al., 2024). For diffusion models, PTQ4DiT and ViDiT-Q reduce weight
and activation costs through timestep-aware quantization
(Wu et al., 2024; Zhao et al., 2025). In contrast, we factorize
precomputed template KV matrices offline and weight approximation
error using token importance shared across references of the same template.
Cache transfer optimization.
CacheGen compresses and streams reusable KV caches to LLM inference servers
with bandwidth-adaptive encoding (Liu et al., 2024a), while LMCache manages KV
movement across GPU, CPU, storage, and network tiers (Cheng et al., 2025).
KVServe selects compression profiles according to bandwidth, latency, and
quality constraints (Liu et al., 2026), and KVCodec pipelines GPU-native
video-codec compression with KV transfer and reconstruction (Mi et al., 2026).
LLM.265 similarly applies hardware video codecs to tensor compression
(Xu et al., 2025), building on the broader idea of scalable,
quality-adaptive transfer (Schwarz et al., 2007). Our setting differs in that
cache segments are streamed during on-device diffusion inference and must
arrive before the corresponding transformer blocks execute. Thus, transfer
decisions jointly depend on bandwidth and denoising execution progress.
## 8. Conclusion
In this work, we show that remote reuse of DiT template caches can make
on-device image editing practical without replicating large cache collections
on the device or offloading private request data to the cloud.
SAKURA combines token-importance-aware offline compression with fine-grained,
bandwidth-adaptive cache streaming and a pipelined mobile runtime, allowing
cache transfer to track both network conditions and device execution.
Our evaluation demonstrates that SAKURA simultaneously improves latency, storage efficiency, and output quality: it is 1.55–1.82 $\times$ faster and 1.54–2.37 $\times$ more storage-efficient than prior KV-streaming systems, while also outperforming fully local execution by 3.27 $\times$ and reducing full-FP16 cache storage by 3.06 $\times$ .
