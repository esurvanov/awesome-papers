## ABSTRACT
The widespread adoption of generative artificial intelligence in recent years has brought a parallel rise in prompt injection and jailbreak attacks. By embedding malicious instructions, these exploits manipulate language models to bypass intended behavior and operational boundaries. In traditional chatbots, such attacks are confined to a single session because state memory is not preserved across conversations. However, persistent memory features in modern conversational interfaces enable cross-session attack propagation, establishing a threat vector known as memory injection. This work explores this emerging vulnerability in leading LLM-as-a-service platforms, highlighting its real-world severity and the need for countermeasures. While existing literature focuses on violations tailored to specific platform features, we present a general threat model. We demonstrate that all NIST attack goals are collectively achievable across ChatGPT Instant 5.3, Claude Sonnet 4.6, and Gemini 3 Flash under this model. We also show that memory injections can exploit multiple attack vectors, including personal memories, projects, skills, organization instructions, and Model Context Protocol (MCP)-connected resources. Our findings reveal that all evaluated services can be manipulated to persistently spread disinformation, generate harmful content, or simulate offline unresponsiveness, even in fresh sessions. In the particular case of Claude, shared-memory features allow an attacker to compromise multiple users within an organization and also exfiltrate user prompts. To address these vulnerabilities, we derive defense mechanisms from our proposed threat model and foundational cybersecurity principles. Our analysis indicates that nearly half of these mitigations remain unimplemented across the target services. Datasets and attack artifacts are available at https://github.com/PedroBarcha/Memory-injection.

## I Introduction

Recent advances in Artificial Intelligence (AI) have enabled its widespread deployment across diverse domains, including finance [34], education [15], and healthcare [19]. This shift is primarily driven by generative AI (GenAI), which leverages underlying large language models (LLMs) to synthesize natural language and generate multimodal content spanning text, images, video, and audio.

As observed with prior emerging technologies [63], the rapid adoption of GenAI-based systems has outpaced the establishment of regulatory policies and cybersecurity protections. This asymmetry introduces significant ethical challenges while expanding the attack surface across deployed systems. Among the various threats targeting GenAI and LLM-driven applications [14], prompt injection stands out as a primary concern. This attack vector manipulates model behavior using carefully engineered malicious inputs and is ranked by the Open Worldwide Application Security Project (OWASP) as the top risk for LLM applications [44]. According to the U.S. National Institute of Standards and Technology (NIST) [55], such attacks can compromise system availability, alter model outputs, or facilitate unauthorized access to private data.

More recently, a new variant of prompt injection has emerged, enabling malicious effects to persist across user sessions [31, 22]. Known as memory injection, this attack strategy leverages memory-related capabilities originally intended to improve output quality by retaining context relevant to the user [40, 5, 25]. However, long-term state retention allows prompt injections previously confined to a single session to be stored and automatically reused across subsequent interactions.

Prior research demonstrates the viability of memory injection attacks across several contexts. For instance, SpAIware exploits native memory features in ChatGPT to plant persistent instructions that exfiltrate user conversations across sessions [31]. Similarly, MINJA inserts malicious records into an agent’s shared memory bank, misdirecting subsequent user queries (e.g., toward another patient’s records) [22]. Finally, ER-MIA plants synthetic memories designed to mimic legitimate records, causing similarity-based retrieval mechanisms to fetch malicious entries and degrade overall response quality [47]. Although only SpAIware targets a production service, these three studies collectively demonstrate that memory injections can compromise both data privacy and system integrity. Nevertheless, each existing work evaluates only a single memory architecture and pursues narrow attack objectives. Furthermore, the literature lacks a general threat model for memory injection and does not systematically derive mitigations from established cybersecurity principles. To address these gaps, this work formulates the following research questions:

• 

RQ1: Which security attack goals can be realized against GenAI systems through memory injection?

• 

RQ2: Which persistent-memory features can serve as vectors for memory injection?

• 

RQ3: How can memory injection be systematically mitigated?

• 

RQ4: To what extent are these mitigations currently implemented in well-established LLM-as-a-service platforms?

This work addresses these questions through a structured analytical and empirical framework. First, we propose a general threat model for memory injection that incorporates all adversarial goals against GenAI systems outlined in the NIST AI security guidelines [55] (RQ1), namely availability breakdown, integrity violation, privacy compromise, and misuse enablement. To complement this theoretical foundation, we design and execute empirical attacks targeting various persistent-memory mechanisms (e.g., personal memories, workspace projects, custom skills, organization instructions, and MCP-connected resources) available in Anthropic Claude (Sonnet 4.6), Google Gemini (3 Flash), and OpenAI ChatGPT (Instant 5.3) (RQ2). Next, we systematically derive defensive countermeasures grounded in our threat model and established OWASP security principles [45] (RQ3). Finally, we analyze the three target services to evaluate the actual implementation status of these mitigations (RQ4).

By addressing these research questions, this work advances the understanding of memory injection, an emerging threat vector that remains largely underexplored in the literature. Our findings demonstrate that memory injections can achieve the full range of NIST-defined attack goals through multiple persistent-memory mechanisms, although some features are more vulnerable than others. Specifically, we experimentally show that persistent injections can induce disinformation, trigger harmful content generation, and simulate service unavailability across all three evaluated platforms. Regarding data privacy, Claude’s shared-memory features allow an injection planted by a single organizational user account to compromise co-workers, enabling the cross-user exfiltration of sensitive prompt data.
Despite the severity of these attacks, our analysis reveals that popular LLM-as-a-service solutions remain largely unprotected, frequently overlooking the mitigations identified in this study. In this context, this work aims to raise awareness of the risks surrounding memory injection and outline practical defensive controls against them11

## II Background

In this section, we present fundamental concepts used throughout the work, following the taxonomy and terminology defined by NIST in its adversarial machine learning report [55].

## II-A Prompt injection and jailbreak

This work concentrates on what NIST refers to as prompting attacks [55], often termed prompt injection in the literature [21, 49]. This class of adversarial machine learning attacks targets GenAI systems by manipulating inputs to influence model behavior in ways that deviate from the intended design and operational objectives [55]. This attack is often enabled by insufficient safeguards, such as weak model-level alignment and input-output filtering [55, 44].

NIST considers that an adversary may use prompt injections to:
disrupt availability by preventing the system from being used reliably or in a timely manner [27];
violate integrity by manipulating the model to deviate from its intended purpose and produce outputs that serve the attacker’s purposes instead [46, 62];
compromise privacy by extracting confidential information such as model parameters, training data, or private data from system users [31];
or enable misuse by bypassing safeguards designed to prevent harmful or restricted content generation [52].

In this work, we aim to achieve all of these attacker goals persistently, through either direct prompt injection, in which the attacker interacts with the target system itself, or indirect prompt injection. According to NIST, the latter embeds malicious instructions in external data sources that are later incorporated into the model’s context [55]. Examples include user-uploaded PDF files and content retrieved through Retrieval-Augmented Generation (RAG) pipelines, which enable model access to private databases and documents [36, 24].

A jailbreak attack is designed to bypass constraints imposed on the model response, such as safety alignment and usage policies [55, 44].
The primary objective of jailbreaking is to enable misuse. After a model is successfully jailbroken, it may become more vulnerable to further attacks, this time pursuing availability breakdown, integrity violation, or privacy compromise. The attacker could attempt to perform, for example, prompt extraction on the jailbroken model, seeking to uncover the hidden system prompt, i.e, obtain the secret instructions that guide and constrain the model behavior.

Several approaches can be used to perform jailbreaking. Manual techniques often exploit LLMs’ competing objectives of helpfulness and harmlessness [12, 51]. For example, when asked how to make a bomb, the model could comply (prioritizing helpfulness) or refuse the request (prioritizing harmlessness). To exploit this tension, jailbreak techniques include role-playing prompts that instruct the model to adopt an unrestricted persona, such as “Do Anything Now” (DAN) prompts [52]. Other techniques explicitly instruct the model to comply unconditionally, bypassing its refusal mechanisms [56, 55, 44]. A further strategy exploits mismatched generalization – inputs that fall within the model’s capability training distribution but outside its safety training scope – using encoded text, simple ciphers, or low-resource languages [56, 55].

## II-B Memory

In conversational agents, memory is traditionally associated with the notion of context. Whereas model parameters encode knowledge acquired during training, context maintains information from the conversation session, including user inputs and the corresponding generated responses. This short-term memory [60] enables the model to maintain conversational coherence and support multi-turn interactions, where responses depend on information from previous turns. Note that generative language models can typically handle only a limited number of tokens, known as the context window limit [8]. Once this limit is exceeded, contextual information is usually discarded or summarized for future interactions [13].

In typical setups, a new conversational session does not contain information from previous sessions. Thus, if such information is necessary for further inferences, it must be provided again by the user. To circumvent this, recent solutions have proposed a feature known as memories, which store key information from conversations outside the context itself, so that it can be added to the context of future chats [40, 25, 5]. This allows the agent to “remember” the topics of previous conversations, as well as user preferences, interests, and traits, thus enabling continuity and personalization [40].

To implement this mechanism, it is necessary to rely on what the literature refers to as persistent memory [31] or long-term memory [60]. Going beyond memories, persistent memory is also present when the user connects external sources or data to the model via the Model Context Protocol (MCP), which standardizes connections between language models and external systems [1]. Persistent memory is also used in Claude skills, which are applied to new conversations to describe specialized knowledge or workflows [2]. For simplicity, throughout this document, the term “memory” is employed to refer to persistent memory.

While all of the above mechanisms are explored in this work, we mainly focus on memories. Public documentation on their implementation in popular applications (e.g., ChatGPT, Gemini, Claude) remains limited, but their general design appears to be grounded in research on LLM-based agents, where an explicit memory module stores, retrieves, and updates information across interaction steps and sessions [61, 60]. This can be implemented by storing a limited amount of information outside the context and injecting it into every new context [60], or by selectively retrieving memories based on their similarity to the user query, as in RAG [5]. The latter uses the context window more efficiently but is more costly and may increase inference time.

In this work, we explore memories in three LLM-as-a-service solutions:

## OpenAI ChatGPT

Memories are used in the following features: “saved memories”, where the user explicitly requests that information be stored so it can be considered in future responses (e.g., “GPT, remember that I am vegetarian”); and “reference chat history”, where pieces of information from past conversations are automatically referenced by the system (e.g., if a user previously mentioned that they like Thai food, the system can use that information when later asked “What should I have for dinner?”) [40].

## Anthropic Claude

Also stores memories when explicitly requested by the user or automatically [5]. Claude condenses past conversations into summaries, which are then used to provide “context for every new standalone conversation” [5]. Furthermore, users can instruct Claude to search past conversations for relevant information to “pull together the appropriate context”. This process is based on RAG [5].

## Google Gemini

The “personal context” feature allows information to be created either by the user or automatically by the system [25]. This may include not only data from past chats but also data from connected applications such as Gmail and Google Photos, when enabled.

Theoretically, in all the services above, users can manage memories via conversation, requesting their creation, editing or deletion. Moreover, Gemini and Claude provide dedicated features for importing memory from other AI tools [26, 5].

## II-C Memory injection

While persistent memory enhances personalization and general usability, it also introduces significant security risks. In particular, it creates a new attack surface by opening up opportunities for memory injections – a term that has been increasingly adopted in the context of adversarial machine learning and GenAI [22, 47].
Since no formal definition for this type of attack was found in the literature, we define it here based on similar characteristics observed across related works.

Memory injections are prompt injections added to long-term memory, allowing them to be applied to future model contexts. This approach can make prompt injections automatically reusable, potentially leading to persistent effects. In a chatbot application, for instance, a typical prompt injection vanishes when a new chat session begins. However, by injecting the attack into persistent memory, an attacker can make the adversarial behavior persist.

One important thing to note is that memory injection does not require direct access to either the language model or retrieval systems [47]. As discussed in the next section, this attack is fundamentally different from model poisoning and RAG poisoning

## LIMITATIONS SECTION
According to NIST [55], indirect prompt injection occurs when the attacker does not interact directly with the target system, but modifies external data sources. This definition holds for memory injection: in our experiments, long-lived PDFs in projects and MCP-connected content persistently inserted adversarial content into the model’s context. NIST’s definition of direct prompt injection (or direct prompting attack), however, assumes that the attacker is the primary user of the system and interacts with it through queries. In our threat model (Section IV-C), query-based injections are instead performed by a third party without the primary user’s knowledge: through a shared device (scenario 2), a shared account (scenario 3), or, in principle, a forged request issued from the victim’s authenticated session (scenario 5).

One possible adaptation to NIST’s definition is to consider direct prompt injection as any injection delivered through direct interaction with the target system, regardless of who performs it. This would also cover attacks delivered through configuration, such as organization-wide skills set by an attacker with access to the admin panel. Such attacks currently fit neither category: they are not made via queries, so they are not direct, and they do not come from external content, so they are not indirect. Furthermore, to make the NIST taxonomy more precise, memory injection could then be treated as a persistent subtype of both direct and indirect prompt injection.
