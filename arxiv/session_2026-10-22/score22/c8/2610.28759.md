## ABSTRACT
The Gabriel graph is a proximity graph widely used in computational geometry and geometric machine learning, underlying large-margin classifiers and, as we show in this work, density-aware clustering methods. Its construction, however, has cubic time complexity $O(N^3)$ in the naive formulation, which severely limits its use on datasets beyond a few thousand samples. This paper presents a set of GPU parallelization strategies, implemented in CUDA, that make Gabriel graph construction practical at scale. We introduce (i) an implicit closed-form mapping from a linear thread index to the corresponding vertex pair $(i,j)$, which removes the need for an explicit $O(N^2)$ adjacency structure and lets every thread locate its pair in constant time and constant memory; (ii) a two-pass, bitmask-based, atomically-compacted edge-list construction that produces a dense edge array proportional only to the number of edges actually found; and (iii) a thread-coarsening strategy in which each thread evaluates several candidate pairs, trading launch and scheduling overhead against load balance. We evaluate these strategies on the acceleration of a Gabriel-graph-based large-margin classifier (NN-clas) and on a novel Gabriel-graph clustering algorithm that identifies connected components on a residual graph and performs GPU-parallel Union-Find with hierarchical edge-based merging. On 14 public benchmark datasets, the GPU implementation reduces Gabriel graph construction time by two to nearly four orders of magnitude relative to a sequential CPU baseline (up to 8484x), without loss of classification accuracy, and the proposed clustering method is statistically competitive with DBSCAN on the topological validity index Dunn while eliminating the need for an explicit density radius parameter.

## 1 Introduction

Proximity graphs occupy a central role in geometric approaches to machine learning: they turn a set of feature vectors into a combinatorial structure whose edges encode a notion of “closeness” that can be exploited for classification, clustering, dimensionality reduction, or anomaly detection. Among proximity graphs, the Gabriel graph, introduced by Gabriel and Sokal (1969) in the context of geographic variation analysis, is particularly attractive because it depends on nothing but pairwise Euclidean distances, requires no free parameters (unlike $k$ -nearest-neighbor or $\varepsilon$ -radius graphs), and is a subgraph of the Delaunay triangulation, which guarantees several useful connectivity and locality properties (Matula and Sokal, 1980).

A vertex pair $(x_{i},x_{j})$ is connected by an edge in the Gabriel graph if and only if the open hypersphere having the segment $\overline{x_{i}x_{j}}$ as diameter contains no other point of the dataset. This purely geometric criterion has made the Gabriel graph a popular structural backbone for large-margin classifiers (Garcia et al., 2015; Arias-Garcia and others, 2024; Hanriot et al., 2024), where edges connecting samples of different classes – the support edges – approximate the decision margin between classes without solving any optimization problem.

The price of this elegance is computational: verifying the empty-hypersphere condition for every candidate pair against every other point costs $O(N^{3})$ in the number of samples $N$ , since there are $O(N^{2})$ candidate pairs and each check is itself $O(N)$ . This cost quickly becomes the dominant bottleneck of any Gabriel-graph-based pipeline once $N$ grows into the thousands, which is precisely the regime in which real-time or large-scale applications – medical diagnosis, network intrusion detection, industrial monitoring – would most benefit from these classifiers.

Because the empty-hypersphere test for a pair $(i,j)$ is completely independent of the test for any other pair $(k,l)$ , Gabriel graph construction is an embarrassingly parallel problem, and is therefore a natural candidate for acceleration on Graphics Processing Units (GPUs), whose Single-Instruction-Multiple-Threads (SIMT) architecture is designed precisely to exploit this kind of massive, independent, data-parallel work (Owens et al., 2008; Nickolls et al., 2008).

## Contributions.

This paper isolates and details the GPU parallelization of Gabriel graph construction – the computational core shared by every Gabriel-graph-based algorithm – and studies it as a problem in its own right. Concretely, we contribute:

1. 

A closed-form, $O(1)$ -time and $O(1)$ -memory mapping from a one-dimensional CUDA thread index $k$ to the pair of vertex indices $(i,j)$ that it must evaluate, which avoids materializing an $O(N^{2})$ index table (Section 4);

2. 

A two-pass, bitmask-based edge construction scheme that uses atomic operations to compact the sparse set of valid Gabriel edges into a dense array proportional to the true edge count, keeping GPU memory usage close to $O(|E|)$ rather than $O(N^{2})$ (Section 4.3);

3. 

An empirical study of thread coarsening – assigning multiple candidate pairs to each thread – showing that the best coarsening factor is dataset-dependent: it reduces execution time on one dataset but not on another (Section 4.4);

4. 

Two downstream applications that validate the approach: an accelerated re-implementation of the NN-clas large-margin classifier (Arias-Garcia and others, 2024), and a new GPU-native clustering algorithm that uses connected components of a distance-filtered Gabriel graph, with an automatic elbow-based cut and a GPU parallel Union–Find with hierarchical merging (Section 5);

5. 

An experimental evaluation on 14 public datasets (synthetic and real), reporting speedups of up to $8484\times$ over a sequential CPU baseline and a statistical comparison of the resulting clustering quality against $K$ -means and DBSCAN (Section 6).

The remainder of the paper is organized as follows. Section 2 reviews related work. Section 3 introduces the Gabriel graph and the relevant CUDA/SIMT background. Section 4 presents the parallelization strategies in detail. Section 5 describes the two applications used to validate the approach. Section 6 reports the experimental results, Section 7 discusses limitations, and Section 8 concludes with directions for future work.

## 2 Related Work

## Gabriel-graph-based classification.

Gabriel and Sokal (1969) originally proposed the Gabriel graph for geographic variation analysis; Matula and Sokal (1980) later characterized its geometric properties. In machine learning, the graph has been used to build hyperparameter-free, geometry-driven large-margin classifiers: edges connecting samples of opposite classes (support edges) delineate the separating margin without an explicit optimization procedure. Garcia et al. (2015) studied the effect of label noise on such classifiers and proposed a quality-based filtering step, which we reuse as a pre-processing stage. Arias-Garcia and others (2024) proposed a hardware (FPGA) implementation of a Gabriel-graph classifier to reduce its computational cost, confirming that acceleration of this family of methods is an open and relevant problem, while Hanriot et al. (2024) extended Gabriel-graph classifiers to the multiclass setting and connected them to neural architectures, and The GGClassification Contributors (2020) provide a reference software implementation. None of these works targets general-purpose GPU acceleration of the underlying graph construction, which is the focus of the present paper.

## GPU-accelerated machine learning.

The suitability of GPUs for data-parallel machine learning workloads is well documented (Owens et al., 2008; Eon and others, 2021; Zhang and others, 2023; Çolhak and others, 2025). Çolhak and others (2025) benchmark GPU versus CPU execution of machine learning libraries and report substantial throughput gains; Zhang and others (2023) present a GPU framework that couples neural simulation and AI at scale. These works motivate GPU acceleration in general but do not address the specific combinatorial structure of proximity-graph construction.

## Thread granularity and coarsening.

Magni et al. (2014) show that automatically tuning the amount of work assigned to each GPU thread – thread coarsening – is essential, because a naive one-thread-per-element mapping can be dominated by scheduling overhead. We adopt this principle for Gabriel graph construction and quantify its effect empirically in Section 6.

## Graph-based clustering.

Clustering by connected components of a proximity graph is a classical idea (Cormen et al., 2001; Jain, 2010); the difficulty lies in choosing which edges to keep. We adopt an elbow-based automatic threshold (Thorndike, 1953) on the sorted Gabriel edge weights, following the general taxonomy of internal cluster validity indices surveyed by Ezugwu and others (2022), which we use throughout for quantitative evaluation.

## 3 The Gabriel Graph

## 3.1 Definition and Basic Properties

Let $S=\{x_{i}\}_{i=1}^{N}\subset\mathbb{R}^{n}$ be a finite point set. The Gabriel graph of $S$ is the undirected graph $G=(V,E)$ with $V=\{1,\dots,N\}$ (one vertex per sample) and

Definition 1 (Gabriel edge).

An edge $(i,j)\in E$ exists if and only if no other point $x_{k}\in S$ , $k\neq i,j$ , lies strictly inside the open hypersphere having $\overline{x_{i}x_{j}}$ as diameter. Equivalently,

 $\|x_{i}-x_{j}\|^{2}\;\leq\;\|x_{i}-x_{k}\|^{2}+\|x_{j}-x_{k}\|^{2},\qquad\forall\,x_{k}\in S\setminus\{x_{i},x_{j}\}.$ 

(1)

Figure 1 illustrates the construction: for the highlighted pair, the dashed circle (the two-dimensional analogue of the empty hypersphere) contains no other data point, so the edge is admitted. In a labeled binary classification setting $S=\{(x_{i},y_{i})\}$ with $y_{i}\in\{-1,+1\}$ , we call support edges the subset $E_{S}\subseteq E$ of edges whose endpoints have different labels; under mild assumptions on class overlap, $E_{S}$ localizes the decision boundary between classes (Gabriel and Sokal, 1969; Arias-Garcia and others, 2024).

Figure 1: A Gabriel graph built on a synthetic two-class point set. Grey edges connect same-class neighbors; red edges are support edges joining points of different classes. The dashed circle illustrates the empty-hypersphere test of Eq. (1) for one admitted edge: no other point falls inside it.

Property 1 (Complexity).

Checking Eq. (1) for a single candidate pair costs $O(N)$ (one pass over all other points). Since there are $\binom{N}{2}=O(N^{2})$ candidate pairs, the naive construction costs $O(N^{3})$ in time. The graph itself is sparse: it is known to be a subgraph of the Delaunay triangulation, so $|E|=O(N)$ in the planar case and generally $|E|\ll N^{2}$ in higher dimensions for non-adversarial data.

The gap between the $O(N^{3})$ construction cost and the $O(N)$ – $O(N^{2})$ size of the resulting graph is precisely what motivates a parallel, memory-conscious construction strategy: work is heavily redundant across candidate pairs (each requiring an independent scan of $N-2$ points) but the eventual output is small and sparse.

## 3.2 The SIMT Execution Model

CUDA organizes computation into a grid of thread blocks; each block contains threads grouped into warps of 32 threads that execute the same instruction stream in lock-step (Single Instruction, Multiple Threads, SIMT) (NVIDIA Corporation, 2025). Performance is maximized when threads within a warp follow the same control-flow path (avoiding warp divergence) and when global memory accesses are coalesced. Concurrent writes to shared memory locations are protected with atomic operations (e.g., atomicAdd, atomicOr, atomicMin), which guarantee indivisible read-modify-write semantics at the cost of potential serialization when many threads contend for the same address (NVIDIA Corporation, 2025).

Gabriel graph construction maps naturally onto this model: each candidate pair $(i,j)$ can, in principle, be assigned to an independent thread, with no data dependency between threads other than read-only access to the (immutable) point set. The remainder of this paper addresses how to organize that mapping efficiently.

## 4 Parallel Construction Strategies

## 4.1 Naive Parallelization and the Indexing Problem

A direct GPU translation of Gabriel graph construction launches one thread per candidate pair $(i,j)$ , $i<j$ , and has each thread evaluate Eq. (1). The number of candidate pairs is

 $T=\binom{N}{2}=\frac{N(N-1)}{2}.$ 

(2)

The immediate difficulty is indexing: CUDA launches a one-dimensional (or low-dimensional) grid of threads, each receiving a linear global index $k\in[0,T-1]$ ; the thread must recover the pair $(i,j)$ that $k$ represents. Materializing a lookup table of size $T=O(N^{2})$ defeats the purpose of an efficient implementation, since it alone can exceed available GPU global memory for large $N$ (e.g., $N=30{,}000$ already gives $T\approx 4.5\times 10^{8}$ pairs).

## 4.2 Implicit Index Mapping $k\mapsto(i,j)$ 

We derive a closed-form inverse of the standard row-major enumeration of the strict upper triangle of the $N\times N$ pair matrix,

 $(0,1),(0,2),\dots,(0,N-1),\;(1,2),(1,3),\dots,(1,N-1),\;\dots,\;(N-2,N-1),$ 

so that every thread can compute its own $(i,j)$ in constant time and constant memory, using only $N$ and its own index $k$ .

Row $i$ contains $L_{i}=N-i-1$ valid pairs. The number of pairs enumerated strictly before row $i$ is

 $P(i)=\sum_{r=0}^{i-1}(N-r-1)=\frac{N(N-1)}{2}-\frac{(N-i)(N-i-1)}{2}.$ 

(3)

Index $k$ belongs to the (unique) row $i$ satisfying $P(i)\leq k<P(i+1)$ . Solving this quadratic inequality for $i$ in closed form gives

 $i=N-2-\left\lfloor\frac{\sqrt{-8k+4N(N-1)-7}}{2}-0.5\right\rfloor.$ 

(4)

The column index then follows directly from the offset within row $i$ :

 $j=k-\left(\frac{N(N-1)}{2}-\frac{(N-i)(N-i-1)}{2}\right)+i+1.$ 

(5)

Equations (4)–(5) let every thread invert its linear index $k$ into a vertex pair $(i,j)$ using a handful of arithmetic operations and one square root – no auxiliary memory, and no per-thread branching that would introduce warp divergence.

Example 1.

For $N=5$ , $T=10$ and the enumeration is

 $\begin{array}[]{c|ccccc}&0&1&2&3&4\\
\hline\cr 0&-&(0,1)_{0}&(0,2)_{1}&(0,3)_{2}&(0,4)_{3}\\
1&&-&(1,2)_{4}&(1,3)_{5}&(1,4)_{6}\\
2&&&-&(2,3)_{7}&(2,4)_{8}\\
3&&&&-&(3,4)_{9}\\
4&&&&&-\end{array}$ 

For $k=5$ , Eq. (4) gives $i=3-\lfloor\sqrt{33}/2-0.5\rfloor=3-\lfloor 2.37\rfloor=1$ , then $P(1)=4$ and Eq. (5) gives $j=1+1+(5-4)=3$ , correctly recovering the pair $(1,3)$ .

To guard against 64-bit overflow when $N$ is large, all index arithmetic (grid sizing, $T$ , and the intermediate terms of Eqs. (4)–(5)) is carried out using 64-bit integer/floating-point types.

## 4.3 Two-Pass Construction with Bitmask Compaction

Even without materializing an index table, naively allocating one flag per candidate pair still costs $O(N^{2})$ memory if a full byte (or worse, a 32-bit int) is used per flag. We instead use a two-pass, bitmask-compacted scheme:

1. 

Pass 1 – Marking. Each thread evaluates Eq. (1) for its pair $(i,j)$ (recovered via Eqs. (4)–(5)). If the pair satisfies the Gabriel condition, the thread sets a single bit in a global bitmask using atomicOr, reducing flag storage by a factor of 32 relative to one int per pair, and increments a global counter with atomicAdd to determine the exact number of valid edges.

2. 

Intermediate allocation. The host reads the counter and allocates exactly the memory required for the dense edge list (and, if needed, the associated edge weights).

3. 

Pass 2 – Compaction. Threads re-scan the bitmask; for every set bit, an atomic increment on a write-cursor determines that edge’s position in the dense output array, which is then populated.

This scheme keeps peak GPU memory proportional to the number of candidate pairs only during the (cheap, bit-packed) marking pass, and proportional to $|E|$ thereafter – the true asymptotic footprint of the graph. All device vectors are managed through the Thrust library (thrust::device_vector), and intermediate buffers are explicitly released (shrink_to_fit) as soon as they are no longer needed, which is important because subsequent stages (noise filtering, classification, or clustering) may need to allocate further structures on the same device.

## 4.4 Thread Coarsening

Mapping exactly one candidate pair to one thread maximizes available parallelism but also maximizes the number of threads that must be created, scheduled and retired, which introduces overhead that is not always amortized by useful work – especially for the many pairs, per warp, that fail the Gabriel test early. We therefore evaluate thread coarsening (Magni et al., 2014): each thread is assigned a contiguous block of $c$ candidate pairs (indices $k,k+1,\dots,k+c-1$ under the mapping of Eqs. (4)–(5)), amortizing per-thread overhead and improving data locality, at the cost of a coarser and potentially less balanced distribution of work across the device. Figure 2 sketches the expected trade-off: execution time can fall as $c$ grows (overhead amortization dominates), reach a minimum, and rise again as load imbalance across threads dominates. Section 6.3 measures whether this holds in practice.

An intermediate “sweet spot” minimizes total execution time; measurements on two datasets, where the optimum turns out to be dataset-dependent, are reported in Section 6.3.

## LIMITATIONS SECTION
The results support two related claims. First, the $O(N^{3})$ cost that has historically limited Gabriel-graph methods to small or medium datasets is not an intrinsic obstacle but an artifact of sequential execution: because the empty-hypersphere test is independent across candidate pairs, a GPU implementation combining implicit pair indexing and bitmask-compacted two-pass construction reduces execution time by two to nearly four orders of magnitude with no loss of downstream accuracy (Table 1, measured with $c=1$ ); thread coarsening can reduce it further on some datasets, but not on all. Second, once construction is fast, the Gabriel graph becomes a practical building block not only for classification (as in NN-clas) but also for density-aware clustering, where it is competitive with DBSCAN on the Dunn index while avoiding an explicit density-radius parameter.

Several limitations should be noted. The reported speedups compare a single-threaded CPU baseline to a single-GPU implementation on hardware with a substantial theoretical performance gap between host and device, which the community’s convention (and our stated intent to isolate parallel-kernel efficiency) accepts but which should be kept in mind when transferring absolute speedup numbers to other hardware pairings; a multi-threaded CPU baseline (e.g., OpenMP) would narrow the reported gap while leaving the qualitative conclusions unchanged. The clustering method’s hierarchical merge stage relies on a global minimum-weight-edge search per merge step, which, while GPU-parallel, adds sequential dependency across merge iterations and could itself be a target for further optimization (e.g., a parallel priority structure). Finally, the largest datasets used for the coarsening study ( $N\approx 10^{5}$ ) already produce several billion candidate pairs ( $T\approx 5\times 10^{9}$ for $N=10^{5}$ ); scaling further, into the range where the bitmask itself exceeds single-GPU memory, would require a multi-GPU or out-of-core extension of the pipeline described here.
