## ABSTRACT
Large language models (LLMs) have shown considerable promise in synthesizing formal specifications from source code. However, existing approaches primarily focus on functional contracts and loop invariants, while largely neglecting frame conditions, which specify the memory locations that may or may not be modified during execution and constitute an essential part of formal specifications. To address this limitation, we propose an LLM-based approach for synthesizing ACSL frame specifications alongside functional contracts from C code. Our approach analyzes code property graphs (CPGs) to extract frame-relevant information from the input code and leverages this information to guide the LLM in generating accurate frame conditions. The resulting specifications capture both region-separation constraints and data dependencies that govern variable modifications. Experimental results demonstrate the effectiveness of our approach. On a benchmark of 84 ACSL-compliant functions from non-trivial real-world systems, our method successfully synthesizes error-free frame specifications for 92.9% of the functions, representing a 179% relative improvement over state-of-the-art techniques. On a second benchmark consisting of 51 functions, the success rate increases from 80.4% to 96.1%. Furthermore, when integrated as an auxiliary component into existing LLM-based ACSL-synthesis frameworks, our approach improves frame-specification generation performance by up to 61.9%.

## I Introduction

Large language models (LLMs) have recently shown strong potential for generating formal specifications from source code. For C programs, several approaches [1, 2, 3, 4, 5] have explored using LLMs to synthesize ACSL specifications, often with feedback from static analyzers or verification tools. These techniques can generate useful functional specifications, such as preconditions, postconditions, and loop invariants, and can substantially reduce the manual effort required for deductive verification. However, little attention has been paid to frame conditions: the part of a specification that describes what memory a function may affect, what values those effects depend on, and what memory must remain independent. Without accurate frame information, a verified function cannot be safely reused by callers, because the caller cannot know which parts of the program state are preserved.

This limitation is especially important for C programs. Recent approaches such as AutoSpec [4] and Preguss [5] push LLM-based specification generation further by combining models with program information and verification feedback. However, their treatment of frame information remains limited. They primarily optimize for whether the generated specification can help discharge verification conditions, while frame completeness is not directly measured. In particular, evaluations based mainly on WP proof success may overlook missing memory-dependence information or imprecise aliasing assumptions, because a proof can succeed even when the contract does not fully describe what state a caller may rely on after the function returns. This gap is difficult to close for C: pointers, arrays, pointer arithmetic, loops, and library calls can hide which memory regions may overlap and which input values may influence each write. As a result, a generated contract may look correct to the verifier but still be too weak for precise modular reasoning. Section II shows a small example where an apparently verified contract still permits an invalid aliased call.

To address this problem, we propose AutoFraming, an approach for synthesizing frame specifications for C programs. AutoFraming analyzes frame-relevant information from a code property graph (CPG) [6], including possible memory interference, caller-visible writes, loop-indexed write ranges, and data dependencies. It then projects this information into a fixed-frame skeleton that captures which memory regions must be kept independent and which inputs may influence each written location. The LLM is used to assemble the full contract and repair remaining verification failures, while the frame-critical structure is generated and preserved during refinement.

We evaluate AutoFraming on two benchmarks: 84 functions from real-world C systems and 51 academic verification examples. On the real-world benchmark, AutoFraming synthesizes error-free frame specifications for 92.9% of functions, a 179% relative improvement over the state-of-the-art baseline. On the academic benchmark, it improves the error-free frame rate from 80.4% to 96.1%. When used as an auxiliary frame-synthesis component for existing specification-generation tools, AutoFraming further improves error-free frame performance by up to 61.9%. Ablation results show that the CPG-derived frame information and deterministic projections are essential to the improvement.

The contribution of this paper is summarized as follows: AutoFraming provides an effective approach to the novel problem of synthesizing
error-free frame conditions with LLMs.
It conducts frame analysis, including caller-visible roots, access windows, interfering pointer pairs, write-set locations, and dependence footprints. It then projects frame-related information into ACSL specification, including region separation for caller-visible memory regions and data dependence for write-set locations.
Moreover, AutoFraming can be used in other ACSL synthesis frameworks, such as Preguss and AutoSpec, to improve their capability of synthesizing frame conditions.

## II A Motivating Example

Consider the C function parse_value, shown below, which reads two values from the memory region pointed to by buf and stores their sum in the memory location pointed to by eaten.

Listing 1: Source code of the motivating example.

⬇

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten) {

 if (len < 2 || buf == NULL || eaten == NULL) return -1;

 *eaten = buf[0];

 *eaten = (uint16_t)(*eaten + buf[1]);

 return 0;

}

To call parse_value, the client needs to provide actual parameters for *buf and *eaten, such as the following:

⬇

uint16_t buf[2] = { 3, 5 };

uint16_t out;

parse_value(buf, 2, &out);

Without a formal specification for parse_value, clients have no precise way to determine whether a call satisfies the function’s assumptions or achieves its intended behavior. To address this issue, we can prompt an LLM to synthesize the following ACSL [7] specification directly from the source code of parse_value:

Listing 2: Preliminary ACSL specification generated by prompting an LLM

⬇

/*@ requires len > 0;

 requires buf != \null;

 ensures \result == 0 || \result == -1; */

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten);

The generated comment enclosed by /*@ and */ defines the ACSL contract for parse_value, including its precondition (the requires clauses) and postcondition (the ensures clause). The precondition specifies the conditions that callers must satisfy before invoking parse_value; specifically, len must be positive and buf must be non-null. The postcondition specifies the property that must hold when parse_value returns, namely that the return value is either 0 or -1.

The ACSL specification can be verified with Frama-C and one of its plug-ins (e.g., WP or Eva) [8]. Given a function and its ACSL contract, Frama-C generates a set of proof obligations, called goals, each expressed as a logical formula whose validity establishes a specific aspect of the contract. These goals are then dispatched to automated SMT solvers. The proportion of discharged goals, referred to as the goal ratio (proved/total), indicates the extent to which the contract has been verified. A goal ratio of $1$ (i.e., a full proof) means that every proof obligation has been discharged, establishing that the implementation satisfies the specified contract for all executions. Otherwise, the result is only a partial proof, indicating that some proof obligations remain unresolved. It is important to note, however, that a full proof does not necessarily imply that the code is correct. Rather, it only guarantees conformance to the given specification. If the specification is incomplete or inaccurate, the implementation may still satisfy it while failing to capture the intended behavior. For example, Frama-C with the WP plugin reports a full proof for the preliminary LLM-generated ACSL contract shown above, even though the contract only partially captures the intended behavior of parse_value. The generated precondition is overly restrictive. It requires len to be positive and buf to be non-null, even though parse_value handles the cases where len is non-positive or buf is NULL without error.

To improve the quality of synthesized ACSL specifications, existing approaches leverage the results of static code analysis to prompt LLMs and refine the specifications.
The following ACSL specification is generated by Preguss [5], the state-of-the-art method:

Listing 3: ACSL specification generated by existing approaches

⬇

/*@ requires \valid_read(buf + (0..len-1));

 requires \valid(eaten);

 assigns *eaten;

 ensures \result == 0 || \result == -1; */

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten);

The requires clauses specify the validity conditions for buf and eaten. The assigns clause, assigns *eaten;, defines the function’s frame condition by specifying that only the memory location referenced by eaten may be modified during execution. Consequently, all other program state, including buf, len, and the memory referenced by buf, must remain unchanged. More generally, the assigns clause consists of a list of variable names or memory locations (referred to as a write set or footprint).

However, the above frame specification is insufficient even though the verification result is a full proof. Consider the following call:

⬇

uint16_t buf[2] = { 3, 5 };

parse_value(buf, 2, &buf[1]);

The call satisfies
both precondition clauses, i.e., buf is readable and &buf[1] is
valid. Although the intended value for *eaten (i.e., buf[1]) is
buf[0] + buf[1] = 8, the actual outcome is 3 + 3 = 6 because parse_value reads buf[1]
after writing through *eaten, so the write clobbers
buf[1] first and the call computes 3 + 3.

The problem arises because the same object, buf, is passed to both pointer parameters, *buf and *eaten. However, parse_value operates correctly only when these pointers refer to separate, non-overlapping memory locations. Therefore, the ACSL specification must explicitly capture this separation requirement to prevent invalid function calls and ensure correct verification.

In summary, existing LLM-based approaches to ACSL specification synthesis do not explicitly address the frame problem, particularly dynamic frame conditions such as the memory separation requirement illustrated above. Dynamic frame conditions precisely specify the memory locations that a function is permitted to read or modify, ensuring that changes to one object cannot inadvertently affect the state of another unrelated object. The goal of this paper is to enable LLMs to synthesize ACSL specifications with accurate frame conditions for C programs that are ACSL-compliant, i.e., programs whose behavior can be completely specified in ACSL. The following specification for the example illustrates the desired result:

Listing 4: ACSL specification with dynamic frames

⬇

/*@ requires \valid_read(buf + (0..len-1));

 requires \valid(eaten);

 requires \separated(buf + (0..len-1), eaten);

 assigns *eaten

 \from buf[0..len-1], len;

 ensures \result == 0 || \result == -1; */

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten);

The additional requires clause,
\separated(buf + (0..len-1), eaten);
specifies that the memory region referenced by buf must be disjoint from the memory location referenced by eaten. The assigns clause,
*eaten \from buf[0..len-1], len;
defines both the function’s write set and the data dependencies of the modified location, stating that only *eaten may be updated and that its value depends solely on buf[0..len-1] and len.
Synthesizing the region separation requirement and the data dependency of the write set is a challenging problem. Because C programs do not expose their memory footprint directly in the source syntax. Pointer aliasing, array ranges, pointer arithmetic, loops, globals, and library calls can hide both the regions that may interfere with one another and the inputs that may affect each write. Therefore, synthesizing accurate dynamic frames requires recovering caller-visible memory regions, separation assumptions, and write dependencies from program structure rather than treating frame clauses as ordinary text to be generated.

## III The design of AutoFraming

## III-A Overview

AutoFraming leverages the code property graph (CPG) representation of C code to synthesize its frame specifications. Given an unannotated function, AutoFraming generates an ACSL specification whose frame part describes not only the memory locations that may be modified, but also the memory regions that must remain disjoint and the caller-visible inputs that may influence each write. Although AutoFraming outputs a complete ACSL specification, this paper focuses on the synthesis of frame conditions. Figure 1 shows the three-stage workflow of AutoFraming.

Stage 1: AutoFraming first constructs the call graph and analyzes functions in bottom-up order, ensuring that verified callee contracts are available when analyzing their callers. For each function $f$ , AutoFraming builds a CPG and extracts the frame-related information $\Phi_{f}$ , which captures the caller-visible roots of memory accesses, accessed regions of pointer roots, pointer pairs whose aliasing may interfere with caller-visible writes, write-set locations used as frame carriers, and the dependence footprint of each write-set location.

Fig. 1: AutoFraming Pipeline for CPG-guided Frame Specification Synthesis.

Stage 2: AutoFraming projects $\Phi_{f}$ into a frame skeleton. The separation projection turns interfering pointer regions into disjointness requirements, while the dependence projection attaches caller-visible dependence footprints to write-set locations. AutoFraming treats projected frame obligations as required constraints.
A candidate is rejected if it deletes or weakens them, but the current
implementation may still allow equivalent or stronger rewritings that
change the proof burden.

Stage 3: AutoFraming asks the LLM to assemble a verifier-checkable contract around the frame skeleton and uses Frama-C feedback to repair remaining failures. During refinement, candidate contracts are accepted only if they preserve the projected frame conditions, avoid degenerate frames, and make proof progress. This design lets AutoFraming use the LLM for auxiliary annotations and repair while keeping the frame-critical content grounded in program analysis.

## III-B CPG-Based Frame Analysis

For each function $f$ , AutoFraming extracts from its CPG the information needed to synthesize the dynamic frame. A CPG overlays three program views on one graph [9]: the abstract syntax tree (AST), which exposes declarations and assignment targets; the
control-flow graph (CFG), which exposes branches, loops, and execution paths; and the program dependence graph (PDG), which exposes data and control dependencies. This combination is essential because frame synthesis is not a purely syntactic task: write-set locations come from syntax, region extents often come from loops and guards, and dependence footprints require following value and control flow.

AutoFraming represents the frame-related information as

 $\Phi_{f}=(\mathcal{R}_{f},\Omega_{f},\mathcal{I}_{f},\mathcal{L}_{f},\Delta_{f}).$ 

The first three components help address the region-separation issue:
which caller-visible regions must be disjoint? The last two deal with the data dependency issue: what does each write set location depend on?

## CPG-to-information extraction.

AutoFraming derives each component of $\Phi_{f}$ by querying specific CPG
nodes and edges rather than by passing the whole graph to the LLM. AST
nodes provide syntactic roots and memory-access forms: parameter and
global declarations identify caller-visible roots; dereference,
array-subscript, field-access, assignment, and update nodes identify
reads and writes; and declaration and cast nodes provide type information
for alias compatibility. CFG edges provide the execution context of these
accesses: loop headers, back edges, and branch guards are used to recover
loop-indexed access ranges and conditional bounds. PDG edges provide
dependence information: data-dependence edges connect values to the
expressions they influence, while control-dependence edges connect guards
to the writes whose execution they control. Together, these CPG views
determine the five information components used by AutoFraming:
caller-visible roots, access windows, interfering pointer pairs,
write-set locations, and dependence footprints.

## CONCLUSION
We have presented AutoFraming for synthesizing ACSL frame specifications for C programs. It extracts frame-related information and projects the information into a deterministic frame skeleton, and uses the LLM only to complete and repair the surrounding contract under verifier feedback. Our experimental results show that grounding LLM-based specification synthesis in explicit program structure and frame-specific constraints leads to more complete and reusable frame specifications than existing generators. Future work will extend AutoFraming to richer heap abstractions, recursive data structures, inter-procedural library summaries, and additional specification languages and verifiers.
