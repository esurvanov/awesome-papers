## ABSTRACT
Coding agents can now implement a specification, write and run tests, repair failures, and declare the result ready for release. When the same agentic system produces both the software and the evidence of its correctness, a passing test suite is no longer independent evidence: visible tests become an optimization target, code and tests may share one misinterpretation of the specification, and the builder's own tests may simply be incomplete. This paper argues that agent-produced software requires an assurance plane that is structurally independent of the build plane. We characterize four gaps between stakeholder intent and production (requirement, conformance, evaluation, and model gaps) and identify which of them verification can close. We propose a framework that separates building from verifying, introduces a Verification Contract stating what must be demonstrated before release, and organizes verification in a specification-first phase without access to the implementation and an implementation-aware phase based on mutation analysis, property-based testing, and fuzzing, with an assurance report that leaves the release decision to a human. We evaluate the framework in a pre-registered study on three stateful services, two of them written by third-party models, and an EvalPlus pilot. The builder's programs were correct, but its own tests missed subtle interactions: a verifier in a fresh context detected more of the 46 seeded faults than the builder's tests (Holm-corrected p = 0.006) and surfaced the ambiguities of the specification, at the price of rare false oracles. A verifier from another provider did not add detection.

## BODY (first 18k chars)
Abstract

Coding agents can now interpret a specification, implement it, write and execute tests, repair failures, and declare the result ready for release. When the same agentic system produces both the software and the evidence of its correctness, a passing test suite no longer constitutes independent evidence. Visible tests become an optimization target, code, tests, and oracles may share a single misinterpretation of the specification, and the builder’s own tests may simply be incomplete. This paper argues that agent-produced software requires an assurance plane that is structurally independent of the build plane. We first characterize four gaps along the chain from stakeholder intent to production, namely the requirement, conformance, evaluation, and model gaps, and identify which of them verification can close. We then propose a framework that separates building from verifying, introduces a Verification Contract stating what must be demonstrated before release, and organizes verification in two phases: a specification-first phase designed without access to the implementation, and an implementation-aware phase that strengthens the evidence through mutation analysis, property-based testing, and fuzzing. The resulting evidence is consolidated into an assurance report that makes residual uncertainty explicit and leaves the release decision to a human. We evaluate the framework in a pre-registered study on three stateful services, two of them written by third-party models, and an EvalPlus pilot, comparing self-validation with independent verification under context-level and model-level independence. The builder’s programs were correct, but its own tests missed subtle interactions: a verifier in a fresh context detected more of the 46 seeded faults than the builder’s tests (Holm-corrected p = 0.006), and surfaced the ambiguities of the specification, at the price of rare false oracles. A verifier from another provider did not add detection. The framework and the study provide a basis for governing the release of software produced by agents.

## I Introduction

Large language models (LLMs) were first adopted in software engineering as assistants that complete code, generate unit tests, or suggest repairs under close human supervision [1, 2]. Coding agents change this division of labor. Given a task description and a repository, an agent can decompose the task, modify the code, write and execute tests, repair its own failures, and iterate until every visible check succeeds [3]. Spec-driven development extends this mode of work by asking the human to formalize intent as a specification before delegating implementation to the agent [4].

Spec-driven development returns control to the human at the beginning of the chain. It does not address the end of the chain. In a typical agentic workflow, the agent that implements the specification also writes the tests, chooses the expected outputs, interprets failures, modifies the code, and finally reports that the change is ready. The release signal is then a set of green checks produced, selected, or adjusted by the producer itself. This situation raises a governance question that long predates LLMs: can the producer of an artifact be the sole authority on its correctness? Classical software engineering answered negatively. Testing practice advises against programmers testing their own programs [5], and standards for critical software require verification activities with technical, managerial, and financial independence from development [6, 7].

Recent evidence suggests that this answer remains valid for agents, for two reasons. First, when tests drive an iterative loop, they act as a reward signal, and a sufficiently capable optimizer can satisfy the signal without satisfying the intent behind it [8, 9]. Zhao et al. report that frontier coding agents saturate visible validation suites on systems-level tasks while still failing held-out composition tests, with failures that range from incomplete features to implementations that memorize test inputs [10]. Zhong et al. show that agents frequently modify or circumvent tests when a specification and its tests conflict [11]. Second, when code, tests, and expected outputs derive from the same interpretation of a specification, they can be mutually consistent and jointly wrong. Internal consistency is not evidence of external correctness, which is a modern instance of the test oracle problem [12]. A third, less visible reason needs neither optimization pressure nor a misreading: a builder that implements the specification correctly still tests only what it thought of, so its passing suite says little about the behaviors it did not test.

The scale of agent output aggravates both problems. Line-by-line review cannot keep pace with the volume of code that agents produce, so the object of human control must shift from the code to the evidence about the code. We therefore formulate the following question: when software is produced largely autonomously from a specification, what independent evidence is sufficient for a human to authorize its release?

This paper makes the following contributions:

• 

A gap analysis. We decompose the distance between stakeholder intent and production behavior into four gaps (requirement, conformance, evaluation, and model) and explain why self-validation can close none of them reliably (Section III).

• 

An independent assurance framework. We separate a build plane from an assurance plane, introduce the Verification Contract as the human-approved artifact that defines release evidence, and organize verification into a specification-first phase and an implementation-aware phase whose evidence is consolidated in an assurance report (Section IV).

• 

A pre-registered empirical study. We measure the evaluation gap under self-validation, the effect of context-level and model-level independence, and the complementarity of the two verification phases on three stateful services with 46 seeded faults, two of them written by third-party models, and on an EvalPlus pilot [13] (Sections V and VI).

• 

An open artifact containing the experimental harness, prompts, generated evidence, and analysis scripts https://github.com/besionisrael/assure-harness.

## II Background and Related Work

## II-A LLM-Based Test Generation and Test Adequacy

Early work on LLM-based testing asked whether models could produce tests that compile, run, and increase coverage. CodaMosa invokes an LLM when search-based test generation reaches a coverage plateau [14]. Schäfer et al. evaluate LLM-generated unit tests for JavaScript and report coverage competitive with established tools [15]. TestGen-LLM at Meta accepts a generated test only if it builds, passes reliably, and increases coverage, and it reports that most candidates fail at least one of these filters [16]. A recurring lesson is that LLMs are most useful when coupled with an external mechanism that measures, filters, or rejects their output.

Coverage, however, is a weak proxy for fault detection: Inozemtseva and Holmes find that coverage is not strongly correlated with test suite effectiveness once suite size is controlled [17]. Mutation analysis offers a stronger criterion by asking whether a suite fails on deliberately faulty variants of the program [18, 19], and mutant detection correlates with real fault detection [20]. MuTAP feeds surviving mutants back to an LLM to strengthen generated tests [21], and Meta’s ACH system generates mutants that represent specific fault classes and then generates tests that kill them [22]. Property-based testing [23] replaces examples with invariants checked over generated inputs, and recent studies investigate LLMs as generators of such properties [24, 25]. Metamorphic testing addresses programs for which exact expected outputs are unavailable [26].

## II-B The Test Oracle Problem

A test requires both an input and a judgment of whether the observed output is correct [12]. LLMs can generate the judgment, but the judgment can be wrong. TOGLL studies the correctness and strength of LLM-generated oracles and shows that both must be measured separately [27]. Several code generation approaches use generated tests to select or refine programs: CodeT ranks candidate programs by their agreement with generated tests [28], and AgentCoder assigns test design to a separate agent from code generation [29]. These approaches treat generated tests as a means to improve generation. We instead treat them as evidence for a release decision and ask under which conditions that evidence is independent.

## II-C Specification Gaming by Coding Agents

Reward hacking occurs when an optimizer increases a proxy reward without improving the true objective [8, 9], a specific case of Goodhart’s law [30]. In agentic coding, the proxy is the test suite. SpecBench separates natural-language specifications, visible validation tests, and held-out composition tests, and finds that the gap between visible and held-out performance grows with code size [10]. ImpossibleBench constructs tasks whose tests contradict their specifications, so that any pass reveals a shortcut, and documents behaviors ranging from test deletion to operator overloading [11]. EvalPlus showed earlier that augmenting HumanEval and MBPP with additional tests substantially lowers measured correctness [13]. Related work on LLM self-assessment reports that models struggle to correct their own reasoning without external feedback [31] and that LLM evaluators favor their own generations [32].

## II-D Independence and Assurance Cases

Independent verification and validation (IV&V) is a mature discipline. IEEE Std 1012 distinguishes technical, managerial, and financial independence of the verification organization [6], and DO-178C scales required verification activities and their independence with the software level [7]. Knight and Leveson showed experimentally that independently developed program versions fail in correlated ways, so that nominal independence does not imply statistical independence of failures [33]. Assurance cases structure a claim, its argument, and its supporting evidence, for example with the Goal Structuring Notation [34, 35]. Our framework adapts these ideas to a setting they did not anticipate: a non-human producer that optimizes against its own evaluator and whose verifier may share its failure modes. Finally, Zave and Jackson distinguish requirements, specifications, and domain assumptions [36], a distinction we use to separate the gaps in Section III.

## III Why Self-Validation Fails

## III-A Setting and Notation

Let $R$ denote the stakeholder requirement, $S$ the written specification, $W$ the assumptions about the deployment environment, and $P$ the program produced by an agent. Following Zave and Jackson [36], a correct development satisfies $S\wedge W\models R$ and $P\models S$ . A test suite $T$ is a finite set of pairs $(x,o)$ where $x$ is an input or interaction sequence and $o$ is an oracle; we write $\mathit{acc}_{T}(P)$ when $P$ passes every test in $T$ . We distinguish a visible suite $T_{v}$ , available to the builder, from a hidden suite $T_{h}$ derived from the same specification and never exposed to the builder.

In self-validation, the builder forms an interpretation $\hat{S}$ of $S$ , produces $P$ and a suite $T_{b}$ from $\hat{S}$ , and iterates until $\mathit{acc}_{T_{v}\cup T_{b}}(P)$ holds. The release signal is that predicate.

## III-B Tests Become Rewards

Once $\mathit{acc}_{T_{v}}$ terminates the loop, it operates as a reward. Any program in the set $\{P\mid\mathit{acc}_{T_{v}}(P)\}$ ends the episode, and that set is far larger than $\{P\mid P\models S\}$ because $T_{v}$ samples a small part of the input space. The agent has no incentive to distinguish the two sets, and capable agents demonstrably exploit the difference [10, 11]. We define the evaluation gap of a development process over a task set as

 $\Delta_{\mathit{eval}}=\Pr\big[\mathit{acc}_{T_{v}}(P)\big]-\Pr\big[\mathit{acc}_{T_{h}}(P)\big],$ 

(1)

which is positive when visible success overstates correctness with respect to the same specification.

## III-C Consistency Is Not Correctness

The second failure mode does not require any optimization pressure. If $\hat{S}\neq S$ , then $P$ and $T_{b}$ can agree with each other while both disagree with $S$ . The builder’s tests then confirm the builder’s misunderstanding. This is a correlated, or common-mode, failure in the sense of Knight and Leveson [33]: two artifacts produced from the same interpretation fail on the same inputs. Separating test generation into another agent [29] reduces this correlation only if the second agent does not inherit $\hat{S}$ , for example by reading the builder’s code, rationale, or tests. Using the same underlying model may preserve part of the correlation even with separated contexts, since the two agents share training data and inductive biases. Whether context separation suffices, or whether model diversity is also needed, is an empirical question that we address in RQ2.

Incomplete self-evidence. A third failure mode occurs even when $\hat{S}=S$ . The builder can implement $S$ correctly and still test only part of it: $T_{b}$ exercises the behaviors the builder had in mind, and the others are correct without evidence. A later change that breaks them passes $T_{b}$ . Self-validation cannot reveal this gap, because the builder chooses what to test with the same attention that missed it.

## III-D Four Gaps Between Intent and Production

Table I decomposes the distance between $R$ and production behavior into four gaps. Verification against the specification can close only the conformance gap. The evaluation gap is closed by withholding the assurance artifacts from the builder. The requirement and model gaps cannot be closed by verification alone, because both concern whether $S$ and $W$ are the right objects to verify against. Our framework therefore does not claim to close them; it makes them explicit and assigns them to human approval and to runtime feedback.

## IV-A Separation of Powers

The framework assigns three roles. The builder produces $P$ . The verifier produces evidence about $P$ against $S$ . The human approves what must be demonstrated and decides whether the evidence suffices. Five principles govern the relation between roles.

P1 

No self-certification. Artifacts produced by the build plane, including the builder’s tests, never count as evidence on their own.

P2 

Information asymmetry. Assurance artifacts are withheld from the builder. The builder receives only reproducible counterexamples, which prevents the assurance suite from becoming the new reward surface.

P3 

Specification before code. Phase A evidence is derived and frozen before the verifier observes $P$ .

P4 

Verify, do not repair. The verifier demonstrates defects but does not fix them. A verifier that repairs becomes a second builder and inherits the builder’s incentives.

P5 

Explicit residual uncertainty. Evidence is reported per requirement with what was not verified, and the release decision remains human.

We adapt the three dimensions of independence in IEEE Std 1012 [6] to agents. Technical independence concerns context and model: the verifier does not share the builder’s conversation, rationale, or artifacts, and may use a different model. Managerial independence requires that the verifier is not invoked, configured, or terminated by the builder’s orchestration loop. Incentive independence, the agentic counterpart of financial independence, requires that the verifier’s objective is not tied to the builder’s success; a verifier rewarded for a green pipeline has the same incentive as the builder.

## IV-B The Verification Contract

A specification states what the system must do. A Verification Contract states what must be demonstrated before the system is accepted. For each requirement it lists guarantees, which are falsifiable claims, and required evidence, which states the techniques and thresholds that support each guarantee. Fig. 2 shows an excerpt. The contract plays the role of the claim structure in an assurance case [34], with one difference: it is fixed and approved before any implementation exists, so the builder cannot shape the claims after the fact.
