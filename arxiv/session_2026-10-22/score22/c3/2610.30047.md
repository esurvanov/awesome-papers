## ABSTRACT
Coding agents are typically evaluated using one-shot, well-formulated prompts. Benchmarks such as SWE-bench use existing GitHub issues as input for a coding agent and evaluate whether the agent successfully solves the task. However, in real-world use cases, prompts are often not as well-formulated or structured as existing GitHub issues. Additionally, a coding agent session is not limited to a single prompt; it typically involves a multi-turn interaction in which the user iteratively adds new tasks and requirements that the agent must fulfill. To benchmark these abilities, we developed SWE-DIVE, a dynamic, interactive validation and evaluation framework for benchmarking coding agents in a multi-turn environment. To achieve this, we introduce a user simulator that can simulate different behavioral patterns and communicate with the coding agent. We also introduce a conversation validator that evaluates the user simulator's outputs to determine whether they fulfill the initial requirements and guide the agent toward successfully solving the task. The entire framework is embedded in a Harbor environment, which orchestrates the coding agent, user simulator, and conversation validator, and executes the test environment to determine whether the agent successfully solves the task. Our results and source code are available in our GitHub repository (https://github.com/lorenzbrehme/swe-dive_usersim).

## 1 Introduction

Agents are typically evaluated on benchmarks collected from GitHub issues or crafted for a certain task, like SWE-bench (Jimenez et al.,, 2024). However, the input format of a complete, detailed github issue is not how users normally interact with agents – users often give a high-level prompt that is lacking detail and iterate on the prototype until it’s complete (Baumann et al.,, 2026). In other words, agent prompting is a process of iteratively defining the problem rather than a one-shot attempt.

Baumann et al., (2026) investigated the behavior of humans using a coding agent and found that the agent is used in multi-turn interactions, where different roles emerge, such as the expert nitpicker or the ambiguous programmer. These multi-turn behaviors are already studied in benchmarks such as CodeFlowBench (Wang et al.,, 2026) and CodeGen (Nijkamp et al.,, 2023), which evaluate coding agents in multi-turn settings. In these benchmarks, tasks typically involve iteratively adding new features, requiring the agent to continually adapt and find solutions. Additionally, AmbigSWE-bench explores the ambiguous behavior of users by providing ambiguous instructions and allowing the agent to ask clarification questions in order to resolve this ambiguity (Vijayvargiya et al.,, 2025).
These multi-turn benchmarks follow a predefined process and do not adapt depending on what the agents ask. Baumann et al., (2026) demonstrates that 41% of the turns were pushbacks, indicating that the agent did not perform as the user expected and that clarification was needed. In addition, Vijayvargiya et al., (2025) shows that the agent is still prompted with the full task list, whereas a more realistic setup involves users providing very nitpicky and vague instructions, iteratively adding new tasks in a multi-turn conversation.

To overcome these challenges, we introduce a dynamic interactive validation and evaluation benchmark, SWE-DIVE, that builds upon the DIVE methodology, originally proposed for evaluating retrieval-augmented generation systems (Brehme et al.,, 2026). SWE-DIVE transforms existing software engineering benchmarks, such as SWE-bench, into dynamic, interactive evaluation environments. It splits the original tasks into incremental sub-tasks and uses an LLM to simulate the user’s discovery process.

## 2 Related Work

Benchmarking software engineering agents requires a collection of tasks consisting of an existing codebase and a corresponding test suite that the agent must satisfy. Benchmarks such as SWE-bench (Jimenez et al.,, 2024) and Terminal-Bench (Merrill et al.,, 2026) provide such tasks by using existing software repositories containing issues that have already been resolved by human developers. Each task includes a predefined initial state, where the provided tests fail, and an expected final state, where the tests pass after the required code modifications have been applied.

These tasks are typically provided to the agent through a single-shot prompt describing the issue to solve. After the agent modifies the codebase, the benchmark executes the associated test suite to determine whether the task has been successfully completed. The resulting success rate is then used as a metric to compare the performance of different software engineering agents.

To extend these benchmarks, approaches such as CodeFlowBench (Wang et al.,, 2026) and CodeGen (Nijkamp et al.,, 2023) introduce multi-turn interactions into the evaluation process. These benchmarks define a sequence of tasks that are provided iteratively to the agent, allowing it to complete multiple development steps over several interactions. Some approaches initialize agents from scratch (Nijkamp et al.,, 2023; Orlanski et al.,, 2025), while others build upon existing repositories by selecting and filtering issues or introducing additional requirements over multiple iterations, such as in CodeFlowBench (Wang et al.,, 2026).
However, these benchmarks remain largely static, as the sequence of tasks and requirements is predefined. They do not capture realistic user behavior, where requirements evolve dynamically, users provide feedback, and goals may change during the development process (Baumann et al.,, 2026; Vijayvargiya et al.,, 2025).

Another approach for introducing multi-turn behavior is to provide feedback based on the final outcome of the agent’s implementation. In this setting, the agent receives information about whether the tests have passed and, if not, is provided with the test results to iteratively improve its solution (Yang et al.,, 2023). However, these benchmarks still rely on highly structured and formalized task descriptions.

To address this limitation, Garg et al., (2025) modifies SWE-bench task descriptions to create more realistic user requests. Similar approaches introduce ambiguity into the task descriptions by incorporating different user personas, where the agent can ask clarification questions to obtain additional information before starting the implementation (Vijayvargiya et al.,, 2025; Zhou et al.,, 2026).

Despite these improvements, an important aspect of realistic software development remains unexplored: users do not only clarify existing requirements but also introduce new tasks and requirements throughout the development process. Existing benchmarks primarily focus on solving a single predefined issue, whereas real-world interactions with coding agents often involve iterative collaboration, where users continuously refine goals and add new requests (Baumann et al.,, 2026). To address this gap, we introduce SWE-DIVE, a new benchmark-agnostic approach for evaluating coding agents through dynamic, multi-turn interactions that better reflect realistic user-agent collaboration.

## 3 SWE-DIVE

Figure 1: Overview of SWE-DIVE

SWE-DIVE is a dynamic, interactive validation and evaluation framework for benchmarking software engineering agents. It builds upon existing benchmarks, such as SWE-bench (Jimenez et al.,, 2024) and Terminal-Bench (Merrill et al.,, 2026), by transforming single-turn benchmark tasks into multi-turn interactive evaluations. This is achieved through a user simulator that collaborates with the agent to complete the original benchmark tasks.
The framework consists of three main components: the user simulator, the conversation validator, and the Task Completion Evaluator. The user simulator interacts with the evaluated agent, the conversation validator assesses the quality and validity of the interaction, and the Task Completion Evaluator determines whether the benchmark task has been completed successfully.

## 3.1 User Simulator

The first component of SWE-DIVE is the user simulator. This component leverages an LLM to simulate a user interacting with the evaluated software engineering agent. To achieve realistic user interactions, we ground the user simulator in existing, validated task descriptions that specify the underlying requirements and implementation context. This grounding enables the simulator to model a collaborative user who interactively discovers, clarifies, and refines requirements throughout the software implementation process. This distinguishes SWE-DIVE from existing benchmarks (Wang et al.,, 2026; Nijkamp et al.,, 2023), where interaction is primarily used to provide missing information rather than to model the iterative process of requirement discovery and refinement. The simulator presents the agent with tasks, responds to its questions, provides additional information as needed, and offers feedback based on the agent’s responses and modifications to the codebase. It iteratively advances the conversation by introducing follow-up requests or clarifications until the task has been completed successfully or no further progress can be made.

## Input: 

Before the interaction begins, the user simulator is assigned a role. We ground our user simulation in behavioral patterns from SWE-Chat (Baumann et al.,, 2026), which were derived from observations of real user interactions with coding agents. Specifically, we leverage three roles. The Expert Nitpicker maintains a stable overall goal while providing a series of precise, targeted corrections to the implementation. Each interaction refines how the agent implements the solution rather than what it is expected to build. The Vague Requester provides broad, underspecified instructions and delegates most implementation decisions to the agent. Finally, the Mind Changer reverses the overall goal during the interaction, fundamentally changing what the agent is expected to build rather than merely modifying the implementation details. These roles are not intended to represent distinct user populations or individual users. Rather, they capture diverse behavioral patterns observed in SWE-Chat and provide controlled conditions for studying how coding agents respond to different user behaviors.

In the first turn, the user simulator is prompted with the initial benchmark task 1. The complete task specification, such as the issue description from SWE-bench (Jimenez et al.,, 2024), is provided together with the reference solution describing the expected outcome.
This original objective serves as the grounding for the user simulator, which provides the context needed to guide the interaction. Rather than following a predefined sequence of subtasks, the simulator adaptively determines what information, clarification, or requirement should be communicated next based on the agent’s progress. In each turn, the user simulator receives the agent’s latest response together with the changes made to the codebase and uses this information to validate and adjust its next message. This enables the simulator to adapt the interaction to the agent’s behavior while maintaining alignment with the original task objective.

## Output: 

Based on the provided information, the user simulator generates an initial prompt for the agent containing the first subtask. This subtask serves as the starting point and is designed to guide the agent toward completing the overall benchmark task. In addition to the initial prompt, the user simulator generates a complete list of subtasks, providing an overall trajectory for solving the issue.

In subsequent turns, the user simulator generates only the next user prompt. Depending on the agent’s progress, this prompt may contain corrections, new subtasks, follow-up requests, or responses to the agent’s questions 5a.

Once the user simulator determines that the overall task has been completed successfully, it returns ‘done’ instead of generating another prompt, thereby terminating the simulation. This allows each agent to complete the task at its own pace 5b. Additionally, a maximum turn limit is enforced to prevent agents from entering endless interaction loops when they are unable to solve the benchmark task.

## 3.2 Conversation Validator

The conversation validator ensures that the conversation generated by the user simulator remains within the defined trajectory, follows the assigned user role, and effectively guides the agent toward solving the benchmark task. To achieve this, SWE-DIVE implements a validation loop, which can be seen as a modified form of chain-of-verification (Dhuliawala et al.,, 2023).

First, the conversation validator receives the output generated by the user simulator 2. It performs two validation steps: subtask validation and agent input validation. During the initial turn, it validates the generated list of subtasks. This list must cover all necessary steps required to solve the issue, avoid irrelevant tasks, and follow a clear and understandable progression toward the final goal.

In the initial and subsequent turns, the conversation validator evaluates the generated user prompts. Each prompt must remain aligned with the original benchmark issue, follow the defined subtask trajectory, match the assigned user role, and be understandable and actionable for the agent.

For each validation step, the conversation validator returns a boolean value indicating whether the generated output is valid 3. If an output is considered invalid, the validator additionally provides a reason explaining why the output does not satisfy the requirements and how it can be improved. This feedback is used within the validation loop to prompt the user simulator again, allowing it to regenerate an improved output 4a. This process continues until the validator approves the generated prompt. Once validated, the prompt is sent to the agent, which executes the requested task and provides its response back to the user simulator for the next interaction cycle 4b.

## 3.3 Task Completion Evaluator

The Task Completion Evaluator assesses the performance of the software engineering agent and provides quantitative metrics to enable a comprehensive evaluation. It is executed when either the maximum number of turns is reached or the user simulator determines that the conversation is complete. The Task Completion Evaluator leverages the execution environment of the original benchmark to verify whether the assigned task has been successfully completed and calculates the overall success rate.
Upon completion of an evaluation, SWE-DIVE provides a comprehensive performance summary, including the average number of conversation turns, and a detailed analysis of the interactions. Furthermore, the evaluation metrics can be analyzed based on the assigned user role, allowing for a comparison of agent performance under different interaction scenarios. SWE-DIVE also enables filtering based on the number of required turns, providing insights into the efficiency and behavior of agents in realistic, multi-turn software engineering tasks.

## CONCLUSION
Our preliminary results demonstrate how the SWE-DIVE benchmark can be used in practice.
The results reveal that different user personas can surface distinct failure modes and robustness properties that would be missed by evaluating an agent through only single-turn interactions or a single interaction style.

This user simulation enables a diverse range of use cases due to the variety of benchmarks implemented in the Harbor framework (Harbor Framework Team,, 2026). Additionally, it supports diverse user roles adapted from real-world users and inspired by SWE-Chat (Baumann et al.,, 2026). We define three user roles–Expert Nitpicker, Mind Changer, and Vague Requester–which differ in how users communicate requirements, provide feedback, and evolve their goals throughout the interaction. These roles provide controlled behavioral variation grounded in observed real-user interactions. While this diversity determines the range of user behaviors represented in the benchmark, the fidelity of the simulation depends on how closely these behaviors reflect real user interactions.

SWE-DIVE aims to improve fidelity by modeling users as interactive participants rather than static prompt generators. The user simulator conditions each turn on the agent’s latest response and code changes, allowing simulated users to provide corrections, introduce follow-up requirements, or modify their requests as the interaction unfolds. These interactions are grounded in validated benchmark tasks and underlying user behaviors, enabling the user simulator to operate in a multi-turn environment while adopting one of the defined user roles. A direct comparison between SWE-DIVE trajectories and held-out human SWE-Chat trajectories remains an important direction for future work.

Beyond fidelity, the interaction between the simulated user and the agent also raises an important question of validity: whether the use of different simulated users can affect the conclusions drawn from an evaluation. The qualitative trajectories provide an initial indication that this may be the case. On the same Astropy task, different simulated user behaviors resulted in distinct agent trajectories and outcomes: the Vague Requester induced broader changes that introduced regressions, whereas the Expert Nitpicker guided the agent toward a successful resolution through targeted corrections.
