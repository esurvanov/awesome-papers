## LLMSeg: Training-Free Text-Prompted Image Segmentation with B-Splines

Abdullah Hamdi

Affiliation: King Abdullah University of Science and Technology (KAUST)

Abstract

Promptable segmentation models such as SAM 3 achieve remarkable open-vocabulary
performance but require dedicated architectures, large-scale annotation
engines, and task-specific training. We ask a different question: can a
general-purpose multimodal large language model (MLLM) segment images
directly, without an added segmentation head, mask decoder, or training?
We present LLMSeg, a training-free pipeline that turns a vision-capable LLM
into a text-prompted image segmenter. LLMSeg decomposes segmentation into three
LLM-driven stages. First, detect localizes all instances matching a
free-form text query and describes their coarse morphology. Next,
segment traces each instance using closed periodic B-splines confined to
its detected box. These splines define an outer boundary and optional hole
loops. Finally, refine iteratively proposes focus boxes around residual
errors and retraces confined splines. The process ends when the mask stabilizes
or the pass budget is exhausted.
The output is a binary mask with inspectable intermediate geometry.
We evaluate LLMSeg across ten referring and reasoning segmentation splits
(ReasonSeg and RefCOCO/+/g). We also evaluate open-vocabulary instance
segmentation (LVIS, COCO, and SA-Co), semantic segmentation, and zero-shot
detection (ODinW13 and RF-100VL). With an off-the-shelf Gemini-3.7-Flash backend, LLMSeg is
competitive with and often surpasses the specialist SAM 3 model on identical
items. It reaches 71.5 cIoU on ReasonSeg val without additional
segmentation-specific training. Backend model updates can improve accuracy without
retraining the pipeline.
The code is available at https://abdullahamdi.com/llmseg/.

## 1 Introduction

Text-prompted segmentation (producing a pixel mask for every instance that
matches a language query) is a foundational capability for multimodal AI.
The dominant approach builds ever-stronger specialist models: the SAM series
(Kirillov et al., 2023; Ravi et al., 2024) introduced promptable
visual segmentation. SAM 3 (Carion et al., 2026) extends this capability to
promptable concept segmentation from noun phrases. It relies on a
dedicated detector-tracker architecture and a massive human- and
model-in-the-loop data engine.

In parallel, multimodal large language models (MLLMs) have acquired remarkable
general visual competence. Their capabilities include grounding, counting, and
coarse localization (Comanici et al., 2025; OpenAI, 2023; Bai et al., 2025; Deitke et al., 2025).
However, they are widely assumed to require a trained segmentation decoder,
such as SAM, to produce dense pixel masks
(Lai et al., 2024; Rasheed et al., 2024; Carion et al., 2026).
We challenge this assumption. We present LLMSeg (Figure 1),
a fully training-free pipeline. A general-purpose MLLM is its only
vision component. It returns geometry: closed curves that deterministic
code rasterizes into a mask and keeps inside each box. The work splits into
three stages. Detect localizes every instance the query matches and
returns its box. Segment traces that instance with closed periodic
B-spline loops confined to the box. Refine reads the rendered overlay
and retraces the errors that remain, each inside a signed focus box.

This design provides an explicit parametric intermediate representation:
cubic traces encode smooth curves, while degree-one traces encode straight edges.
Rasterization and refinement need not preserve a smooth final boundary. With
topology enabled, holes are specified as subtractive loops.
Reasoning queries (“the food that the bird likes to eat”) work off the shelf
because each query is interpreted by the same LLM that performs the segmentation.
Every stage emits human-readable JSON, making geometric decisions
inspectable. Since LLMSeg adds no trained parameters, backend upgrades require no pipeline
retraining and usually come with segmentation accuracy gains.

Contributions:
(i) We propose LLMSeg, a training-free promptable segmentation pipeline
in which an MLLM predicts parametric B-spline geometry confined to each detected box and
then refines it inside signed focus boxes.
(ii) We show for the first time at benchmark scale that a
general-purpose MLLM can perform dense text-prompted segmentation without any
trained segmentation component. LLMSeg with Gemini-3.7-Flash as the backend is
competitive with SAM 3 (Carion et al., 2026) on ReasonSeg, RefCOCO/+/g, LVIS,
COCO, SA-Co, ADE20K, Cityscapes, ODinW13, and RF-100VL, and reaches 71.5 cIoU on
ReasonSeg val, the best among methods not fine-tuned for the task.
Further analysis shows LLMSeg’s segmentation quality follows the backend strength without retraining, offering automatic improvement in segmentation with better backends.

## 2 Related Work

Segmentation models and MLLM-driven segmentation.
SAM (Kirillov et al., 2023) introduced promptable segmentation.
SAM 2 (Ravi et al., 2024) extended it to video.
SAM 3 (Carion et al., 2026) extended it to open-vocabulary concept
prompts.
GLIP (Li et al., 2022b), GroundingDINO (Liu et al., 2024a),
OWLv2 (Minderer et al., 2023), and
DINO-X (Ren et al., 2025) are trained specialists.
MLLM-based methods add language reasoning but retain a trained mask
component. LISA (Lai et al., 2024) decodes an LLM’s
<SEG> token with SAM. GLaMM (Rasheed et al., 2024), PSALM
(Zhang et al., 2024c), and X-SAM (Wang et al., 2025a) also use trained
mask components. SAM4MLLM (Chen et al., 2024) and Seg-Zero
(Liu et al., 2025) train MLLMs to prompt SAM.

Training-free alternatives include RSVP (Lu et al., 2025) and
attention-based grounding (Kang et al., 2025). Agentic systems include
SAM 3 Agent (Carion et al., 2026) and the piipeline in Colon-Bench
(Hamdi et al., 2026). These approaches still delegate mask
production to a segmentation model. In contrast, LLMSeg uses only text
queries to a frozen, general-purpose MLLM. It requires no exemplars, input
boxes, or video prompts. The MLLM emits the final geometry, which our loop
revises directly.

Geometry as text and contour representations.
Representing geometry as text is not new. VisionLLM
(Wang et al., 2023) represents boundaries as short polygons in a
trained multitask pipeline.
VisionLLM v2 (Wu et al., 2024a) uses task-specific trained decoders.
PixelLLM (Xu et al., 2024) learns localization heads and obtains masks
through SAM. Text4Seg (Lan et al., 2025) generates segmentation tokens
but requires fine-tuning. General models such as Molmo
(Deitke et al., 2025) and Gemini (Comanici et al., 2025; Voigtlaender et al., 2025)
also provide pointing and coarse localization. Classical boundary
representations include spline snakes (Brigger et al., 2000). Trained
vertex predictors include Polygon-RNN++ (Acuna et al., 2018) and
Curve-GCN (Ling et al., 2019). LLMSeg uses this output space without
training a contour predictor. A frozen, general-purpose backend emits
control points that define the mask prediction. Only deterministic
geometric processing follows. Confined signed regions then allow the
refinement process to correct local parts of the mask.

## 3 Method

Figure 2: LLMSeg pipeline overview.
Detection localizes instances, segmentation traces box-confined B-splines,
and refinement corrects the mask within signed focus boxes ( $+$ adds pixels,
 $-$ removes them). Each MLLM call serves all instances (one is shown).

Overview.
Given an image $I$ and a free-form text query $q$ , LLMSeg predicts binary masks
for $N$ retained instances. We index these instances by $k=1,\ldots,N$ .
Stage 2 initializes each mask as $M_{k}^{(0)}$ . Refinement pass $t$ produces
 $M_{k}^{(t)}$ . Their union is $M^{(t)}=\bigcup_{k=1}^{N}M_{k}^{(t)}$ .
The final output $M$ is the union at termination.
A frozen multimodal LLM $f_{\phi}$ is the only vision component. No parameters
are updated, and no segmentation head is attached. The pipeline accesses
 $f_{\phi}$ only through fixed text prompts, with one prompt per stage call.
Each call is stateless and uses no tools. Deterministic code controls the
sequence. It also turns the returned geometry into masks.
Figure 2 shows the three stages.

## 3.1 Stage 1: detecting instances and their structure

A single detection call to $f_{\phi}$ takes $I$ and $q$ as input. For every
instance matching $q$ , it returns an axis-aligned box
 $b_{k}=[x_{k,1},y_{k,1},x_{k,2},y_{k,2}]$ and a confidence score. It also returns
a short morphology description of the coarse shape and aspect.
Optionally, it provides a topology descriptor that specifies the
component and hole counts. Near-duplicate boxes
are merged at IoU $\geq 0.9$ . Instances are then ordered in reading order. At
most $N_{\max}$ are kept, so $0\leq N\leq N_{\max}$ . Coordinates are given in
absolute pixels. The origin is at the top left. In set operations, $b_{k}$ 
denotes the pixel region inside that box. If $N=0$ , the output is empty.

## 3.2 Stage 2: from language to geometry

One batched call traces every instance at once. It returns an outer loop for
each instance. With topology conditioning, it also returns one
loop per predicted hole, each a list of control points.

Representation. A loop is a closed periodic B-spline of
degree $d$ . It is defined over a control polygon
 $P=(p_{1},\dots,p_{n})$ containing $n$ two-dimensional control points indexed by
 $i$ . The count $n$ can vary between loops. The polygon is wrapped so that
 $p_{i+n}=p_{i}$ :

 $C_{P,d}(u)\;=\;\sum_{i=1}^{n}B_{i,d}(u)\;p_{i},\qquad u\in[0,n],\quad C_{P,d}(n)=C_{P,d}(0),$ 

(1)

where $u$ is the curve parameter and $B_{i,d}$ are the uniform periodic
B-spline basis functions of degree $d$ (Piegl & Tiller, 1997).
Eq. (1) is a piecewise polynomial consisting of $n$ 
degree- $d$ segments. Each $B_{i,d}$ is supported on only $d{+}1$ knot spans.
Thus, each control point influences only $d{+}1$ segments, and a misplaced
point changes a bounded arc rather than the whole curve. Stage 3 does not edit
these original control points. Its locality comes from adding or
subtracting focus-box regions.

We also let the model choose the degree. The same call that places the control
points first chooses $d\in\{1,3\}$ based on the object’s form. It uses $d=3$ 
for rounded and organic silhouettes and $d=1$ for angular, straight-edged
ones. It then places the points as the selected degree requires. Cubic control
points are pushed outward toward the edge, whereas degree-1 vertices lie
directly on it. One degree is shared by all loops of all instances in the
stage-2 call.

Rasterization by sampling. Masks are produced by sampling the curve
and filling the resulting polygon, not by evaluating an implicit function.
Let $\mathrm{clip}_{b}$ denote the per-coordinate clamp onto a box $b$ . Let
 $\mathrm{Fill}$ denote even-odd polygon fill (Foley et al., 1996). One
loop then becomes the region

 $\mathcal{R}_{b,d}(P)\;=\;\mathrm{Fill}\Big(\big(\mathrm{clip}_{b}(C_{P,d}(u_{r}))\big)_{r=1}^{m}\Big),\qquad u_{r}=\tfrac{r-1}{m-1}\,n,$ 

(2)

with $m$ samples indexed by $r$ , uniformly spaced in the curve parameter
and including the repeated endpoint. For cubic loops, $m$ is proportional to
the perimeter of $b$ , so small and large objects are rasterized at comparable
boundary resolution. For $d=1$ , the control polygon is filled directly.
Eq. (2) applies $\mathrm{Fill}$ to an ordered sequence of boundary
samples. The control points are used as returned, and the sampled boundary is
clamped to $b$ before filling.
A trace can never leave its own detected box, so a hallucinated control point
cannot paint across the image. Overlapping instance boxes can still produce
overlapping masks. Consequently, detection quality upper-bounds segmentation
quality.
With topology conditioning off, the initial instance mask is
 $M_{k}^{(0)}=\mathcal{R}_{b_{k},d}(P_{k}^{\mathrm{out}})$ , where
 $P_{k}^{\mathrm{out}}$ is instance $k$ ’s outer control polygon.
When topology conditioning is enabled, regions rasterized from predicted hole
loops are subtracted from the outer region to obtain $M_{k}^{(0)}$ .
The predicted hole count is not guaranteed to survive loop overlap,
rasterization, refinement, or cleanup.

## 3.3 Stage 3: iterative refinement

The initial outline often identifies the right object but misses boundary
detail. Each refinement pass asks the model to locate errors on the current
mask overlay. It then retraces those regions within smaller boxes. In pass
 $t=1,\ldots,T$ , both calls receive $I\oplus M^{(t-1)}$ , the previous union
mask rendered over the image. Leaving the fixed prompts and structural context
implicit, we write the loop as

 $\displaystyle\{(k_{j},\beta_{j},\sigma_{j})\}_{j}$ 
 $\displaystyle=f_{\phi}(I\oplus M^{(t-1)},q),$ 

(3)

 $\displaystyle M_{k}^{(t)}$ 
 $\displaystyle=\mathrm{Compose}\!\left(M_{k}^{(t-1)},\{(\sigma_{j},\mathcal{R}_{\beta_{j},3}(P_{j}))\}_{j:\,k_{j}=k}\right).$ 

Here $j$ indexes the focus boxes in the current pass. The value $k_{j}$ identifies
the instance corrected by the $j$ th focus box. The box $\beta_{j}$ is confined
to that instance’s box. The sign $\sigma_{j}\in\{+1,-1\}$ requests addition or
removal. A second call uses the same overlay, query, and box geometry. It
returns cubic control polygons for all retained boxes in one batch, where
 $P_{j}$ is the control polygon of the $j$ th focus box, which corrects instance
 $k=k_{j}$ .
Before this call, an effect gate discards boxes with negligible potential to
change the mask. If none remain, retracing is skipped.

Composition applies each correction to instance $k_{j}$ and cleans up small
artifacts. It carries a per-instance commitment field that is implicit in
Eq. (3). This field resists opposing edits and reduces oscillation.
Boolean composition and cleanup need not leave a globally smooth spline boundary.
The updated union $M^{(t)}$ feeds the next pass. Both model calls batch all
instances, so each pass uses at most two MLLM calls regardless of $N$ .
The gating and cleanup settings, the per-pixel composition rule, and a
worked example of each call are given in Section B.
Refinement ends after at most $T$ passes, or once the
union mask changes only negligibly for $s$ consecutive passes (the patience
criterion).
Section 4 gives additional details, and Section 5 examines convergence.

## 4 Experiments

## 4.1 Experimental setup

Benchmarks and metrics.
We follow the image evaluation suite of SAM 3 (Carion et al., 2026). We
use each benchmark’s standard metrics.
(i) Referring and reasoning segmentation: We evaluate on
ReasonSeg (Lai et al., 2024) (val/test) and all splits of RefCOCO, RefCOCO+,
and RefCOCOg (Kazemzadeh et al., 2014; Mao et al., 2016). We report
gIoU (mean per-item IoU) and cIoU (cumulative
 $\nicefrac{{\sum\text{I}}}{{\sum\text{U}}}$ ).
(ii) Open-vocabulary instance segmentation: We evaluate on
LVIS (Gupta et al., 2019) and COCO (Lin et al., 2014), and additionally on SA-Co/Gold
(Carion et al., 2026), which is reported in the appendix
(Table 8). We report presence-gated cgF1 and pmF1 (with hard
negative prompts), positive-set IoU, and COCO-style box/mask AP.
(iii) Semantic segmentation: We report 19-class mIoU on
Cityscapes (Cordts et al., 2016), using deterministic mask compositing.
We use ADE20K (Zhou et al., 2019) as a class-prompted oracle upper bound.
(iv) Zero-shot detection: We evaluate on ODinW13
(Li et al., 2022a) and RF-100VL (Robicheaux et al., 2025). We report
AP0, the mean per-subset box AP computed from masks.

Protocol: complete splits and sampled subsets.
We run each split in full whenever end-to-end evaluation is practical.
This includes ReasonSeg val (200) and test (779), Cityscapes val (500), and
every ODinW13 and RF-100VL subset ( $6{,}237$ and $1{,}987$ items). In total,
we fully evaluate $9{,}703$ of the $17{,}703$ scored items. Four of the ten
benchmarks are run in full.
The remaining annotation files contain $10^{4}$ to $10^{5}$ items, making full
MLLM inference impractical. We instead draw uniform random samples with
seed 0. We do not take the first items because the annotation files are
strongly ordered. We sample $1{,}500$ items each from LVIS and COCO,
 $1{,}000$ from ADE20K, and $500$ from each RefCOCO/+/g split. The item
counts above cover the ten benchmarks of the main tables. The appendix
SA-Co/Gold evaluation uses a further $2{,}500$ items covering all seven domains.
On these sampled splits, we run every baseline once on the full split.
We then recompute its metrics on exactly the item set seen by LLMSeg, using a
shared-key intersection. Negative sampling is also identical: 3 negatives per
positive for LVIS and COCO, with seed 0.

LLMSeg configuration.
The main results use Gemini-3.7-Flash as the backend for all
three stages. The backend selects the Stage-2 curve degree
 $d\in\{1,3\}$ (Section 3). This degree is shared across all
instances in a call. Refinement curves are always cubic.
Refinement uses a budget of $T{=}8$ passes, a cap of $N_{\max}{=}200$ 
instances per image (matching SAM 3’s cap), and a focus-box budget of 6
per instance per pass.
The stopping criterion is
 $|M^{(t)}\triangle M^{(t-1)}|<\varepsilon\,|\bigcup_{k=1}^{N}b_{k}|$ ,
where $\varepsilon{=}0.005$ . The loop stops when this criterion holds for
 $s{=}3$ consecutive passes with $t\geq 1$ . Here, $s$ is the stopping patience,
 $|\cdot|$ counts pixels, and $\triangle$ denotes symmetric difference. The
denominator is the union of the instance boxes. By Eq. (2), this is
the only region that a pass can alter. Normalizing by the full image would
make the same threshold behave very differently for small and large objects
(Section 5).

A full run uses 2 MLLM calls for detection and segmentation. Each refinement
pass adds at most 2 calls. Thus, the maximum is $2T{+}2=18$ calls, although
early stopping keeps the measured mean well below this limit. The stage-1
topology descriptor (Section 3) is optional. The main results
disable it for all three stages (Section 5). We use the same
settings on every benchmark and tune nothing per dataset.

Baselines.
Our two main baselines are from the SAM 3 paper (Carion et al., 2026).

## 4.2 Main results

Tables 1 to 3 summarize ten benchmarks.
Figure 4 shows one example per setting. Additional examples
appear in Figures 10 to 14.

Reasoning segmentation.
On ReasonSeg (Table 1), LLMSeg reaches 71.5 cIoU on
validation. This is the best result among methods not fine-tuned for the task.
Refinement adds 6.9 cIoU over the segment stage alone. The gIoU scores and
complete published results for both tasks appear in
Section D.1.

Referring expression segmentation.
On RefCOCO/+/g (Table 1), LLMSeg substantially outperforms
SAM 3, while SAM 3 Agent generally remains stronger. Refinement improves
cIoU across all eight splits. On RefCOCO testB, LLMSeg reaches 76.0 cIoU, the
best zero-shot result on that split. This result shows that refinement narrows
the gap to SAM 3 Agent.

Open-vocabulary instance segmentation.
LLMSeg reaches 53.9 and 56.1 cgF1 on LVIS and COCO
(Table 3). It outperforms both SAM 3 baselines in
cgF1 but trails SAM 3 in mask AP.

Semantic segmentation and zero-shot in-the-wild detection.
LLMSeg achieves 59.2 gIoU on ADE20K and 53.3 mIoU on Cityscapes
(Table 2). On Cityscapes, it trails SAM 3 by 10.4
points. Dense scene labeling therefore remains a limitation. On zero-shot
detection, LLMSeg reaches 57.2 AP0 on ODinW13 and 31.4 on RF-100VL
(Table 2). It exceeds SAM 3 on all four metrics in both
benchmarks. Its AP0 on RF-100VL is $2.2\times$ that of SAM 3, showing
strong cross-domain transfer.

## 5 Analysis

## 5.1 Backend progress transfers without segmentation training

We hold the pipeline fixed ( $T{=}12$ , topology on) and test 21 backends from
six developers. Stage-2 gIoU ranges from $13.4$ to $74.2$ on ReasonSeg val
(Figure 5). Recently-released GPT-6 Astra reaches $74.2$ without a
segmentation model, compared with $72.4$ for SAM 3 Agent driven by Gemini-3.7-Flash.
The benefit is that LLMSeg can use better backends without retraining.
General benchmark capability is a weak
predictor of segmentation quality. Strong public scores do not reliably
translate into strong masks (e.g., Claude Opus 5). The full ranking and generation
comparisons are in Section E.2. The appendix also reports
the stage-2 and final results and the study protocol.

## 5.2 Refinement improves the boundary and usually stops early

With Gemini-3.7-Flash, refinement improves every benchmark in
Tables 1 to 3. Focus boxes let the model
correct a local boundary without redrawing the object. In the topology-enabled
ablation, removing refinement reduces cIoU by $5.4$ on ReasonSeg and $12.7$ 
on RefCOCO (Table 4). This is the clearest component
effect. However, refinement is also the largest source of inference cost.
The loop has no convergence guarantee, so we measure both mask stability and
quality. In the $T{=}12$ ReasonSeg study, $79\%$ of items stop before the cap
(Figure 15a). The median item uses six passes, while $18.5\%$ 
reach the cap.
We score the mask after each pass budget (Figure 6). Four
passes recover $2.7$ of the eventual $3.2$ gIoU gain. Raising $T$ from $8$ to $12$ changes gIoU by under $0.1$ . The main results
therefore use $T{=}8$ . At $T{=}12$ , early stopping cuts mean calls from $26$ to $14.7$ .

final-mask quality and inference calls with Gemini-3.7-Flash on 200 items per split. The shaded row uses the

Detection helps the initial trace. Removing detection lowers initial
cIoU from $68.3$ to $60.3$ on ReasonSeg. On RefCOCO, it lowers initial cIoU
from $66.0$ to $63.5$ . After refinement, the no-detection configuration closes
these gaps with fewer total calls. Detection’s initial advantage is larger on
the 63 ReasonSeg targets with disconnected ground-truth masks ( $+11.3$ cIoU).
After refinement,

Batching bounds the cost as instance count grows. Per-instance cropped refinement
increases ReasonSeg calls from $14.3$ to $21.3$ (49%). This yields a
 $2.3$ -point cIoU increase. On RefCOCO, it adds calls for only a $0.4$ -point
increase. Batched tracing uses one call, regardless of the instance count, and hence it is our default choice. In contrast, crop-based
calls grow with the number of instances.

Letting the model choose the degree helps. Forcing polygon loops
(B-splines of degree $1$ ) degrades performance on some instances. Letting the
model pick the degree improves it, specially on curved structures that are difficult to represent with straght lines ( see Figure 22 in the Appendix).

## 6 Conclusion

We presented LLMSeg, a training-free pipeline that transforms a multimodal LLM
into a text-prompted segmenter using box-confined B-spline geometry and
iterative focus-box refinement. Across ten benchmarks spanning four task
families, LLMSeg is competitive with SAM 3 and performs better on reasoning
queries, rare domains, and some metrics. Its limitations include
detection errors, imprecise pixel-level boundaries, amorphous classes, and
inference cost. The code, prompts, and evaluation harness are available at https://abdullahamdi.com/llmseg/.

## Appendix A Extended Related Work

Promptable and open-vocabulary segmentation.
SAM (Kirillov et al., 2023) introduced promptable segmentation with
points, boxes, and masks. SAM 2 (Ravi et al., 2024) extended it
to video, while SAM 3 (Carion et al., 2026) extended it to open-vocabulary
concept prompts by training a DETR-based detector-tracker
(Carion et al., 2020; Kamath et al., 2021) with data from a purpose-built data
engine.
Open-vocabulary detection and segmentation methods
(Gu et al., 2021; Minderer et al., 2022; Ding et al., 2022; Liang et al., 2023) leverage
vision-language encoders such as CLIP (Radford et al., 2021). GLIP
(Li et al., 2022b) and GroundingDINO (Liu et al., 2024a) cast detection
as phrase grounding, with OWLv2 (Minderer et al., 2023),
LLMDet (Fu et al., 2025), APE (Shen et al., 2024), DINO-X
(Ren et al., 2025), GLEE (Wu et al., 2024b), and T-Rex2
(Jiang et al., 2024) pushing scale and prompt modalities. All of these are
trained specialists. LLMSeg instead treats segmentation as an emergent
capability of a general MLLM, requiring no segmentation training at all, and
uses only text prompts (no exemplars, boxes, or video, unlike SAM 3).

MLLMs for grounding and segmentation.
A large family attaches a trained mask decoder to an (M)LLM. LISA
(Lai et al., 2024) introduced reasoning segmentation by decoding a
<SEG> token with SAM. GLaMM (Rasheed et al., 2024), GSVA
(Xia et al., 2024), OMG-LLaVA (Zhang et al., 2024a), PSALM
(Zhang et al., 2024c), EVF-SAM (Zhang et al., 2024b), HyperSeg
(Wei et al., 2024), and X-SAM (Wang et al., 2025a) refine this recipe.
SAM4MLLM (Chen et al., 2024) and Seg-Zero (Liu et al., 2025) train the
MLLM to emit prompts for SAM. Training-free alternatives still delegate the
pixels to a segmentation model. RSVP (Lu et al., 2025) and attention-based
grounding (Kang et al., 2025) use the MLLM for localization only, and
SAM 3 Agent (Carion et al., 2026) lets an MLLM drive SAM 3 as a tool,
similar in spirit to set-of-mark prompting (Yang et al., 2023).
Native MLLM segmentation has appeared only as coarse per-token masks in
Gemini 2.5 (Comanici et al., 2025; Voigtlaender et al., 2025). SAM 3 reports that
these masks lag far behind those of specialists. LLMSeg is, to our knowledge,
the first pipeline in which a frozen, general-purpose MLLM produces the
final mask geometry itself, as parametric splines rather than pixels. No
downstream component is trained, and the pipeline achieves accuracy competitive
with trained systems. The prior work closest to this output space is discussed
next.

MLLMs that emit coordinates as text.
Writing geometry down as tokens rather than decoding it is not itself new. What
is new here is that the tokens are the final answer. In prior work the emitted
text is an intermediate consumed by a trained head, and the pipeline around it
is trained. VisionLLM (Wang et al., 2023) is the closest precedent. It
represents an instance boundary as a short polygon, typically 16 points, emitted
by the language model, but keeps a trained decoding head per task, which both
ties generalization to the task set seen in training and caps mask resolution at
the vertex budget. VisionLLM v2 (Wu et al., 2024a) scales that recipe to
hundreds of vision-language tasks by routing a special per-task token to a
decoder fine-tuned for that task, while fine-tuning the MLLM for each task.
PixelLLM (Xu et al., 2024) adds an MLP head to regress locations and an
encoder to embed an input box, giving the MLLM localization and grounding. It
trains the pipeline end to end and still obtains masks by prompting SAM with a
box. Text4Seg (Lan et al., 2025) makes the most extensive use of text as
an output space: it defines segmentation tokens over a row-ordered grid that is
encoded and decoded so that masks are produced by generating text, yet the MLLM
must be fine-tuned to generate them. Beyond segmentation,
Jiang et al. (2026) cast detection as
next-point prediction over the same kind of structured coordinate text, training
the full pipeline with supervised fine-tuning followed by reinforcement learning,
and report detection and grounding but no masks. PixelVLA
(Liang et al., 2026) carries pixel-level grounding into
vision-language-action models with trained pixel modules. Perceive Anything
(Lin et al., 2025) instead couples SAM 2 with a modern LLM in a single
jointly trained pipeline for fine-grained region understanding, and its gains
are in recognition, explanation and captioning: the masks come from the SAM 2
branch, not from the language model. Frontier general-purpose models are
acquiring coarse localization on their own, with Molmo
(Deitke et al., 2025) able to point at queried objects and the Gemini series
grounding boxes well (Comanici et al., 2025; Voigtlaender et al., 2025), but neither comes
close to a specialized segmentation network or SAM 3 at the pixel level.
LLMSeg departs from all of the above in one consistent way: the backend is frozen
and general-purpose, nothing downstream of it is trained, and the control points
it writes out are the prediction itself rather than a prompt, a latent, or a
seed for a decoder.

Agentic MLLM pipelines.
Beyond single-call inference, MLLMs increasingly act as agents that decompose
visual tasks, call tools, and verify intermediate results
(Fan et al., 2024; Ge et al., 2023; Yang et al., 2023), including for
large-scale annotation (Carion et al., 2026). Colon-Bench
(Hamdi et al., 2026) shows such a workflow producing dense
lesion masks in a niche clinical domain where SAM 3 fails. However, the
masks are drawn by EdgeTAM (Zhou et al., 2025), a compact SAM 2 tracker
invoked by the MLLM as a tool. The pixel-level competence therefore remains
with the tool. LLMSeg follows this philosophy
with a fixed, budgeted loop: every stage is a structured JSON exchange, and
deterministic geometry code (rasterization, clamping, composition) provides
the reliability that free-form agent loops lack. The iterative
focus-box refinement can be seen as the model self-verifying its own
rendered prediction, an ability that improves with backend reasoning strength
(Section 5).

Contour and curve parameterizations of masks.
Describing a mask by its boundary rather than by a pixel grid has a decades-long
history. Active contour models (Kass et al., 1988) evolve a spline under
internal smoothness and external image forces, and Brigger et al. (2000)
showed that the optimal solution to the curvature-constrained snake energy is a
cubic spline, the classical argument for the representation we adopt. Deep
learning recast the same idea as vertex prediction. Polygon-RNN
(Castrejon et al., 2017) and Polygon-RNN++ (Acuna et al., 2018)
emit polygon vertices autoregressively for interactive annotation. Curve-GCN
(Ling et al., 2019) predicts all vertices at once with a graph network and
supports spline as well as polygon outputs. Deep Snake (Peng et al., 2020)
deforms an initial contour with circular convolutions, and PolarMask
(Xie et al., 2020) regresses boundary rays in polar coordinates.
PolyTransform (Liang et al., 2020) and SharpContour
(Zhu et al., 2022) deform the polygon of an existing mask to sharpen
it, and E2EC (Zhang et al., 2022) learns the contour initialization end to end.
BoundaryFormer (Lazarow et al., 2022) regresses polygons with a
transformer supervised only through a differentiable rasterizer. Parametric
curves are standard in text spotting as well, where ABCNet
(Liu et al., 2020) localizes curved text with Bézier control points.
LLMSeg shares its output space with this literature but little else. Each method
above is a network trained to regress vertices from image features over a fixed
label set, whereas LLMSeg obtains control points as text from a frozen
general-purpose MLLM, without added contour or mask supervision or a closed
vocabulary. This representation makes that possible: a handful of control
points is short enough to serve as a language-model output, and focus-box
confinement lets the refinement loop add or subtract local regions without
retracing the whole outline.

## Appendix B Method Details

## B.1 Structured replies and coordinate conventions

Prompts and output schemas.
Each stage uses a single prompt with a strict structured-output schema. Detect
returns a list of detections, each with a box, a label, a confidence, and a
morphology description. When topology conditioning is enabled, it also returns
the component and hole counts. For each instance ID, Segment returns a list of
spline loops, each with a role (outer boundary or hole), a degree, and control
points. The model chooses a degree of $1$ or $3$ , shared by every loop of every
instance in the call. The refinement schema has no degree field because focus
loops are always cubic. The two refinement calls return, respectively, typed
focus boxes tagged with their instance IDs and confined spline loops for every
surviving focus box. Each instance line in the segment prompt restates its box
as explicit numeric inequalities. Points are clamped in any case, but a
clamped-in point produces a worse outline than a correctly placed one.
§F gives the templates themselves.

Coordinate conventions across backends.
Everything passed between stages is expressed in absolute pixels, with the
origin at the top left. Boxes use the order $[x_{1},y_{1},x_{2},y_{2}]$ . Gemini-family
models natively emit boxes in the order
 $[y_{\min},x_{\min},y_{\max},x_{\max}]$ on a grid from $0$ to $1000$ .
Requesting $x$ -first order does not solve the problem: on some multi-instance
images, these models transpose their output, and no downstream check can catch
this because a swapped box is still well formed. We therefore request each
family’s native order and convert it afterward, transposing before
rescaling. All families return control points in $[x,y]$ order. If a loop is
transposed, we detect and repair it against its box: the swapped interpretation
lies almost entirely inside the box, whereas the raw interpretation does not.
Unlike boxes, points can be checked this way because their box is known ground
truth.

Recovering truncated replies.
Batched replies covering several instances can hit output limits. Rather than
discard a truncated reply, we keep every instance completed before the cut and
treat the rest as missing. The refinement stage can still grow them from their
boxes. The prompts fix the emission order by ascending instance ID, so
truncation affects the tail rather than an arbitrary subset. We recover Detect
replies in the same way. An instance that survives with no loops is scored as
an empty mask and is never dropped from the item.

## B.2 Rasterization and composition

Rasterization.
A cubic loop is rasterized with
 $m=\min\{2000,\max\{64,\operatorname{round}(2(w_{b}+h_{b}))\}\}$ samples
for a rasterization box $b$ of width $w_{b}$ and height $h_{b}$ . Before clipping,
this corresponds to roughly one sample per pixel of the box perimeter. Samples
include both endpoints, as in Eq. (2). Degree-1 loops use the closed
control polygon directly. The box is $b_{k}$ for an initial instance loop and
 $\beta_{j}$ for a refinement loop.

Composing a refinement pass.
 $\mathrm{Compose}$ in Eq. (3) is deterministic. Naively reapplying
the signed regions each pass makes the mask oscillate: a boundary pixel added
by one pass is removed by the next and added again. We therefore carry a signed
commitment field alongside each instance mask, marking every pixel as
committed to foreground, committed to background, or uncommitted, with a
magnitude that records the strength of agreement across passes. A refinement writes
freely into uncommitted pixels. One that agrees with an existing commitment
reinforces it. One that opposes it must first cancel one unit of commitment,
and only flips the pixel once the accumulated resistance is spent. Repeated
agreement makes a pixel progressively harder to overturn. Setting the unit an
opposing edit cancels ( $\alpha$ below) to zero would freeze committed pixels
permanently.
Eq. (4) gives the per-pixel rule.

Two deterministic steps bracket the composition. Before the re-tracing call,
an effect gate drops any focus box whose largest achievable change to
the current mask is negligible, and a pass whose boxes are all dropped skips its
re-tracing call. Afterwards, a deterministic cleanup, described below, removes
specks and spurious holes.

The soft lock, per pixel.
This expands $\mathrm{Compose}$ in Eq. (3). Let $\Lambda_{k}^{(t)}$ 
be instance $k$ ’s signed commitment field after pass $t$ , initialized to zero
before refinement. Fix a pass $t$ , a focus box $j$ that corrects instance
 $k=k_{j}$ , and a pixel $x$ in its correction region
 $\mathcal{R}_{\beta_{j},3}(P_{j})$ . Write $a$ for the pixel’s current binary mask
value and $\ell$ for its current signed commitment, initially
 $a=\mathbf{1}[x\in M_{k}^{(t-1)}]$ and $\ell=\Lambda_{k}^{(t-1)}(x)$ .
These values carry forward after each correction within the pass.
Let $\chi=\operatorname{sgn}\ell$ and $v=|\ell|-\alpha$ , the resistance
remaining after an opposing edit erodes it by $\alpha$ ( $\alpha=1$ 
throughout).
With $\sigma=\sigma_{j}$ , one correction updates the pixel to

 $(a^{\prime},\ell^{\prime})=\begin{cases}(\mathbf{1}[\sigma=+1],\;\sigma)&\ell=0\quad\text{(free: commit)},\\[2.0pt]
(\mathbf{1}[\sigma=+1],\;\ell+\sigma)&\chi=\sigma\quad\text{(agree: reinforce)},\\[2.0pt]
(a,\;\chi\,v)&\chi=-\sigma,\;v>0\quad\text{(oppose: erode)},\\[2.0pt]
(\mathbf{1}[\sigma=+1],\;\sigma)&\chi=-\sigma,\;v\leq 0\quad\text{(oppose: flip)}.\end{cases}$ 

(4)

Here $\mathbf{1}[A]$ is $1$ when statement $A$ is true and $0$ otherwise.
Primes denote a single correction, not a complete refinement pass.
After all corrections and the cleanup below, the resulting mask and field
are $M_{k}^{(t)}$ and $\Lambda_{k}^{(t)}$ , and the union is $M^{(t)}$ .
Negative regions are applied before positive ones within a pass. After
composition, nearby positive islands disconnected from the main mask are
bridged. A deterministic cleanup then applies a minor closing and opening,
sized as percentages of the instance box’s minimum dimension, and removes
specks and spurious holes using thresholds scaled by object area. When the
stage-1 topology descriptor is used, its component and hole counts gate this
cleanup so that objects predicted to have holes retain them.

## B.3 One item, step by step

Figure 7 follows a single ReasonSeg item through every
call the pipeline makes, on the query “the spare wheel”. Stage 2 is
already competent here, scoring $84.1$ IoU, and the loop takes it to $91.9$ :
this is the ordinary case, not a rescue. What makes it a useful example is
what is wrong with the stage-2 trace. The wheel is mounted behind a
black fender that cuts across its lower-left, and the outline runs straight
past the occlusion, so the entire error is one wedge of car body inside an
otherwise good boundary. Nothing in the figure is drawn for illustration. Every
box, control point and loop is the geometry the model actually returned for
that item, and every mask is rebuilt from those records by the pipeline’s own
composition code, which reproduces the stage-2 and final masks exactly.

Three things stand out in the figure. First, the spline is
cubic: stage 2 chose $d{=}3$ and placed $24$ control points around a circle,
all inside the supplied box. Eq. (1) turns them into a smooth closed
curve rather than a $24$ -gon. Second, the loop is mostly subtractive. Pass 1
removes $15{,}118$ pixels of fender, $9.4\%$ of the object’s area, and
increases IoU by $7.3$ points. The two later passes shave slivers off the same
edge. Third, pass 3 is the interesting one. It proposes adding a wedge
back along that lower-left edge, but the mask is effectively unchanged:
composing the proposal against the commitment field left by the first two
passes changes only one pixel. Against an empty field, the same proposal would
have added $7{,}791$ pixels (a further $4.8\%$ of the object). This is the
signed resistance of Eq. (3) doing its job: it refuses an edit that
contradicts earlier commitments instead of letting the boundary oscillate.
The loop then stopped itself after $4$ of the $12$ allowed passes.

## C.1 Benchmarks

An item is one (image, query) pair. Negative shares are percentages of the total number of items in the split.

## C.2 Configuration of LLMSeg

The main results use Gemini-3.7-Flash as the backend for all
three stages. For each call, the backend chooses a stage-2 curve degree
 $d\in\{1,3\}$ , shared across the instances in that call
(Section 3). Refinement curves are always cubic. Their
rasterization is described in Section B.2.
The budget constants and stopping rule are given in
Section 4. A full run costs 2 MLLM calls (detect and
segment) plus at most 2 per refinement pass, so at most $2T{+}2=18$ . Measured
over ReasonSeg val, the reported configuration averages $13.4$ calls per image (median $14$ ), because
the effect gate and early stopping terminate many loops well
before $T$ (Figure 15). Mean wall-clock time is
 $159$  s per image. Runs at $T{=}12$ use more passes and average $14.3$ to
 $15.0$ calls per image, depending on the run (Section E.1,
Section E.3, Section E.6). The stage-1 topology descriptor
(Section 3) is an option rather than a fixed part of the
configuration, and the main results leave it off on all three stages.
Section 5 and Section E.3 report both settings, and the difference
between them is within run-to-run variation. These settings are
used unchanged on every benchmark. Nothing is tuned per dataset.

Study configuration.
The backend study (Section E.2) and the ablations
(Section E.3) were run with a budget of $T{=}12$ and
topology conditioning on. We call this the study configuration. It differs
from the reported configuration in exactly these two settings: rows inside one
study are comparable with each other, while a comparison between a study row
and a main-results number mixes both differences. In the ablation tables the
reference row uses the reported setting (topology conditioning off) at $T{=}12$ ,
and the + topology conditioning row is the study configuration.

## C.3 Evaluation protocol and matched-subset scoring

Evaluation protocol.
Four of the 200 ReasonSeg val items and two of the 779 test items have a
legitimately empty ground-truth mask: the queried thing is absent from
the image. We score these items rather than excluding them, so a system that
correctly predicts nothing is credited, while one that hallucinates a region is
penalized. This distinction matters because dropping these items raises the
reported gIoU of systems that do not handle absence well and makes our val
numbers incomparable to the published ReasonSeg results we quote.
For LVIS/COCO/ADE20K, presence-gated metrics use 3, 3, and 0 sampled negative
prompts per image, respectively, with seed 0 shared across all systems.
Cityscapes mIoU is computed from corpus-level, per-class intersections and
unions over the 19 classes: SAM 3 is queried one class at a time, while
LLMSeg labels all classes in an image with a single query and groups spline
instances by label. All backends use the same deterministic composition: stuff
masks are painted before thing masks, with larger masks first within each
group, so smaller masks overwrite larger ones. Uncovered pixels remain
unassigned. No confidence argmax is used. ADE20K is class-prompted, with each
item defined as (image, class). Its score is a union-IoU oracle upper bound and
is not comparable to published argmax mIoU.

Matched-subset scoring.
Item keys are constructed in the data loader before items are split by backend,
so every backend sees the same items. gIoU/cIoU/cgF1/pmF1/mIoU are recomputed
from per-item components over the key intersection. AP is re-evaluated with
COCOeval on the matched items only, with boxes derived from masks for all
systems. For LLMSeg, pipeline failures (detection or segmentation errors) count
as zero.

Five evaluations use their entire split, so their key intersection is the full
split and their results can be compared with published full-split results.
These are ReasonSeg val and test, Cityscapes val mIoU, and AP0 on both
detection collections, averaged over all 13 ODinW13 subsets and the 99 of 100
RF-100VL subsets on which AP is defined. Sampling affects box and mask AP on LVIS and
COCO. Because AP ranks detections across categories, an image can enter the
evaluation only if every ground-truth category it contains was queried. Our
items are uniformly sampled (image, category) pairs, so usually only one
category is queried for each sampled image, and the image is excluded: only 48
of $1{,}449$ LVIS images and 62 of $1{,}304$ COCO images survive. The surviving
images are skewed toward those with few categories. These AP results are
not comparable to published full-split federated AP. We use them only
to compare systems on the same images. Every other reported metric is computed
per item and is unaffected by this sampling issue.

## C.4 Reproducing the SAM 3 Agent baseline

SAM 3 Agent is the agent baseline of Carion et al. (2026), not part of LLMSeg.
Our reproduction follows their reference agent implementation. The MLLM
iterates over three tools: one runs SAM 3 on a simple noun phrase and
returns the resulting masks as a numbered overlay, another selects the mask
numbers that match the full query, and the third reports that nothing in the
image matches.
The loop is capped at 8 rounds, and the union of the selected masks is scored
through the same path as every other system. We run it with Gemma-4-31B,
Gemini-3.5-Flash and Gemini-3.7-Flash rather than the paper’s Qwen2.5-VL and Gemini 2.5 Pro
backends, so our SAM 3 Agent scores are somewhat below the published ones
(Table 1). The Gemini-3.5-Flash run is reported only in
the cost table (Table 12).

## C.5 Backend study protocol

Protocol.
The backend study in Section 5 holds LLMSeg completely fixed
and changes only which MLLM answers its three calls. All 21 backends run the
full pipeline on all 200 ReasonSeg val items in the study configuration
(Section C.2), with every other setting fixed. Metrics are
recomputed from the per-item records rather than copied from any summary, so
gIoU is the mean per-item IoU and cIoU is
 $\nicefrac{{\sum\text{I}}}{{\sum\text{U}}}$ over all 200 items, with pipeline
failures scored $0$ . Confidence intervals are percentile bootstraps over items
(2000 resamples). Each call has a wall-clock budget. Backends with high
serving latency (marked $\dagger$ in Table 9) receive a
longer budget so that provider latency, rather than model capability, does not
determine their scores. The budget limits only how long a call may take. It
does not alter any reply. Qwen3-VL-235B is included despite failing to return a
usable reply on $49\%$ of items, so its score reflects reply rate as well as
segmentation quality. Every row of Table 9 covers the same
200 items. The two reference lines in Figure 5 show
SAM 3 and SAM 3 Agent scored with the same code on the same items. These are
the ReasonSeg val entries from Table 6. The SAM 3 Agent line uses Gemini-3.7-Flash as its driver, and its gIoU varies by only $0.7$ points
( $72.4$ , $72.5$ , $73.1$ ) across the three MLLMs we ran it with, compared with
 $10.8$ points for LLMSeg across one Gemini Flash product line.

Serving the backends.
The eight Gemini and Gemma models are called through Google’s native Gemini
API, and the other thirteen through OpenRouter11
 1

 https://openrouter.ai,
a gateway for models from many developers. The route changes only how a request
is transported, not the prompt, parser, or geometry code. Images are sent at
their original resolution because returned coordinates use the image’s pixel
frame. Sampling parameters remain at each provider’s defaults, so every
backend is evaluated as its developer serves it. A call that fails or exceeds
its budget is a pipeline failure scored $0$ . OpenRouter’s public listings also
provide the prices used in Section E.6.

The capability axes.
Public benchmark coverage is uneven: no single published benchmark is reported
for all 21 backends, and the available benchmarks use incomparable scales. We
build each capability axis by z-scoring every benchmark within
this set of backends and averaging the axis’s benchmarks for which a model
reports a score. Missing values are never imputed: models with no published
score for an axis are omitted from that axis’s panel. The four axes are
software engineering (AA Coding Index, SWE-bench Verified, SWE-bench
Pro, LiveCodeBench),
reasoning and knowledge (AA Intelligence Index, GPQA Diamond, HLE),
agentic and tool use (AA Agentic Index, OSWorld, Terminal-Bench), and
vision and multimodal (MMMU, MMMU-Pro, CharXiv). Two consequences follow. Each axis is relative: adding a backend
re-centres it, so its zero carries no meaning beyond this set. And the
underlying numbers are vendor-reported, so the slopes and rank correlations we
report are indicative of which skills matter, not claims of statistical
significance.

## C.6 Cost accounting

Protocol.
Table 12 and Figure 25 price the same 200
ReasonSeg val items scored in Table 9, covering all
twenty-one LLMSeg backends and both the SAM 3 and SAM 3 Agent baselines.
Nothing here was
rerun: every number is either measured from records those runs already wrote
or quoted from the published model table. Wall clock is the median
seconds per item among the items a backend answered, based on per-item
timers recorded during the runs. We use the median rather than the mean because
a run that hits its per-call budget on a handful of items can have a mean that
reflects the timeout rather than the backend. The call count includes
both types of model invoked for each image. The MLLM call count is reconstructed from each
item’s recorded pass list. It counts one detect and one segment call, plus one focus
call per refinement pass and one batched spline call for each pass whose focus
boxes survived the effect gate. For SAM 3 Agent, it is the mean number of agent
rounds. The SAM 3 figure is the number of forward passes of the
 $860$  M-parameter model. It counts one pass for
SAM 3 itself and one per phrase the agent chooses to segment. It counts
none for LLMSeg, which calls no segmentation model. SAM 3 and SAM 3 Agent were timed with SAM 3 running on one RTX-class GPU. Prices and time-to-first-token
come from the providers’ published figures. Call counts come from the single
study run of each backend, so they can differ slightly from repeated-run means
elsewhere (for Gemini-3.7-Flash, $15.0$ here against $14.3$ in Table 10).

The dollar column is an estimate, and a lower bound.
The spend column is an estimate rather than a billed measurement. We price
every row using one shared budget: $1900$ input tokens per call (the stage
prompt templates, which measure $522$ to $953$ tokens, plus one image with a
full-resolution allowance of about $1.1$ k) and $175$ output tokens per call
(the mean structured payload recorded across all twenty-one runs). The column
depends only on the published price and the measured call count, so it ranks
backends consistently under these assumptions. Its
absolute values are lower bounds because reasoning tokens, which several
providers bill for, are not included.

SAM 3 is not free either.
We ran SAM 3 on a local GPU, so we incurred no charge, but a forward
pass has a market price. Pricing it at zero would flatter LLMSeg. We charge
each SAM 3 pass at $\$0.0043$ per image, the pay-as-you-go rate for a
serverless endpoint serving the same checkpoint,22
 2

 Segmind serverless
inference, pay-as-you-go credits, retrieved 2026-09. which puts SAM 3 at
 $\$4.30$ per thousand images for one pass and adds the cost of $1.4$ passes to
each SAM 3 Agent image, in addition to its MLLM calls. LLMSeg calls no segmentation
model, so it carries no such term.

## E.1 Refinement and convergence

Does the loop actually converge?.
This matters more than a typical hyperparameter question. Eq. (3) is
an open loop driven by a stochastic model that can propose a fresh set of focus
boxes at every pass, with no contraction guarantee. Left unchecked, such a loop
can cycle indefinitely, repainting a boundary one way and then the other. A
reader is right to ask whether the pass budget $T$ provides a genuine
early stop or merely truncates an unstable process.

Figure 15(a) answers this empirically on ReasonSeg val. The
stopping criterion of Section 4 ends the loop for $79\%$ of
items before they reach the budget ( $81\%$ of the items that enter the loop).
The median item uses $6$ passes, $36\%$ stop within $4$ , and only $18.5\%$ are
still running when $T$ cuts them off. This behavior is consistent with the
intended damping mechanism: when successive passes agree on a boundary, the
commitment field makes those pixels progressively harder to overturn. However,
the study does not isolate the soft lock’s contribution. The minority that
reaches the cap is a harder set to begin with: its stage-2 masks are already
 $5.7$ gIoU behind ( $60.0$ vs. $65.7$ ), and its final masks remain $7.0$ behind
( $62.3$ vs. $69.3$ ).
Normalizing the criterion by box area rather than image area makes its
threshold relative to the region the loop can alter.

Figure 15(b) ties this to accuracy rather than to mask
stability alone. Quality saturates well inside the budget: the first pass buys
 $+2.0$ gIoU, four passes buy $+2.7$ of the eventual $+3.2$ , and passes $8$ to
 $12$ move it by less than $0.1$ . These figures come from this one run. Other
runs of Gemini-3.7-Flash give different totals ( $+3.7$ in Table 9, and
 $5.4$ gIoU between the ablation reference and its no-refinement row), because
the pipeline is stochastic and the runs differ in configuration. Because most items have already stopped, the
measured cost is far below the worst-case cost of $2T{+}2=26$ calls: $14.7$ 
calls per image on average at $T{=}12$ in this run (other $T{=}12$ runs give
 $14.3$ to $15.0$ ), and about $9$ at the $T{=}4$ knee. $T$ is
a safety net rather than an operating point.

Figure 15: The refinement loop stops on its own. ReasonSeg val, all
200 items, Gemini-3.7-Flash. (a) Share of items still inside the loop at each
pass. A run stops once the mask changes by less than $0.5\%$ of its box
area for three consecutive passes.
(b) The same run’s mask after the first $T$ passes, scored at every
budget, with the mean MLLM calls on the top axis.

The residual as a stopping signal.

The stopping criterion of Section 4 acts on the residual
 $\delta^{(t)}=|M^{(t)}\triangle M^{(t-1)}|\,/\,|\bigcup_{k=1}^{N}b_{k}|$ ,
the fraction of the instance-box union that a pass repaints, rather than on
quality: the pipeline sees no ground truth at run time, so the amount of mask
change is its only observable. Figure 16 shows
that quantity pass by pass on a $16$ -image development set (free text
queries on images that belong to no evaluation benchmark), which is where
 $\varepsilon$ and $s$ were set before any benchmark was run. The $16$ images
and their queries are released with the code.

Three observations stand out. First, the residual decays. It is not monotone,
since a pass is free to propose a large new edit at any point, but every trace
ends below where it started, most of them by an order of magnitude or more,
and several reach the axis floor, that is, passes that changed no pixel at
all. Second, the rate is a property of the image, not a constant. The first
pass repaints between $0.2\%$ (person) and $27\%$ (toy) of the
box union, a $175\times$ spread (based on unsmoothed values, whereas the figure plots
the $3$ -pass average), and the starting value does not predict the decay:
toy starts highest and stops itself at pass $10$ , while taxis,
with six crowded instances of the same class, starts at $6\%$ and is still
moving $0.7\%$ of its box union at pass $12$ ( $1.3\%$ after the $3$ -pass
average). Boundary length, occlusion, and instance count may affect how quickly
an item stabilizes, but the first pass does not reveal it. This is why the
budget must be allocated per image rather than fixed globally.
Third, $\varepsilon{=}0.005$ with $s{=}3$ sits where those two regimes
separate: $11$ of the $16$ items stop on their own, the earliest at pass $3$ 
(the patience floor, which no item can beat), the median at $6$ , and $5$ run
to the cap.

A small residual indicates stability, not correctness. A loop could in
principle settle on a wrong mask. Its use as a surrogate is supported by the
benchmark-scale behavior above: quality saturates over the same passes in which
these residuals collapse, and the items that never stop are the ones that end
furthest behind.

Figure 16: Per-item refinement residuals on the development set.
Each curve is one development image, run with Gemini-3.7-Flash at budget $T{=}12$ .
The curve is the $3$ -pass moving average of the mask residuals $\delta^{(t)}$ on a
logarithmic axis, and the dashed line is the threshold $\varepsilon=0.005$ .
Blue curves are images that stop on their own with stopping patience $s=3$ , orange curves are images that
exhaust the budget, and $\times$ marks the first smoothed pass below
 $\varepsilon$ . The residuals decay as the masks stabilize, which is the
signal the stopping criterion uses in LLMSeg.

## E.2 Backend study

Because LLMSeg adds no trained parameters, backend progress is the only thing
that has to improve for segmentation to improve. We test this directly by
running the same pipeline, in the study configuration
(Section C.2), on ReasonSeg val with twenty-one MLLM
backends from six developers. The only change is which model answers the three
calls.
Figure 18 is the complete ranking, read on the stage-2 mask
so that one bar carries one backend. Table 9 repeats every
row with its final mask, both bootstrap intervals and the signed effect of
refinement. First, scores range from $13.4$ to $74.2$ gIoU at stage 2 and from
 $14.2$ to $72.9$ after refinement, a spread far wider than that of any design
choice in Table 10.
Second, refinement lowers gIoU on eleven of the twenty-one backends,
especially the weaker models, which cannot refine their own masks well.
Its gains therefore depend on the model’s ability to inspect and correct
its own masks.
Every backend scores at least as high
as the SAM 3 baseline score ( $13.1$ ) on this benchmark, although the weakest
is not clearly above it: GLM 4.6V scores $13.4$ ( $[10.2,16.8]$ ) at stage 2 and
 $14.2$ ( $[11.0,17.6]$ ) after refinement. The other twenty backends score clearly above SAM 3. At $72.4$ , the SAM 3 Agent baseline uses the
same Gemini-3.7-Flash as our pipeline and a segmentation specialist as its tool. It is
close to our best backend, GPT-6 Astra, which scores $74.2$ ( $[70.4,77.9]$ ) at
stage 2 and $72.9$ ( $[69.2,76.6]$ ) after refinement. The gaps are $1.8$ and
 $0.5$ gIoU, respectively, and the SAM 3 Agent score lies within both corresponding
GPT-6 Astra item-bootstrap intervals. By contrast, SAM 3 alone trails
GPT-6 Astra by $59.8$ .
The two dashed lines also respond very differently to the MLLM. Swapping the
agent’s MLLM among Gemma-4-31B, Gemini-3.5-Flash, and Gemini-3.7-Flash changes its score by
just $0.7$ gIoU ( $72.4$ to $73.1$ ), because its masks come from SAM 3 either way. Swapping our MLLM across the same Gemini generations changes our
score by $10.8$ . Our score is therefore far more sensitive to the backend than the agent’s is,
and the backend is the part of the stack that continues to improve.
Figure 21 shows what that spread looks like on single
items: the same five ReasonSeg queries traced by seven of the backends, where
the object being selected barely changes down a row and the outline drawn
around it does.

Figure 17: Backend progress is LLMSeg progress. LLMSeg final segmentation gIoU
on ReasonSeg val against backend release date, one coloured line per product
line with two or more releases. All other backends are gray. Nothing in the
pipeline changes between the points of a line.

Public capability and segmentation quality.
Figure 19 plots that quality against four capability axes
built from public benchmark scores (§C.5), one panel per axis.
Two things follow. First, no published capability is a reliable predictor of
segmentation quality: no axis reaches significance. The reasoning-and-knowledge
axis comes closest ( $\rho=0.43$ , $p=0.09$ , $n{=}17$ ), followed by the
vision-and-multimodal axis ( $\rho=0.36$ , $n{=}8$ ) and software engineering
( $\rho=0.21$ , $p=0.42$ ). Agentic skill carries no signal ( $\rho=-0.05$ ,
 $n{=}14$ ). The exceptions run in both directions.
Claude Opus 5 ( $96.0$ on SWE-bench Verified) and GLM 5.3 Flash score high on
software engineering and reasoning yet segment at $46.6$ and $49.6$ ,
fourteenth and twelfth of twenty-one. GPT-5.4 sits on the right of every panel
but near the bottom in segmentation quality ( $27.1$ ). Muse Glimmer 30B performs
similarly ( $23.5$ ). We did not diagnose where these backends lose accuracy.
The reverse holds as well. Gemma 4 31B and Gemma 4 26B sit at the low end of
the agentic, software and reasoning axes and still segment seventh and eighth
at $56.2$ and $56.1$ , and Gemini-3.7-Flash lies further above the fit than any other
backend on two of the four axes (agentic and vision). The practical reading rests on those
exceptions rather than on the fit. No published headline score, whether for
vision or coding, is a reliable way to pick a backend for LLMSeg, and the only dependable
test is to run the pipeline on the model.

Second, and more directly useful, Figure 17 re-plots the
same runs against backend release date, joining models within each product
line. All four product lines with multiple releases improve over the period
shown while the pipeline remains unchanged. Gemini Flash goes
 $58.6\to 66.2\to 69.4\to 66.7$ over four releases in nine months, Gemini
Flash-Lite $28.8\to 44.5$ , GPT $27.1\to 55.9\to 72.9$ , and Qwen $49.5\to 51.0$ .
The trend is not monotone at the release level: Gemini 3.8 Flash scores $2.7$ 
below Gemini 3.7 Flash, a reminder that a
newer model is not automatically a better backend. The Flash-Lite line is the
most economical evidence: a $+15.7$ gIoU gain without retraining anything.
Size within a generation buys little: Gemma 4 31B and its
mixture-of-experts sibling Gemma 4 26B, released the same day, land $0.1$ 
apart ( $56.2$ and $56.1$ ). The two Z.ai models are not one product line and the
generation plot joins no arrow between them, but they bracket the same eight months as
the Gemini Flash line: GLM 4.6V, of December 2025, is the weakest backend in
the study at $14.2$ , and GLM 5.3 Flash, of August 2026, reaches $49.6$ . Price
buys much less than generation does ( $\rho=0.25$ against input price,
Figure 20). The second-best backend here costs
 $21\times$ less than the best.

One caveat belongs with these numbers. Refinement is not uniformly positive
across backends: it hurts on eleven of the twenty-one. It adds $+3.7$ gIoU on
Gemini-3.7-Flash but costs $8.3$ on GPT-5.4, $6.8$ on
Gemini-3.1-Flash-Lite, $2.4$ on Claude Opus 5, $1.3$ on Gemma 4 31B and $1.2$ on GPT-6 Astra,
our strongest backend. The loop can only re-trace what the backend proposes, so a
backend that mislocates its focus boxes spends its passes moving the mask off
the object. The refinement gains reported elsewhere in this paper are Gemini-3.7-Flash’s,
and the appropriate refinement budget must be checked for each backend. This is also why
Figure 5 ranks the backends on what they trace: a bar pair
would read as a refinement result on rows where refinement is not one.

## E.3 Ablations and design alternatives

Table 10 and Table 11 test the design choices of
Section 3 on two splits, comparing final-mask quality
(gIoU and cIoU) with MLLM calls per image. Each
split (ReasonSeg val and RefCOCO val) contains 200 items. The reference
(shaded) row is the configuration reported in the paper, with topology
conditioning off, run at the study budget $T{=}12$ . The tables report fourteen
variants per split: three change the reported configuration directly (cleanup
and box adjustment), one adds topology conditioning, and the remaining ten
(indented) apply their change on top of topology conditioning, so each of them
is compared with the topology-on row. Both tables give
gIoU, cIoU and calls per image, and the ReasonSeg table adds run-to-run
deviations and wall-clock time. Every ReasonSeg
configuration was run three times with an identical setup, and each cell
reports the mean. Across repeated runs, a fixed configuration’s score varies
by $0.1$ to $1.3$ gIoU, which sets the scale for interpreting the comparisons
below. Each RefCOCO configuration was run once, so no deviation is reported.
These results should be read for direction only.
At similar call counts, adding topology conditioning to the reported
configuration reduces observed cIoU by $2.1$ on ReasonSeg and $2.5$ on RefCOCO.
The reductions have the same sign on both splits and for gIoU as well ( $1.5$ 
and $2.6$ , respectively), so we leave topology off by default and retain it as
an option for the item type it was designed for (Section E.4). The
largest effect of any component is refinement: removing it costs $5.4$ gIoU
and $5.4$ cIoU on ReasonSeg, and $9.8$ gIoU and $12.7$ cIoU on RefCOCO,
relative to the topology-on row it modifies, and refinement accounts for $12.3$ 
of that row’s $14.3$ calls per image. The remaining changes generally produce
smaller differences. Apart from removing refinement, the largest gIoU drop
relative to the reported configuration is for low image detail: $3.5$ gIoU
( $3.2$ cIoU) on ReasonSeg and $4.5$ gIoU ( $4.4$ cIoU) on RefCOCO. Most
variants are within two points of the reported configuration on both splits.
No variant outperforms the reported configuration on both metrics across both
splits. Cost varies more across
the alternatives than quality does: calls range from $8.8$ without the detect
stage to $21.3$ with per-instance cropped refinement, while on ReasonSeg the
final gIoU of every other variant stays between $67.2$ and $71.8$ . The pipeline
does not appear to be delicately balanced on prompt conditioning or on how its
calls are batched.

Prompt conditioning. Cutting the stage-1 morphology or topology
description from the prompts does not measurably change final-mask quality.
The topology-on row includes both descriptions. Relative to its
 $69.2\pm 1.3$ gIoU, removing morphology yields $69.9$ and removing topology,
which gives the reported configuration, yields $70.7$ . Both differences are
small relative to the spread across configurations. On RefCOCO, the
corresponding rows are $2.4$ and $2.6$ gIoU above the topology-on row
(Table 11).
Topology conditioning is a design option, not a component on which
the aggregate results depend. We report the configuration without the extra
topology prompt text because describing holes does not measurably improve
split-level scores. Topology information does provide structural control:
Stage 2 uses it for hole carving and gated cleanup. Without it, the model is
not told how many closed curves to fit, and a holed or multi-part object may be
cleaned as if it were one solid blob.
The fraction of benchmark targets for which this control applies ranges
from $0\%$ to $7\%$ . On items scored both ways, the paired difference is
 $-0.3$ gIoU overall and $+0.1$ on holed items. The option is
retained for explicit structural control, not claimed as a source of aggregate
accuracy (Section E.4).
Reducing the backend’s reasoning effort or the image detail sent with each
call leaves quality flat to slightly below the topology-on row it modifies:
the corresponding cIoU scores are $72.3$ and $71.5$ here, against $72.6$ . On
RefCOCO, they are $74.3$ and $75.4$ , against $77.3$ .
Low reasoning effort is the only setting that is cheaper: at the same
call count, backend-call time per image falls by about a quarter, from $175\,s$ 
to $133\,s$ . The deterministic cleanup likewise does not carry the result.
Removing it from the reported configuration gives $74.1$ cIoU against $74.7$ 
( $77.9$ against $79.8$ on RefCOCO), and removing it from the topology-on row
gives $73.8$ against $72.6$ ( $76.8$ against $77.3$ ). This matters because it is
the only step in LLMSeg whose geometry the model did not choose.

Is the detection stage needed? Asking the model for splines directly,
with no detect stage and therefore no box to confine control points to, tests
whether stage 1 is worth its call. Without a box, the model must place absolute
coordinates over the whole image, and no invariant prevents a loop from
wandering across the scene.
On ReasonSeg, the no-detection variant is within the run-to-run band of the
topology-on row it modifies ( $69.5$ gIoU and $72.1$ cIoU versus $69.2$ and
 $72.6$ ) and uses fewer
calls ( $8.8$ vs. $14.3$ ).
RefCOCO is also competitive ( $78.5$ gIoU at $10.4$ calls against $76.7$ at
 $16.8$ ). Stage-2 cIoU does favor detection on both splits
(Table 4). The advantage is concentrated on targets
whose ground-truth masks are disconnected (at least two components above the
annotation-speck threshold: $63/200$ ReasonSeg and $18/200$ RefCOCO items). On
ReasonSeg, the initial cIoU on these targets is $52.6$ without the detect stage
and $63.9$ with it. On RefCOCO, it is $61.7$ without and $63.9$ with.
Thus detection provides box confinement (Eq. (2)), instance identities,
and structural conditioning, not a demonstrated general accuracy advantage on multiple objects.

Why one batched call rather than per-instance crops? An obvious
alternative runs the segment stage once per detected instance on a crop of its
box, which gives the model more effective resolution per object at a cost that
grows linearly with instance count, against the fixed single call of
Section 3. It reaches $75.4$ cIoU ( $71.8$ gIoU) at $14.2$ 
calls per image, the best ReasonSeg cIoU in the table. This is $2.8$ above the
topology-on row it modifies but only $0.7$ above the reported configuration at
the same cost, in part because most
ReasonSeg items have one instance, making one crop equivalent to one call.
On RefCOCO, however, it scores $78.3$ cIoU at $15.4$ calls, a point and a half
below the reported configuration ( $79.8$ ). The advantage does not carry over to the second
split.

Why one batched refine rather than per-instance crops? The same crop
alternative applied to stage 3: keep the batched segment call, then run the
refinement loop once per instance on a crop of its box, each with its own
overlay. Cost again grows with instance count. The batched refine of
Section 3 stays two calls per pass regardless of $N$ . This is
the most expensive variant in the table, $21.3$ calls per image against
 $14.6$ for the reported configuration, a $46\%$ increase, for $74.9$ cIoU
against $74.7$ , and on RefCOCO it
costs two points ( $77.7$ against $79.8$ ). Its cost
would grow further on multi-instance benchmarks, where the batched refine’s
cost does not.

Why B-splines rather than polygons? Asking for a dense polygon instead
of spline control points is the natural baseline for our output primitive: it
removes the cubic smoothness prior and allows more coordinates per object. The
variant uses degree-one loops in both stages, with prompted vertex ranges of
 $32$ to $160$ initially and $6$ to $24$ in refinement, against $16$ to $64$ and
 $4$ to $12$ for the B-spline topology-on row, so this comparison matches neither coordinate
nor token budgets. At similar call cost, the final masks score comparably
( $69.8$ gIoU and
 $73.1$ cIoU against $69.2$ and $72.6$ , with $78.7$ and $79.1$ on RefCOCO), and so do
the stage-2 masks over three runs ( $65.3/66.2$ against $65.1/68.3$ gIoU/cIoU).
The ablation is self-limiting because the backend chooses the degree itself
(Section 3) and chooses $1$ (the polygon) for $125$ of the
 $195$ objects it traced. Thus, on most of the split, the ablation changes the
vertex budget and placement rules rather than the primitive. By ground-truth
area, stage-2 polygon traces lead in the smaller two strata, while the
B-spline run leads in the largest quartile on both metrics ( $75.6$ against
 $73.4$ gIoU and $76.0$ against $69.7$ cIoU). As a pixel-mass metric,
cIoU is dominated by large objects, which is where the B-spline run leads. On
cubic-traced items, it does so with fewer coordinates: it emits
 $28.9$ per image, compared with $48.5$ for the polygon variant, a
 $1.7\times$ difference. Figure 22
shows three examples. These results support a compact parametric
representation, not a uniform or equal-budget accuracy advantage.

The topology ablation of Table 10 removes the hole and
component description from all three prompts and produces no measurable change
( $70.7$ vs. $69.2$ gIoU, within the run-to-run band). That average is taken
over a split where almost no target has a hole, so it cannot distinguish
“topology does not help” from “too few items benefit for the effect to show
up.” We measure each item’s ground truth directly to find the holed
targets. A hole is an enclosed background component that never touches the
image border and covers at least $0.5\%$ of the object’s area. Anything smaller
is annotation speckle. Items with an empty ground truth are excluded, since a hole
needs an object.

The first finding is prevalence. Over the eleven splits measured,
holed targets are $7.1\%$ of ReasonSeg val and $6.6\%$ of ReasonSeg test,
 $4.7\%$ of LVIS positives, and between $0\%$ and $1.4\%$ of every
RefCOCO/RefCOCO+/RefCOCOg split: COCO’s polygon annotations essentially never
carve one. The subset the topology machinery exists for is a small minority of
what these benchmarks contain, which helps explain the null split-level
ablation.

The second finding closes the ablation. On the $396$ ReasonSeg items scored by
both the topology-on and topology-off runs, the mean per-item IoU
difference is $-0.3$ ( $[-1.8,1.2]$ ) overall and $+0.1$ ( $[-5.3,5.3]$ ) on the
 $19$ holed ones: targeting the subset does not reveal a hidden effect. This is
the measurement behind the conclusion in Section 5:
topology conditioning makes explicit hole-loop specification possible when a
target has holes, but it is not a source of the accuracy we report, and we do
not claim it as one. Two caveats limit this result’s interpretation: the runs
also differ in pass budget (Section C.2), and $19$ holed items
make up a small sample, as reflected in the interval.

## E.5 Localization or boundary?

Table 3 reports the gap to SAM 3 as two scalars per
benchmark, each averaged over the ten COCO IoU thresholds
 $0.50{:}0.05{:}0.95$ . This averaging hides the shape of the effect: a system
that finds every object but traces it loosely can report the same mean AP as
one that finds fewer objects but traces them tightly. Their behavior becomes
clear from how AP changes across the threshold axis. To show this,
Figure 24 plots AP at each threshold for the main-results
pipeline configuration (Gemini-3.7-Flash, $T{=}8$ , topology conditioning off), using the
same matched subsets and COCOeval pass.

At AP50 on LVIS, box scores are nearly tied ( $79.3$ vs. $79.6$ ). On
COCO, LLMSeg leads in box AP ( $87.4$ vs. $79.5$ ) and is close in mask AP
( $80.0$ vs. $81.3$ ). The mask AP gap widens at tighter thresholds. By IoU
 $0.90$ , LLMSeg scores $16.4$ on both benchmarks, while SAM 3 scores $42.5$ 
and $24.3$ , respectively. Averaged over the ten thresholds, the mask gap is
 $3$ to $6\times$ the box gap. On COCO, the interval for the box gap includes
zero. This pattern is consistent with masks that identify the right object
and place it within the right box, but have filled, closed-spline boundaries
that remain a few pixels loose. A threshold sweep reveals this boundary error,
whereas mean AP obscures it. Refinement improves the boundary but does not
eliminate the error: relative to the unrefined stage-2 mask, mask AP improves
by $+10.4$ on LVIS and $+12.5$ on COCO across thresholds up to $0.85$ , peaking
at $+14$ to $+20$ in the $0.65$ to $0.85$ band. By IoU $0.95$ , the gains fall
to $+2.4$ and $+1.5$ , respectively. Refinement moves the outline substantially
closer to the object but does not produce pixel-tight masks. The remaining gap
is concentrated at high overlap thresholds. These subset results do not
establish full-dataset AP parity.

Figure 24: LLMSeg localizes like SAM 3 and loses the boundary.

Where the time goes.
Refinement dominates: stage 3 accounts for $76$ to $94\%$ of wall-clock time on
every backend ( $89\%$ on Gemini-3.7-Flash), consistent with a loop of up to $T{=}12$ passes
at two calls per pass, compared with one detection and one segmentation call.
The cost comes from the number of calls, not their content: at a published
 $2.3$  s time-to-first-token, Gemini-3.7-Flash spends about $34$ of its $153$ median seconds
waiting for first tokens alone across its $15$ calls. Call count is not a proxy
for useful effort: the best backend averages $11.7$ calls per image, while the
three highest-call backends average $24.0$ to $24.4$ and score $58.6$ , $43.2$ 
and $27.1$ . This reflects stopping behavior: a sequence may stop while its mask
is still changing, while an unproductive sequence may run to the budget.

LLMSeg is the expensive way to reach this quality.
On this benchmark SAM 3 Agent is both better and cheaper. Driven by the same
Gemini-3.7-Flash, it reaches $72.4$ gIoU against our $69.4$ in roughly one-fourteenth of
the wall-clock time ( $11$  s against $153$  s) and at just over half the estimated
serving cost ( $\$8.31$ against $\$15.61$ per thousand images). It makes $2.4$ 
agent rounds and $1.4$ SAM 3 passes where we make $15$ vision calls, and
the mask itself comes from a $860$  M-parameter forward pass rather than from
coordinates the MLLM has to write out. Charging for the
SAM 3 passes narrows that gap rather than closing it: the agent’s
 $1.4$ passes cost it $\$5.85$ of its $\$8.31$ , and SAM 3 on its own costs
 $\$4.30$ , a cost undercut by only two LLMSeg backends. That advantage is
specific to what SAM 3 can already segment: SAM 3 Agent inherits SAM 3’s
mask, so where SAM 3 collapses (Section 4.2) the agent
collapses with it, while LLMSeg is bounded only by its detect box. In summary, predicting a mask as text buys open-vocabulary reach at the
price of calls, latency and dollars, and the price is set by the backend
rather than by the pipeline: across the twenty-one backends, spend per thousand
images ranges from $1.4$ to $324$ , a factor of $238$ , across a gIoU range of
 $14.2$ to $72.9$ , with cost only weakly tracking gIoU. The most expensive
backend is also the best, but costs $21\times$ as much as the second-best for
a $3.5$ -point gIoU gain, and the two cheapest backends outscore nine dearer ones.

## E.7 Where the LLM route wins and loses

The results support a consistent picture. LLMSeg wins where (i) the query
needs reasoning (ReasonSeg, Figure 3),
(ii) the domain is rare (RF-100VL, $2.2\times$ SAM 3’s AP0),
including medical and industrial imagery, (iii) presence judgment
matters (hard-negative cgF1 on LVIS and COCO), where the LLM can reason about
whether the concept is in the image. This does not carry over to SA-Co/Gold,
where LLMSeg trails SAM 3 by $9.0$ cgF1 while pmF1 is level, so the loss
lies in the presence decision. The last case is (iv) a regular shape:
such shapes admit compact cubic or straight-edged traces, and, with topology
enabled, holes can be specified by interior loops. Neither final boundary
smoothness nor hole count is guaranteed. Holed targets are a small
minority in these benchmarks (see Figure 23), and prevalence is quantified in Section E.4. LLMSeg loses on pixel-tight mask AP
and on thin, amorphous or highly irregular regions
(Figure 26), where compact geometric traces lose fine
boundary detail. In practice, LLMSeg takes minutes per image and makes multiple
API calls, compared with a median of $2$  s per image for SAM 3 on a local GPU (Table 12). However, it runs on the heavily
optimized LLM serving stack, needs no GPU of its own, and produces inspectable
intermediate records (boxes, optional topology, per-loop splines, and focus
boxes with a type and a short shape description). These records are not verified explanations of the
model’s internal reasoning.

Limitations.
LLMSeg inherits its backend’s failure modes: hallucinated detections on
ambiguous prompts, occasional coordinate-format instability (mitigated but
not eliminated by the repairs of §B), and per-call latency
of seconds to minutes, which makes video and real-time use out of scope.
Spline loops are a poor primitive for thin or fractal structures
(Figure 26), and segmentation quality is upper-bounded by
detect-box quality due to the confinement invariant. Finally, API-served
backends make exact reproducibility subject to provider model updates. We
pin model versions and release all records.

## Appendix F Prompt Templates

This section gives the three prompt templates that drive the pipeline, in the
form the model receives them: box 1 is the detection call
of Section 3, box 2 the initial tracing call, and box 3
the focus-box proposal call. Text in angle brackets is filled in at run time. The
instance and focus-region blocks are shown filled for a two-instance example,
since their layout is part of what the model reads. Long lines are re-wrapped
to the column width. Everything in black is template text. The
#-prefixed green lines are ours, not the
model’s, so a box can be copied whole and the notes stay comments. The green
leading line stands for the image, which is attached to the request
alongside the prompt text. The boxes show the study configuration, which
includes the stage-1 topology description. The reported configuration drops
that description from all three prompts: the topology block of box 1’s schema,
the topology lines of the instance and detection-box listings in boxes 2 and 3,
and the sentences that refer to topology. The fourth call, the re-tracing half of a
refinement pass, is box 2’s spline rules restated
once per focus region. It repeats the coordinate paragraph and the overlay
description of box 3, lists the surviving focus regions with their type and
reported shape, fixes the degree to cubic, asks for four to twelve control
points per region instead of sixteen to sixty-four, and returns the same
id-keyed list of closed loops.

The templates share three properties. First,
every call states the coordinate space explicitly and every call that returns
points restates the box those points must fall inside as a numeric inequality.
The code clamps regardless, but a clamped-in point is a worse outline than a
correctly placed one. Second, each prompt offers an escape hatch, an empty
detection list, an empty loop list for an instance whose box holds nothing, an
empty proposal list for a pass that finds no error, so that a failure to find
something is expressible and does not have to be invented. Third, batched
calls pin the emission order to ascending instance id, which is what makes a
truncated reply salvageable.

Prompt #1: Instance Detection
(Stage 1)

⬇
# <the input image>

The image is <W>x<H> pixels (origin top-left, x right, y down).

ALL coordinates are absolute PIXELS with 0 <= x <= <W> and 0 <= y <= <H>.

Find every DISTINCT instance of the following in the image: "<query>"

Return ONLY a JSON object (no prose, no markdown fences) with this exact schema:

{"detections": [{

 "id": <int starting at 0>,

 "label": "<short label>",

 "box": [x1, y1, x2, y2],

 "confidence": <0..1>,

 "morphology": {

 "shape": "<overall silhouette in a few words, e.g. ’compact rounded body with two upright

 protrusions’>",

 "aspect": "<tall|wide|square>",

 "convexity": "<convex|slightly-concave|highly-irregular>",

 "parts": ["<protruding/notable parts, e.g. ’left protrusion’>", "<’base contact’>", "..."]

 },

 "topology": {

 "components": <int number of disconnected pieces of the object silhouette>,

 "holes": <int number of enclosed background holes inside the silhouette>,

 "boundary_loops": <int total closed boundary curves = components + holes>,

 "notes": "<one short phrase, e.g. ’single blob, no holes’>"

 }

}]}

where box is [x1, y1, x2, y2] in the coordinate space described above (x1 < x2, y1 < y2, all values

inside the valid range for that space).

- One entry per DISTINCT instance -- do NOT return duplicate or nested boxes for the same object. Order

 detections in reading order (top-to-bottom, then left-to-right); ids will be reassigned by code, but

 keep them contiguous from 0.

- morphology.aspect must describe the instance as you SEE it, independently of the numbers you wrote in

 box; it is cross-checked against them.

- Make each box LARGE enough to ENTIRELY encompass that instance -- leave generous margin so no part of

 the silhouette (protrusions, extremities, soft edges, head, ears, paws) is clipped by the box. Prefer

 a roomy box over a tight crop; a later stage confines all outline tracing to this box, so an

 undersized box truncates the segmentation.

- morphology describes the object’s FORM (shape of its outline) so a later stage can trace it; topology

 describes its STRUCTURE (how many separate blobs and how many holes) so a later stage knows how many

 closed curves to fit.

If nothing matches, return {"detections": []}.

Output the JSON and nothing else.

Prompt #2: Outline Tracing
(Stage 2)

⬇
# <the input image>

The image is <W>x<H> pixels (origin top-left, x right, y down).

ALL coordinates are absolute PIXELS with 0 <= x <= <W> and 0 <= y <= <H>.

We have already DETECTED <N> instance(s) of "<query>" (same query / class). Each instance has its own

bounding box; a later stage confines that instance’s outline to ITS box only.

INSTANCES (trace EVERY one):

- id=0 label="<label>" box=[120, 80, 540, 610]

 every x,y you return for id=0 must satisfy: 120 <= x <= 540 and 80 <= y <= 610

 morphology: {"shape": "compact rounded body with two upright ears", "aspect": "tall",

 "convexity": "slightly-concave", "parts": ["left ear", "tail", "front paws"]}

 topology: {"components": 1, "holes": 0, "boundary_loops": 1, "notes": "single blob, no holes"}

- id=1 label="<label>" box=[600, 140, 930, 585]

 # ... (one such entry per detected instance)

Your job has TWO parts:

 (1) pick ONE shared overlay tint color for the mask (same for all instances),

 (2) CHOOSE a spline degree (1 or 3) shared by every instance of this class, then for EACH instance

 trace its silhouette with piece-wise CLOSED 2D B-splines of that degree so the spline(s) tightly

 SURROUND that instance.

MASK COLOR (part 1):

Pick ONE color name from this fixed list:

 "lime", "green", "spring_green", "mint", "teal", "cyan", "turquoise", "sky_blue", "blue",

 "periwinkle", "indigo", "violet", "purple", "magenta", "hot_pink", "pink", "coral", "orange",

 "chartreuse"

Choose the color that maximizes contrast of a light translucent tint against BOTH the "<query>" AND its

surrounding background, so a later pass can clearly see what is covered vs not. Rules for the choice:

- ONE tint is shared by every instance: pick a hue that reads clearly on ALL of them and against each

 one’s own local background, not just the first.

- Prefer a hue that is NOT already dominant in the object or in the nearby background.

- Do NOT pick a color that would wash out or blend into the object’s own colors or hide fine edge

 detail under the tint.

- Return the name EXACTLY as listed (lowercase, underscores).

SPLINE RULES (part 2):

- Return exactly one entry per instance, keyed by the same integer "id".

- Every control point for instance id=K MUST lie inside THAT instance’s box=[x1, y1, x2, y2] listed

 above.

- Fit ONE closed B-spline per connected blob of that instance (topology.components), plus ONE

 additional closed B-spline per interior hole (topology.holes), marking holes with "role":"hole".

 Outer silhouette loops use "role":"outer".

- Use each instance’s morphology to place control points on the true outline (follow protrusions,

 concavities, corners, and curves named in the morphology).

- If one instance’s box is empty, unreadable, or holds nothing matching the "<query>", return an EMPTY

 "splines" list for that id rather than inventing an outline. Still return its id, and still trace

 every other instance normally.

- Your whole reply must fit in ONE response, and <N> instances is a lot of coordinates. Emit entries in

 ASCENDING id order and FINISH each entry before starting the next; stay near the LOW end of the

 control-point range for the simple ones so that nothing gets cut off.

CHOOSE THE SPLINE DEGREE (1 or 3) from the object’s form, then place the control points the way that

degree requires:

- Pick DEGREE 1 (closed polyline) for angular / polygonal / straight-edged objects, or simple

 silhouettes where a polygon is enough. Its control points are vertices ON the true object outline

 (not a looser control polygon): place them directly on the edge, ordered around the loop, denser at

 corners/bends and sparser on long straight spans.

- Pick DEGREE 3 (closed cubic B-spline) for organic / rounded / smoothly curved silhouettes. Its

 control points are the B-spline CONTROL POLYGON (the curve is smoother than and sits inside the

 polygon), so push them slightly OUTWARD toward the object edge, ordered around the loop.

- Use the SAME degree for EVERY spline (outer loops and holes). Report it in the top-level "degree"

 field AND set "degree" on each spline to that value.

- Choose the NUMBER of control points from the object’s morphology and what you actually see inside the

 box -- typically 16-64 per loop. Use MORE points for intricate / irregular / many-parted outlines

 (closer to 64) and FEWER for simple, smooth, or rounded ones (near 16). Do not aim for a fixed count

 -- let the shape’s complexity decide within that range; under-sampling a complex outline is worse

 than a few extra points on a simple one.

Return ONLY this JSON (no prose, no markdown fences):

{"mask_color": "<one name from the list>",

 "mask_color_reason": "<short why this hue contrasts with object+background>",

 "degree": <1 or 3>,

 "degree_reason": "<short why this degree fits the object’s form>",

 "instances": [

 {"id": 0, "splines": [

 {"role": "outer", "degree": <same as top-level degree>, "closed": true,

 "control_points": [[x, y], [x, y], ...]}

 ]}

]}

Output the JSON and nothing else.

Prompt #3: Proposing Focus Regions
(Stage 3)

⬇
# <the current overlay image>

This image shows the CURRENT segmentation of the "<query>":

 - the translucent <tint> tint marks the current MASK REGION (coverage),

 - the RED outline is the current mask BOUNDARY -- the main edge to compare,

 - each YELLOW rectangle is one instance’s detection box (ids drawn beside them).

The <tint> fill is light on purpose: you can still see the <query>’s real edges/texture underneath. Use

the <tint> tint to tell what is already covered; use the red outline + the underlying pixels to judge

where the TRUE edge runs. Do NOT treat the soft tinted edge as the object boundary.

The image is <W>x<H> pixels (origin top-left, x right, y down).

ALL coordinates are absolute PIXELS with 0 <= x <= <W> and 0 <= y <= <H>.

DETECTION BOXES (each focus box MUST lie inside ONE of these):

- id=0 label="<label>" box=[120, 80, 540, 610]

 topology: {"components": 1, "holes": 0, "boundary_loops": 1, "notes": "single blob, no holes"}

- id=1 label="<label>" box=[600, 140, 930, 585]

 # ... (one such entry per detected instance)

Your task is a COMPARISON: follow the RED outline and, at each part of it, look through the <tint> tint

at the actual object pixels to see where the TRUE edge of the <query> is. Report the places where the

two disagree.

Find FOCUS BOXES that mark where the mask is wrong and needs local fixing:

 - type "positive": a box that FULLY encloses an area that IS part of the <query> but is NOT tinted /

 - type "negative": a box that FULLY encloses an area that IS tinted / INSIDE the red outline but is

(negative). Do not only hunt for misses.

- Tag every focus box with "instance_id" naming which detection box it belongs to.

- Check EVERY one of the <N> instances listed above, not only the largest or the most obviously wrong

- Anchor each box on what you can actually SEE: it should cover the full gap between the red outline

 soft tint alone.

- A pass may be ALL positive, ALL negative, or a mix -- there is NO requirement to include both types.

 Return only boxes that are genuinely wrong; never add a box of the other type just to have one of

 each.

- Only flag areas that are CLEARLY wrong in the current image; if a spot already looks correct, do not

 propose a box there (earlier fixes already show in the tint).

- For each box, describe the SHAPE of the region to be added/removed in a few words, and how intricate

 its outline is (e.g. "thin curved sliver", "small round bump", "jagged notch", "simple triangular

Return ONLY this JSON (no prose, no markdown fences). Example shape (mix of types; your list may be

all-positive, all-negative, or mixed):

{"focus_boxes": [

 {"type": "positive", "instance_id": 0, "shape": "<shape + complexity of the region to add>",

 "box": [x1, y1, x2, y2]},

 {"type": "negative", "instance_id": 0, "shape": "<shape + complexity of the region to remove>",

 "box": [x1, y1, x2, y2]}

]}

Output the JSON and nothing else.
