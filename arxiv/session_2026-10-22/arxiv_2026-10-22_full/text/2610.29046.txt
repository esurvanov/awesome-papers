Abstract

Large language models (LLMs) have shown considerable promise in synthesizing formal specifications from source code. However, existing approaches primarily focus on functional contracts and loop invariants, while largely neglecting frame conditions, which specify the memory locations that may or may not be modified during execution and constitute an essential part of formal specifications.
To address this limitation, we propose an LLM-based approach for synthesizing ACSL frame specifications alongside functional contracts from C code. Our approach analyzes code property graphs (CPGs) to extract frame-relevant information from the input code and leverages this information to guide the LLM in generating accurate frame conditions. The resulting specifications capture both region-separation constraints and data dependencies that govern variable modifications.
Experimental results demonstrate the effectiveness of our approach. On a benchmark of 84 ACSL-compliant functions from non-trivial real-world systems, our method successfully synthesizes error-free frame specifications for 92.9% of the functions, representing a 179% relative improvement over state-of-the-art techniques. On a second benchmark consisting of 51 functions, the success rate increases from 80.4% to 96.1%. Furthermore, when integrated as an auxiliary component into existing LLM-based ACSL-synthesis frameworks, our approach improves frame-specification generation performance by up to 61.9%.

## I Introduction

Large language models (LLMs) have recently shown strong potential for generating formal specifications from source code. For C programs, several approaches [1, 2, 3, 4, 5] have explored using LLMs to synthesize ACSL specifications, often with feedback from static analyzers or verification tools. These techniques can generate useful functional specifications, such as preconditions, postconditions, and loop invariants, and can substantially reduce the manual effort required for deductive verification. However, little attention has been paid to frame conditions: the part of a specification that describes what memory a function may affect, what values those effects depend on, and what memory must remain independent. Without accurate frame information, a verified function cannot be safely reused by callers, because the caller cannot know which parts of the program state are preserved.

This limitation is especially important for C programs. Recent approaches such as AutoSpec [4] and Preguss [5] push LLM-based specification generation further by combining models with program information and verification feedback. However, their treatment of frame information remains limited. They primarily optimize for whether the generated specification can help discharge verification conditions, while frame completeness is not directly measured. In particular, evaluations based mainly on WP proof success may overlook missing memory-dependence information or imprecise aliasing assumptions, because a proof can succeed even when the contract does not fully describe what state a caller may rely on after the function returns. This gap is difficult to close for C: pointers, arrays, pointer arithmetic, loops, and library calls can hide which memory regions may overlap and which input values may influence each write. As a result, a generated contract may look correct to the verifier but still be too weak for precise modular reasoning. Section II shows a small example where an apparently verified contract still permits an invalid aliased call.

To address this problem, we propose AutoFraming, an approach for synthesizing frame specifications for C programs. AutoFraming analyzes frame-relevant information from a code property graph (CPG) [6], including possible memory interference, caller-visible writes, loop-indexed write ranges, and data dependencies. It then projects this information into a fixed-frame skeleton that captures which memory regions must be kept independent and which inputs may influence each written location. The LLM is used to assemble the full contract and repair remaining verification failures, while the frame-critical structure is generated and preserved during refinement.

We evaluate AutoFraming on two benchmarks: 84 functions from real-world C systems and 51 academic verification examples. On the real-world benchmark, AutoFraming synthesizes error-free frame specifications for 92.9% of functions, a 179% relative improvement over the state-of-the-art baseline. On the academic benchmark, it improves the error-free frame rate from 80.4% to 96.1%. When used as an auxiliary frame-synthesis component for existing specification-generation tools, AutoFraming further improves error-free frame performance by up to 61.9%. Ablation results show that the CPG-derived frame information and deterministic projections are essential to the improvement.

The contribution of this paper is summarized as follows: AutoFraming provides an effective approach to the novel problem of synthesizing
error-free frame conditions with LLMs.
It conducts frame analysis, including caller-visible roots, access windows, interfering pointer pairs, write-set locations, and dependence footprints. It then projects frame-related information into ACSL specification, including region separation for caller-visible memory regions and data dependence for write-set locations.
Moreover, AutoFraming can be used in other ACSL synthesis frameworks, such as Preguss and AutoSpec, to improve their capability of synthesizing frame conditions.

## II A Motivating Example

Consider the C function parse_value, shown below, which reads two values from the memory region pointed to by buf and stores their sum in the memory location pointed to by eaten.

Listing 1: Source code of the motivating example.

⬇

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten) {

 if (len < 2 || buf == NULL || eaten == NULL) return -1;

 *eaten = buf[0];

 *eaten = (uint16_t)(*eaten + buf[1]);

 return 0;

}

To call parse_value, the client needs to provide actual parameters for *buf and *eaten, such as the following:

⬇

uint16_t buf[2] = { 3, 5 };

uint16_t out;

parse_value(buf, 2, &out);

Without a formal specification for parse_value, clients have no precise way to determine whether a call satisfies the function’s assumptions or achieves its intended behavior. To address this issue, we can prompt an LLM to synthesize the following ACSL [7] specification directly from the source code of parse_value:

Listing 2: Preliminary ACSL specification generated by prompting an LLM

⬇

/*@ requires len > 0;

 requires buf != \null;

 ensures \result == 0 || \result == -1; */

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten);

The generated comment enclosed by /*@ and */ defines the ACSL contract for parse_value, including its precondition (the requires clauses) and postcondition (the ensures clause). The precondition specifies the conditions that callers must satisfy before invoking parse_value; specifically, len must be positive and buf must be non-null. The postcondition specifies the property that must hold when parse_value returns, namely that the return value is either 0 or -1.

The ACSL specification can be verified with Frama-C and one of its plug-ins (e.g., WP or Eva) [8]. Given a function and its ACSL contract, Frama-C generates a set of proof obligations, called goals, each expressed as a logical formula whose validity establishes a specific aspect of the contract. These goals are then dispatched to automated SMT solvers. The proportion of discharged goals, referred to as the goal ratio (proved/total), indicates the extent to which the contract has been verified. A goal ratio of $1$ (i.e., a full proof) means that every proof obligation has been discharged, establishing that the implementation satisfies the specified contract for all executions. Otherwise, the result is only a partial proof, indicating that some proof obligations remain unresolved. It is important to note, however, that a full proof does not necessarily imply that the code is correct. Rather, it only guarantees conformance to the given specification. If the specification is incomplete or inaccurate, the implementation may still satisfy it while failing to capture the intended behavior. For example, Frama-C with the WP plugin reports a full proof for the preliminary LLM-generated ACSL contract shown above, even though the contract only partially captures the intended behavior of parse_value. The generated precondition is overly restrictive. It requires len to be positive and buf to be non-null, even though parse_value handles the cases where len is non-positive or buf is NULL without error.

To improve the quality of synthesized ACSL specifications, existing approaches leverage the results of static code analysis to prompt LLMs and refine the specifications.
The following ACSL specification is generated by Preguss [5], the state-of-the-art method:

Listing 3: ACSL specification generated by existing approaches

⬇

/*@ requires \valid_read(buf + (0..len-1));

 requires \valid(eaten);

 assigns *eaten;

 ensures \result == 0 || \result == -1; */

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten);

The requires clauses specify the validity conditions for buf and eaten. The assigns clause, assigns *eaten;, defines the function’s frame condition by specifying that only the memory location referenced by eaten may be modified during execution. Consequently, all other program state, including buf, len, and the memory referenced by buf, must remain unchanged. More generally, the assigns clause consists of a list of variable names or memory locations (referred to as a write set or footprint).

However, the above frame specification is insufficient even though the verification result is a full proof. Consider the following call:

⬇

uint16_t buf[2] = { 3, 5 };

parse_value(buf, 2, &buf[1]);

The call satisfies
both precondition clauses, i.e., buf is readable and &buf[1] is
valid. Although the intended value for *eaten (i.e., buf[1]) is
buf[0] + buf[1] = 8, the actual outcome is 3 + 3 = 6 because parse_value reads buf[1]
after writing through *eaten, so the write clobbers
buf[1] first and the call computes 3 + 3.

The problem arises because the same object, buf, is passed to both pointer parameters, *buf and *eaten. However, parse_value operates correctly only when these pointers refer to separate, non-overlapping memory locations. Therefore, the ACSL specification must explicitly capture this separation requirement to prevent invalid function calls and ensure correct verification.

In summary, existing LLM-based approaches to ACSL specification synthesis do not explicitly address the frame problem, particularly dynamic frame conditions such as the memory separation requirement illustrated above. Dynamic frame conditions precisely specify the memory locations that a function is permitted to read or modify, ensuring that changes to one object cannot inadvertently affect the state of another unrelated object. The goal of this paper is to enable LLMs to synthesize ACSL specifications with accurate frame conditions for C programs that are ACSL-compliant, i.e., programs whose behavior can be completely specified in ACSL. The following specification for the example illustrates the desired result:

Listing 4: ACSL specification with dynamic frames

⬇

/*@ requires \valid_read(buf + (0..len-1));

 requires \valid(eaten);

 requires \separated(buf + (0..len-1), eaten);

 assigns *eaten

 \from buf[0..len-1], len;

 ensures \result == 0 || \result == -1; */

int parse_value(const uint16_t *buf, uint16_t len, uint16_t *eaten);

The additional requires clause,
\separated(buf + (0..len-1), eaten);
specifies that the memory region referenced by buf must be disjoint from the memory location referenced by eaten. The assigns clause,
*eaten \from buf[0..len-1], len;
defines both the function’s write set and the data dependencies of the modified location, stating that only *eaten may be updated and that its value depends solely on buf[0..len-1] and len.
Synthesizing the region separation requirement and the data dependency of the write set is a challenging problem. Because C programs do not expose their memory footprint directly in the source syntax. Pointer aliasing, array ranges, pointer arithmetic, loops, globals, and library calls can hide both the regions that may interfere with one another and the inputs that may affect each write. Therefore, synthesizing accurate dynamic frames requires recovering caller-visible memory regions, separation assumptions, and write dependencies from program structure rather than treating frame clauses as ordinary text to be generated.

## III The design of AutoFraming

## III-A Overview

AutoFraming leverages the code property graph (CPG) representation of C code to synthesize its frame specifications. Given an unannotated function, AutoFraming generates an ACSL specification whose frame part describes not only the memory locations that may be modified, but also the memory regions that must remain disjoint and the caller-visible inputs that may influence each write. Although AutoFraming outputs a complete ACSL specification, this paper focuses on the synthesis of frame conditions. Figure 1 shows the three-stage workflow of AutoFraming.

Stage 1: AutoFraming first constructs the call graph and analyzes functions in bottom-up order, ensuring that verified callee contracts are available when analyzing their callers. For each function $f$ , AutoFraming builds a CPG and extracts the frame-related information $\Phi_{f}$ , which captures the caller-visible roots of memory accesses, accessed regions of pointer roots, pointer pairs whose aliasing may interfere with caller-visible writes, write-set locations used as frame carriers, and the dependence footprint of each write-set location.

Fig. 1: AutoFraming Pipeline for CPG-guided Frame Specification Synthesis.

Stage 2: AutoFraming projects $\Phi_{f}$ into a frame skeleton. The separation projection turns interfering pointer regions into disjointness requirements, while the dependence projection attaches caller-visible dependence footprints to write-set locations. AutoFraming treats projected frame obligations as required constraints.
A candidate is rejected if it deletes or weakens them, but the current
implementation may still allow equivalent or stronger rewritings that
change the proof burden.

Stage 3: AutoFraming asks the LLM to assemble a verifier-checkable contract around the frame skeleton and uses Frama-C feedback to repair remaining failures. During refinement, candidate contracts are accepted only if they preserve the projected frame conditions, avoid degenerate frames, and make proof progress. This design lets AutoFraming use the LLM for auxiliary annotations and repair while keeping the frame-critical content grounded in program analysis.

## III-B CPG-Based Frame Analysis

For each function $f$ , AutoFraming extracts from its CPG the information needed to synthesize the dynamic frame. A CPG overlays three program views on one graph [9]: the abstract syntax tree (AST), which exposes declarations and assignment targets; the
control-flow graph (CFG), which exposes branches, loops, and execution paths; and the program dependence graph (PDG), which exposes data and control dependencies. This combination is essential because frame synthesis is not a purely syntactic task: write-set locations come from syntax, region extents often come from loops and guards, and dependence footprints require following value and control flow.

AutoFraming represents the frame-related information as

 $\Phi_{f}=(\mathcal{R}_{f},\Omega_{f},\mathcal{I}_{f},\mathcal{L}_{f},\Delta_{f}).$ 

The first three components help address the region-separation issue:
which caller-visible regions must be disjoint? The last two deal with the data dependency issue: what does each write set location depend on?

## CPG-to-information extraction.

AutoFraming derives each component of $\Phi_{f}$ by querying specific CPG
nodes and edges rather than by passing the whole graph to the LLM. AST
nodes provide syntactic roots and memory-access forms: parameter and
global declarations identify caller-visible roots; dereference,
array-subscript, field-access, assignment, and update nodes identify
reads and writes; and declaration and cast nodes provide type information
for alias compatibility. CFG edges provide the execution context of these
accesses: loop headers, back edges, and branch guards are used to recover
loop-indexed access ranges and conditional bounds. PDG edges provide
dependence information: data-dependence edges connect values to the
expressions they influence, while control-dependence edges connect guards
to the writes whose execution they control. Together, these CPG views
determine the five information components used by AutoFraming:
caller-visible roots, access windows, interfering pointer pairs,
write-set locations, and dependence footprints.

## Caller-visible roots.

 $\mathcal{R}_{f}$ contains the formal parameters and globals that the
function may read or write, each recorded with its type. These roots are
the only memory roots that can appear in the external frame of $f$ .
Local variables are excluded because their storage does not escape the
function call. Pointer roots are recorded with their pointed-to types,
since type compatibility determines whether two roots may denote
overlapping storage.
For a pointer-typed root $p$ with C type $T*$ , we call $T$ the
pointed-to type of $p$ . For example, the pointed-to type of
const uint16_t *buf is uint16_t, and the pointed-to
type of uint16_t *eaten is also uint16_t. Hence,
buf and eaten may refer to overlapping
uint16_t storage at a call site.

AutoFraming uses pointed-to types as a conservative
alias-compatibility filter. Two pointer roots are considered compatible
when their accesses may refer to the same kind of object storage. This
includes roots with the same pointed-to type after removing qualifiers
such as const and volatile, roots accessed through
byte-level pointer types such as char * or
unsigned char *, roots accessed through generic
void * interfaces, and roots whose type information is weakened
by casts. Conversely, roots with clearly different non-byte pointed-to
types, such as int * and double *, are filtered out
when the function contains no casts, byte-level accesses, or generic
pointer operations that could make overlap relevant.

## Access windows.

For each pointer root $p\in\mathcal{R}_{f}$ , $\Omega_{f}(p)$ records the
entry-expressible region of $p$ that the function may access:

 $\Omega_{f}(p)=\mathsf{window}\bigl(\mathsf{Accesses}_{f}(p)\bigr).$ 

The access set $\mathsf{Accesses}_{f}(p)$ is collected by traversing AST
memory-access nodes rooted at $p$ , including dereferences, array
subscripts, field accesses, and summarized library calls. It then uses
CFG loop and guard edges to attach path conditions and ranges to these
accesses. A constant access such as p[c] contributes offset
 $c$ ; a loop-indexed access such as p[i] contributes the loop
range recovered from the loop header and back edge; and an access guarded
by a condition such as i < n contributes a range bounded by $n$ 
when $n$ is available at function entry. These
windows allow AutoFraming to emit separation constraints over accessed
regions rather than over pointer names alone.

## Interfering pointer pairs.

 $\displaystyle\mathcal{I}_{f}=\{\,\{p,q\}\mid$ 
 $\displaystyle p,q\in\mathcal{R}_{f}\land\mathsf{ptr}(p)\land\mathsf{ptr}(q)$ 

 $\displaystyle}{\displaystyle\land\mathsf{compatible}(p,q)\land\mathsf{interferes}_{f}(p,q)\,\}.$ 

Here, $\mathsf{compatible}(p,q)$ applies the pointed-to-type filter:
it keeps same-type, byte-level, generic-pointer, and cast-related pairs,
and filters out clearly incompatible typed accesses. The predicate
 $\mathsf{interferes}_{f}(p,q)$ checks whether aliasing the two roots can
change a caller-visible write or the value written:

 $\displaystyle\mathsf{interferes}_{f}(p,q)\triangleq$ 
 $\displaystyle\bigl(\mathsf{writes}_{f}(p)\land\mathsf{affectsWrite}_{f}(q)\bigr)$ 

 $\displaystyle}{\displaystyle\lor\bigl(\mathsf{writes}_{f}(q)\land\mathsf{affectsWrite}_{f}(p)\bigr).$ 

A root satisfies $\mathsf{affectsWrite}_{f}$ when it either roots a write
or is read into a value that flows to a write. This interference test
prevents AutoFraming from over-restricting callers by separating
unrelated pointer parameters.

## Write-set locations.

 $\mathcal{L}_{f}$ contains the caller-visible locations that may be
modified by $f$ , normalized into ACSL assignable locations. AutoFraming
first collects write targets from AST write nodes in the CPG, including
assignment left-hand sides, array-cell updates, structure-field updates,
and dereferences. We use $w$ to denote one such write target. A target
 $w$ is kept only when it can be expressed using a caller-visible root in
 $\mathcal{R}_{f}$ , such as a parameter or global. If a write is performed
through a local pointer alias, AutoFraming uses CPG data-dependence edges
only to rewrite the target back to its caller-visible root; the local
alias itself is never emitted in an ACSL frame clause.

When a write target $w$ is an array access indexed by a loop variable,
for example $w=A[i]$ , AutoFraming uses CFG loop and guard edges to
recover $\mathsf{range}_{f}(i)=(lo,hi)$ and normalizes the target to the
whole loop-written range:

 $\mathsf{norm}_{f}(w)=\begin{cases}A[lo..hi-1],&\text{if }w=A[i],\\
w,&\text{otherwise.}\end{cases}$ 

The write-set location set is therefore

 $\mathcal{L}_{f}=\{\,\mathsf{norm}_{f}(w)\mid w\in\mathsf{Writes}^{vis}_{f}\,\},$ 

where $\mathsf{Writes}^{vis}_{f}$ denotes the collected write targets that
can be expressed using caller-visible roots. These locations supply the
left-hand side of ACSL assigns clauses. In AutoFraming, however,
the write location is not the main synthesis target; it is the carrier to
which dependence information is attached.

## Dependence footprints.

For each write set location $L\in\mathcal{L}_{f}$ , $\Delta_{f}(L)$ contains
the caller-visible inputs whose values may influence the value written to
 $L$ :

 $\Delta_{f}(L)=\{\,r\in\mathcal{R}_{f}\mid r\leadsto^{data/control}_{f}\mathsf{write}(L)\,\}.$ 

The relation $\leadsto^{data/control}_{f}$ is computed from the PDG. It
includes data dependencies, where a root contributes to the expression
being written, and control dependencies, where a root controls whether a
write occurs. Local intermediate variables are followed transitively but
are not reported; the final dependence set contains only caller-visible
inputs. Pointer reads are lifted to accessed regions using $\Omega_{f}$ , so
a loop that writes an output from buf[i] contributes the
accessed region of buf, rather than only the syntactic root
buf.

## III-C Synthesis of Region-Separation Constraints

The first dynamic-frame synthesis issue is region separation:
for pointer-accessed memory, a frame specification must identify the
caller-visible regions that must be disjoint for the declared frame to be
valid. If two such regions may overlap at a call site, a write through
one pointer can affect a read or write through another, making the
specified frame unsound or incomplete for modular reasoning.

Regional separation analysis is difficult for C code because the
required disjointness is not explicit in the source text. The same
function body can be called with separated or aliased actual arguments,
and the relevant regions may be hidden behind pointer arithmetic,
loop-indexed accesses, local pointer aliases, casts, or library calls.
Thus, the synthesis problem is not merely to emit a
\separated clause, but to determine which
caller-visible pointer regions require such a clause and what region
extent should be used.

AutoFraming uses frame information extracted from the CPG to synthesize region-separation requirements. The interfering-pair
component $\mathcal{I}_{f}$ identifies caller-visible pointer roots whose
aliasing can affect a caller-visible write, while the access-window
component $\Omega_{f}$ identifies the region of each root that the function
may access. The separation projection then maps each pair in
 $\mathcal{I}_{f}$ and its corresponding access windows to an explicit
caller-side \separated precondition.

For each $\{p,q\}\in\mathcal{I}_{f}$ , AutoFraming emits
 $\mathsf{Sep}_{f}(p,q)$ .

 $\displaystyle\rho_{p}$ 
 $\displaystyle=\mathsf{region}(p,\Omega_{f}(p)),$ 

 $\displaystyle\rho_{q}$ 
 $\displaystyle=\mathsf{region}(q,\Omega_{f}(q)),$ 

 $\displaystyle\mathsf{Sep}_{f}(p,q)$ 
 $\displaystyle=\text{requires}~\text{\char 92\relax separated}(\rho_{p},\rho_{q})\text{;}.$ 

The function $\mathsf{region}$ converts a pointer root and its access
window into an entry-expressible ACSL memory region, such as
p, p+(0..n-1), or another slice expressible at function
entry. A constant offset contributes a singleton extent; a loop-indexed
offset contributes the loop range; and a guarded access contributes the
guard bound when that bound is available at function entry.

Type compatibility alone is insufficient: many C functions take multiple
pointers of the same type without requiring them to be disjoint.
AutoFraming emits a separation constraint only when aliasing the two
roots can affect the function’s caller-visible frame. This distinction is
important for C APIs such as copy, parse, and decode routines, where
source and destination pointers have compatible types but only some
pairs need disjointness.

When an access window cannot be expressed at function entry,
AutoFraming emits the strongest entry-expressible approximation available
and sends the candidate to the verification-repair stage. Such a
candidate is not accepted merely because the clause was generated; it
must still preserve the projected frame and discharge the relevant frame
obligations.

## III-D Synthesis of Data Dependencies for Write Sets

The second frame synthesis issue is data dependence for
write sets: for each location that a function may modify, the frame
specification must identify the caller visible inputs that may influence
the value written there. An ACSL assigns clause without a
\from footprint states where the function may
write, but not what information the written value may depend on. Such a
frame is incomplete for modular reasoning because callers cannot
determine which parts of the prestate are relevant to the modified
location.
Inferring this footprint is difficult in C because the dependence of a
written value is often separated from the final assignment. The value may
flow through local temporaries, pointer aliases, loop carried updates,
control predicates, globals, or summarized library calls before reaching
the write. As a result, reading the left hand side and right hand side of
the final assignment is not enough to recover the frame dependence.

AutoFraming handles this by using the write-set locations in
 $\mathcal{L}_{f}$ as carriers and attaching to each one the dependence
footprint $\Delta_{f}(L)$ extracted from the CPG. The projection therefore
turns the internal value-flow information for each write into the ACSL
form expected by modular verification.

For each normalized write set location $L\in\mathcal{L}_{f}$ ,
the data dependence projection attaches $\Delta_{f}(L)$ :

 $\frac{L\in\mathcal{L}_{f}\quad\Delta_{f}(L)=\{r_{1},\ldots,r_{m}\}\quad m>0}{\texttt{assigns}~L~\texttt{\textbackslash from}~r_{1},\ldots,r_{m}\texttt{;}}\quad\textsc{right={{Dep}}}$ 

If $\Delta_{f}(L)=\emptyset$ , AutoFraming emits:

 $\frac{L\in\mathcal{L}_{f}\quad\Delta_{f}(L)=\emptyset}{\texttt{assigns}~L~\texttt{\textbackslash from}~\texttt{\textbackslash nothing}\texttt{;}}\quad\textsc{right={{Dep-Const}}}$ 

The dependence footprint includes both data and control dependencies. A
root is included in $\Delta_{f}(L)$ if its value flows into the expression
written to $L$ , or if it controls whether a write to $L$ is executed. For
example, in a branch that writes different constants to *out
depending on flag, the output depends on flag even
though flag does not appear on the right-hand side of either
assignment. Capturing this control dependence is necessary for the
\from clause to describe the value written, not
just the memory location modified.

The result of the two projections is a frame skeleton $S_{f}$ . The
region separation projection contributes the \separated
preconditions, and the data dependence projection contributes the
assigns … \from clauses. Thus,
AutoFraming’s synthesis target is not merely the static write set, but
the dynamic-frame information attached to that write set.

## III-E Frame-constrained contract synthesis

The two projection rules produce a frame skeleton $S_{f}$ consisting of
\separated preconditions and
assigns … \from clauses. This
skeleton is the output of the frame-constrained projection step. AutoFraming
does not ask the LLM to invent or reinterpret it. Instead, $S_{f}$ is
inserted into the prompt as a set of required
frame obligations in the candidate contract.

Frama-C verifier, however, checks frame clauses only inside a complete ACSL
contract. A frame skeleton can introduce proof obligations that require
additional surrounding annotations. For example, a separated region
 $p+(0..n-1)$ requires preconditions establishing that the region is
well-formed and valid at function entry; an assigned slice
 $A[lo..hi-1]$ may require loop annotations showing that the loop writes
only that range; and a \from footprint may require
auxiliary assertions or invariants that expose how values flow through
local temporaries. AutoFraming therefore asks the LLM to synthesize a
contract envelope $E_{f}$ around the locked frame skeleton:

 $C_{f}^{(0)}=E_{f}\cup S_{f}\qquad\text{with}\qquad S_{f}\subseteq C_{f}^{(0)}.$ 

The envelope may contain validity preconditions, simple functional
postconditions, loop invariants, loop variants, loop assigns clauses, and
auxiliary assertions needed by the verifier.

The frame information $\Phi_{f}$ guides this envelope synthesis. Access
windows $\Omega_{f}$ suggest validity requirements such as
\valid_read for input regions and
\valid for written regions. write-set locations in
 $\mathcal{L}_{f}$ guide loop assigns annotations and frame-preserving loop
invariants. Dependence footprints $\Delta_{f}(L)$ identify the inputs that
are relevant to postconditions over assigned outputs. When a function
calls another function, AutoFraming provides the verified callee contract
as context, so the LLM can use the callee’s frame and functional clauses
rather than re-analyzing the callee body.

This design separates the role of program analysis from the role of the
LLM. Program analysis and frame-constrained projection synthesize the frame-critical
content $S_{f}$ . The LLM supplies only the verifier-facing envelope $E_{f}$ 
needed to make $S_{f}$ checkable in a complete ACSL contract. As a result,
AutoFraming avoids relying on the LLM to guess dynamic-frame clauses from
source code alone, while still using the LLM to fill
in auxiliary annotations and functional context that are necessary for verifier to discharge the generated frame.

## III-F Frame-constrained refinement

The contract produced by frame-constrained synthesis already contains the
projected frame conditions, but it may still fail the frame-error-free
checks. These failures can arise because the surrounding contract envelope
is incomplete: the candidate may lack validity preconditions needed to
justify an accessed region, loop annotations needed to prove an assigned
slice, or auxiliary assertions needed to expose a dependence relation to
the verifier. AutoFraming therefore performs verifier-guided refinement
using feedback from Frama-C/WP and Eva.

The refinement loop is frame-constrained. The LLM may revise the contract
to make the projected frame conditions checkable, but it may not delete,
weaken, or replace them with degenerate frame clauses.

In each round, the LLM reads the function body, the current contract, the
projected frame skeleton, and the verifier feedback, and proposes a
revised contract. A revised candidate $C_{f}^{(k+1)}$ is accepted only when
the following conditions hold.

First, the frame structure must be preserved. Every
\separated precondition and every
assigns … \from clause projected
from $\Phi_{f}$ must remain present. The LLM may strengthen these clauses,
but it cannot delete them or replace them with a weaker frame.

Second, the candidate must not contain a degenerate frame. In particular,
AutoFraming rejects candidates with missing assigns clauses,
missing loop assigns clauses, or vacuous frames that hide
caller-visible writes.

Third, the candidate must make strict proof progress: it must close at
least one previously unresolved proof obligation without reopening any
obligation that was already discharged.

The first two conditions prevent the LLM from satisfying the verifier by
weakening the frame. The third keeps the repair loop making
monotone progress. The loop ends when Frama-C/WP and EVA discharge the relevant
frame conditions or when it reaches the maximum number of rounds $N$ .

## IV Evaluation

We evaluate AutoFraming with respect to three questions.

RQ1 (Performance). How effectively does AutoFraming synthesize frame specifications?

RQ2 (Ablation). How do CPG-based frame analysis and frame-constrained projection contribute to the efficiency of AutoFraming?

RQ3 (Generality). Can AutoFraming improve existing frameworks’ capability of synthesizing frame specifications?

## IV-A Datasets

We use the following existing datasets:

## $\mathcal{D}_{\mathrm{a}}$ : Real-world C code 

Nine real-world C programs from the Preguss public benchmark [5],
across an embedded RTOS (Atomthreads), four
Contiki OS subsystems (ctimer, etimer, process, trickle), a TLS X.509
certificate parser (x509-submodule-2), an authenticated-encryption mode
(AES-CCM), and an embedded database (Antelope memb, Antelope relation). We include functions whose frame specifications are expressible in first-order ACSL without user-defined inductive predicates, yielding 84 benchmark functions. Functions requiring such predicates are excluded because their verification rests on the quality of a hand-written predicate, which is orthogonal to the frame synthesis we study in this paper. The same inclusion criterion is applied to all compared configurations. For transparency we also report the excluded set, where Preguss’s error-free frame rate is only 3.3% of the predicate-dependent functions, confirming that these cases are omitted because they need inductive-predicate reasoning outside our target problem, not because their exclusion advantages AutoFraming.

## $\mathcal{D}_{\mathrm{b}}$ : Frama-C Problems

Fifty-one small C programs from the Frama-C tutorial suite widely used by formal verification works, organised into eight categories including arrays_and_loops, general_wp_problems,
immutable_arrays, loops, miscellaneous,
more_arrays, mutable_arrays, pointers.

## IV-B Experimental Setup

For each function we measure two frame-quality metrics.
Frame warning: a warning emitted by the Frama-C WP plugin indicating
that the contract has no assigns clause or that the clause is
incomplete.
Frame fail: reported by the Frama-C WP plugin together with the Eva
plugin; a function is frame-failing if it fails at least one
typed_<f>_assigns_* or
typed_<f>_loop_assigns_* goal during WP discharge, or if it
fails the Eva dependence-set check.
We classify a function as frame-error-free only when all three checks
pass: (1) Frama-C emits no missing/incomplete assigns warning, (2) WP
discharges every generated assigns and loop-assigns proof obligation
within the timeout, and (3) Eva reports no dependency set mismatch for
the write-set locations. Timeouts on frame conditions are counted as
frame failures. We do not count a function as error-free merely because
the contract is syntactically accepted.
To confirm that strengthening a frame does not weaken the functional
specification, we also report the proof ratio (goals proved / total goals)
from the WP results.

To show that our results are not specific to a single model, we instantiate
the pipeline identically with two different models, Gemini-2.5-Pro and
GPT-5.2.
Verification uses Z3 and Alt-Ergo with a 30-second per-goal timeout.

## IV-C RQ1: How effectively does AutoFraming synthesize frame specifications?

RQ1 evaluates whether AutoFraming can synthesize frame specifications
that are accepted by frame specific checks. We instantiate the same
pipeline with two LLMs, Gemini-2.5-Pro and GPT-5.2, using the same configurations. We denote AutoFraming as AF in the result tables. Accordingly,
AF-GPT and AF-Gemini refer to AutoFraming instantiated with GPT-5.2 and
Gemini-2.5-Pro, respectively. We
compare against the strongest available ACSL specification generators on
our benchmarks: Preguss on both benchmarks and AutoSpec on the academic
benchmark. All methods are evaluated using the same frame-error-free
criterion.

Tables II and III report the number of functions for which each method
synthesizes a frame-error-free specification. On the real-world benchmark
 $D_{a}$ , AutoFraming substantially improves over Preguss: AF-Gemini
succeeds on 78 of 84 functions (92.9%) and AF-GPT succeeds on 77 of 84
functions (91.7%), compared with 28 of 84 functions (33.3%) for
Preguss. On the academic benchmark $D_{b}$ , AF-Gemini succeeds on 49
of 51 functions (96.1%) and AF-GPT succeeds on 48 of 51 functions
(94.1%), compared with 41 of 51 functions (80.4%) for Preguss and 23
of 51 functions (45.1%) for AutoSpec.

These results show that frame synthesis exposes failures that are not
captured by overall proof success alone. Preguss and AutoSpec can produce
contracts that are useful for functional verification, but their frame
clauses are often missing, incomplete, or insufficiently precise for the
frame-specific checks used in this study. AutoFraming improves because it
targets the frame conditions directly: region separation and data
dependence for write-set locations are synthesized before the LLM
synthesizes the rest of the contract.

Table IV further decomposes each method’s failures into frame warnings and
frame proof failures. The breakdown shows that the main weakness of the
baselines is frame incompleteness. On $D_{a}$ , Preguss emits 51 frame
warnings and has 5 frame failures, leaving only 28 functions
frame-error-free. AutoFraming sharply reduces these warnings: AF-GPT has
2 warnings and 5 frame failures, while AF-Gemini has 4 warnings and 2
frame failures. On $D_{b}$ , both AutoFraming variants leave only one
frame warning, compared with 10 for Preguss and 28 for AutoSpec.

The few functions AutoFraming leaves unverified falls into two categories. The first is a limit of the verifier. For example, memb_alloc writes
m->count[0..m->num-1], an extent whose bound m->num is a
mutable struct field; the synthesized frame names exactly this region and is
correct, but the verifier cannot decide the completeness of a range whose bound is a
runtime value.

The second failure type occurs when the LLM overrides the projected
frame skeleton with its own reading of the code during contract synthesis.
Although AutoFraming is designed to preserve the projected frame, the
final candidate still passes through an LLM generation step. In a small
number of cases, this generation changes the structure of the frame in a
way that remains syntactically valid but becomes harder for WP to
discharge. For example, set_iv, our analysis gives its
write set as a single contiguous region, assigns iv[0..15], and
AF-Gemini keeps it: WP discharges the frame at once. AF-GPT, handed the very
same input, re-derives the frame to mirror the four write statements in the
body—iv[0], the thirteen bytes copied into iv[1..13] by
memcpy, iv[14], and iv[15], and emits them as four
disjoint slices. This
forces WP to re-establish the memcpy’s separation against four separate
regions, which causes the timeout. That is a limitation of our approach because our approach still depends on LLM generation.

Answer to RQ1. AutoFraming synthesizes frame-error-free
specifications for more than 90% of functions on both benchmarks and
substantially outperforms existing ACSL generation frameworks under
frame-specific checks. The improvement is consistent across two different
LLMs, suggesting that the gain comes from the frame-synthesis design
rather than from a single model choice.

## IV-D RQ2: How do CPG-derived frame information and frame-constrained projection contribute to the efficiency of AutoFraming?

To isolate the source of AutoFraming’s frame quality, we compare the full
pipeline with three reduced variants. The first variant removes
CPG-derived frame information but keeps frame-constrained projection and
frame-constrained refinement. The second keeps the CPG information but
removes frame-constrained projection. The third removes both CPG information
and frame-constrained projection, leaving only LLM-based refinement.

The full AutoFraming pipeline synthesizes frame-error-free specifications
for 78 of 84 functions. Removing the frame-constrained projection while
keeping the CPG information and the full frame-constrained refinement loop
reduces the result to 54 of 84 functions, a loss of 24 functions. This
drop shows that CPG information alone is not sufficient: without the
projection step, the LLM must still infer how the extracted information
should be translated into ACSL frame clauses.

The other reduced variants support the same conclusion. The configuration
without frame-constrained projection reaches 54 functions, which is close
to the refinement-only configuration with 53 functions. Removing the
CPG-based frame information reduces the result further to 48 functions.
Thus, neither CPG information alone nor frame-constrained refinement alone
explains AutoFraming’s improvement. The main gain comes from the
frame-constrained projection.

The two frame constraints govern where the variants fail. Most failures fall
under the data dependence projection for write sets, in two forms. Some are
data-dependence errors: the model names the right locations but omits
the \from dependence (e.g. assigns *dest;
instead of assigns *dest \from *src;), or it declares
an unsound dependence, as when set_iv gives
\from nonce[0..12] that cannot be discharged through the
library memcpy. Others are write-set errors, where the extent
of the write set is wrong rather than merely its name:
aes_128_set_padded_key and set_key declare
assigns round_keys[0..10] but miss the inner array dimension—the
sound frame is round_keys[0..10][0..15]; atomCurrentContext,
list_head, and arg_alloc omit the
\result location entirely; and _parse_arc
declares assigns \nothing for a function that writes two
outputs. The remaining failures fall under region separation. For example,
parse_PolicyInformation and parse_policyQualifierInfo
declare the correct write set but hedge their precondition, weakening the
\separated guarantee until the frame condition can no
longer be discharged.

Answer to RQ2.
The ablation shows that the frame-constrained projection is the central
component of AutoFraming. Removing this projection reduces the
frame-error-free count from $78/84$ to $54/84$ , a loss of 24 functions.
This indicates that CPG information and frame-constrained refinement are
not sufficient by themselves; the extracted information must be projected
into explicit ACSL frame conditions before the LLM assembles the final
contract. The refinement-only configuration reaches a similar result
( $53/84$ ), and removing CPG-based frame information lowers the result to
 $48/84$ . Thus, AutoFraming’s improvement comes primarily from the
frame-constrained projection.

RQ3 evaluates whether AutoFraming can be used as a modular

AutoFraming generalizes as a frame-specification refinement layer for
existing ACSL generators. With Preguss and AutoSpec as upstream tools, it
raises the frame-error-free rate to $95.2\%$ – $98.0\%$ while also

This indicates that AutoFraming strengthens the frame specification
rather than improving the frame score by weakening the surrounding
contract. We do not claim that the goal-prove rate establishes semantic
completeness of the functional clauses; rather, it checks that the added
frame clauses remain compatible with the evaluated verifier.

## V Related Work

## V-A Program-Analysis-Based Specification Inference

Early work on specification inference mainly relies on program analysis to derive likely contracts, invariants, or behavioral properties from source code. These approaches can be broadly characterized by whether they reason from observed executions or from static program semantics.

Dynamic inference techniques generate candidate specifications from execution traces. Daikon [10], for example, instruments programs and infers likely invariants from recurring value patterns observed at program points such as function entries and exits. CLIPER [11] similarly mines temporal behavioral patterns from traces. Although such techniques are useful for discovering common runtime properties, their results depend heavily on input coverage and may overfit to observed executions. To improve generalization, later systems combine concrete traces with symbolic reasoning. DySy [12] integrates dynamic execution and symbolic execution, using counterexamples to refine inferred invariants, while SymInfer [13] combines concrete traces with symbolic states to produce more general specifications. SPEEDY [14] further connects runtime monitoring with Frama-C static analyzers to suggest specifications during development.

Static approaches infer specifications without executing the program, often aiming to cover all feasible paths. Kindspec [15, 16] applies symbolic execution to KernelC programs and synthesizes abstract preconditions and postconditions as logical contracts. TriCera [17] translates C programs into constrained Horn clauses and uses SMT solving to infer ACSL function contracts. AutoDeduct [18] also automates contract generation through symbolic execution and Horn clause reasoning. In contrast to these automated techniques, Araujo et al. [19] demonstrate a manual specification and verification process by translating avionics requirements into ACSL annotations and checking them with Frama-C. These works show the value of program analysis for contract inference, but they generally focus on functional behavior rather than frame specifications.

## V-B LLM-Assisted Formal Specification Generation

Recent work has explored large language models as a flexible mechanism for generating formal specifications from code, natural language requirements, examples, or verifier feedback. For C programs, George et al. [1] prompt GPT-4 to synthesize ACSL contracts directly from source code, showing that LLMs can often produce specifications that capture intended behavior rather than merely restating implementation details. In follow-up work, George et al. [2] enrich the prompt with outputs from Frama-C Eva [20] and PathCrawler [21], demonstrating that static-analysis warnings and test-based traces can guide the model toward more useful contracts.

Several systems combine LLM generation with formal-verification feedback. AutoSpec [4] constructs program information such as call graphs and iteratively refines LLM-generated specifications using verifier feedback. Janßen et al. [3] evaluate ChatGPT on small C programs and show that generated loop invariants can help Frama-C and CPAchecker complete proofs, while also identifying common failure modes such as weak or invalid invariants. Guangyuan et al. [22] use GPT-3.5 to propose loop invariants and rely on CBMC counterexamples to guide refinement. ACInv [23] extracts loop context through static analysis, prompts an LLM to generate invariants, and uses an LLM-based evaluator to iteratively strengthen, weaken, or reject candidates. NL2Contract[24] translates informal natural-language hints into formal functional contracts with both preconditions and postconditions for automatic software verification. Preguss [5] improves the scalability of LLM-assisted specification synthesis by using potential runtime-error assertions to decompose large C verification tasks into prioritized units. These studies suggest that LLMs are most effective when combined with symbolic information and verifier feedback, but their primary focus remains on functional contracts and loop invariants.

LLM-based specification generation has also been studied beyond C and ACSL. For Java, Teuber and Beckert [25] use GPT to complete JML annotations and repair invalid contracts with feedback from the KeY verifier, while Greiner et al. [26] train CodeT5-based models to generate JML preconditions and postconditions from a large corpus of examples. SpecGen [27] adopts a two-stage process that first prompts an LLM to draft specifications and then uses mutation and heuristic selection to repair them. For Rust, SAFE [28] generates Verus specifications from function signatures and documentation, followed by iterative self-refinement. ClassInvGen [29] targets C++ class invariants and validates candidates through execution. In the smart-contract domain, PropertyGPT [30] retrieves examples from Certora reports to guide GPT-4 in generating Solidity properties, which are then checked and refined by custom provers. VeCoGen [31] studies the related problem of generating C programs from ACSL specifications, natural-language descriptions, and tests.

## VI Threats to Validity

## Internal validity

Internal threats mainly concern LLM behavior and the implementation of our analysis rules. Since LLMs are trained on large code and specification corpora, benchmark or similar examples may have appeared during pretraining and could inflate performance. To mitigate this concern, our ablation with only LLM-based refinement, without CPG-derived information or frame-constrained projection, performs substantially worse, suggesting that the gains mainly come from the proposed frame analysis and rules. Another threat is that our CPG-based rules are derived from frame-relevant program information and expert knowledge, but may still miss uncommon C patterns such as complex pointer manipulation or unusual data dependencies. Missing rules or implementation errors may lead to incomplete frame specifications or unresolved verification goals.

## Construct validity

Our main evaluation metric is error-free frame status, which is determined using Frama-C/WP diagnostics and Frama-C’s dependency analysis. This metric provides practical information that the generated frame specifications are accepted by the verification toolchain, but it is not a complete semantic oracle for all possible client contexts. For example, a generated frame specification may verify successfully while imposing preconditions that are stronger than necessary and may exclude some valid calls. Similarly, the goal-prove rate measures verifier discharge rather than specification minimality or user intent. Therefore, our results should be interpreted as verifier-accepted frame correctness under the evaluated toolchain.

## External validity

Our experiments are conducted on 84 functions from real-world C systems and 51 academic verification examples. Although these benchmarks cover common frame-relevant patterns such as pointers, arrays, loops, and data dependencies, they may not represent all C programs. The results may not generalize to software with complex low-level features, such as unrestricted casts, concurrency, etc. In addition, our approach is designed for ACSL and Frama-C/WP; applying it to other specification languages, verification tools, or programming languages may require adapting the frame rules and verification workflow. Finally, LLM behavior can vary across model versions, prompts, and decoding settings, so future work should evaluate additional models and release prompts, generated specifications, tool versions, and verification scripts to support replication.

## VII Conclusion

We have presented AutoFraming for synthesizing ACSL frame specifications for C programs. It extracts frame-related information and projects the information into a deterministic frame skeleton, and uses the LLM only to complete and repair the surrounding contract under verifier feedback. Our experimental results show that grounding LLM-based specification synthesis in explicit program structure and frame-specific constraints leads to more complete and reusable frame specifications than existing generators. Future work will extend AutoFraming to richer heap abstractions, recursive data structures, inter-procedural library summaries, and additional specification languages and verifiers.
