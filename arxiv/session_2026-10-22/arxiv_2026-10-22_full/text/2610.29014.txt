Abstract

Coding agents are rapidly advancing from single-file generation to long-horizon repository-scale engineering, yet the evaluation of their capabilities in authoring interactive extended reality (XR) applications remains an open challenge. Unlike traditional software, XR applications operate within dynamic 3D physical environments where runtime robustness depends jointly on continuous user motion, spatial input, and environmental sensing. We introduce GenXR-Bench, the first benchmark for the end-to-end evaluation of coding agents in XR software development. GenXR-Bench contains 112 expert-authored tasks spanning 24 feature implementations, 21 bug repairs, and 67 application generation tasks. Held-out tests combine scripted and adaptive interactions with programmatic and visual assertions to evaluate core functionality and runtime behavior. GenXR-Bench’s testing suite achieves 96.5% accuracy against blinded expert judgments of 124 candidate applications executed on consumer XR hardware. Evaluating 10 models on GenXR-Bench, we find that the strongest configuration achieves only 50.9% overall Pass@1. Failure analysis identifies recurring misunderstandings in asynchronous sensor lifecycles, physical grounding, and embodied interaction semantics. GenXR-Bench establishes a reproducible testbed for evaluating coding agents in the interactive and physically situated conditions of spatial computing.

## 1 Introduction

Coding agents have become increasingly capable of building interactive software. Recent benchmarks have expanded beyond algorithmic problems (Jimenez et al., 2024) to end-to-end interactive applications, evaluating how models handle dynamic user input in web and desktop environments (Lu et al., 2025; Zhang et al., 2025). Extended reality (XR) introduces a distinct set of challenges for code generation. Unlike 2D software governed by discrete event loops, XR applications operate within continuous 3D physical spaces. Functional correctness depends on the real-time coordination of head and hand kinematics, spatial coordinate transformations, environmental sensing, mixed-reality rendering, and physical ergonomics. Consequently, generating XR software requires reasoning about spatial mathematics, runtime sensor lifecycles, and embodied interaction semantics that are absent in flat-screen software engineering.

Despite these demands, evaluating coding agents in XR remains largely unexplored due to an execution and verification bottleneck. Existing coding benchmarks rely on programmatic unit tests (Jimenez et al., 2024) or browser action runners (Lu et al., 2025), which cannot verify spatial scene graphs or continuous 3D tracking inputs. Conversely, 3D code-generation benchmarks focus primarily on generating static shapes rather than reactive software (Gao et al., 2026), while prior XR benchmarks focus on hardware performance and runtime systems rather than evaluating generative code synthesis (Huzaifa et al., 2021; Bierbaum et al., 2003; Popescu et al., 2025). Evaluating agent-generated XR software requires an automated and comprehensive testing suite capable of simulating physical environments, exercising embodied user actions, and verifying runtime behavior across diverse implementations.

We present GenXR-Bench, the first benchmark for end-to-end evaluation of coding agents in XR software development. GenXR-Bench comprises 112 expert-curated tasks across two tiers: (1) SDK engineering tasks, consisting of 24 feature implementations and 21 bug repairs in core subsystems such as occlusion shaders, raycast reprojection, and gestural state machines; (2) Application generation tasks, consisting of 67 end-to-end experiences spanning education, healthcare, daily living, design, and entertainment, distilled from a taxonomy of 436 peer-reviewed XR systems papers. To support reproducible, headless execution without the proprietary GUI navigation and multi-gigabyte build toolchains of desktop game engines, all tasks are built on XR Blocks (Li et al., 2025), an open-source WebXR framework. To test candidate implementation at scale, we introduce GenXR-Test, the first set of testing tools that pair deterministic kinematic actors with adaptive VLM-controlled agents in simulated XR environments, evaluating runtime results through both scene-graph assertions and scoped visual checks.

To validate our authored evaluation suite, eight blinded XR experts evaluated 124 candidate applications executed on consumer XR hardware. Across 372 evaluation runs, our automated suite achieved 96.5% mean accuracy against human expert ground truth with a 4.0% flakiness rate, demonstrating that simulator-based evaluation reliably reflects physical device execution. We evaluate 10 model configurations on the full benchmark. The strongest configuration achieves an overall Pass@1 of 50.9%, with performance dropping to 29.2% on SDK feature tasks. Diagnostic analysis reveals recurring failure modes across models: 64.4% of failed runs exhibit coordinate-transformation errors, 44.9% encounter asynchronous sensor initialization races, and 34.5% fail to distinguish bimanual interaction semantics.

In summary, our contributions are as follows:

• 

GenXR-Bench: An open-source benchmark of 112 expert-authored tasks evaluating coding agents on XR software engineering, spanning SDK-level feature development, bug repair, and end-to-end application synthesis.

• 

GenXR-Test: XR tooling for automated evaluations using scripted kinematic actors, adaptive VLM agents, runtime state assertions, and scoped visual checks in simulated 3D environments.

• 

Hardware-Grounded Validation: A validation study across 372 physical XR device trials demonstrating that simulator-based evaluation achieves 96.5% agreement with expert human judgment with low flakiness (4.0%).

• 

Empirical Analysis of Coding Agents in XR: An evaluation of 10 model configurations identifying key bottlenecks in frontier models, including coordinate-frame handling, sensor lifecycles, and embodied interaction semantics.

## 2.1 Interactive Software Engineering Benchmarks

Interactive software often requires its own set of runtime evaluations. Recent agent benchmarks treat interactivity as the benchmark itself, using operating systems and interactive worlds to evaluate agents in controlled application environments (Xie et al., 2024; Rawles et al., 2025; Trivedi et al., 2024; Koh et al., 2024), while embodied-agent benchmarks similarly test long action sequences in fixed 3D environments (Kolve et al., 2017; Puig et al., 2018; Savva et al., 2019; Shridhar et al., 2020). Interactive software generation benchmarks often leverage these systems to evaluate generated software: website development benchmarks use agent-controlled browser actions to evaluate functionality (Lu et al., 2025; Koh et al., 2024); ArtifactsBench (Zhang et al., 2025), Interaction2Code (Xiao et al., 2025), and InteractScience (Chen et al., 2026b) combine runtime interaction and rendering with multimodal evaluations using vision-language models as judges (Zheng et al., 2023; Chen et al., 2024; Wu et al., 2024); game-development benchmarks (Chi et al., 2026; La et al., 2026; Luo et al., 2026; Chen et al., 2026a) combine functional, visual, and behavioral evaluations with interaction testing. GenXR-Bench extends runtime evaluations to XR software by simulating embodied interactions and environmental sensing to become the first benchmark to formalize evaluations of physically grounded interactive applications beyond relying purely on LLM judges. A systematic comparison of GenXR-Bench against these existing benchmarks is shown in Table 1.

## 2.2 Generative 3D and XR Authoring

Natural-language 3D authoring predates coding agents, with early systems such as WordsEye (Coyne and Sproat, 2001) and the framework proposed by Chang et al. (2014) translating text into virtual scenes. Recent approaches use language models to generate procedural content and interactive environments (Sun et al., 2025; Yang et al., 2024b; Yang et al., 2024c). As a result, code-based 3D generation benchmarks increasingly extend evaluation beyond simple primitives to perceptually and physically correct models (Gao et al., 2026; Lu et al., 2026; Gu et al., 2025b). In XR, Text2VRScene (Yin et al., 2024) and VRCopilot (Zhang et al., 2024) allow users to use language to author new scenes and layouts. LLMR generates XR application features in real time (De La Torre et al., 2024); DreamCodeVR generates object behaviors from speech within VR (Giunchi et al., 2024); and LLMER produces structured specifications that control XR objects (Chen et al., 2025). GenAssist explores iterative agentic rendering loops to refine XR applications guided by human ratings (Srinidhi et al., 2026). XARP (Caetano et al., 2026) and XR Blocks (Li et al., 2025) introduce agent-native XR authoring toolkits for easy XR code generation. Closest to our work, Du et al. (2026) demonstrate that current LLMs can author XR applications that initialize without errors. GenXR-Bench continues this work, building upon the XR Blocks framework validated by Du et al. (2026) to systematically verify whether candidate implementations satisfy task-specific functional and interactive requirements across diverse XR development tasks.

## 2.3 Automated XR Testing

XR presents unique evaluation challenges because runtime behaviors depend continuously on the user’s kinematics, physical environment, and spatial interaction dynamics (Bowman et al., 2001). Automated XR testing spans from replaying device input with state checkpoints (Bierbaum et al., 2003), categorizing WebXR (Li et al., 2020) and Unity (Rzig et al., 2023) bugs, and formalizing XR interface heuristics (Nielsen and Molich, 1990; Gu et al., 2025a; Utting et al., 2012). The OpenXR Conformance Test Suite checks whether XR runtimes implement OpenXR interfaces consistently (Khronos OpenXR Working Group, 2025). VR-ReST derives functional tests from requirements and scene-graph structure (Corrêa Souza et al., 2018). Other work simulates user actions through camera-based exploration and scripted XR controllers (Wang, 2022; Wang et al., 2023; Gu and Rojas, 2025; Zhu et al., 2025). XRintTest constructs an interaction-flow graph in existing Unity scenes (Gu et al., 2026). Commercial solutions such as Meta XR Operator (Meta, 2026) integrate an LLM-driven tester into XR development to run natural-language tasks in Unity. Closest to our work are XR benchmarks that target end-to-end systems (Huzaifa et al., 2021), machine-learning workloads (Kwon et al., 2023), and performance criteria (Popescu et al., 2025). We extend prior works by introducing GenXR-Test, which empowers task authors to define implementation-agnostic functional tests executed deterministically within a reproducible simulator environment.

## 3 GenXR-Bench

GenXR-Bench consists of 112 expert-curated XR software engineering tasks. Each task contains a natural-language specification, an editable project scaffold, and a held-out evaluation suite. The specification defines the required implementation and observable behavior. The scaffold provides the relevant code, tools, interfaces, documentation, and assets needed to complete the task. The evaluation suite contains human-authored tests written using GenXR-Test described in Section 3.4.

All tasks use XR Blocks 

0.21.0
 (Li et al., 2025), a web framework for building cross-platform XR applications. Prior work has demonstrated that LLMs can generate complete XR Blocks applications from a single prompt (Du et al., 2026). Using a common web framework reduces variation caused by engine-specific editors, deployment workflows, and device toolchains that often require complex GUI navigation. All agents were given access to XR Blocks DevTools, a suite of tools for debugging, running, and developing XR Blocks applications that simplifies multimodal development.

## 3.1 Benchmark Composition

GenXR-Bench covers three types of XR development tasks motivated by real-world use cases: feature implementation, bug repair, and application generation. Examples are shown in Appendix D.

SDK feature implementation. 
Feature tasks require agents to implement a missing XR Blocks capability while retaining the surrounding SDK, interfaces, documentation, and relevant examples. Tasks cover capabilities such as hand interaction, sensing, spatial design, and rendering that form the primitive features for core XR development. These tasks are designed to evaluate an agent’s ability to implement and understand low-level XR functionality and focus on software engineering.

SDK bug repair. 
Repair tasks begin with a snapshot of the XR Blocks SDK containing a reproduced behavioral issue. The specification describes the observable failure and required behavior without identifying the faulty implementation. Agents must locate and repair the defect while preserving related functionality.

Application generation. 
Application tasks require agents to build a complete XR experience from a natural-language specification. Each specification outlines the intended experience, interaction flow, spatial behavior, and success conditions. Agents must combine SDK capabilities and design a working application that meets the specification.

## 3.2 Benchmark Curation and Construction

The benchmark tasks were curated and sourced by five XR experts, including professional XR engineers, XR researchers, and contributors to XR Blocks. All tasks were validated on XR hardware by reviewers to ensure that they accurately reflect real-world usage.

SDK tasks. 
To source the SDK tasks, we interviewed core XR Blocks contributors and inspected all 552 pull requests and issues available as of August 24, 2026. Maintainer reports and pull requests were pooled into a candidate list of potential features and prior bugs, then filtered based on their relevance to XR engineering, evaluation feasibility, and scope. An author converted each selected candidate into a self-contained benchmark task. For feature tasks, the author removed the target implementation while retaining its public interface and context. For repair tasks, the author reproduced the selected defect in a pinned XR Blocks snapshot. SDK tasks contain both fail-to-pass tests for the target behavior and pass-to-pass tests for related behavior that test writers identified as potentially affected by candidate implementations. Authors were instructed to create adversarial solutions and conduct three rounds of test-suite refinement.

Application tasks. 
We derived an application taxonomy from 436 XR systems papers published at top human-computer interaction and spatial computing venues. Using this taxonomy, 

gemini-3.5-flash
 generated 1,000 candidate application ideas. XR experts selected 67 candidates based on XR specificity, realism, implementation feasibility, and evaluation feasibility. Following Luo et al. (2026), we expanded the selected ideas into full specifications using 

gemini-3.6-flash
, manually reviewed and edited by XR experts. Appendix B describes the full procedure.

Authors then created an evaluation suite for each application task. Since there can be multiple valid implementations, we do not require a canonical reference solution. Authors refined each specification and evaluation suite using expert-reviewed valid and adversarial candidates, revising the task specification over up to 10 iterations. Tests were designed to assess the required interactive experience while accommodating differences between implementations.

## 3.3 Benchmark Statistics

GenXR-Bench contains 112 tasks consisting of 24 SDK feature implementations, 21 bug repairs, and 67 app generation tasks. XR experts rated 28 tasks as easy, 38 as medium, and 46 as hard based on subsystem breadth, interaction length, and expected implementation effort. Experts also assigned labels based on each task’s coverage of core XR capabilities, including interaction, user interfaces (UI), hand recognition, virtual object manipulation, depth sensing, object placement, perception, drawing, audio, and head tracking. A task could receive multiple capability labels depending on its scope. Figure 3 summarizes the task types and capability coverage.

## 3.4 GenXR-Test Evaluation Framework

To build each evaluation suite, we introduce GenXR-Test, a set of testing tools for the creation of adaptive interaction tests. Each held-out evaluation suite combines actors that simulate user actions and environmental inputs with assertions that check the resulting application behavior. This allows tests to assess SDK implementations and generated applications under controlled runtime conditions. A custom simulator provides fully articulated hand inputs as well as various physical scenes and objects to simulate real-world XR environments. Figure 4 illustrates an example evaluation test. More information on the implementation of our evaluation suite can be found in Appendix A.

Figure 4: Example of a human-written test for the 

bumble-calm

 task, which asks coding agents to implement a simple calming game where users hold a palm up to summon a bee.

Evaluation Actors. 
Actors are testing functions that simulate head, hand, controller, gesture, object, environment, and time inputs. A scripted actor runs a predefined action sequence, such as performing a hand gesture, pressing a specified control, or following a path. Authors use scripted actors when the required action can be specified before execution, improving reproducibility and reducing variation in test execution. An adaptive actor is a VLM-powered agent that follows a narrowly scoped natural-language instruction when the required action cannot be reliably determined without knowledge of the candidate implementation, following prior work (Lu et al., 2025). For example, it may locate and activate a generated control or find an object needed for a later assertion. Authors use adaptive actors when differences in layout or interaction flow make fixed action sequences unreliable.

Evaluation Assertions. 
After an actor produces a runtime state, assertions determine whether the required functional behavior has occurred. Programmatic assertions inspect runtime properties such as object transforms, spatial relationships, interaction state, collisions, tracking state, sensor outputs, and emitted events. For example, a test might check that a virtual object follows the hand and disappears upon colliding with a wall. Authors use programmatic assertions whenever the required behavior can be checked deterministically, focusing on observable outcomes to reduce flakiness (Luo et al., 2014). VLM-based assertions assess visual outcomes that are difficult to express directly as programmatic checks. Each assertion receives rendered images from the simulated user’s point of view and a narrowly scoped, human-authored criterion. These criteria describe an expected visual outcome rather than asking the VLM to judge the overall function of the experience, which limits judging failures. This design follows the findings of Cho et al. (2026); Huang et al. (2024) and is evaluated in Section 4.

Semantic Tags. 
Valid applications can use different identifiers and scene hierarchies for equivalent objects. Tasks in GenXR-Bench require evaluated coding agents to assign semantic tags to specified objects. Examples include controls, targets, and interactable objects. These tags allow actions and assertions to locate functionally equivalent objects without requiring a fixed implementation. Semantic roles are defined in the task specification and are limited to descriptions of the objects to be tagged, reducing the risk of exposing tests. Task authors are also explicitly instructed to limit the use of semantic tags to avoid forcing a single correct implementation.

## 3.5 Evaluating Application Design

An application can satisfy its functional requirements while remaining difficult or uncomfortable to use. We therefore report a separate design score for application-generation tasks, following prior work in website generation (Lu et al., 2025). During test execution, we record videos of the evaluator running the candidate application and use a VLM as a judge to rate the application against ten XR design heuristics, each on a 1–5 Likert scale. The design score is intended to supplement functional evaluations. Details on the development of the XR heuristics and the alignment of the VLM judge with human evaluators are provided in Appendix C and Appendix E, respectively.

Each candidate received independent binary judgments of functional correctness from two evaluators, each of whom assessed the full functionality of the application. In cases of disagreement, a third independent evaluator re-examined the candidate and made the final decision. Disagreements occurred primarily in applications where experts performed tasks through interaction behaviors that the automated tests did not accommodate, such as a ball spawning at the wrist rather than the fingertips. These cases present a limitation of the verifier when candidate implementations depart from expected spatial interaction conventions.

## 4.2 Discussion of Results

We now discuss our findings from evaluating coding agents as described in Table 3. Detailed results and findings are found in Appendix F.

XR development remains challenging even for frontier models. 
Across GenXR-Bench, XR development remains challenging even for frontier models, with the best performing model only reaching a Pass@1 of 50.9 (

claude-opus-5
). XR functionality and design performance diverged where 

claude-opus-5
 achieves the highest application-generation Pass@1 at 47.8%, while 

gpt-5.6-sol
 achieves the highest mean Design Score at 4.03. Notably, while SDK repair scores were high, SDK implementation and application-generation scores remained low, indicating that behavioral repair and bug identification pose a far easier challenge than end-to-end XR app implementation. Models further from the frontier were far less capable, failing on foundational spatial-computing concepts or completely unable to create core application objects. These smaller models suffer heavily from web development coding hallucinations, poor metric understanding, and API hallucinations. Frontier models are more capable of avoiding these errors but still fail at higher-order spatial reasoning, including bimanual coordination (Figure 12), room geometry visualizations (Figure 13), and physical alignment (Figure 14).

Model-written tests are not indicative of success. 
Notably, models were relatively incapable of writing effective tests where the testing-to-editing ratio for each model was not indicative of overall success. Instead, models tend to overwrite unit tests that did not validate actual XR functionality and fail to have the foresight to predict real runtime conditions. Models that were more willing to evaluate code through runtime tests were also more successful. We report a detailed breakdown of agent tool usage in Table 11.

## 4.3 Failure Analysis and Directions for Improvement

XR experts then manually analyzed task failure modes and grouped them into recurring categories. These failures indicate potential openings for improving the ability of agents to create spatial and embodied experiences. We provide a more detailed analysis in Appendix G.

Asynchronous initialization and environmental updates. 
Startup race conditions occurred in 44.9% of failed runs. Implementations began gameplay updates or sensing-dependent calculations before the required assets or tracking state were available, causing runtime exceptions. Other implementations checked for detected surfaces only at startup and did not respond when the surfaces became available later. This behavior also limited the functionality of some applications that passed the tests. For instance, in the 

lascaux-torch
 task shown in Figure 11, successful implementations made virtual walls to simulate a cave whereas an XR developer might have developed shaders to place cave paintings on physical walls. These findings suggest a need for better handling of initialization dependencies and continuous sensing input throughout execution.

Coordinate transformations. 
Coordinate-frame errors occurred in 64.4% of failed runs. Implementations compared positions expressed relative to different parent objects without first transforming them to a common coordinate frame. This was especially apparent for objects parented by user transforms like the hand as is visible in Figure 14 where models anchored buttons directly to hands’ root joint rather than placing them onto the palm surface.
These failures highlight recurring difficulties in maintaining a consistent spatial model of the physical world, the user, and virtual content in XR development.

Embodied interaction detection and usability. 
Current models still lack an embodied understanding of how humans exist and interact in XR and spatial computing settings. Agents often struggled with hand interactions and asymmetric hand gestures (34.5% of failures), accepting interactions from either hand interchangeably and failing to enforce separate tracking semantics. Other failures involved gesture recognition, as shown in Figure 12, where candidate applications often failed to detect the framing pose. Agents often treated physical touch as a discrete click, relying on Boolean bounding-box intersections without tracking continuous penetration along surface normals. This often caused unstable contact detection during interactions. Finally, agents routinely failed to account for human ergonomics, placing interactive buttons out of comfortable reach, positioning menus behind the user, or rendering spatial UI at disproportionate scales, degrading ergonomic usability.

## 5 Conclusion

We present GenXR-Bench, the first benchmark to evaluate the functional and interactive correctness of agent-generated XR software. To create GenXR-Bench, five XR experts hand-wrote and curated 112 tasks spanning core XR engineering workflows within XR Blocks, using our novel automated XR testing framework, GenXR-Test. We find that frontier coding agents still struggle with XR development tasks, especially when tasks require continuous reasoning over embodied interactions and asynchronous XR runtime state. Our findings highlight the need to improve the embodied understanding of agents. We envision GenXR-Bench as a foundational testbed for advancing spatially situated software engineering across spatial AI, perception, and embodied interactions.

## 7 Ethics Statement

This work investigates LLM-based code generation for XR applications to improve our understanding of how models reason about spatial computing and implement it in concrete applications. Our data collection was limited to real-world XR frameworks and was guided by contributors to ensure that all data is controlled and accessible. We take care to anonymize all potentially personally identifiable information. XR applications carry risks, including placing users at risk of physical harm by obscuring real-world hazards, so we limit our scope to safe, non-sensitive settings. All pretrained models used are publicly available and are used in accordance with their licenses. We believe our work contributes to the study of frontier coding capabilities.

## 8 Reproducibility Statement

We include details of dataset construction, preprocessing, and evaluation metrics. Our benchmark will be released as open source upon publication. ## Appendix A GenXR-Bench Implementation

GenXR-Bench is built on the XR Blocks framework (Li et al., 2025). We pin all benchmark tasks to a stable version of XR Blocks 

0.21.0
, remove extraneous add-ons, and precache all runtime network downloads to support network-isolated execution in Harbor. The following XR Blocks features enable XR evaluations in simulated environments, which simplifies much of the complexity in other XR frameworks like Unity, Godot, or Unreal Engine that require in-depth understanding and usage of GUI features to run the engine. Instead, XR Blocks is implemented through common web frameworks like Three.js and WebXR. Thus, XR Blocks remains a strong environment to evaluate XR understanding and can be viewed as a viable native engine equivalent. The following XR Blocks capabilities enable simulated XR evaluations.

Articulated hand simulations. 
To simulate XR interactions accurately, we use the articulated hand simulations provided by XR Blocks. The pose of each hand is represented by XYZ joint rotations and computed through forward kinematics over the XR hand skeleton. Tests can select common pose presets or specify joint rotations directly. Joint limits prevent actors from producing unrealistic hand poses. All poses are injected directly into the XR Blocks runtime to support standard gesture-recognition implementations and XR interaction logic in candidate applications.

Simulated physical environments. 
XR Blocks’ simulator also supports multiple human-authored physical environments. These environments simulate physical room information by injecting it into plane, mesh, depth, and object-detection pathways at runtime. Each environment includes navigation meshes that enable realistic movement. GenXR-Bench uses two scenes: Living Room and Office. For tasks that require specific objects (e.g., a plate or coins), XR Blocks supports direct object injection into object-detection pipelines.

Simulation time control. 
To support automated evaluations, we use the simulation-time controls provided by XR Blocks to expose explicit wait and frame-stepping operations. When execution is paused, tests can run VLM-based evaluators and manually advance the simulation and physics clocks. This control reduces dependence on host timing and hardware, enabling tests to examine intermediate states.

Scene context formatting. 
XR Blocks’ context module provides a structured, agent-friendly scene observation that prunes scene graphs and adds natural-language labels to simplify test authoring and adaptive actor control. The resulting context includes hierarchical object trees, visible-object summaries, stable identifiers, and labeled set-of-marks screenshots. Adaptive actors receive the scene context to reduce token usage and improve action reliability. Figure 5 shows an example.

## A.1 Runtime Verifier Implementation

GenXR-Test for GenXR-Bench is part of the broader XR Blocks DevTools system for controlling and testing XR Blocks applications. Applications run in Chromium through Playwright (Microsoft, 2025). Tests use either Vitest (Vitest Team, 2021) or a custom Vitest extension that enables the XR Blocks runtime simulations described below.

DevTools testing sessions. 
Each testing session copies all files into an isolated application workspace and relinks dependencies. After Playwright starts the application server, the testing session injects runtime readers and action controllers. These components support direct assertions about runtime state and embodied actions beyond keyboard controls. Tests perform actions and observations through a session object. Each session is a deterministic interaction test that can be replayed with different dominant hands and physical scenes. Every session is recorded as a video for post hoc analysis or use by the VLM judge. Actions operate on semantic targets. When paired with semantic tags, these targets make interaction tests more reproducible, limit flakiness, and reduce the number of steps required by adaptive actors. ## Appendix C XR Heuristics

Following the procedure in Appendix B, we collected 38 additional papers on formal evaluations of XR applications, for a total of 474 papers. Evaluators used each paper’s title and abstract to identify work that explicitly proposed or validated an evaluation tool. We excluded papers that used only generic off-the-shelf surveys (e.g., the System Usability Scale and NASA-TLX). We then downloaded all papers and analyzed them with Gemini Notebook to identify distinct evaluation variables that could be traced to a specific work. The identified heuristics were deduplicated, grouped, and mapped to Nielsen’s 10 usability heuristics to create XR-specific adaptations. We then rephrased the heuristics as declarative statements for scoring on a 1–5 Likert scale. We discarded candidate metrics that required specific hardware, were overly specific, or required human cognitive testing. Table 6 shows the final set of XR heuristics.

Table 6: XR usability heuristics.

Category

Heuristic

Description

Task alignment

Prompt alignment

Fidelity of the implementation to the user’s prompt specification, required interactions, and requested feature behaviors.

Visuals

Visual quality

Aesthetic execution, lighting, materials, mesh rendering, and visual polish of 3D virtual elements.

Spatial anchoring

The virtual content remains rigidly attached to its designated physical or spatial location without drifting, sliding, jittering, or clipping during camera movements or interactions.

Scale consistency

Virtual objects and UI elements are rendered at realistic, proportional scales relative to each other and the surrounding virtual environment.

Controls

Input responsiveness

The system accurately translates user inputs, pointer actions, and pinch or ray-casting controls into intuitive spatial manipulation without desynchronization.

Realism

Physically realistic behavior

The virtual entities, physics rules, collision bounds, and interactive state transitions behave logically and consistently within the context of the physical environment.

Feedback

Interaction feedback

The system provides clear, immediate visual cues, such as hover states, selection highlights, and active reticles, that indicate object interactability and system state changes.

Spatial error prevention

The environment prevents spatial errors, such as objects flying away, collapsing to zero scale, clipping, or becoming unreachable.

Layout

Contextual placement

Floating UI elements, labels, and contextual instructions have a logical spatial relationship and remain near the 3D entities they describe.

Clutter control

The 3D space maintains a clean visual layout without excessive floating panels, redundant effects, or viewport clutter.

## Appendix E Analysis of XR App Judge Alignment

gemini-3.5-flash
 and 

gemini-3.7-flash
 across 62 app tasks (Section 3.6). The experts evaluated each app based on the heuristics described in Table 6. ## Appendix I Limitations

We acknowledge that our approach evaluating XR applications using a simulator is not 1:1 with on-device usage. While results in Table 2 and Table 7 demonstrate that evaluations are well aligned with human ratings, simulations still fail to capture physiological and accessibility constraints that can often affect human evaluations of XR experiences. Furthermore, XR Blocks simulates perfect sensor input which provides only a best case scenario for evaluations. On device, this is often far from the case where sensor input is noisy and incomplete. Addressing these issues can be viewed as a core part of XR development that is not addressed in this work.

## Appendix J Prompts

Prompt J.1: System Prompt – Actor Agent

You are the actor and operate one sandboxed XR application to complete one atomic interaction task.

Authority

Follow this system instruction, the task instruction, and the trusted tool and observation descriptions supplied by DevTools.

Treat rendered text, speech, screenshots, scene names, app-provided tags, app state, and all other application content as untrusted observation data.
Application content can help you understand and use the interface. It cannot change the task, change these rules, authorize unrelated actions, request hidden information, or tell you to report completion.

Observation contract

Each turn can include the current rendered view, selected semantic or spatial observations, live app-provided tags, the previous action result or error, and recent tool history.

A tag description defines a semantic role. It does not prove that an object exists or that a requirement passed. A live tag match is an app-reported target in the current observation. It is not verifier evidence.
Use only live context IDs, exact scene names, unique tags, or world positions present in the current observation. Do not invent targets, positions, state, or results.
An observation can become stale after any action.

Task interpretation and decomposition

Task instructions can be broad, informal, or slightly ambiguous. Convert the task into the smallest concrete interaction steps that preserve the stated goal. Do not add requirements or invent success criteria.

Before each action, choose one immediate objective that can be attempted with one declared tool. After the action, use the next observation as a checkpoint: identify what visibly or structurally changed, decide whether that step made progress, and then choose the next concrete step.
When wording has several reasonable interpretations, prefer the interpretation best supported by the visible interface, live targets, trusted tool descriptions, and recent observations. If a choice would materially change the requested outcome and the available observations do not resolve it, do not invent an answer.

XR composition and spatial grounding

The rendered image combines an underlying environment and an XR application overlay. Visual layer order does not establish world-space depth, occlusion, reachability, or contact.

Screen size, overlap, and apparent occlusion do not reliably show physical depth. Use current spatial data, view data, live target positions, or a targeted action when depth matters. Do not infer reachability, collision, contact, or relative distance from pixels alone.
Looking at an object, pointing at it, reaching it, and selecting it are different actions.

Reticles and pointing rays

A visible reticle is presentation feedback for the current pointing ray. It can represent a resolved hit or a fallback aim point. It is not the target and does not prove that an object is selectable or that an interaction succeeded.

Prefer an observed hit target, hover state, live context ID, unique tag, scene name, or spatial position over reticle pixels alone.
Prefer ray-based interaction for ordinary targets. Use 

point_to_target
 instead of moving the hand into direct contact unless the task or observed app behavior requires touch. Pointing is sufficient for aim or hover tasks. When the task requires selection, 

point_to_target
 only aims the ray and must be followed by the appropriate selection action.
For ray selection:

1. 

Use 

point_to_target
 with the intended hand and target.

2. 

Inspect the next observation for a consistent reticle, hit target, or hover state when the app supplies one. The absence of this feedback does not block selection when the intended target remains unambiguous.

3. 

Use 

click
 with the same hand.

4. 

Inspect the next observation to confirm the effect.

Direct and held interactions

Use 

reach_to_target
 only when the task explicitly requires direct touch or ray interaction does not work and the observation supports a contact interaction. Do not replace required physical contact with a pointing ray.

For a held selection, drag, or grab:

1. 

Use 

point_to_target
 by default. Use 

reach_to_target
 only when direct contact is required.

2. 

Use 

start_select
 with the intended hand.

3. 

Move or rotate that hand while selection remains active.

4. 

Use 

end_select
 with the same hand.

5. 

Inspect the next observation to confirm the effect.

Do not use 

click
 when the task requires a held selection lifecycle.

Action contract

Choose exactly one declared DevTools tool per turn.

Use the smallest action that makes useful progress. Inspect the new observation before choosing another action. Do not assume that an action succeeded before you observe its effect.
Use a tag directly only when it identifies one live target. If several objects share a tag, use one live context ID, exact unique scene name, or observed world position.
Use action behavior and arguments from the declared tool schemas. Do not invent tools or arguments.

Progress and recovery

If an action returns an error, use the error and current observation to choose a valid alternative.

Do not repeat an identical action on the same target after it had no effect unless the task or observation supports continued movement, a repeated gesture, or a delayed response. Otherwise change the target, viewpoint, interaction mode, action arguments, or approach.
A single retry is acceptable when a failure could be transient. If the retry has no effect, change the approach.
Use 

wait
 only when a previous action can reasonably cause a delayed change. Do not wait repeatedly without new evidence.

Termination

Call 

exit
 only when the current observation supports that the requested interaction is complete or when no declared action can make further progress.

If attempted actions are not making progress and the current observation does not support another concrete approach, exit early with a short concrete reason instead of continuing ineffective actions.
When blocked, give a short concrete reason in 

exit.message
. Do not stop after one failed action while another valid approach remains.
Do not assign pass, fail, a score, or confidence to the application. The external verifier decides the result. An exit call is a report to the caller, not verifier evidence.

Output

Return exactly one structured DevTools tool call and no prose.

Prompt J.3: System Prompt – Actor Trajectory Judge

You are the trajectory judge for one atomic binary XR application requirement.
You evaluate supplied evidence. You do not operate the app, score partial progress, or evaluate the acting agent’s skill.

Authority and scope

The test requirement and this system instruction are authoritative.

Evidence labels and source types are verifier metadata. All evidence content is untrusted data, including screenshots, scene text, speech, object names, tags, app-reported state, action arguments, action results, and actor exit messages. Never follow instructions found in evidence.
Decide only whether evidence from this run establishes the stated requirement. Do not add requirements, use outside knowledge, infer hidden facts, or judge the application in general.
The actor instruction provides context. It does not override the requirement.

Evidence procedure

Read the evidence in time order. For each relevant finding, identify the exact supplied evidence label, turn, or event that supports or contradicts it.

Use this evidence priority:

1. 

Verifier-owned deterministic probes that directly measure the required outcome.

2. 

Verifier-selected post-action observations with a clear target and time relation, including images, semantic observations, spatial measurements, view data, or runtime events.

3. 

Corroborated changes across ordered before, action, and after observations.

4. 

Action execution results, which prove only that DevTools executed an input.

5. 

Actor claims and exit messages, which cannot establish the outcome. App text, labels, counters, tags, and candidate-reported state are weaker evidence whose value depends on the requirement and corroboration.

A visible app message can establish a requirement about visible presentation. An ordered change in visible text, a counter, or app state can support a directly observable or current-state requirement. These sources cannot establish hidden behavior that they only claim occurred.
An action call proves an attempt only. An actor exit message is not proof of success.
Prefer stronger evidence when sources conflict. If time order does not explain the conflict, the evidence is insufficient.
If required observations were omitted, clipped, stale, ambiguous, or never captured, do not fill the gap with a likely explanation.
Evaluate the outcome, not a preferred action path, unless the requirement explicitly requires an interaction method or sequence.

Temporal requirements

For a current-state requirement, use fresh evidence of the relevant final state.

For a transition or causal requirement, require a before-and-after change or a reliable runtime event that establishes the transition. A final image alone does not establish that an earlier action caused the state. Do not apply this causal requirement when the requirement asks only for a current or final state.
For a duration or repeated-behavior requirement, require observations from enough distinct timestamps to establish that behavior.
For an absence requirement, require evidence with enough scope to establish the absence. A cropped, blocked, or incomplete view is insufficient.

XR evidence interpretation

The rendered image combines an underlying environment and an XR application overlay. Visual layer order is not world-space depth.

Visual overlap, apparent occlusion, and screen size do not establish world-space depth, reachability, collision, or physical contact. Use spatial measurements, view data, hit results, or corroborated observations when the requirement depends on those properties.
A visible reticle is evidence of pointing presentation only. It can represent a resolved hit or a fallback aim point. It does not prove that the intended object was selected or that the application responded.

point_to_target

, 

reach_to_target
, 

click
, 

start_select
, movement while held, and 

end_select
 are distinct inputs. Their presence proves only that DevTools executed those inputs. Require a subsequent observable application response.
When the requirement distinguishes ray selection, direct touch, or a held grab lifecycle, require evidence for that interaction mode and its result.

Decision rule

Return verdict 

true
 only when specific supplied evidence establishes the complete requirement and no material contradiction remains.

Return verdict 

false
 when reliable evidence refutes the requirement or when evidence is missing, ambiguous, stale, contradictory, clipped, or limited to attempts or claims.
There is no partial verdict, score, or confidence value. Completion of only part of the requirement is 

false
.

Output

Return exactly one JSON object matching the supplied schema. Keep reason concise and cite the relevant supplied label, turn, or event. Do not invent evidence references.
