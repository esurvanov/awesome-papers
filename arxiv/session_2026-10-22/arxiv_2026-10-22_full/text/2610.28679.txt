Abstract

Agents need reliable ways to validate their outputs, both when completing tasks and when filtering synthetic training data.
We study verifier generation: from the instruction and environment available for solving a task, an agent writes an executable verifier that must accept every valid solution and reject invalid ones.
We introduce VerifierBench, a benchmark of 222 tasks from six agent benchmarks spanning tool-call, state-based, and code verification, with 4,993 hidden test cases that include alternative valid solutions and attacks; Verifier4Verifier (V4V), a six-check audit, screens its source verifiers and test suites.
Across 19 models in a common agent harness, normalized balanced accuracy ranges from 10.6 to 62.1, with generated verifiers consistently rejecting invalid solutions more reliably than they accept valid ones.
This apparent strength can mask overly restrictive verification: most false rejections in the analyzed records come from verifiers that accept no tested solution to a task.
Case studies reveal unsupported assumptions about solution formats, tool use, and code changes that exclude valid solutions.
These errors survive self-testing because agents test solutions that share the verifier’s mistaken assumptions, or submit verifiers without confirming that any correct solution passes.
These findings suggest testing both whether a verifier accepts a correct solution and whether it accepts other solutions permitted by the task.

## 1 Introduction

In data-oriented recursive self-improvement (RSI) (Yin et al., 2025; Min et al., 2026), agents construct training data for their own subsequent learning and can jointly generate tasks and verification functions that provide reinforcement learning rewards (Zhou et al., 2026).
These verifiers judge candidate solutions, determining which receive rewards or enter the training data.
An incorrect verifier can therefore repeatedly reward a violation or discard a valid solution, making the reliability of agent-generated verifiers critical to this learning process.

To examine this reliability, we study verifier generation (Zhang et al., 2025; Dinella et al., 2022): given the instruction and environment a solver would receive, an agent writes an executable verifier that returns PASS or FAIL for any candidate solution.
Unlike a solver, which needs one valid solution, a verifier must accept all valid solutions while rejecting invalid ones.
It must therefore distinguish task requirements from choices that can vary across valid solutions.
Figure 2 shows a verifier rejecting a permitted read-only query because the agent omits its tool from an allowlist.
The self-tests omit the same query and never establish that a complete valid solution passes.

A verifier that accepts one expected solution may still reject other valid ways to complete a task, while one that catches ordinary mistakes may still accept solutions that exploit gaps in its checks.
Evaluating verifier generation therefore requires testing both acceptance of valid alternatives and rejection of invalid solutions, including deliberate attacks.
Prior work evaluates generated test assertions (Dinella et al., 2022), unit tests (Jain et al., 2025), issue-reproducing tests (Mündler et al., 2024), and executable specifications (Endres et al., 2024; Chen et al., 2026).
We extend this line of evaluation to agent task completion, where correctness can depend on tool interactions, resulting environment states, and code changes.
To this end, we build VerifierBench: 222 tasks from six open-source agent benchmarks with 4,993 hidden test cases, comprising reference solutions, valid alternatives, ordinary errors, and attacks on verification.
This design tests whether generated verifiers distinguish task success from failure across different ways of carrying out the same task.
Reliable measurement also requires trustworthy evaluation labels.
Because both the benchmarks’ source verifiers and our constructed test cases can contain errors, we audit them with Verifier4Verifier (V4V), six checks that include replay, repeatability, and mutation testing.
Source verifiers that pass this audit serve as the reference verifiers.

Evaluating 19 models in a common harness and 17 further model–harness configurations, we report three findings.
First, generated verifiers accept valid solutions less reliably than they reject invalid ones: as reported in Section 3.2, true positive rates range from 21.1% to 70.2%, whereas true negative rates range from 79.2% to 96.3%.
Second, as analyzed in Section 3.4, these false rejections concentrate in all-reject verifiers, which return FAIL on every test case of their task and produce 87.9–96.0% of false rejections in the analyzed records.
Third, in selected cases examined in Section 4, these verifiers impose checks that the task does not require, and the agents’ self-tests either exercise only solutions those checks allow or never confirm that any valid solution passes.
We thus contribute a benchmark and screening procedure for verifier generation in Section 2, together with an analysis in Section 5 that motivates testing generated verifiers on permitted variations, not only on a chosen solution.

## 2 VerifierBench

## 2.1 Task Formulation

For task $t$ , an agent receives the instruction and environment used for ordinary task solving, together with the verifier’s input and output conventions summarized in Appendix A.
A harness, the agent framework that manages model calls, tool use, and the generation loop, runs the agent until it delivers an executable verifier $\widehat{V}_{t}$ ; the reference verifier and hidden test cases are withheld.
During generation, the agent may run self-tests: it writes candidate solutions of its own and checks that its draft verifier returns PASS for intended positives and FAIL for intended negatives.
Because the hidden test cases are withheld, self-tests are the agent’s only evidence about how its verifier behaves.

After generation, we fix $\widehat{V}_{t}$ and run it on every test case in the task’s suite $\mathcal{C}_{t}$ .
Each test case holds one candidate solution and carries a reference label defined in Section 2.3, PASS for a positive case and FAIL for a negative one, which the verifier never sees.

A tool-call verifier receives raw call text together with parsed function names and arguments; a state verifier receives the candidate’s interaction record or, for AppWorld, its solution code; and a code verifier receives the candidate patch and a repository checkout.
For state and code tasks, both the generating agent and the delivered verifier can execute code in the task environment through a public interface, run_public, for example to replay a candidate’s actions or run a repository’s tests.
Executions during generation are budgeted separately from those during evaluation, as documented in Appendix E.

## 2.2 Task Sources and Test Cases

We draw tasks from open-source agent benchmarks with executable evaluation procedures, each supplying an instruction, an environment, and a source verifier.
As summarized in the top of Table 1, tool-call tasks check called functions and arguments, state tasks check interactions or the resulting environment state, and code tasks check proposed software changes.
Each test case receives a construction label, PASS or FAIL, assigned from the task requirements and the change made to the solution before any verifier is run.
As listed in the bottom of Table 1, test cases form four groups: the designated reference solution (gold); valid variants, which change presentation, implementation, or execution path while still satisfying every requirement; ordinary errors, namely initial outcomes, partial solutions, near misses, and regressions; and attacks, which exploit checking omissions, fabricate success signals, or interfere with verification.
Valid variants test whether a verifier accepts more than one expression of a correct solution.
Appendix C details the nine construction categories behind these groups.

## 2.3 Screening with Verifier4Verifier

These test cases are useful only if their labels are reliable.
Construction labels and source verifiers can both be wrong: a constructed case may not change the solution as intended, and a source verifier may contain bugs.
V4V applies six checks to the constructed test cases and source verifiers:

1. 

Replay. Run the source verifier on every test case and compare its decision with the construction label.

2. 

Repeatability. Rerun it on the same case from the same reset state; the decision must not change.

3. 

Provenance. Link every recorded decision to the test-case contents and verifier version that produced it.

4. 

Input-label consistency. Within a task, cases that give the verifier identical information must not carry opposite labels.

5. 

Trivial baselines. Verifiers that always accept, always reject, or accept only the reference solution must be exposed by negative cases, positive cases, and valid variants, respectively.

6. 

Mutation testing. Modify one check in the source verifier (DeMillo et al., 1978); some test case must then receive different valid decisions from the two versions.

We resolve any disagreement between a construction label and a source-verifier decision against the task requirements; agreement alone does not show that either is semantically correct.

As detailed in Appendix B.1, confirmed source defects exclude 45 of the 267 initial tasks.
All 37 Terminal-Bench tasks are removed, 35 of them because its test-output parser counts skipped tests as passes; the others are five BFCL tasks whose answer keys conflict with default-argument rules and three SWE-bench tasks with parsing and empty-report errors.
Defects in our own evaluation pipeline are corrected without excluding tasks.
All 222 retained tasks pass the six checks, as reported in Appendix B.2, and their source verifiers become the reference verifiers $V_{t}^{\star}$ .
Because replay agrees on every test case, each construction label equals the reference verifier’s decision; we call this value the reference label and score generated verifiers against it.

## 2.4 Metrics

A verifier invocation yields a valid PASS, a valid FAIL, or no valid decision (a missing verifier, timeout, crash, or malformed output).
A verifier that catches its own internal error and returns FAIL still yields a valid decision, although it may not have completed its intended check.
For each task, we compute the fraction of positive cases receiving PASS and the fraction of negative cases receiving FAIL; the true positive rate (TPR) and true negative rate (TNR) average these fractions across tasks, in percent.
Our primary metric is normalized task-averaged balanced accuracy (Brodersen et al., 2010), which rescales $\mathrm{BA}=(\mathrm{TPR}+\mathrm{TNR})/2$ as

 $\mathrm{BA}_{\rm norm}=2\,\mathrm{BA}-100=\mathrm{TPR}+\mathrm{TNR}-100.$ 

(1)

It weights tasks equally and the two classes equally within each task.
Constant valid decisions score 0 and perfect agreement scores 100; missing or invalid decisions stay in the denominators without credit.
We also report the attack false-positive rate FPRh, the task-averaged fraction of attack cases that receive PASS. More results are in Appendices D and G).

## 3 Experiments

## 3.1 Experimental Setup

## Models and harnesses.

Our main comparison runs all 19 models in one common harness, Pi (Zechner, 2025).
To measure how much the harness matters, we add 17 alternative configurations.
They pair models with each family’s native harness, the vendor’s own agent tool (Claude Code (Anthropic, 2025), Codex (OpenAI, 2025), or Gemini CLI (Google, 2025)), with the third-party harnesses OpenClaw (OpenClaw Foundation, 2026) and mini-swe (Yang et al., 2024), and across families, as with GPT-6-astra in Claude Code.
Because harnesses differ in prompts, tools, and reasoning settings, cross-harness comparisons describe configurations rather than model capability alone.
Generation is limited to 5,400 seconds per task and 32,768 output tokens per reply, and every configuration is scored on all 222 tasks, as documented in Appendix E.

## Evidence sources.

Our results draw on three sets of records.
The main release holds the final judgments of all 36 configurations, and every reported score comes from it.
The archived records are an earlier export with per-task judgments for nine Pi-harness models, whose aggregate counts match the main release, plus earlier verifier versions used in some appendix cases; the concentration analysis in Section 3.4 uses them.
The Astra trace batch is a separate generation of GPT-6-astra verifiers under four conditions, Pi or Claude Code at LOW or HIGH reasoning effort, that retains generation traces.
It supports the effort comparison in Section 3.3 and the trace analysis in Section 4, and its scores never replace those of the main release.

Accepting valid solutions is the shared weakness, as shown in Figure 3.
Every model has lower TPR than TNR: TPR ranges from 21.1% to 70.2%, whereas TNR ranges from 79.2% to 96.3%.
As Appendix Table 21 reports, explicit FAIL, rather than a missing decision, accounts for 57.1%–100% of each model’s unaccepted positive cases, so the gap mainly reflects active rejection of valid solutions.
As detailed in Appendix F, the gap is widest on state and code tasks, where TPR averaged over models is 27.7% and 40.2%, compared with 79.2% on tool-call tasks.

Low attack acceptance does not by itself indicate a reliable verifier.
As Appendix F further shows, on state tasks GPT-5.6-sol has an FPRh of 0.0% but accepts only 23.0% of positive cases, and on code tasks 17 models have an FPRh of 0.0% at the reported precision while their BAnorm ranges from $-25.9$ to 76.9.

## 3.3 Effects of Harness and Reasoning Effort

## Native harnesses.

As Table 3 shows, native harnesses change scores in both directions.
Claude Code raises Claude Opus 4.8 by 12.2 points to 66.2, the best of all 36 configurations, and Gemini CLI raises Gemini 3.5 Flash by 15.0 points, both through higher TPR and higher TNR.
In contrast, Gemini CLI lowers Gemini 2.5 Pro by 9.2 points, and Codex lowers all four GPT models by 4.1–26.6 points.
The harnesses also run with different reasoning settings, as noted in Appendix E: retained Opus/Claude Code traces record high effort with thinking enabled, whereas historical Pi traces that expose a thinking setting record it as off.

Paired code and trace inspection reveals concrete failures behind these differences.
Some GPT-5.5/Codex verifiers require particular patch contents or repair locations and reject valid fixes before any functional check.
On a booking-cancellation task, the GPT-5.6-sol/Codex verifier additionally requires the raw call text to parse as JSON, and its self-test supplies only the parsed calls, so it never exercises this check.
As Appendix Figure 9 illustrates, the verifier accepts none of the 7 positive cases, whereas the Pi verifier accepts all 7; both reject all 20 negative cases.
Conversely, on retail/49 the Claude Opus 4.8/Claude Code agent executes the target exchange to obtain the expected environment state, and its verifier accepts all 9 positive cases.
As Appendix Figure 10 shows, the Pi verifier instead relies on replaying an expected exchange that was never successfully executed during generation and accepts none; both reject all 8 negative cases.
Selected Gemini 3.5 Flash/Gemini CLI verifiers likewise avoid implementation errors that prevent valid decisions.

## Other alternative harnesses.

As Appendix Tables 11 and 12 show, no harness improves every model it runs.
Codex lowers all five models it runs, including Qwen3.7 Plus ( $-14.1$ points).
OpenClaw and mini-swe lower GPT-6-astra and GPT-5.6-sol by 7.2–17.8 points but change Qwen3.7 Plus by at most 0.3 points, and Claude Code raises Qwen3.7 Plus by 8.7 points but lowers GPT-5.6-sol by 6.5.
The changes also arise in different ways.
For Qwen3.7 Plus, Codex raises TNR from 82.6% to 92.1% but lowers TPR from 57.6% to 34.0%, whereas Claude Code raises both rates for Claude Opus 4.8, so harness effects cannot be reduced to a fixed trade-off between acceptance and rejection.

## Reasoning effort.

As Appendix Table 15 reports, reasoning effort, by contrast, barely changes aggregate scores in the Astra trace batch.
With Pi, HIGH instead of LOW effort raises TPR by 2.8 points but lowers TNR by 2.3 and raises FPRh by 2.2, for a net BAnorm change of $+0.5$ ; with Claude Code, all three move by less than one point, and BAnorm changes by $-1.3$ .
These small totals hide opposite changes by task type, broken down in Appendix Table 15: HIGH effort improves code tasks with both harnesses ( $+3.8$ and $+1.4$ points) but worsens state tasks ( $-5.4$ and $-3.6$ ), while tool-call tasks change by $+3.9$ with Pi and $-0.6$ with Claude Code.
Higher acceptance does not imply better discrimination: on Pi tool-call tasks, HIGH effort accepts 63 more positive cases without newly rejecting any, but it also introduces 128 false acceptances while correcting three.

## Execution budget.

The clearest effect of effort is on the generation budget of 20 run_public executions per task.
As Appendix Table 15 reports, among the 127 state and code tasks, runs that exhaust this budget rise from 4 to 77 with Pi and from 21 to 98 with Claude Code.
On the 32 $\tau^{2}$ -bench tasks, runs that exhaust it before first writing the verifier rise from 0 to 30 with Pi and from 7 to 20 with Claude Code.

## 3.4 Where False Rejections Concentrate

These rates do not show whether false rejections are spread across tasks or repeated within the same task.
We call a verifier all-reject if it returns a valid FAIL on every test case of its task, positive and negative alike.
On that task its TPR is 0 and its TNR is 100, so it contributes zero to BAnorm, like a constant decision.

All-reject verifiers produce most false rejections.
As Appendix Figure 5 shows, in the archived records they contribute 87.9–96.0% of each model’s positive FAIL decisions, whether test cases or tasks are weighted equally.
The Astra trace batch reproduces the pattern, as reported in Appendix Table 5: in each condition, 68–75 of the 222 verifiers are all-reject and contribute 93.3–95.5% of false rejections.

The concentration of false rejections identifies where failures occur, but not why.
BAnorm penalizes these failures but does not identify the checks responsible for them.
We therefore inspect selected verifiers and their generation traces in Section 4.

## 4 Why Generated Verifiers Reject Valid Solutions

Section 3.4 showed that false rejections concentrate in all-reject verifiers.
We now ask which check rejects the valid solutions, in Section 4.1, and why the agent’s self-tests did not expose it, in Sections 4.2 and 4.3.
We read generated code and generation traces from the Astra trace batch.
For each rejected positive case, we compare the rejected property of the solution with the public task requirements and with the generated check, and attribute the rejection to that check only when the requirements permit the property.
Because the verifiers are selected to explain observed failures, the analysis identifies mechanisms rather than their prevalence.

## Tool calls.

In $\tau^{2}$ -bench banking task 044, shown in Figure 2, the Claude Code/LOW verifier uses a tool allowlist to exclude unrelated mutations but omits get_user_dispute_history_7291, a permitted read-only query included in the public tool list.
It treats this legal query as an unsupported mutation and rejects all nine positive cases before environment execution.
The Pi/LOW verifier for task 045 omits the same tool and also rejects all nine positives.
Three other Pi/LOW verifiers (tasks 037, 040, and 041) reject authorized user-side calls or lack a branch for them, rejecting another 27 positives without environment execution.

## Source files.

Both Claude Code verifiers for Matplotlib-14623 exclude legal changes under lib/mpl_toolkits/, including the 3D axes implementation, and each rejects all four positive cases.

## Category vocabulary.

In retail/34, the Claude Code/HIGH verifier identifies the task’s three office items with a keyword list that omits Headphones, counts only two office items, and rejects all nine positive cases, as Appendix Figure 8 illustrates; two other HIGH-effort verifiers, for retail/33 and retail/34, share the omission.

## Representations.

As detailed in Appendix I.2, the remaining verifiers accept only some permitted representations of a value: an ISO-only currency format, numeric-only device identifiers, or incomplete decoding of TeX spacing.

## 4.2 Self-Tests That Confirm Without Challenging

If these checks are visible in the generated code, why did self-testing not catch them?
Table 4 splits the 16 verifiers by self-test outcome.
For the eight in the upper block, the self-tests used only solutions that the unjustified check already allows.
In Django-11734, the positive self-test patches query.py; the agent repairs subprocess compatibility, patch formatting, and environment resets until its positive and negative self-tests return PASS and FAIL as intended, yet no self-test edits an __init__.py file.
The passing Matplotlib self-tests modify other locations under lib/matplotlib/, such as axes/_base.py and ticker.py, and the representation self-tests use only representations the checks accept.

We call this confirmatory self-testing: the tests confirm that the verifier accepts a chosen solution but never ask whether its other conditions follow from the task.
More tests at the same permitted locations would not expose the restriction, and neither would negative self-tests: an invalid patch may violate a genuine requirement while also tripping the unjustified check, so rejecting it correctly does not justify the check.
As Appendix Figure 7 shows, a Qwen3.7 Plus verifier exhibits the same pattern outside the Astra batch: it treats an omitted optional argument as empty instead of applying its documented default, and every positive self-test supplies that argument explicitly.

## 4.3 Self-Tests That Never Confirm Acceptance

The eight verifiers in the lower block of Table 4 are the banking and retail verifiers of Section 4.1.
Their agents ran intended-positive self-tests but never obtained a complete positive PASS, as each agent’s final response acknowledges, so these runs do not establish acceptance even of the agent’s own intended solution.
In the running example of Figure 2, the intended-positive self-test omits the permitted dispute-history query and fails when replay is unavailable after budget exhaustion; the tool restriction remains untested.
At evaluation, the eight verifiers reject all 72 of their positive judgments without environment execution.

Generation-time testing is constrained more broadly.
Exploration and self-testing share one execution budget, which most HIGH-effort state and code runs exhaust as described in Section 3.3, and in two appendix traces shown in Appendix Figures 9 and 10 local execution fails because unshare is unavailable.
These limits do not directly cause hidden rejections, since evaluation has its own budget, but they can leave a verifier’s checks unresolved when generation ends.

## 5 Implications

Self-testing a generated verifier serves two goals: confirming that it accepts a chosen solution, and checking that it does not reject other solutions the task allows.
The second requires tracing every acceptance condition to the instruction, tool definitions, or environment rules, and testing it with cases derived from those requirements.
One test varies a permitted property while keeping the task satisfied, for example editing fields/__init__.py instead of query.py, omitting a defaulted argument, or using an authorized user-side call; another violates one required condition.
Examples drawn from solutions a check already allows cannot challenge that check, and the Django configurations show that permitting legal source changes need not weaken rejection of tested violations.

Testing must also be completed.
Generation should reserve execution budget for testing the final verifier and should distinguish an execution failure from a failed requirement: a blocked test leaves its check unresolved, and repairing the execution does not validate checks the test never exercises.
We do not evaluate the effectiveness of these directions.

## 6 Related Work

Executable verifier generation. nl2postcond (Endres et al., 2024) and CodeSpecBench (Chen et al., 2026) generate executable specifications and evaluate them on valid and faulty behavior; CheckerBench (He et al., 2026) studies agent-generated static-analysis checkers. We evaluate task-completion verifiers for tool-call, state, and code tasks, generated from the instruction and environment available for task solving.
Test-oracle and test generation. TOGA (Dinella et al., 2022) generates test assertions, TestGenEval (Jain et al., 2025) evaluates unit-test generation, and SWT-Bench (Mündler et al., 2024) generates issue-reproducing tests that also assess candidate patches. Our suites contain multiple valid variants and violations per task, and our trace analysis examines whether self-tests challenge unjustified checks.
Automated training-data construction. Absolute Zero (Zhao et al., 2026) learns from self-proposed tasks with execution-based verification. Self-Challenging Language Model Agents (Zhou et al., 2026) jointly generates tasks, verification functions, and test examples for reinforcement learning. We hold tasks fixed to evaluate verifier generation in isolation, and identify errors that could affect which solutions enter training data.

## 7 Conclusion

VerifierBench evaluates whether agents can write verifiers from the information available for solving a task.
Across all 36 configurations, generated verifiers accept valid solutions less reliably than they reject invalid ones, and in the analyzed records most false rejections come from verifiers that reject every case of their task.
Code and trace inspection links these verifiers to unjustified checks and to self-tests that either confirm only solutions those checks allow or never confirm acceptance at all.
Verifier generation therefore needs tests that challenge each acceptance condition against the task requirements; otherwise, where generated verifiers select training data, as in data-oriented RSI, such checks could repeatedly exclude legitimate solution strategies.

## Limitations

Scores measure agreement with retained reference verifiers on finite, constructed test suites.
As detailed in Appendix B, V4V excludes 45 tasks with confirmed source defects, but agreement between construction labels and reference decisions does not certify that every label is semantically correct.
The 36 configurations differ in harness prompts, tools, and reasoning settings, so cross-harness differences describe configurations and do not isolate any harness component; rankings are point estimates without repeated generations or significance tests.
The concentration analysis uses archived per-task records for nine models and the Astra trace batch for one model, rather than final per-task records for all 19 models.
The code and trace analysis covers verifiers selected to explain observed failures, mostly from GPT-6-astra.
It attributes rejections by inspecting source code rather than by intervention experiments, and it reads self-test outcomes from traces without reconstructing the verifier version at each self-test; it therefore identifies mechanisms but not their prevalence.

## Appendix D Metrics and Scoring Protocol

## Outcome categories.

For each test case, $P$ denotes a valid PASS, $F$ a valid FAIL, and $U$ no valid decision.
The last category includes missing verifiers and invocations that fail to return a conforming decision.
Positive $F$ outcomes are false rejections, while negative $P$ outcomes are false acceptances.
Both differ from $U$ , even though all receive zero correctness credit on the affected test case.
Optional confidence values do not change the scoring label: a well-formed FAIL with low or missing confidence remains $F$ .

## Equal task weighting.

Let $\mathcal{C}_{t}^{+}$ and $\mathcal{C}_{t}^{-}$ be the positive and negative test cases for task $t$ .
If $A_{m,t}$ counts positive test cases receiving PASS and $R_{m,t}$ counts negative test cases receiving FAIL, define

 $\displaystyle r^{+}_{m,t}$ 
 $\displaystyle=\frac{A_{m,t}}{|\mathcal{C}_{t}^{+}|},$ 

(2)

 $\displaystyle r^{-}_{m,t}$ 
 $\displaystyle=\frac{R_{m,t}}{|\mathcal{C}_{t}^{-}|}.$ 

(3)

Both denominators include test cases with missing or invalid outputs.
All tasks have positive and negative test cases, so both denominators are nonzero.
For the full task set $\mathcal{D}$ , scores in percentage units are

 $\displaystyle\mathrm{TPR}_{m}$ 
 $\displaystyle=\frac{100}{|\mathcal{D}|}\sum_{t\in\mathcal{D}}r^{+}_{m,t},$ 

(4)

 $\displaystyle\mathrm{TNR}_{m}$ 
 $\displaystyle=\frac{100}{|\mathcal{D}|}\sum_{t\in\mathcal{D}}r^{-}_{m,t},$ 

(5)

 $\displaystyle\mathrm{BA}_{m}$ 
 $\displaystyle=\frac{\mathrm{TPR}_{m}+\mathrm{TNR}_{m}}{2},$ 

(6)

 $\displaystyle\mathrm{BA}_{\rm norm,m}$ 
 $\displaystyle=2\mathrm{BA}_{m}-100.$ 

(7)

A missing verifier contributes zero to both class-specific rates for its task.
Always accepting or always rejecting yields BA ${}_{\rm norm}=0$ when a valid decision is returned throughout; independent random binary decisions have the same expected score.
Perfect agreement yields 100, and no valid decisions on any test case yields $-100$ .
Normalization preserves the ordering induced by task-averaged BA.

## Attack acceptance.

Let $\mathcal{H}_{t}$ contain the hack and process_violation test cases for task $t$ .
Each of the 222 retained tasks has at least one such test case.
If $B_{m,t}$ counts attack test cases receiving a valid PASS, the attack false-positive rate is

 $\mathrm{FPR}_{h,m}=\frac{100}{|\mathcal{D}|}\sum_{t\in\mathcal{D}}\frac{B_{m,t}}{|\mathcal{H}_{t}|}.$ 

(8)

An invalid or missing output does not count as an accepted attack.
Consequently, low FPRh must be interpreted alongside valid-output coverage and the primary accuracy metric.

## Pooled diagnostics.

Submission is the number of tasks with a submitted verifier divided by 222.
Valid-output rate is $100(P+F)/(P+F+U)$ over the relevant test cases.
On positive test cases, rejection share is $100F/(F+U)$ , the fraction of unaccepted test cases receiving an explicit rejection.
These diagnostic proportions weight test cases equally, whereas the main metrics weight tasks equally.

## Harness comparisons and rounding.

Every final harness pair uses the same 222 tasks, with missing results retained in the denominator.
For configurations $a$ and $b$ , $\Delta S=S_{a}(\mathcal{D})-S_{b}(\mathcal{D})$ .
Scores and source-reported differences are rounded independently to one decimal place, which can produce a 0.1-point discrepancy when subtracting displayed values.
The reported ranking uses point estimates rather than significance tests or repeated-generation estimates.

## Budgets and tools.

The global limits are 5,400 seconds per task and 32,768 output tokens per reply.
There is no additional benchmark-wide cap on total output tokens per task or context length, although model and harness limits apply.
Generation tools permit task inspection, public environment execution, and reset where supported, together with the harness’s code-authoring tools.
Test cases and reference implementations are withheld during generation.

## Harness and reasoning settings.

Recorded versions include Pi harness 0.84.2, Codex 0.149.0, Claude Code 2.1.263, Gemini CLI 0.60.0, OpenClaw 2026.6.34, and mini-swe-agent 2.4.6.
Reasoning settings also differ.
For example, retained structured Opus/Claude Code traces record high effort with thinking enabled, while historical Pi harness traces that expose a thinking setting record it as off.
Later configurations include other settings.

## Generation instructions.

The verifier-generation prompts require a binary PASS/FAIL decision and provide optional score or confidence fields that do not affect the binary outcome used for scoring.

## Retained attempts.

The release selects the latest authorized attempt for a task and configuration, including attempts that do not deliver a verifier; it does not select the highest-scoring attempt.
Earlier attempts remain in the attempt manifest and are not combined with a later verifier’s judgments in the case analysis.

## Judgment rounds.

Tool-call tasks use the first judgment round, while state and code tasks are judged three times.
For each aggregate round, metrics are computed over the full 222-task pool with the first-round tool-call judgments held fixed.
The round with median aggregate BA determines the entire reported row; columns are not selected independently.
The grouped diagnostics use the same selected verifiers and judgment rounds as the main table.
These rounds execute fixed generated verifiers and do not constitute independent generations.
Native traces retain task-specific prompts and available configuration records, although complete system prompts and structured traces are not uniformly available.

## Model rankings depend on task type.

GPT-5.6-sol leads tool-call verification at 85.2, Claude Opus 4.8 leads state-based verification at 34.6, and Kimi K3 leads code-based verification at 76.9.
Ranks also reverse: Kimi K2.6 ranks third on tool-call tasks but seventeenth on state tasks, whereas Qwen3.7 Plus ranks fourteenth and second, respectively.
DeepSeek V4 Pro ranks third on code tasks and fifteenth on state tasks.
These comparisons concern the benchmark’s task groups, which also differ in source benchmarks, environments, and test-case composition; they do not isolate the effect of task type alone.

## The acceptance deficit is strongest on state and code tasks.

Across the 19 models, mean TPR is 79.2% on tool-call tasks, 27.7% on state tasks, and 40.2% on code tasks, while mean TNR is 85.8%, 85.2%, and 90.6%, respectively.
These are arithmetic means of the models’ task-averaged rates.
All 19 models have lower TPR than TNR on state and code tasks, but eight have higher TPR than TNR on tool-call tasks.
The aggregate asymmetry therefore coexists with a different pattern on some task types.
State-task TPR remains below 50% for every model, even for the highest-ranked configuration.
Low positive acceptance includes both explicit rejection and missing or invalid decisions; the rates alone cannot distinguish their causes.

## Low attack acceptance does not establish reliable verification.

On state tasks, GPT-5.6-sol has $\mathrm{FPR}_{h}=0.0\%$ but accepts only 23.0% of positives, yielding $\mathrm{BA}_{\mathrm{norm}}=16.1$ .
On code tasks, 17 models have $\mathrm{FPR}_{h}=0.0\%$ at the reported precision, yet their $\mathrm{BA}_{\mathrm{norm}}$ scores range from $-25.9$ to 76.9.
A low attack-acceptance rate must therefore be interpreted alongside acceptance of valid solutions and successful rejection of negatives.
Appendix I.1 compares input handling, checking rules, and execution on identical test cases.

## Concentration definition.

For model $m$ , let $\mathcal{A}_{m}$ contain the tasks whose submitted verifier is all-reject, that is, returns a valid FAIL on every test case for that task.
Tasks with any missing or invalid decision are excluded from $\mathcal{A}_{m}$ .
If $F^{+}_{m,t}$ is the number of positive test cases rejected on task $t$ , the test-case-weighted contribution is

 $Q_{m}=\frac{\sum_{t\in\mathcal{A}_{m}}F^{+}_{m,t}}{\sum_{t\in\mathcal{D}}F^{+}_{m,t}}.$ 

(9)

Figure 5 and Table 5 report $100Q_{m}$ .
This observed response pattern on the test suite does not establish that the verifier returns a constant decision on all possible inputs.

An equal-task-weight version replaces each $F^{+}_{m,t}$ with $F^{+}_{m,t}/|\mathcal{C}_{t}^{+}|$ in the numerator and denominator.
Its range across the nine models is also 87.9–96.0%; for GPT-6-astra it is 91.1%, compared with the test-case-weighted 92.7%.
Thus, concentration is not explained solely by some tasks having more positive test cases.

## Concentration in the Astra trace batch.

We apply the same definition to the four conditions of the Astra trace batch.
These comprise 888 selected verifiers and 19,972 judgments, with 222 tasks and 4,993 judgments per condition.
Every judgment returns a valid binary decision.
Table 5 shows that verifiers returning FAIL on every test case for a task account for 93.3–95.5% of all false rejections.
These results come directly from the Astra trace batch, independently of the archived records above.
The four conditions concern one model and do not estimate variation across independent generation seeds.

The equal-task-weight concentration is 93.9%, 95.1%, 93.4%, and 94.4% for Pi harness/LOW, Pi harness/HIGH, Claude Code/LOW, and Claude Code/HIGH, respectively.
Table 5 separately reports whether each verifier accepts none, some, or all positive cases.

## I.6 Incorrect Handling of a Specified Default

The Qwen3.7 Plus/Pi harness case in Appendix Figure 7 uses task vgb-t-d78e768308367722, a DNA-analysis task from BFCL.
The actual generation prompt states that mutation_type is optional and defaults to insertion; only the two sequence arguments are required.
The generated checker compares expected argument values with values obtained using

actual_args.get(key, "")

Consequently, an omitted optional parameter becomes the empty string rather than its defined default.
The positive test case vgb-c-e6ede484b58a7c02 omits this parameter in an insertion call and receives FAIL, while the designated fully specified solution receives PASS.

The same verifier searches for the presence of six expected calls and rejects extra calls only when their tool name is unexpected.
Negative test case vgb-c-9c2f334fedb91aae preserves those calls and adds another call using the same tool; the generated verifier returns PASS.
The default omission is explicitly justified by the tool schema.
The treatment of extra calls is assessed relative to the reference acceptance rule and should not be generalized into an assumption that every redundant operation is invalid.

The visible self-tests use fully specified calls, an incomplete subset, and a raw-text representation of the fully specified calls.
They do not test omission of the default argument.
The case therefore links a specific comparison error to a behavior specified in the tool definitions but absent from the self-tests.

## I.7 Self-Tests That Share a Parsing Assumption

The GPT-5.6-sol/Claude Code case uses task vgb-t-0480046e6a2a021f, an ACEBench booking-cancellation task.
Its recorded generation includes a test described as a function call, constructed by placing a JSON dictionary inside the function’s parentheses.
The test passes.
The reference solution in the test suite instead expresses the arguments as Python keywords, including bookingId=’R123’.

The generated parser extracts the text inside the parentheses and attempts to decode it with json.loads or ast.literal_eval.
A keyword-argument list is neither a JSON value nor a Python literal expression, so neither operation parses that text.
The verifier maps this failure to FAIL; the designated reference solution receives a recorded rejection with confidence 0.99.
The self-test passes because it uses precisely the representation accepted by the parser.

The verifier input format provides raw and parsed call fields, but the generation prompt gives no concrete grammar for the raw field.
This case supports input incompatibility and inadequate self-test coverage, rather than a claim that the model ignored an explicit syntax requirement.
It comes from the Claude Code configuration; Appendix Figure 9 shows a related raw-input parsing failure under Codex.
