## Racer: Hunting GPU Kernel Bugs with Symbolic Equivalence Checking

Tuan Truong Vu and Cheng Tan

Affiliation: Northeastern University

Abstract.

GPU kernels are critical to the performance of today’s AI services, yet the
same operators are rewritten repeatedly: for each GPU generation, numeric
format, serving regime, and kernel language. Every rewrite must preserve the
function computed by the implementation it replaces. Today, this obligation
depends almost entirely on differential testing: run the new kernel and a
trusted reference on randomly sampled tensors, then compare their outputs
within a tolerance.
This approach has blind spots that additional test cases cannot eliminate. For
example, a logical bug may produce an error smaller than the tolerance
required to accommodate a correct optimized kernel.

We propose symbolic equivalence checking , which executes a kernel and its reference on
symbolic inputs, turning each output cell into an exact algebraic expression,
and then checks whether the paired expressions agree for all inputs. Because
these expressions are exact, symbolic equivalence checking distinguishes floating-point error from
logical bugs, while a single check covers the entire input space.

We implement Racer, a PTX-level symbolic equivalence checking engine, with three techniques that make
this approach practical for production kernels:
(1) Shape Reduction to control checking cost,
(2) a lockstep CTA scheduler to handle concurrency,
and (3) idiom templates with exact numeric refutation for otherwise inconclusive results.
Across 2,408 production kernels from 41 collection targets, Racer found
82 real bugs in 23 libraries, including 76 previously unknown bugs and 41 confirmed so far.

## 1. Introduction

GPUs power modern AI, and GPU kernels largely determine its performance.
AI model throughput is closely tied to the throughput of its GPU kernels (Wang et al., 2025).
Optimized kernels are therefore central to the performance of modern AI
systems: they directly determine inference latency and serving throughput, and
can make impractical workloads feasible. FlashAttention, for example,
substantially reduced the cost of attention and enabled efficient long-context
inference (Dao et al., 2022).

Because performance matters,
the same GPU kernel gets written over and over.
Attention alone has been rewritten for each architecture
generation as new primitives arrived,
from Ampere’s asynchronous copies to Hopper’s TMA and warpgroup MMA (Dao, 2024; Bikshandi and Shah, 2023; Chen et al., 2026);
specialized per head dimension and per serving regime, prefill against decode (Zhong et al., 2024);
re-tuned for each numeric format (Micikevicius et al., 2022; Frantar et al., 2025; Lin et al., 2024);
and written again in new languages such as Triton (Hsu et al., 2024; Yang and Zhang, 2024; Spector et al., 2025).
It happens across serving platforms too:
vLLM (Kwon et al., 2023) and SGLang (Zheng et al., 2024)
each ship their own fused RMSNorm,
one written to accept any hidden size,
the other optimized for the shapes it expects to serve.

This rewriting paradigm is the norm in modern GPU kernel development: a
set of mathematical functions is implemented repeatedly, with each new
implementation striving to outperform its predecessors.

Beyond performance,
every rewrite carries a critical obligation:
it must still compute the same function as the implementation it replaces.
For today, meeting that obligation is left almost entirely
to differential testing: run the new kernel and a trusted
implementation, usually PyTorch’s, on randomly sampled input tensors, and
compare the outputs elementwise within an absolute and relative tolerance (McKeeman, 1998; Paszke et al., 2019).
This practice is widespread in production, and for good reason.
The operator set is bounded, and each operator has a precise mathematical
meaning, so a trusted reference implementation is almost always available.
Moreover, kernels are typically pure functions from input tensors to output
tensors, making side-by-side execution straightforward.

And yet, production systems still ship GPU kernels with bugs.
By studying 82 bugs we found in deployed libraries (§7)
that slipped through differential testing, we identified four major obstacles:
(a) sampling cannot cover the input space:
some bugs trigger only on needle-in-a-haystack values that random sampling is unlikely to produce;
(b) not every input is an explicit argument:
many bugs depend on implicit inputs, such as uninitialized memory that happens
to contain zeros during testing but may hold arbitrary values in practice;
(c) not every output is checked:
some bugs we found corrupt memory outside the intended output region, which tests therefore never inspect;
and most notably,
(d) floating-point error can be indistinguishable from a bug:
6 bugs we found cause only small numerical errors—smaller than the
tolerance required for correct optimized kernels.

As a real bug example,
FlagGems’ InstanceNorm reconstructs the variance from the stored
 $\mathrm{rstd}=1/\sqrt{\mathrm{var}+\epsilon}$ as
 $1/\mathrm{rstd}^{2}+\epsilon$ , instead of the correct
 $1/\mathrm{rstd}^{2}-\epsilon$ .
Such a bug cannot be detected by differential testing.
This is because, for typical input tensors, the output deviation caused by the
logical bug is smaller than the tolerance required to accommodate normal
floating-point error.
But this is not harmless numerical noise: the kernel computes the wrong
function, and the resulting systematic error can compound over millions of
training steps and ultimately cause training to fail.

We argue that ensuring the correctness of GPU kernels requires a more systematic and principled approach than differential testing.
To this end, we propose symbolic equivalence checking .
Symbolic equivalence checking executes two GPU programs over symbolic inputs rather than concrete values.
As a result, each output element is represented by an algebraic expression over
free variables rather than a concrete number.
The two kernels are equivalent exactly when, for every output element, the
corresponding expressions evaluate to the same value for all possible inputs.

In symbolic equivalence checking,
each blind spot of differential testing is eliminated by design
rather than by testing harder.
First, a free variable stands for every input value at once,
so one check covers the entire space.
Second, uninitialized memory is symbolic too, so a kernel
that depends on what the previous launch left behind is checked over every
value it could have left.
Third, symbolic execution knows the address of every
store, so a write outside a declared tensor is caught where it happens.
Finally, expressions are exact rather than floating-point, removing
floating-point error from the checking problem.
Any difference between the two
kernels therefore reflects a difference in the function they compute, rather
than an artifact of rounding.

In this paper,
we introduce Racer, a symbolic equivalence checking engine for GPU kernels.
Racer takes two kernels—one under test and one reference implementation—together with a launch configuration,
and returns one of three outcomes:
Equivalent, Inequivalent with a concrete input that distinguishes the two kernels,
or Unknown.

Racer executes symbolic equivalence checking at the level of PTX,
NVIDIA’s virtual instruction set (, 2026).
PTX provides a stable interface across GPU generations and is, in fact,
the lowest-level instruction set that NVIDIA publicly documents.
As a result, many front ends, including CUDA C++ and Triton, compile to it.
Moreover, PTX exposes memory operations explicitly,
allowing the engine to model the address space that a kernel actually accesses.

Checking production GPU kernels poses three technical challenges for Racer.
First, symbolic equivalence checking is expensive at the scale of real kernels.
For example, a naive implementation of symbolic equivalence checking times out under a 600s
budget even for a simple Softmax kernel with tensor shape $4\times 64$ .
Second, a kernel launch is not a single piece of code running on one core, but
thousands of concurrent threads executing and interacting through
synchronization and shared memory. Racer must therefore reason not only about
each thread’s arithmetic computation, but also about synchronization and
cross-thread interactions.
Finally, deciding the equivalence of arbitrary arithmetic expressions is
fundamentally difficult. In many cases, the underlying computer algebra
system cannot establish equivalence and returns
Unknown. Racer must therefore reduce the frequency of such inconclusive
cases while preserving soundness.

Racer introduces three techniques to answer the three challenges:
Shape reduction proves one representative output cell per uniformity class and transports the
proof to the rest by a verified renaming, rather than paying for every cell
(§5.1);
a CTA scheduler steps every thread in
lockstep between synchronization points and refuses what it cannot order,
so that no verdict rests on an interleaving the engine chose
(§5.2);
and idiom templates with exact numeric refutation plus a second prover for inconclusive results (§5.3).

We evaluate Racer on production kernels from 41 GitHub repositories.
In total, Racer checks 2,408 GPU kernels.
It identifies 82 real bugs, including 76 previously
unknown bugs, of which 41 have been confirmed.
These bugs are nontrivial:
among the 82 bugs, an oracle differential tester could, in theory, detect only 47.
In comparison, NVIDIA’s compute-sanitizer (, 2026)
detects 18, while Volta (Driscoll et al., 2026), the
closest existing equivalence checker, detects only 9 (§7.2).

We are not the first to check GPU kernels symbolically, nor the first to
decide equivalence of tensor programs (Driscoll et al., 2026; Arora et al., 2025; Lu et al., 2025).
We are, to our knowledge, the first to scale symbolic equivalence checking to
bug detection in production GPU kernels: handling whole grids rather than a
single thread block, multi-launch programs, atomics, and asynchronous copies,
while achieving the performance needed to check real-world kernels.
This paper contributes:

• 

A study of 82 real bugs in production GPU kernels that identifies
four blind spots of differential testing and shows, bug by bug, why the
practice cannot close them (§2, §6).

• 

Racer, a symbolic equivalence checking engine that decides kernel equivalence at PTX level
over exact arithmetic, models GPU execution faithfully, and fails closed
rather than approximating (§4).

• 

Three techniques that make the check practical on production kernels:
shape reduction,
a lockstep CTA scheduler,
and idiom templates (§5).

• 

An evaluation on 2,408 production kernels: 82 real bugs across 23 libraries, 76 previously unknown,
and 41 confirmed at the moment.
(§7).

## 2. Motivation: Kernel Correctness Today

The same operators are repeatedly rewritten.
Unlike traditional software,
the functionality of GPU kernels for LLMs is bounded:
a few dozen operators (e.g., matrix multiply,
attention, normalization, activation) account for nearly all
of the computation a large language model performs.
Yet those same operators are written again and again: once per framework,
per hardware generation, per data type, per fusion opportunity, per
workload regime (Zhong et al., 2024; Yu et al., 2026; Dao et al., 2022; Dao, 2024; Bikshandi and Shah, 2023; Hsu et al., 2024; Spector et al., 2025; Yang and Zhang, 2024; Beck et al., 2026).

What forces the rewrites is performance.
A kernel that is correct but slow is worthless,
because the functional implementation already exists;
the only reason to write it at all is to make it faster or cheaper.
Each rewrite therefore buys speed with specialization: tiling and vectorization tuned to a shape, hand-staged
shared memory, warp-level collectives, asynchronous copies, low-precision accumulation (Dao et al., 2022; Dao, 2024; Chen et al., 2026; Bikshandi and Shah, 2023; Beck et al., 2026).
Every one of those is a place to get the code wrong.

Compounding these optimizations,
the code can also go wrong because of the underlying arithmetic: tensor algebra,
whose indices, strides, reductions, and broadcast semantics
are tricky and error-prone.
An index offset by one stride, or a reduction over the wrong axis, is easy to write and difficult to spot.
For example, a buggy log-softmax kernel in FlagGems (contributors, 2024)
normalizes along the tensor’s last axis, even when asked to normalize
along a different one, thereby combining the wrong group of elements.
Similarly, a buggy multi-head attention kernel in attorch (Ahmadzadeh, 2024)
maps every head to head 0, causing all heads to compute the same output.

Differential testing is the de facto approach for correctness evaluation:
a test samples random input tensors,
runs the newly developed kernel and a trusted reference (e.g., PyTorch’s implementation)
on the same data, and compares the two outputs element-wise.
The comparison uses absolute and/or relative tolerances.
The kernel passes only if the discrepancy falls within a predefined threshold.

Differential testing fits naturally into GPU kernel development.
Because the operator set is bounded and each operator has a crisp mathematical meaning, a trusted
reference is almost always at hand, and because kernels are pure functions
from input tensors to output tensors, comparing the two is simple.
In practice, nearly all GPU kernels today ship with tests of this form.

However, differential testing misses bugs.
Despite widespread use of differential testing,
GPU kernels continue to ship with bugs:
scanning 2,408 GPU kernels from 41 production-quality libraries,
we found 82 bugs (§7.1).
Studying those bugs, we find four reasons why differential testing is
insufficient, each a challenge that any stronger correctness check must meet.

(1) 

Sampling cannot cover the input space.
Testing samples insufficient input space is an old complaint, but the kernel setting amplifies it.
A single argument is a tensor of thousands
of elements, and an element is not drawn from a handful of categories but
from a floating-point domain of billions of bit patterns.
The combination of the two makes good coverage infeasible.
Meanwhile, we do find bugs that manifest only for specific input tensor values,
for example,
attorch’s hardshrink keeps an input equal to exactly $\pm\lambda$ , where
PyTorch’s keep-set is strict ( $|x|>\lambda$ ); the two differ only where an
input element equals the threshold $\lambda$ exactly (default $0.5$ ).

(2) 

Not every input is an argument.
Further, a kernel’s result depends on state that never appears in its signature.
Some kernels depend on allocated but uninitialized memory, which often happens
to contain zeros during testing but is not guaranteed to be zero in production.
For example, a reduction kernel in
Triton-distributed (Zheng et al., 2025) has each CTA atomically
add its partial sum into an output cell that is only allocated but not
initialized as zero, so the result is the sum plus whatever the cell held
before the launch.

(3) 

Not every output is checked.
A test compares the tensors the kernel declares; the kernel writes wherever
its computed addresses point. A miscomputed index or a missing bounds guard
on a ragged final tile scribbles outside the intended region, into a
neighboring tensor or into a buffer another kernel owns, while the declared
output still matches the reference element for element.
For example,
fla’s squared-ReLU (Yang and Zhang, 2024) backward writes past the tensor end when the length is
not a multiple of block size.

(4) 

Floating-point error is indistinguishable from a bug.
Most importantly,
numeric thresholds cannot distinguish an incorrect function from a correct one evaluated under a different floating-point order, leading to errors in both directions.
A correct kernel may exceed the tolerance due to reduction reordering; more seriously, an incorrect kernel may remain within the tolerance on sampled inputs.
Loosening the tolerance suppresses false alarms but can also mask real bugs.
We have found 6 cases in this category, where incorrect logic is hidden by the floating-point error threshold.

These four points lead to one conclusion:
a test compares numbers, but correctness
is a statement about functions.
What the setting calls for is a check that
ranges over all inputs rather than sampled ones, that accounts for the
memory a kernel actually touches rather than the tensors it declares, and
that decides whether two implementations compute the same value rather than
producing nearby ones.

## 3. Equivalence Checking for GPU Kernels

## 3.1. Beyond Testing: Toward Principled Checking

We believe testing cannot address the four challenges described in §2.
Our answer is symbolic equivalence checking .

Symbolic equivalence checking.
This method executes a kernel over symbolic inputs, so each instruction
builds an algebraic expression instead of computing a number, and every
output tensor holds one expression per cell rather than one value.
Running the new kernel and its reference this way yields, for every
output cell, a pair of expressions over the same input variables.
The two kernels are equivalent when both expressions result in the same value
for all possible inputs.
Nothing is sampled and compared numerically.

All four challenges dissolve at this level.
Input coverage:
a free variable stands for every value at once, so a single check covers the
entire input space.
Implicit inputs: the cells of an
uninitialized buffer are free variables too, so the check ranges over
whatever the running context may have left in that memory.
Unchecked outputs: the execution records the
address of every store, and each expression records which inputs reached the
cell, so a write outside a declared tensor is caught where it happens instead
of surfacing later as someone else’s wrong number.
Floating-point error: expressions are exact rather than
floating point, so reordering a reduction changes an expression’s shape but
not its value.
There is no tolerance parameter to tune; any difference between two expressions
corresponds to a difference in the computed function, not to floating-point rounding.

Prior equivalence checkers.
The idea of proving two implementations equivalent is not new, and
§8 returns to it.
For example,
TrainVerify (Lu et al., 2025) checks a distributed training
program against its single-device specification;
TensorRight (Arora et al., 2025)
applies equivalence reasoning to tensor-graph rewrites, certifying that a
rewritten graph computes what the original did;
Volta (Driscoll et al., 2026), the closest to us,
brings equivalence checking to GPU kernels themselves.
Racer differs from prior work in its focus on finding bugs:
of the 82 bugs Racer finds, Volta detects only 9.
We explain this gap in §7.2.

## 3.2. Background: GPU Execution and PTX

GPU programs have distinctive characteristics that shape how symbolic equivalence checking must be
built. This subsection reviews the basics of GPU execution, then PTX (, 2026),
the instruction set at which Racer operates.

GPU execution.
A GPU is a massively parallel processor that runs tens of thousands of
threads at once. The program those threads run is a kernel: a single
function, written from the perspective of one thread, that every thread
executes over its own slice of the data. To run a kernel, the CPU host
launches a grid of cooperative thread arrays (CTAs), also called
thread blocks; the grid and block dimensions, chosen at launch time
together with the kernel’s arguments, form the launch
configuration. Every thread runs the same kernel body and is distinguished
only by its block and thread indices: the single-instruction,
multiple-thread (SIMT) model. Threads advance in groups of 32, called
warps, whose members can exchange values directly.

A kernel reads and writes three memory spaces of different scope and
lifetime: registers and local memory, private to a thread; shared memory, a
per-CTA scratchpad that dies with the CTA; and global memory, visible to
every thread in the launch and persistent across launches. Threads within a
CTA synchronize with a barrier (bar.sync), but threads in different
CTAs cannot synchronize within an ordinary launch, so a computation needing
a grid-wide handoff is split into several launches, each reading through
global memory what the previous one wrote.
Split-K matrix multiplication is
the standard example: one launch has each CTA reduce its own slice of K into
a partial-product buffer, and a second launch sums those partials.
Both facts matter later: the engine must reproduce this ordering discipline
faithfully (§5.2).

PTX.

PTX is NVIDIA’s stable virtual instruction set. Kernels written in different
front ends, such as CUDA C++ (, 2026), Triton (Tillet et al., 2019), Numba (Lam et al., 2015), TVM (Chen et al., 2018), and CuPy (Okuta et al., 2017),
all lower to PTX before reaching the GPU, which makes it the one level at
which kernels from different front ends can be compared instruction for
instruction.
For example,

shows one add-and-narrow computation in CUDA C++
and Triton, both of which are compiled to
the same PTX instructions.

Symbolic execution and computer algebra.
Symbolic execution runs a program over free variables instead of
concrete data: each arithmetic instruction builds an algebraic expression in
those variables rather than computing a number, and each branch on a
symbolic condition is resolved under the constraint that selects its path.
A computer algebra system (CAS) (Meurer et al., 2017; Wolfram Research, Inc., 2024; Maplesoft, a division of Waterloo Maple Inc., 2024; The Sage Developers, 2024; Maxima.sourceforge.net, 2024)
then manipulates those expressions exactly,
using unbounded-precision rational arithmetic
and algebraic rewriting instead of evaluating them as floating-point approximations.
We use SymPy (Meurer et al., 2017), a CAS implemented as a Python library.
To check whether two expressions are equivalent,
we simplify their difference and check whether it reduces to zero.
Figure 2 shows an example.

Symbolic executing PTX code.
Applying symbolic execution on PTX code yields a recipe for symbolic equivalence checking.
Bind every cell of every input tensor to a free variable instead of a number. Execute the
kernel’s PTX one instruction at a time, interpreting each by the mathematical
operation it denotes in the CAS: a floating-point instruction becomes the
corresponding operation over the reals.
When the launch ends, every output cell holds an
exact expression in the input variables, and no rounding has been lost to an
approximation along the way. Checking two kernels is then subtraction: run
both over the same symbolic inputs, form the difference of their
expressions cell by cell, and ask the CAS whether every difference is zero.
A logical bug is found if the two kernels disagree.

Challenges.
Naively applying a CAS to PTX instructions, however, does not work.
Three challenges arise in practice.

• 

Scalability.

A GPU kernel launch can contain thousands of threads, each performing thousands
of arithmetic operations. Executing all threads and proving each output
cell independently scales poorly with both thread count and expression
size: an output at the end of a long reduction carries the full
expression chain that produced it, which the CAS must repeatedly simplify.

• 

Concurrency.
GPU kernels are highly concurrent, with many threads cooperating to complete a computation.
A symbolic engine must therefore model concurrency primitives such as
barriers,
warp collectives,
asynchronous copies,
atomic instructions,
and tensor-core instructions.
Moreover, the result may depend on thread interleavings, so the engine must
detect and reason about data races. Each construct must either be
modeled faithfully or rejected outright (§5.2).

• 

Inconclusive results.
Deciding whether two symbolic expressions are equal is a hard problem.
For expressions involving a sufficiently rich set of functions, modern CASs may fail to reach a conclusion or may time out.
In practice, this happens often.
We therefore need to minimize the chance that the engine returns Unknown (§5.3).

Racer answers the question:
do the two given GPU kernels compute the same function?
A user poses this question as a checking instance containing two GPU programs—the
second serving as the reference implementation, as in differential testing—the
tensors they read and write, and their launch configurations.
Racer runs the checking instance.
When done,
Racer returns one of three verdicts: Equivalent,
Inequivalent with a concrete input that separates the two,
or Unknown.

It takes four steps for Racer to produce the verdict.
Racer (1) reads the checking instance,
(2) lowers both programs to PTX whatever front end they were written in,
(3) executes every thread of every CTA of both programs
symbolically, leaving one algebraic expression in each output cell,
and (4) decides, cell by cell, whether
the two expressions denote the same value.
The rest of this section walks the four steps on a running example in
Figure 3, a bug from vLLM (#941).

Step 1: posing the question as a checking instance.
In Racer,
a checking instance is a Python class with three methods.
The first, setup, declares the tensors both sides share;
the other two, program_a and program_b, each declare one program as a
sequence of launches.
Tensor declarations specify shapes, data types, and initial contents:
vk.input() introduces a free variable for each cell,
vk.empty() leaves cells uninitialized, and
vk.zeros() or vk.full() initializes cells
to a specified constant.
Each program records a sequence of kernel launches through
launch call, specifying the kernel, its arguments,
and its launch configuration.
Tensor arguments are wrapped in vk.read,
vk.write, or vk.readwrite to declare
how each launch accesses them.
Successive launches exchange data by accessing the same tensors.
Each program method returns a dictionary naming the output tensors
whose corresponding cells Racer should compare.

In Figure 3(b),
setup declares the tensors:
a $2{\times}4$ activation x and the rotation tables
cosv and sinv as inputs (free variable)
and the output out as empty. Each program is a single
launch of one of the two kernels over the same arguments: one CTA per
token, one thread per CTA, the head dimension $D{=}4$ passed as a scalar,
and out wrapped as vk.write where the inputs are
vk.read.
The checking instance poses the question: at this
configuration, do these two kernels compute the same function of
x, cosv, and sinv?

Step 2: lowering GPU programs to PTX.
Each launched kernel is lowered to PTX before analysis, making all subsequent stages front-end agnostic (§3.2).
The current Racer implementation supports three input forms: CUDA C++, Triton, and PTX.
In principle, Racer can support any GPU programming language whose toolchain compiles to PTX.
Racer only requires a language-specific adapter.

In our example, both programs are written in CUDA and lower to different PTX
instructions: Figure 3(c) excerpts the loop body.
The bug lives in the address arithmetic.
rope_gptj loads adjacent elements from
[%rd40+-4] and [%rd40], advancing
%rd40 by 8 bytes per iteration.
rope_neox instead loads from [%rd45]
and [%rd39], where %rd39 is computed as
%rd45 plus $(D/2)\cdot 4$ bytes.
Advancing %rd45 by 4 bytes per iteration therefore
pairs elements from the two halves of the head.

Step 3: executing PTX symbolically.

Across threads, Racer uses a lockstep scheduler to coordinate execution within

Step 4: checking output cells.
When both programs have run, their declared output tensors are paired by
name, giving for every output cell a pair of expressions to compare.
The checker forms the difference of each pair and hands it to the underlying CAS (§3.3).
A checking instance is Equivalent only if every cell of
every output tensor simplified to zero; a single refuted cell fails the case.

If the CAS leaves a cell unresolved, Racer applies exact numeric refutation,
which substitutes a concrete rational assignment for the free variables and evaluates expressions exactly:
a non-zero result is an Inequivalent witness,
and its absence leaves the cell Unknown,
since exact evaluation at one point can
refute but never prove.

In the running example, for cells at position $[t,0]$ ,

 $e_{a}[t,0]=c_{0}\,x_{t,0}-s_{0}\,x_{t,2},\quad\overset{?}{=}\quad e_{b}[t,0]=c_{0}\,x_{t,0}-s_{0}\,x_{t,1}.$ 

Their difference is
 $e_{a}-e_{b}=s_{0}\,(x_{t,1}-x_{t,2})$ .
Exact numeric refutation establishes that this expression is not
identically zero: substituting $s_{0}{=}1$ , $x_{t,1}{=}1$ , and
 $x_{t,2}{=}0$ yields $e_{a}-e_{b}=1$ .
This assignment is a concrete witness, so Racer returns Inequivalent.

## 5. Technical Challenges

The design in §4 must address the three challenges
introduced in §3.3: scalability, concurrency,
and inconclusive results. This section explains how Racer addresses them
with shape reduction, a lockstep CTA scheduler, and idiom templates
with exact numeric refutation and a second prover based on Z3.

## 5.1. Scalability

To prove equality at output cell $c$ , the CAS attempts to simplify
 $e^{a}_{c}-e^{b}_{c}$ to zero using algebraic transformations such as expanding
products, cancelling factors, and combining fractions. This process can
be costly for large expressions. For an output tensor with thousands of cells,
deciding each cell independently repeats this work even when the
expression pairs differ only in the input variables they reference.
Shape reduction reduces the deciding cost by reusing proofs across
output cells with the same expression structure.

Reusing a representative’s proof.
GPU kernels commonly apply the same function to different slices of an
input tensor. Their output expressions then differ only in the input
variables they reference. Shape reduction groups output cells into uniformity classes: their expression pairs match under a shared renaming of input variables.

Let $e^{a}_{r}$ and $e^{b}_{r}$ be the expressions produced by the two programs
at a representative cell $r$ , and suppose the deciding procedure has proved
 $e^{a}_{r}=e^{b}_{r}$ . Another cell $c$ can reuse this proof if a renaming
 $\tau$ satisfies

 $e^{a}_{c}=\tau(e^{a}_{r})\quad\text{and}\quad e^{b}_{c}=\tau(e^{b}_{r}),$ 

hence $e^{a}_{c}=e^{b}_{c}$ .

For each output tensor, Racer processes cells in sequence and tries to
reuse a proved representative. It validates each candidate renaming by
comparing both expression pairs structurally, allowing reordering of
commutative arguments without invoking CAS simplification.

Candidates come from input footprints: the indices in each input

representative position with the target position.

## 5.2. Concurrency

Threads can compute correct expressions individually and still produce
an incorrect result if one reads a value before another writes it.
To address the concurrency challenge in
§3.3, Racer models both what each thread
computes and when threads can exchange values.

Coordinating threads.
Racer executes every thread symbolically. Within each CTA, its scheduler
runs a thread until it exits or reaches a synchronization point.
At a barrier, the thread waits until all required participants arrive;
only then can they continue. The scheduler also coordinates the
participants of supported warp and tensor-core collectives. If required
threads cannot meet at the same synchronization point, execution is
refused. Thus, a thread cannot pass a barrier simply because the engine
happened to execute it first.
Algorithm 2 in Appendix A
gives the scheduler pseudocode.

Ordering memory accesses.
Scheduling alone cannot detect a missing barrier: running a writer
before a reader could hide the error. Racer therefore records reads and
writes in epochs, the intervals between CTA-wide barriers, and
reports conflicting accesses that lack the required ordering. A CTA
barrier orders accesses within that CTA; conflicts across CTAs are
tracked separately, and global memory is retained across launches.
Asynchronous copies require another ordering rule: issuing a copy does
not make its data available. Racer exposes the copied data only at the
modeled completion point—the corresponding wait for cp.async,
or completion of the associated barrier for TMA—and refuses accesses
that would use it earlier.

Combining atomic updates.
Multiple threads may atomically update the same cell in different
orders. Racer collects these updates and combines them at the next CTA
barrier for shared memory, or at launch completion for global memory.
This is valid only when the final value is independent of update order
under the arithmetic model, as with addition over exact reals
(§3.3) and supported integer add, min, max,
and bitwise operations. The engine refuses uses of an atomic’s returned
old value, mixtures of atomic operations on one cell, and ordinary
accesses that conflict with pending updates.

## 5.3. Inconclusive Results

The CAS may fail to prove equality within its time budget even when two
expressions denote the same function (§3.3).
Racer uses three techniques to reduce these inconclusive outcomes.

Idiom templates.
Compilation can turn a familiar function, such as $\log(x)$ , into a
long sequence of bit operations and polynomial arithmetic that obscures
its meaning to the CAS. Racer recognizes supported routines using
templates that match their coefficients, operations, guards, and
register dependencies. It replaces each matched sequence with the
corresponding mathematical operation under the real-arithmetic model
of §3.3.
For example, an inlined libdevice __nv_logf contains the
following PTX instructions:

⬇

mov.b32 %

add.s32 %

and.b32 %

// ...

mov.f32 %

fma.rn.ftz.f32 %

// ...

setp.lt.u32 %

// ...

selp.f32 %

Matching the full
routine lets Racer represent its result in %f37 as $\log(x)$ 
for a positive input $x$ , rather than carrying this instruction sequence
into the output comparison.

Exact numeric refutation.
If the CAS leaves a cell unresolved, Racer evaluates both expressions
at the same concrete input: rational values for free real inputs and
integers for index inputs, satisfying the checking instance’s constraints and the
expressions’ domains. It computes their difference using exact fractions
for rational arithmetic. For functions such as square roots, exponentials,
and logarithms, it uses interval evaluation with outward rounding to
bound the true difference. A nonzero exact difference, or an interval
excluding zero, yields an Inequivalent witness; otherwise, the cell remains
unresolved.

A second prover.
When both the CAS and numeric refutation leave a cell unresolved, Racer uses Z3 (de Moura and Bjørner, 2008) to search for an input where its expressions
differ. This can target boundaries that random inputs rarely reach:
 $x\geq\lambda$ and $x>\lambda$ , for example, differ only at
 $x=\lambda$ . For supported expressions, the query encodes both outputs
and the checking instance’s input constraints. A proposed counterexample yields
Inequivalent only after the numeric procedure above confirms a nonzero
difference in the original expressions. An unsatisfiable query proves
equality only if the encoding preserves the expressions’ arithmetic
semantics and input domain. Like a CAS proof, this proof can be reused
by shape reduction after validating the shared renaming. Unsupported
translations, timeouts, inconclusive solver results, and unvalidated
candidates leave the cell unresolved.

A concrete refutation yields Inequivalent. Otherwise, the checking instance is Equivalent only when every output cell has been proved equal, directly or by proof
reuse; any remaining unresolved cell makes it Unknown.
For an Unknown case, we manually inspect the kernel code alongside
the unresolved symbolic expressions. This helps us identify bugs or
limitations of the deciding procedure.

## 6. Bug Study

Our study of 82 bugs across 23 libraries, including 76 previously unknown bugs and six rediscoveries, reveals how real GPU
kernel defects escape testing. We assign each bug to one category based
on the primary reason a test can overlook it, illustrating the four
limitations in §2 before describing the other findings.

Sampled input.
Some bugs manifest only at a special input value that random tests rarely
produce, even when they exercise the faulty code.

For example, hardshrink should return zero when $|x|\leq\lambda$ 
and leave the input unchanged otherwise. The attorch implementation
instead keeps values equal to the threshold: with $\lambda=0.5$ ,
it returns $0.5$ for input $0.5$ instead of zero. Inputs on either
side give correct results, so exposing the bug requires hitting the
boundary. The seven findings in this category require values rarely
produced or omitted by the studied generators, including special labels
that mark elements to ignore.

Implicit input.
A kernel’s result can depend on memory state or execution conditions
that tests leave unchanged while varying tensor values.

For example, a Triton-distributed reduction allocates an output cell
with torch.empty and atomically adds each block’s partial sum
without first setting the cell to zero. The cell may retain data from
an earlier use: if it initially contains $c$ , the result is $s+c$ 
instead of the intended sum $s$ . Atomic addition prevents lost updates
but does not initialize the cell. Racer reports an uninitialized-memory
diagnostic, which disappears after zero-initialization.
The 11 findings in this category also involve tensor layouts and
parameter settings left unvaried by the studied tests, even when these
are explicit arguments.

Unchecked output.
A kernel can compute the output tensor correctly yet write past its
allocated buffer. A test comparing only that tensor does not inspect
the extra writes.

For example, fla’s squared-ReLU backward kernel handles 4,096
elements per block and should limit the final block’s writes to valid
elements. Instead, it writes all 4,096 results even when the output
has only 64 elements. Those 64 values match the reference, but the
remaining 4,032 writes exceed the output allocation and overwrite
memory beyond it. This category contains six out-of-bounds write bugs
across five libraries.

Below tolerance.
A wrong formula can produce values close enough to the reference to
pass a test: tolerances intended to allow floating-point rounding can
also hide programming errors.

For example, FlagGems’ InstanceNorm recovers variance from a stored
value $\mathrm{rstd}=1/\sqrt{\mathrm{var}+\epsilon}$ .
Squaring and inverting gives $\mathrm{var}+\epsilon$ , so recovery
requires subtracting $\epsilon$ . The kernel adds it instead,
overestimating the variance by $2\epsilon$ before updating the running
statistics. For small $\epsilon$ , the resulting error can fall within
the test’s tolerance. The six findings in this category are masked by
the tolerances used for the studied inputs.

Other.
Other findings involve gaps in test coverage, invalid memory accesses,
and synchronization errors. For example, the rotary-embedding kernel
in Figure 3 pairs the wrong input elements.
Of these 52 bugs, 40 can be exposed by comparison
with an independent reference at a triggering configuration; existing
tests miss relevant paths, share faulty logic, or omit a comparison.
Seven read outside an allocated buffer, e.g. FlagGems’ bucketize fetches elements past the input’s end.
Four are data races: threads access the same memory, with
at least one writing, without synchronization to order the accesses.
Their effects depend on thread timing, so a passing run does not
establish correct synchronization.
One further bug modifies padding within the allocation without changing the operator’s semantic output.

## 7. Evaluation

We evaluate Racer’s bug findings, detection by other methods,
equivalence coverage, and end-to-end checking cost.

Experimental setup.
We conduct the experiments on a server with two AMD EPYC 9575F CPUs
(128 cores), Python 3.11.16, and SymPy 1.13.1. An NVIDIA RTX PRO 6000
captures launches, replays witnesses, and runs
the concrete baselines. The server runs Rocky Linux 9.6 with CUDA 13.1.
Racer compiles CUDA sources with nvcc 12.4 and
Triton kernels with Triton 3.2.0, both emitting PTX ISA 8.4.

## 7.1. Finding Bugs in Production Kernels

We examine production kernels from 41 collection targets with Racer and identify 82 distinct bugs across 23 libraries:

Pipeline.

## 7.2. Comparison with Other Methods

We compare Racer with differential testing and two tools:
Volta (Driscoll et al., 2026), used as shipped, and
compute-sanitizer from NVIDIA (, 2026).
The comparison uses the set of 82 bugs found by Racer.

We assess an oracle differential tester with unlimited compute:
given a triggering launch configuration and an independent reference,
it tests every possible tensor input using a tolerance-based output
comparison. This is a per-bug assessment, not a measured testing campaign.
Sanitizer and Volta results come from recorded runs.
Figure 5 groups the results using the categories
of §6.

Figure 5. Comparison of Racer, oracle differential-testing, compute-sanitizer, and Volta on the 82-bug set.

Differential testing.
Under exhaustive input enumeration, differential testing can detect
all seven sampled-input bugs: it reaches the exact boundary values
and special inputs that random generators can miss. Together with the
40 bugs in Other identified by the audit, this gives 47 of 82 bugs. Exhausting tensor inputs does not by itself ensure variation of
prior memory state or thread schedules, inspection of writes outside
the output tensor, or detection of differences within the tolerance.
The remaining assessments retain the audit’s judgments under these
conditions; they do not establish that no concrete test can expose
those bugs.

compute-sanitizer.
The recorded runs detect 18 bugs:
four in implicit input, three in unchecked output, and eleven in Other.
Seven of the detections in Other are read-only overruns. These
results illustrate the value of checking memory accesses in addition
to comparing output values. None of these runs reports the four race bugs;
this result is specific to the configurations and executions evaluated.

Volta.
We run the shipped Volta baseline and it detects 9 bugs:
one in implicit input, two in unchecked output, and six in Other.
It detects none of the sampled-input or below-tolerance bugs,
and none of the four races.

The recorded failures identify concrete barriers to applying Volta
to these kernels. In 41 cases, unsupported instructions prevent
execution. One example is the Triton-distributed
reduction in §6: Volta stops at an atomic instruction
before it can expose the uninitialized-memory bug.

Another limitation arises when the two implementations divide work
differently across CTAs. In the FlagGems MSE-backward comparison,
the tested kernel writes four output cells in CTA 0, while the
reference writes one cell per CTA across four CTAs. Because Volta
compares only CTA 0 on each side, it encounters different sets of
written cells and cannot compare their values. Racer executes both
grids in full, allowing it to compare corresponding output cells
regardless of which CTA writes them. Three study cases encounter
this limitation in Volta. Four others require comparing programs
with multiple launches, which Volta does not support.

## 7.4. Shape Reduction vs. Whole-Grid Checking

We compare deciding each output cell independently (whole-grid
checking) with reusing proofs through shape reduction
(§5.1). We measure end-to-end wall-clock time,
including symbolic execution, deciding, and other engine stages.

Our sample contains 50 kernels: 40 with Equivalent verdicts at their
captured shapes and ten with bugs. We run each at its captured
shape ( $\times 1$ ) and at $\times 2$ and $\times 4$ , scaling one
selected dimension while keeping the others fixed. This gives
150 kernel–configuration pairs.

Shape reduction preserves every proof and refutation returned by
whole-grid checking: the methods agree on all 148
kernel–configuration pairs that both decide. Both decide all
50 kernels at $\times 1$ and $\times 2$ , and both refute all ten
bugs at every shape. At $\times 4$ , whole-grid checking decides
48 kernels and shape reduction decides 49; one kernel times out
under both methods. Thus, there are no contradictory verdicts,
and shape reduction proves one additional configuration within
the budget.

Shape reduction substantially reduces the cost of repeated proofs.
For the linear-attention backward kernel
chunk_ttt_linear_bwd_dv, it reduces end-to-end time
from 204.9 s to 17.4 s at $\times 1$ and from 415.8 s to
34.0 s at $\times 2$ , speedups of $11.8\times$ and $12.2\times$ .
At $\times 4$ , whole-grid checking exceeds 600 s without a
proof, whereas shape reduction proves equivalence in 70.7 s.
It uses only 16 representative proofs for 2,048, 4,096, and
8,192 output cells, respectively. A separate configuration of
this kernel, scaling a different shape dimension, shows the same
benefit: whole-grid checking again exceeds 600 s, while shape
reduction requires only 66.7 s.

Across the 40 equivalent kernels at $\times 1$ , shape reduction
lowers mean end-to-end time from 14.5 s to 6.0 s, an aggregate
speedup of $2.4\times$ . Aggregate speedup is the ratio of summed
end-to-end times over the same completed comparisons.
Table 3 follows the fixed set of 38 equivalent
kernels completed by both methods at every shape. It excludes
both kernels with timeouts from all three columns. Shape reduction
reduces their mean end-to-end cost by $1.72\times$ , $1.55\times$ ,
and $1.55\times$ , respectively. At $\times 4$ , mean deciding time
falls from 18.7 s to 2.1 s, while symbolic execution still takes
about 28 s under either method. Symbolic execution therefore
limits the end-to-end speedup even when proof reuse substantially

## 8. Related Work

Testing and property checking for GPU kernels.
Existing tools expose functional errors through testing or check specific
kernel properties.
NNSmith (Liu et al., 2023a), Tzer (Liu et al., 2022), and
NeuRI (Liu et al., 2023b) generate or mutate tensor programs to expose
compiler bugs. Differential output comparisons can reveal functional
errors, subject to the testing limitations discussed in §2.
cuFuzz (Tarek Ibn Ziad and Kozyrakis, 2026) uses coverage-guided fuzzing of CUDA
applications with sanitizer integration. NVIDIA’s
compute-sanitizer (, 2026)
checks memory accesses and synchronization during execution.
Race detectors include Barracuda (Eizenberg et al., 2017),
CURD (Peng et al., 2018), and ScoRD (Kamath et al., 2020);
Simulee (Wu et al., 2020) models
memory accesses to detect synchronization bugs.
PUG (Li and Gopalakrishnan, 2010), GPUVerify (Betts et al., 2012; Betts et al., 2015),
GKLEE (Li et al., 2012), and ESBMC-GPU (Pereira et al., 2016)
use symbolic execution or formal verification to check properties such as
race freedom and synchronization correctness within their supported
execution models and analysis bounds;
PUG and GKLEE also check functional assertions.
Model execution can provide input constraints for checking kernel memory safety.
M2K (He et al., 2026) checks CUDA memory safety under argument constraints
inferred from model execution, using symbolic tensor sizes and thread identifiers to cover
variable shapes and launch configurations.
Racer instead compares the functions computed by two programs at declared
tensor shapes and launch configurations, an equivalence question that
memory and synchronization checks alone do not resolve.

Program equivalence and translation validation.
Comparing program behavior provides a basis for validating compiler
transformations and alternative implementations.
Translation validation checks the correctness of individual compiler
transformations (Pnueli et al., 1998; Necula, 2000);
Alive2 (Lopes et al., 2021) provides bounded validation for LLVM.
Regression verification, SymDiff, and product programs reason about
relationships between programs (Godlin and Strichman, 2009; Lahiri et al., 2012; Barthe et al., 2011);
KLEE (Cadar et al., 2008) uses symbolic execution to cross-check
implementations along explored paths.
GPU-kernel equivalence additionally requires modeling communication and
synchronization among threads whose work assignments may differ between
implementations (§3.3).

Tensor-program verification.
Tensor-program verifiers reason about computations expressed in tensor
graphs or specialized languages.
At the tensor-graph level, TASO (Jia et al., 2019) and
TensorRight (Arora et al., 2025) prove rewrites correct under their
operator semantics.
TrainVerify (Lu et al., 2025) checks a distributed training plan
against its single-device specification. Its shape reduction shrinks
tensor shapes while preserving the equivalence question over the modeled
operators. Racer instead executes the compiled kernels and reuses an
output-cell proof only when a validated shared renaming relates both
programs’ expression pairs (§5.1).
Mirage (Wu et al., 2025) uses probabilistic equivalence verification
with formal guarantees over its representation of tensor programs at the
kernel, thread-block, and thread levels.
Ave (Mai et al., 2026) guides kernel optimization by checking data-flow
invariants expressed as symbolic tags and assertions in its tensor language,
and tests candidate kernels for functional correctness.
Racer compares symbolic output expressions derived from compiled PTX,
modeling the memory accesses and synchronization that implement the computation.

GPU-kernel equivalence checking.
Functional proofs can also connect CUDA kernels to high-level specifications.
ProofWright (Chatterjee et al., 2025) uses LLMs to generate VerCors
annotations for CUDA memory and thread safety, and combines Rocq proofs
with functional annotations to relate kernels to PyTorch specifications.
Its evaluated functional proofs cover a subclass of element-wise kernels;
the translation from Rocq specifications to VerCors annotations is
manually validated.

Volta (Driscoll et al., 2026) is the closest prior work, sharing Racer’s approach of
symbolically executing PTX over exact reals to check equivalence.
It provides an equality decision procedure for its
supported expression class. It also checks concurrency properties under
its structured-CTA model and rejects programs outside that model.
Racer compares complete output tensors across all CTAs and successive
launches, allowing the two implementations to partition work
differently. It also supports additional production PTX constructs
and reuses output-cell proofs through shape reduction.
