Abstract

Programmable Logic Controller (PLC) coding remains a manual, IDE-centric task that demands constant context switching between documentation, project files, and code editors. Recent work has demonstrated that retrieval-augmented large language models can generate vendor-compliant Structured Text at high compilation rates [1], yet these systems treat code generation as a one-shot pipeline: the engineer submits a query and receives code, with no persistent knowledge of the specific plant. We present a plant-aware conversational copilot that extends this paradigm in three directions: plant-specific context ingestion, a chat-first interaction model for explanation and debugging, and a graduated tool-access ladder from chat to deployment. The system is designed for real plant infrastructure and keeps the engineer in control of each step that produces real-world effects.

## I Introduction

Every production facility runs on control logic authored by automation engineers who navigate a demanding workflow: read the I/O specification, open the vendor IDE, locate the relevant function-block documentation, write Structured Text (ST) code, compile, fix errors, and repeat. Large language models have begun to reduce this friction. Prior work [1] demonstrated that a retrieval-augmented coding assistant for Mitsubishi Electric’s GX Works3 environment can generate vendor-compliant ST code at high compilation rates using only a structured knowledge base of function-block definitions and documentation excerpts, without exposing proprietary code to cloud providers.

Yet that earlier system operates as a pipeline. The engineer submits a natural-language task, the model generates code, and the compilation server validates it. There is no persistent knowledge of the specific plant, let alone an iterative dialogue, and no path from chat to deployment.

The gap we address is not code generation per se, but the engineering interaction model. A copilot that knows the plant-specific I/O list, labels, and existing program fragments can generate code that is immediately appropriate for the target namespace. Moreover, in our setting we find that agents often only write correct code when they know the real-world setup of the plant. Together, these aspects form the difference between a generic coding tool and an engineering companion.
Unlike generic copilots (e.g., GitHub Copilot on a CODESYS MCP server), our contribution is not the chat mechanism itself but its coupling with plant-specific context retrieval and a domain-tailored, safety-graduated tool ladder.

## II Related Work

LLM-based PLC code generation. One line of work establishes iterative generation pipelines: a user-guided approach combines compiler, grammar-checker, and formal verification feedback, raising ST generation success on a manufacturing testbed from 47% to 72% [2]. A fully automated multi-agent successor adds RAG and Chain-of-Thought planning with dedicated syntax and verification agents; on a benchmark of 23 programming tasks (16 easy, 7 medium), the framework achieves a verifiable rate of 68% on easy tasks and 42.3% on medium tasks with GPT-4o [3]. A vendor-aware framework targets ST fragmentation across two proprietary platforms with a four-stage pipeline (planning, case retrieval, API recommendation, IDE-guided validation), reporting high compilation pass rates on a large benchmark at low average per-task cost [4]. A complementary fine-tuning direction applies iterative online Direct Preference Optimization, using compiler feedback and a specialist LLM as synthetic annotators to construct preference pairs without manual labelling [7]; a separate system extends generation beyond ST to Sequential Function Charts, achieving 75–94% syntactically valid output [8].

LLM-based DCS engineering. A series of incremental contributions culminating in Spec2Control established a complete LLM workflow for Distributed Control System (DCS) control logic: an initial study evaluated LLM capabilities across 100 PLC/DCS prompts in ten categories [9]; a follow-up integrated vendor function-block libraries via RAG [10]; a third variant generated code from P&ID diagrams using vision-capable models [11]. Spec2Control presents an end-to-end LLM workflow to generate graphical IEC 61131-3 Function Block Diagrams directly from natural-language control narratives and deploy them to an automation controller [5]. It produces FBDs from proprietary ABB libraries and achieves 98.6% correct strategy connections across 65 test cases from 10 narratives, with a 94–96% reduction in engineering effort [5]. The key distinction from our work is the interaction model: Spec2Control is a batch workflow in which the engineer is consulted at low-confidence steps, whereas our system is conversational-first and leaves each tool action to explicit engineer initiation.

Commercial engineering copilots. Several vendors have shipped conversational code assistance integrated into their proprietary IDEs [6, 12, 13], showing that major automation vendors are productizing this paradigm in commercial tools. These products lack controlled evaluation datasets; Spec2Control characterises them as targeting textual notations with limited automation support [5].

Human-in-the-loop and graduated autonomy. HITL patterns for LLM agents are well established in orchestration frameworks [14, 15], where agents pause before high-stakes tool calls pending explicit approval; human-guided development workflows following this pattern have been deployed in production software engineering [16]. Recent work formalises agent autonomy as a five-level spectrum of user roles—from full operator control to passive observation—providing a principled vocabulary for autonomy-level design [17]. Our contribution applies this design pattern to the industrial PLC domain, where an uncontrolled LLM-to-hardware action can cause physical damage and production downtime.

Evaluation methodology. Existing work measures primarily compilation success and formal verification rates [2, 3, 4]; Spec2Control adds GQM-structured quality and effort metrics [5]. For conversational copilots, however, metrics capturing interaction efficiency (turns to task completion), error distribution by correction cause, and cognitive load remain absent—gaps that our planned evaluation aims to address.

## III System Design

The system extends the RAG-enhanced compilation architecture from [1] with three new layers: a persistent plant-context retrieval segment, a conversational interaction model, and a graduated tool-access mechanism.

## III-A Conversational Engineering Interface

The copilot presents a persistent, multi-turn chat interface. Unlike the single-query model of [1], the engineer can engage in extended dialogue: asking the system to explain an existing program fragment, identify potential interlock conflicts, discuss design alternatives, or propose modifications before any code is generated.

Fig. 1: The prototype web application used to control generation, compilation, and plant-aware context. The left panel exposes generation settings and MCP actions, while the main pane shows the conversation and generated ST code.

Figure 1 shows the web application that orchestrates the generation workflow, the plant context toggle, and the manual compile and deployment actions.

Code generation is explicitly request-triggered.
When the engineer asks for code, the model draws on all context layers; in subsequent turns the engineer can ask for modifications, and the model maintains the generated program as a shared artefact in the conversation.

## III-B Plant Context Integration

We define plant-awareness as the system’s ability to ground generated code in the target plant’s I/O list,
label namespace, module configuration, and physical signal topology.
The key architectural addition over [1] is a dedicated plant-context retrieval segment.
On project initialization, the engineer provides:

• 

I/O list: signal names, addresses, data types, and descriptions for all inputs and outputs.

• 

Device labels: the complete GX Works3 label table, including internal variables and inter-program signals.

• 

Module configuration: rack layout, CPU type, and special-function module assignments.

• 

Existing program fragments: current ST programs and function-block instances already deployed on the plant.

These materials are chunked, embedded, and indexed in a dedicated plant-context retriever,
separate from the general function-block and specification retrievers established in [1].
At query time, a four-retriever strategy is used: library definitions, specification rules, general context, and plant-specific context.
Hence, similarity search operates within homogeneous chunk spaces and avoids cross-source interference.

## III-C Graduated Tool Access

Safety in industrial environments demands that LLM-generated artefacts are never silently applied to running machinery.
The copilot enforces four explicit levels of tool access:

• 

Level 1 – Advisory: text only, no tool call.

• 

Level 2 – Code generation: code is displayed in the chat interface on explicit request.

• 

Level 3 – Compilation: the engineer triggers the compilation server and receives structured diagnostics.

• 

Level 4 – Deployment: the engineer explicitly confirms deployment to the PLC.

Each level transition produces real-world effects of increasing consequence.
The graduated structure ensures that advisory interactions carry no risk of unintended hardware modification.

## IV Demonstration and Preliminary Results

Fig. 3: Demonstration plant setup at a research test facility providing metal discs in different colors, inserts, sensors, and actuators for sorting them. The plant is equipped with a Mitsubishi Electric iQ-R series CPU (model R04).

## IV-A Setup

Figure 3 shows the physical setup used in the demonstration.
The demonstration plant is a sorting machine that, based on air pressure and light sensors, can push metal discs of different colors onto a conveyor belt. The colors are chrome, red and black. Since these colors reflect differing amounts of light, the sensors can be configured to detect them with different thresholds.
Another actuator with sensors can put inserts into the discs. Users may configure their own sorting app that configures a mixture of colored discs with or without inserts using AI. The plant can thus be reconfigured based on users’ current needs. The prototype may serve as a demonstration for more complex plants, e.g., in the automotive industry.

The demo setup uses a conveyor belt that transports discs to the right where, having passed all magazines, they are sorted into three boxes.
Chrome, as the most reflective color, comes first, followed by red and black.
Chrome and red are actively sorted by a pneumatic cylinder that pushes them off the belt, while black discs are passively sorted by gravity.
In Fig. 3, the plant is pushing red off the conveyor belt.

The plant is equipped with a Mitsubishi Electric iQ-R series CPU programmed via a prototype web interface and GX Works3. Plant context was ingested as an I/O list, a label table, and existing ST program fragments. Moreover, the actual plant setup had to be explained to the model, since the I/O list and labels alone do not capture the physical layout and signal semantics. That is, the model had to be informed where magazines are, when they are loaded (i. e. the corresponding sensor must be triggered as TRUE) and that the discs are pushed on a conveyor belt to the right, where actuators in a certain order are situated.

## IV-B Example Interaction Trace

The following excerpt shows the intended interaction pattern for plant-aware code generation and validation.

Engineer: Are there blue discs available?

Copilot (Advisory – L1): No. The plant context defines only chrome, red, and black discs. There is no blue disc magazine, sensor, or sorting path.

Engineer: Generate the sequence red, red with insert, chrome, black with insert, chrome.

Copilot (Code gen – L2): The generated Structured Text uses the plant’s actual labels and control flow, including the black-disc branch gated by BLACK_MAG_FUELLSTAND and INSERT_MAG_FUELLSTAND.

Engineer: [Triggers compilation]

Copilot (Compile – L3): GX Works3 compilation successful.

Engineer: Can the black disc also receive an insert?

Copilot (Code gen – L2): Yes. The same insert-station logic applies to the black disc before it continues on the black path. Code: …

Engineer: [Triggers compilation]

Copilot (Compile – L3): GX Works3 compilation successful.

Engineer: [Triggers deployment to PLC, chooses to delete latches and variable status; Starts PLC run]

Copilot (Deploy – L4): Code deployed to PLC. The plant is now executing the new sequence. See Fig. 3.

## V Discussion & Conclusion

This paper presented a plant-aware conversational copilot for PLC engineering that extends the RAG-enhanced code generation architecture of prior work [1] with persistent plant-context ingestion, a chat-first multi-turn interaction model, and a graduated tool-access ladder from chat to deployment. By retrieving plant-specific signal names at query time, the copilot is intended to generate code that is more appropriate for the target plant’s namespace. A structured quantitative evaluation comparing plant-aware and generic-context generation on matched task sets is planned.

Limitations include that the current system is demonstrated on a single plant within Mitsubishi Electric’s iQ-R ecosystem. Cross-vendor generalizability is not in the scope. An evaluation methodology should capture functional correctness, which requires hardware-in-the-loop testing or domain-expert review beyond compilation success. Human evaluation from a single organizational context may limit generalizability.

Future Work includes (A) execution feedback connecting PLC runtime signals and the copilot context,
(B) multi-PLC orchestration for cross-controller installations,
(C) graphical IEC 61131-3 extensions for Ladder diagram generation and legacy AWL code, and (D) a quantitative evaluation across multiple industrial-size plants with plant-awareness metrics.
