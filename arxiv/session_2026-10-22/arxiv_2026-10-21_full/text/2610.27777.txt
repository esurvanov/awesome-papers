Abstract

Tool-using LLM agents increasingly answer e-commerce queries through multi-step tool interactions. The expected output of a tool call can shift between agent development and execution, allowing a plausible but incorrect value to be returned without an explicit failure signal.
These silent errors may propagate through subsequent decisions into final answers.
To study agents’ resilience across this end-to-end process, we formulate Silent-error Resilience Task, an interactive task that evaluates whether they complete the original query after a silent error corrupts an intermediate state.
We introduce RITE, a benchmark built from human-authored industrial workflows and production-log-derived inputs. To enable controlled and reproducible evaluation, we use a semantic error taxonomy to inject errors into fixed workflow prefixes, freeze recorded tool behavior, and let agents continue freely.
It contains 167 matched units across nine e-commerce workflows, yielding 501 silent-error, correct-value, and explicit-failure instances.
Across 10 recent LLMs, silent errors roughly halve task success and are consistently harder than explicit failures. Recognition, use of an available verification path, and integration of the resulting evidence form successive bottlenecks.
We also propose a light State Checker as an intervention to test whether resilience can be improved.

## 1 Introduction

Agentic LLM systems increasingly complete e-commerce tasks through multi-step workflows that invoke multiple external tools and pass their outputs from one step to the next.
In industrial deployments, a tool’s runtime output may differ from what the agent was built to expect because underlying business data, tool implementations, or deployed versions can change between development and execution.
This build-time–runtime mismatch can remain hidden: a call may complete and conform to the expected API schema while returning a plausible value that is incorrect for the current task.
We refer to such plausible-but-wrong intermediate values without an explicit failure signal as silent errors.
For example, suppose a user mainly watches local football videos, one of which mentions blockchain-based fan tokens. During agent development, the profile tool returns “local sports”; after an update that overweights “blockchain,” it returns “blockchain” at execution. The new label remains plausible and schema-valid, so no failure is signaled.
The absence of an explicit failure signal makes silent errors particularly severe: an agent may have no immediate basis for detecting that the value is incorrect. It may therefore propagate the corrupted value through subsequent tool calls, allowing a single intermediate error to directly alter the final user-facing output.

Existing benchmarks evaluate tool use in nominal settings (Qin et al., 2024; Trivedi et al., 2024; Ma et al., 2024), recovery from explicit or implicit faults injected while agents run (Zhu et al., 2026; Tian et al., 2026; Chen et al., 2026), silent-error detection (Sun et al., 2024; Mazumder and jahan Lia, 2026), or how corrupted intermediate values affect later outputs (Gurram, 2026).
In these fault-based settings, each agent runs freely and meets a fault only if and when its own trajectory reaches the perturbed call, so different agents face silent errors at different points and with different histories. They therefore cannot compare different agents on the same silent error at the same decision point, nor pair that error with correct-value and explicit-failure counterparts at that point.

To address this gap, we formulate Silent-error Resilience Task, in which a plausible but incorrect tool result enters an agent’s execution history without an explicit failure signal.
Given the query and toolbox, the agent operates in an agentic loop, repeatedly reasoning, calling tools that may return silent errors, and incorporating their outputs until it produces a final answer.
The task asks whether the agent can recognize the error, reacquire reliable evidence, and complete the original query instead of propagating the error into its final answer.

To evaluate this task under controlled conditions, we introduce RITE (Resilience to Incorrect Tool Evidence).
Each human-authored workflow specifies a pre-orchestrated agentic process, and its execution log records tool calls and observations in the same format as an agent trajectory. We use this log as a fixed trajectory, allowing us to control where a silent error is introduced.
We select a semantically important slot in the log and inject a silent error at that point.
The trajectory up to and including this slot is provided as the agent’s prefix, while the workflow’s tools and their recorded input–output behavior are frozen to form the evaluation world, so that recorded calls return identical outputs across models and conditions.
The agent then continues in an agentic loop, allowing us to compare its behavior while controlling for error type, slot, and environment.

Following this protocol, we first construct a semantic taxonomy covering errors in object or category selection and in attributes or values.
We sample inputs from the production logs of one internal platform and use them to run workflows deployed on a separate internal platform.
From the resulting traces, we select task-relevant checkpoints and instantiate taxonomy-guided plausible but incorrect values.
Each resulting unit contains matched prefixes for the silent-error, correct-value, and explicit-failure conditions, all paired with the same evaluation world. RITE contains 167 matched units from nine e-commerce workflows, yielding 501 instances.

We evaluate 10 recent closed and open-weight LLMs on RITE. Across all models, silent errors reduce task success to roughly half of correct-condition performance and are consistently harder to handle than matched explicit failures. Our analysis traces this weakness through a three-stage chain: agents often fail to recognize that an inherited value may be wrong; recognition does not reliably lead them to refetch its source; and refetching does not guarantee that the corrected value is carried through to final recovery. We further find that most benchmark corruptions would change the downstream e-commerce task output, with damage varying substantially by error type and workflow position. Finally, a lightweight State Checker makes agents notice and refetch more often but yields only limited improvement in final task success. Making agents look is therefore easier than making them repair what they find. In summary, our contributions are:

• 

Task formulation. We formulate Silent-error Resilience Task as an interactive agentic task for studying resilience to silent errors throughout the query-to-answer process. It evaluates whether an agent can recognize an unreliable tool result, reacquire trustworthy evidence, and still produce a correct final answer rather than propagate the error downstream.

• 

Benchmark construction. We introduce RITE, which replays a human-authored workflow execution up to a selected point, returns a correct, silently incorrect, or explicitly failed result there, and lets the agent continue freely. Using inputs sampled from one internal platform’s production logs, workflows deployed on another, and a semantic error taxonomy, we construct 167 matched units across nine e-commerce workflows, comprising 501 silent-error, correct-value, and explicit-failure instances.

• 

Empirical analysis. Across 10 LLMs, silent errors roughly halve task success. We identify recognition, producer refetch, and recovery as successive failure points, characterize effects by error type and position, and propose a lightweight State Checker as an intervention to test whether resilience can be improved.

## 2 Related Work

## Tool-use and agent evaluation.

Agent evaluation spans three levels.
At the tool-call level, MetaTool (Huang et al., 2024b) asks whether a tool is needed and which one to select, while ToolBench, BFCL, and API-Bank (Qin et al., 2024; Patil et al., 2025; Li et al., 2023) evaluate call construction and extend to multi-tool, dependent, and stateful multi-turn interactions; ToolACE (Liu et al., 2025) provides synthesized data for improving these abilities.
At the task-outcome level, AppWorld, GAIA, and WebArena (Trivedi et al., 2024; Mialon et al., 2024; Zhou et al., 2024) judge a complete rollout by its final answer or by the state it leaves in the environment, while allowing different valid action paths.
At the process level, AgentBoard (Ma et al., 2024) tracks task progress, WorFBench (Qiao et al., 2025) evaluates generated workflow structure, ToolScan (Kokane et al., 2025) diagnoses call-level errors, and process-mining methods (van der Aalst, 2016) compare executed and expected flows.
Across these levels, the benchmarks above vary task difficulty and agent behavior but do not systematically manipulate the semantic correctness of intermediate tool values.
We instead vary the intermediate business value and ask whether an agent can still complete the task correctly when that value is wrong. To keep the test controlled and reproducible, we provide the recorded workflow execution up to the selected checkpoint as the agent’s initial history, then let it continue freely.

## Tool-failure recovery, silent-error detection, and error propagation.

Work on unreliable tools can be separated by the stage of the error-handling chain that it evaluates.
One line studies recovery from tool failures: agents resume from the environment left by a failed attempt (Tan et al., 2025), rewind to an earlier checkpoint (Zhuang et al., 2026), recover from explicit or implicit faults injected into tool responses while the agent runs (Zhu et al., 2026; Tian et al., 2026; Chen et al., 2026), or diagnose failed trajectories and characterize recovery cost (Vuddanti and Chittiprolu, 2026; Zhu et al., 2025; Zhang et al., 2026).
Resumption settings start from uncontrolled natural failures, while injection settings expose an agent to a fault only if and when its own trajectory reaches the perturbed call.
A second line studies silent-error detection, asking whether agents identify faulty outputs that trigger no exception (Sun et al., 2024) or silent data-quality faults introduced during controlled replay (Mazumder and jahan Lia, 2026).
In both, the faulty response is delivered when the agent’s own run issues the corresponding call.
A third line studies error propagation, tracing a schema-valid but semantically wrong argument to the final answer (Gurram, 2026) and measuring how perturbed requests or tool responses alter later calls and task outcomes (Xiong et al., 2025; Wang et al., 2026b).
To our knowledge, RITE is the first benchmark to evaluate business-semantic silent errors at controlled decision points: every agent encounters the same plausible but incorrect value after the same recorded execution history, the same point is also instantiated with the correct value and with an explicit failure, and the agent then continues freely to a final answer.

## E-commerce and business-domain agents.

Work in this domain spans three forms of capability.
Domain models test whether a model understands products and users well enough to answer questions (Peng et al., 2024), while recommender agents use that understanding to retrieve, rank, and recommend products (Gao et al., 2023; Huang et al., 2024a).
Shopping benchmarks place agents in interactive stores, where they must search, compare, and purchase while satisfying constraints on products, vouchers, budgets, and sellers (Yao et al., 2023; Wang et al., 2026a).
Business-service benchmarks require agents to interact with users over multiple turns, operate on business records through tools, and comply with domain policies (Yao et al., 2025; Wang et al., 2025), while CRMArena-Pro additionally tests confidentiality in enterprise workflows (Huang et al., 2026).
These benchmarks do not systematically test what happens when a task-critical business value is silently corrupted.
Grounded in production execution logs and human-authored industrial e-commerce workflows, our benchmark instead examines this reliability risk involving tools developed and maintained by multiple parties: a call may complete while an intermediate business value is silently wrong.

## 3 Problem Formulation

We study whether an agent can remain reliable when a tool silently returns an incorrect result and still complete the original task. We first formulate this end-to-end resilience as Silent-error Resilience Task, then define how RITE evaluates it in this section.

## Silent-error Resilience Task.

In a standard agentic task, an agent $A$ receives a task query $q$ and repeatedly selects and executes tool calls from a tool set $\mathcal{T}$ provided by an environment $E$ .
The interaction begins without a preloaded execution history, i.e., $h_{0}^{\mathrm{std}}=\varnothing$ . At each step $t$ , the agent observes the current history $h_{t}$ and selects an action $a_{t}$ . The environment executes the action and returns an observation $o_{t}$ , which is appended to the history:

 $a_{t}=A(q,h_{t},\mathcal{T}),\qquad o_{t}=E(a_{t}),\qquad h_{t+1}=h_{t}\oplus(a_{t},o_{t}).$ 

(1)

The standard action set is $\mathcal{A}_{0}=\{\text{call},\text{reason},\text{stop}\}$ . The interaction ends when the agent stops or reaches the step budget, producing a final answer.

Figure 1: Silent errors from build-time–runtime mismatch. Tool-side data or implementation changes can make a runtime result diverge from what the agent was built to expect while signaling no failure.

As illustrated in Figure 1, the standard loop does not guarantee that a returned observation is semantically correct. In deployed systems, changes to business data, tool implementations, or deployed versions can cause runtime results to diverge from the expectations under which the agent was built.
A call may still complete and conform to its API contract while returning a result that is incorrect for $q$ .
At a tool-call step $j$ , let $o_{j}^{\star}$ denote the task-correct result and $\tilde{o}_{j}$ the result actually returned by the tool.
A silent error occurs when $\tilde{o}_{j}$ differs from $o_{j}^{\star}$ in task-relevant meaning but remains plausible, schema-valid, and free of an explicit failure signal.
Because the ordinary update rule still appends $(a_{j},\tilde{o}_{j})$ to the history, subsequent actions condition on unreliable evidence and may propagate it into the final answer.

The Silent-error Resilience Task measures whether the agent can still complete $q$ after such a result has entered its execution history.
Process measures track whether the agent recognizes the unreliable result, reacquires trustworthy evidence, and integrates that evidence into a correct final answer.
The agent retains $\mathcal{A}_{0}$ and may reason from the current state, revisit or reissue an earlier tool call, seek corroborating evidence, or pursue another continuation.

## Benchmark evaluation.

For each benchmark unit $i$ , RITE constructs three matched instances $D_{i}^{k}=(q_{i},p_{i}^{k},c_{i})$ for $k\in\{\mathrm{correct},\mathrm{implicit},\mathrm{explicit}\}$ . The instances share the query $q_{i}$ , result constraint $c_{i}$ , and continuation environment $E_{i}$ , keeping the user task, required result, and available recovery paths fixed. They differ only in the affected evidence in $p_{i}^{k}$ : the correct condition provides the recorded value as a baseline, the implicit condition provides a silently incorrect value, and the explicit condition provides an overt failure to expose the effect of a visible failure signal.

For each condition, RITE initializes the agent with $h_{0,i}^{k}=p_{i}^{k}$ and provides $q_{i}$ as the task query. Starting from the matched checkpoint controls variation in the preceding execution, while free continuation in $E_{i}$ with the standard action set $\mathcal{A}_{0}$ lets the agent choose its own recovery path. The run ends when the agent stops or reaches the step budget.
Let $\hat{r}_{i}^{k}$ denote the agent-generated continuation, which ends with a final answer $y_{i}^{k}$ ; the complete trace is
 $r_{i}^{k}=p_{i}^{k}\oplus\hat{r}_{i}^{k}$ .

We use three evaluation measures. Noticed records whether the agent explicitly identifies a content or result anomaly and takes a related remedial action. Result Success Rate (RSR) records whether $y_{i}^{k}$ resolves $q_{i}$ , capturing end-to-end task success. Retention, the ratio of implicit-condition RSR to correct-condition RSR, reports how much baseline performance is preserved under silent errors.

## 4 Benchmark Construction and Evaluation Environment

Each human-authored workflow specifies a pre-orchestrated agentic process. Its execution produces a controlled trace of tool calls and observations in the same format as an agent rollout.
We use this trace to construct matched prefixes that share the preceding history and differ only in selected intermediate evidence; all prefixes are paired with the same continuation environment.
This section first describes the data sources and silent-error taxonomy, then explains how each clean trace yields paired benchmark instances $D_{i}^{k}$ and an evaluation environment $E_{i}$ , and reports its distribution.

## 4.1 Data Sources and Silent-Error Taxonomy

## Data sources.

Benchmark construction begins with two source collections.
The first is the workflow collection $\mathcal{W}$ , drawn from human-authored e-commerce workflows already deployed and running on an internal industrial workflow platform.
We screen these existing workflows for structural validity and task diversity, yielding nine golden workflows with explicit control flow and deterministic tool dependencies.
The second source is the input collection $\mathcal{X}$ from a separate internal e-commerce data platform. Candidate production-log records are mapped to workflow inputs and selected only when their executions yield complete traces with task-relevant intervention points; the corresponding traces are retained. Appendix A defines the workflow- and log-selection criteria.

## Taxonomy definition.

We constructed the silent-error taxonomy through a targeted, literature-grounded synthesis of adjacent error and failure taxonomies. We selected studies whose source categories could clarify the boundary of a silent state corruption or be operationalized as schema-valid, plausible-but-wrong workflow values. For each relevant source category, two authors independently assessed its observable error signal, workflow locus, and suitability for conversion into a single-slot implicit perturbation. They then reconciled overlapping categories and clarified the resulting boundaries.
The final taxonomy contains seven leaf types organized into two semantic groups.
Object or category selection errors cover substitution with a same-level category (category sibling drift), an ancestor or descendant (category granularity mismatch), or a similar but incorrect real entity (entity near-duplicate).
Attribute or value errors cover changes to an entity’s attribute (profile attribute drift), movement to a neighboring valid numeric range (numeric bucket shift), superficially similar text with a different business meaning (semantic synonym drift), and reuse of a formerly valid but outdated value (temporal staleness).
The benchmark instantiates every leaf type except temporal staleness. Although a stale value can be schema-valid and lead to an incorrect answer, recognizing that it is stale requires prior or time-indexed evidence that the agent does not observe. Appendix B provides the complete definitions, category boundaries, and literature grounding.

## 4.2 Benchmark Infrastructure Construction

The infrastructure has a shared start followed by two sibling construction branches:

 $(W_{i},x_{i})\longmapsto\tau_{i},\qquad\tau_{i}\longmapsto D_{i}^{k}=(q_{i},p_{i}^{k},c_{i}),\qquad(W_{i},\tau_{i})\longmapsto E_{i}.$ 

The data branch constructs the paired prefixes initializing an agent, whereas the environment branch independently constructs the world where the agent continues acting (Fig. 2).

Figure 2: RITE benchmark construction and rollout pipeline. A workflow $W_{i}$ and paired log-derived input $x_{i}$ are used to activate a side-effect-free workflow replica and reconstruct a clean trace $\tau_{i}$ . A task-relevant slot then yields a shared query and result oracle together with three matched prefixes (correct, explicit, and implicit). The workflow and clean trace define the fixed evaluation environment $E_{i}$ , in which the evaluated LLM continues from each prefix to produce a complete rollout.

## Workflow trace reconstruction.

To avoid polluting the internal platform data, which may record the workflow execution result, we first post-process every selected workflow into a deployable replica by mocking out reporting and other side-effecting nodes and deploy the modified workflow back onto the platform.
Then, a local central controller connects the log and workflow to provide an execution trace. It initially maps the production log record to the start schema of the deployed replica, producing the input $x_{i}$ . It then invokes the deployed workflow through the platform API with $x_{i}$ and retrieves the full execution trace of that run, which records every executed node with its arguments, outputs, status, and data dependencies.
We retain only executions that complete successfully and contain full information needed to reconstruct the workflow state.
The retained $\tau_{i}$ is therefore the clean execution record shared by the two downstream branches.

## Paired prefix construction.

Slot selection.
We align the workflow graph with $\tau_{i}$ and obtain an execution graph whose edges carry the values propagated between nodes. We then search this graph along
 $\text{producer}\rightarrow s_{i}\rightarrow\text{consumer}\rightarrow\text{downstream result}$ : an intermediate slot $s_{i}$ qualifies when it carries business-relevant content, is consumed downstream, and plausibly affects the task outcome. For each retained slot, we record its producer and consumer and determine the locus at which the intervention is realized, either in the producer observation (tool_output) or in a downstream tool argument (tool_input). A single execution yields multiple such slots, and each retained slot defines one task through the prefix built around it.

Task construction.
This stage converts each retained slot into a task including the task query and corresponding three paired prefixes.

(i) 

Three conditions at the same slot. We truncate the common trace at the same slot and render the three prefixes $p_{i}^{\mathrm{correct}}$ , $p_{i}^{\mathrm{explicit}}$ , and $p_{i}^{\mathrm{implicit}}$ (Sec. 3), with neutral historical rationales and no corruption marker.
The correct condition preserves the recorded value.
The explicit condition replaces access to that value with an overt failure, such as an empty argument or an error-bearing observation.
The implicit condition obtains its value in two steps. First, it selects an applicable error type from the taxonomy and constructs a substitute that is type- and schema-compatible, remains locally plausible, and changes the task-relevant meaning of the slot. Depending on the error type and carrier, candidates come from compatible values observed in other cases or from a type-specific controlled transformation. Second, the selected substitute is written into the slot at its predetermined locus: the producer observation under tool_output, or a downstream tool argument under tool_input.

(ii) 

Query and oracle. From the clean trace, we extract the correct value of $s_{i}$ and construct the result constraint $c_{i}$ that a correct final answer must satisfy.
We then generate or refine $q_{i}$ so that it is designed to depend on this value: answers grounded in the gold and polluted values should be distinguishable under $c_{i}$ .

Verification.
Before delivery, each candidate must preserve prefix executability and structural compatibility. Four additional gates then check the intervention itself. (1) Plausibility. The implicit value must remain schema-valid and locally reasonable while differing from the recorded value in task-relevant meaning. (2) Explicit-failure clarity. The explicit condition must expose an unambiguous failure signal. (3) Non-leakage. Neither the query nor the prefix may reveal that an intervention was applied. (4) Discriminability. The query remains solvable, and answers grounded in the gold value and in the polluted value must remain distinguishable under $c_{i}$ . The surviving artifacts are delivered in the formulation’s schema $D_{i}^{k}=(q_{i},p_{i}^{k},c_{i})$ , with all three conditions sharing the same query and result constraint.
Providing every model with the same recorded execution before the affected value deliberately reduces variation in reaching that point, so the matched conditions focus on how agents handle the evidence they receive there.

## Evaluation environment construction.

In parallel with prefix construction, we extract the callable tool set $\mathcal{T}_{i}$ from $W_{i}$ and build one replay world $R_{i}$ for that workflow by integrating the recorded responses of all collected traces.

 $(W_{i},\tau_{i})\longmapsto E_{i}(a_{t})=\begin{cases}R_{i}(a_{t}),&a_{t}\in\operatorname{dom}(R_{i}),\\
\operatorname{Live}_{\mathcal{T}_{i}}(a_{t}),&\text{otherwise}.\end{cases}$ 

(2)

Under this interface, a covered call returns the recorded response from $R_{i}$ , while an unseen valid call is dispatched to the live implementation in $\mathcal{T}_{i}$ deployed on the internal industrial workflow platform.
RITE changes only the condition-specific prefix, not $E_{i}$ ; because the replay world is built from the clean trace, re-querying a recorded producer returns the corresponding unpolluted response, giving the agent a direct path to recover reliable evidence and produce a correct final answer.
Every instance is therefore recoverable by design, isolating whether agents use an available verification path; faults that persist across re-queries are discussed in Appendix G.

## 4.3 Dataset Statistics

The final RITE release contains 167 paired units, each defined by a unique slot–locus pair and expanded into correct, explicit, and implicit conditions. This yields 501 instances, with 167 instances per condition and complete triplets throughout. Nine workflows contribute data, and the release covers six of the seven taxonomy error types because temporal staleness has no retained instance. Of the 167 units, 147 intervene at tool_output; the remaining 20 intervene at tool_input. Detailed distributions are reported in Appendix F.

## 5 Experiments

We evaluate 10 recent LLMs in three groups: two closed frontier models (Claude-Opus-4.8 and GPT-5.5), five open-weight frontier models (GLM-5.2, Kimi-K3, DeepSeek-V4-Pro, Hy3, and Qwen3.5-397B), and three smaller open-weight models (Qwen3.6-35B, Qwen3.5-35B, and Qwen3.5-122B). Each model runs all 501 instances at temperature 0 with a 25-step budget. Rollouts invalidated by environment-side tool anomalies are excluded. The evaluation environment follows Section 4.2, and the rollout and judging protocol is detailed in Appendix C, and a human validation of the Result and Noticed labels is reported in Appendix D. Following Section 3, we report condition-specific RSR and Noticed, Retention, and the paired gap: the paired explicit-minus-implicit RSR difference over slots observed in both conditions.

## F1: Silent errors substantially degrade task performance across models.

Across all ten models, implicit errors reduce RSR from 0.716–0.827 in the correct condition to 0.277–0.403, yielding Retention of only 0.345–0.526 (Table 1).
This loss is tied to the absence of an observable failure signal: when the corresponding failure is explicit, RSR rises to 0.507–0.564, producing a positive explicit-minus-implicit paired gap for every model (+0.089 to +0.265; +0.214 pooled).
Stronger task performance does not eliminate this vulnerability. Correct-condition RSR spans only 0.111 across models, whereas Retention spans 0.182; closed frontier models have higher mean Retention than open-weight models (0.517 versus 0.391), yet even the best model preserves barely half of its correct-condition performance. Thus, susceptibility to silent errors is widespread rather than confined to models with weak baseline task ability.

Across models, implicit-condition Noticed ranges only from 0.208 to 0.336 (Table 1), so most silent errors go unrecognized. Table 2 shows that recognition helps but is not sufficient: the latest producer observation matches the gold value in 0.3% of Unnoticed rollouts and 23.3% of Noticed rollouts, while 57.8% of Noticed rollouts still match the polluted value.
To examine whether recognition leads to active verification, we track producer refetch, defined as re-invoking the tool that produced the affected value. Among scored Noticed rollouts, RSR is 0.387 without a producer refetch and 0.655 with one.
GLM-5.2 illustrates this gap: its Noticed rate is 0.217, but its producer-refetch rate is only 0.071 and its Retention is the lowest at 0.345. Across the eight open-weight models, producer-refetch rate is positively but not significantly associated with Retention ( $r=0.491$ , $p=0.217$ ). These results identify two bottlenecks: models rarely notice silent errors, and noticing one often does not lead to refetching its source.

## F3: Producer refetch does not ensure recovery.

To test whether producer refetch restores the correct evidence, the state judge compares the latest valid producer observation with the gold and polluted values. Among the 147 implicit-condition rollouts with a producer refetch, 87 (59.2%) match the gold value and 60 (40.8%) match neither value; none match the polluted value. Of the 87 matches, 85 are obtained in one re-query and the remaining two require multiple rounds.
Among Noticed rollouts with a producer refetch, about one third still fail the task (RSR 0.655; F2).

To understand why refetching does not ensure recovery, we manually inspect the 60 trajectories that did not match value, focusing on unsolved rollouts in which the re-query nonetheless returns usable evidence. After usable evidence is acquired, we identify three recurring patterns. First, reasoning overwrite occurs when a model initially uses recovered evidence but later replaces it with a self-imposed heuristic. In one trajectory, an agent reconstructs the correct timestamps and uses them in the next RPC call, but then redefines the “opening warm-up” boundary and selects the wrong final comment.
Second, lossy selection occurs when a model alters recovered candidates while choosing among them. One agent merges two recovered topic clusters despite an instruction to select one, while another replaces the retrieved topic with a plausible but unsupported reformulation. Third, unsupported synthesis occurs when a model uses corrected evidence but adds claims absent from it. Agents incorporate corrected profile or interest labels but add unsupported viewing-duration, interaction, or presentation claims.
Across these patterns, usable evidence is obtained, but the correction does not carry through to the final answer.

## 6 Discussion

The main results separate silent-error handling into recognition, use of an available verification path, and integration of the resulting evidence into final recovery. This section asks three follow-up questions: whether the resulting performance loss corresponds to changed e-commerce task outputs (D1), where the vulnerability concentrates (D2), and how far a light check can go (D3).

## D2: Damage concentrates by error type and slot position.

Damage varies across both silent-error types and slot positions: it is greatest for category errors (Table 4(a)) and for slots that occur early in the workflow trace (Table 4(b)).

Error type. Category errors are the most damaging error types in RITE: category granularity mismatch is hardest, category sibling drift is next, and numeric bucket shift is most noticeable but remains destructive (Table 4(a). One possible explanation is that in the benchmark’s recoverable environment, a wrong number or ID is checked against the producer response, whereas a wrong category appears anomalous only in context. For example, identifying “blockchain” as an implausible interest requires knowing the user watches local sports; the category value alone carries no anomaly.

Slot position. Early slots have the highest Noticed rate (0.264) but the lowest implicit-condition RSR (0.309) and Retention (0.399; Table 4(b)). One plausible explanation is that an early checkpoint yields a shorter prefix with fewer inherited observations, making its corruption easier to notice. ## D3: A lightweight intervention for handling silent errors.

F2 shows that blind trust in inherited tool results is the dominant failure pattern, suggesting an additional reliability check during execution.
We test State Checker, which asks the model to treat every tool result as potentially unreliable and, before using it, conduct an additional step to reflect on whether the result is trustworthy and should be verified.
The underlying tools and benchmark instances remain unchanged. Claude-Opus-4.8, DeepSeek-V4-Pro, and GLM-5.2 each rerun half of their slots (Appendix C) with the additional check, paired against the same slots without it.
State Checker increases Noticed and producer-refetch rates, but produces only modest gains in implicit-condition RSR (Figure 3).

Figure 3: (a) State Checker adds a reliability check before a tool result is used. (b) Noticed, producer-refetch, and implicit-condition RSR with/without State Checker on paired implicit slots.

State Checker changes behavior in all three models, with larger increases in Noticed and producer refetch than in final RSR. The clearest behavioral shift is in GLM-5.2, whose producer-refetch rate more than triples; by contrast, Claude-Opus-4.8 gains no RSR despite noticing more errors.

State Checker makes evidence-seeking behavior steerable: an explicit reliability check increases recognition and use of the available verification path. The smaller RSR gains locate the remaining bottleneck in evidence integration and final task success, while the surfaced contradictions improve observability for a human or downstream controller.
State Checker relies on the unpolluted verification path in RITE’s single-site corruption setting. Persistent or system-wide tool faults may invalidate this path, requiring independent sources, tool substitution, redundancy, or human check.

## 7 Conclusion

We study silent errors in agentic tasks, where a plausible but incorrect tool result enters the execution history without an explicit failure signal and propagates through subsequent steps.
We formulate a task that measures whether an agent can tolerate this corrupted state and still complete the original task, and introduce RITE, a benchmark built from 167 corruption slots across nine industrial e-commerce workflows grounded in real service logs.
Across 10 recent LLMs, silent errors roughly halve task success and usually remain unnoticed; recovery remains incomplete even when models question the affected evidence and re-query its producer.
Further analysis shows that these errors often alter downstream e-commerce outputs, with category errors and early-stage corruptions causing the greatest damage.
Beyond the benchmark, we provide a simple reliability check that increases error detection and producer refetching more than final task success.

## Appendix A Workflow and Log Data Sources

This appendix documents two data-source stages: selecting the workflow collection $\mathcal{W}$ and mapping production logs to workflow inputs that yield eligible traces. It also records the resulting golden workflows. Workflow identifiers are anonymized and stable across the released artifacts.

## Workflow selection: structural validity.

We inspected e-commerce applications at the DSL level and retained complete deterministic DAGs with explicit control flow. We excluded graphs containing autonomous agentic nodes, atomic retrieval wrappers, short utility graphs, AB-test fragments, dangling references, or incomplete subgraphs. Fixed tool calls, read-only requests, code and LLM transformations, and explicit branch or loop nodes remained eligible.

## Workflow selection: task diversity.

Because the application library contains multiple versions of many task families, we deduplicated each family, selected a representative complete version, and formed a set spanning different business stages, task objectives, and data dependencies. These two workflow checks yielded nine golden workflows.

## Log selection and trace retention.

For each selected workflow, we mapped each candidate production-log record to the required start inputs and executed it on a structure-preserving replica. We selected a log only when its execution yielded a complete node-level trace with sufficient process depth and at least one business-semantic intermediate state that was produced upstream, consumed downstream, and locatable at a producer or consumer checkpoint. The corresponding trace was retained with the selected log. For safe trace collection, the replicas retained node identities, graph edges, data references, read-only retrieval, deterministic computation, and model-inference nodes, while writes, reporting calls, locks, memory updates, and external sends were neutralized or guarded.

## Appendix B Silent-Error Taxonomy and Literature Evidence

We synthesize 15 papers spanning agent and tool failures, data quality, and factuality. Two authors independently coded the error phenomena and boundaries described by each source, mapped overlapping concepts to a common vocabulary, and reconciled the mappings. The resulting taxonomy describes the semantic form of a plausible but incorrect intermediate value. Injection location is recorded separately.

## B.1 Operational Definitions

The main taxonomy contains two semantic groups and seven leaves (Table 6). The first group changes which object or category is referenced; the second preserves the object while changing one of its attributes or values. Each leaf requires a schema-valid value whose task-relevant meaning differs from the recorded value.

numeric_bucket_shift

Move a numeric value or interval to a neighboring valid range.

Malformed, impossible, or plainly out-of-range values are explicit failures.

L2.3

semantic_synonym_drift

Substitute text that appears semantically close but changes the business interpretation used downstream.

Meaning-preserving paraphrases are not errors.

L2.4

temporal_staleness

Reuse a value that was valid previously but is no longer correct at the task time.

A contemporaneous neighboring numeric value belongs to L2.2.

The injection locus is annotated independently of the semantic leaf and takes one of two values: tool_output, where the substitute is written into the producer observation, or tool_input, where it is written into a downstream tool argument.

## B.2 Literature Grounding

## Silentness and exclusion boundaries.

Tools Fail (Sun et al., 2024) establishes the central operational criterion: a tool output may be schema-valid and wrong without raising an exception. The Tool-Augmented LLM Failure Taxonomy (Winston and Just, 2025) reinforces the distinction between explicit and silent failures. The LLM Hallucination Survey (Huang et al., 2025) and Where LLM Agents Fail (Zhu et al., 2025) further separate entity, context, profile, memory, and parameter errors, motivating value-level interventions while excluding failures that arise only from the agent’s internal reasoning or memory. Other taxonomies delimit the scope from adjacent phenomena: the Multi-Agent Failure Taxonomy (Cemri et al., 2025) covers behavioral and system failures, $\tau$ -bench (Yao et al., 2025) emphasizes domain-policy compliance, CRMArena-Pro (Huang et al., 2026) adds confidentiality failures, and Reasoning Error Localization (Tyen et al., 2024) distinguishes recognizing an error from correcting its downstream effects. Together, these sources define silent error as an incorrect intermediate value rather than a planning, collaboration, policy, confidentiality, or reasoning failure.

## Semantic distinctions.

Data-quality and factuality research supplies the distinctions used to organize the seven leaves. The Dirty Data Taxonomy (Kim et al., 2003) separates category, value, relation, and stale-data errors, supporting category-level substitutions, attribute and numeric changes, and temporal staleness. Faithfulness versus Factuality (Maynez et al., 2020) frames an error as a contradiction with its source evidence, providing a common criterion across all leaves. The taxonomy of Factual Errors in Summarization (Tang et al., 2023) distinguishes entity, attribute, numeric, and temporal errors, which map naturally to entity near-duplicates, profile-attribute drift, numeric-bucket shifts, and temporal staleness.

## Specialized leaves and loci.

Several sources refine particular boundaries. Butterfly Effects in Toolchains (Xiong et al., 2025) shows how incorrect tool arguments propagate downstream, motivating tool_input as an intervention locus in addition to tool_output. Work on Duplicate Record Detection (Elmagarmid et al., 2007) motivates the distinction between real near-duplicate entities and superficially similar text. FreshLLMs (Vu et al., 2024) grounds temporal staleness in answers that change over time. Finally, LM-Emulated Sandbox Risks (Ruan et al., 2024) helps exclude system and safety failures from the semantic taxonomy.

Taken together, the agent and tool literature defines when an error is silent and what lies outside scope, while the data-quality and factuality literature supplies the semantic forms of the corrupted value. We adapt these distinctions into schema-valid, single-slot workflow interventions; the semantic leaf describes what changed, and the locus records where that change enters the trajectory.

## Appendix C Evaluation Protocol Details

This appendix specifies the rollout, judging prompts, and process measures used in evaluation.
All prompts, trajectories, and case-study contents in this paper are English translations.

## Evaluation flow.

Each rollout follows four stages:

(i) 

Initialize. For benchmark unit $i$ and condition $k\in\{\mathrm{correct},\mathrm{implicit},\mathrm{explicit}\}$ , the query is $q_{i}$ , the continuation environment is $E_{i}$ , and the condition-specific prefix $p_{i}^{k}$ initializes the agent history as $h_{0,i}^{k}=p_{i}^{k}$ . The correct prefix preserves the recorded value, the implicit prefix substitutes a silently incorrect value, and the explicit prefix presents an overt failure. The agent receives the task instruction and task inputs, followed by the prefix rendered as a numbered record of thoughts, actions, and observations.

(ii) 

Execute. The agent follows Eq. 1 for at most 25 steps. At each step, it outputs a thought and a JSON action that either calls a tool with arguments or stops with a final answer. Each condition uses a newly initialized copy of the same workflow-specific tool registry and case-specific replay snapshot. Tool names are normalized through workflow aliases. For each call, $E_{i}$ first searches for an argument-matched recorded response and returns it if found; repeated unmatched calls may consume the next unconsumed response in recorded order, while calls absent from or exhausted in the snapshot fall back to the live read-only toolbox. Replay hits, misses, live fallbacks, and observation lengths are recorded for audit.

(iii) 

Judge. GLM-5 at temperature 0 independently applies the state-judge and result-judge prompts below. The same model also judges whether an agent that faithfully uses the gold versus the polluted value would reach a different business conclusion, which defines the output-changing slots in D1 (Section 6).

(iv) 

Measure. Producer refetch and Noticed are computed from the trajectory independently of both judge outputs.

## Rollout counts and exclusions.

Across the ten models, each condition has 1,670 scheduled rollouts; in total, 73 scheduled rollouts produced no valid record. A rollout is excluded if any of its observations contains a tool-execution error message, which indicates an environment-side anomaly; this rule removes 201 rollouts. The retained rollouts number 1,599, 1,575, and 1,562 for the correct, implicit, and explicit conditions. Noticed is computed on all retained rollouts, and RSR on the 1,576, 1,555, and 1,543 retained rollouts that received a result judgment.

## Appendix D Human Validation of Result and Noticed Labels

This appendix reports an independent human validation of two automatically produced evaluation labels: the LLM-based Result judgment that defines RSR and the trajectory-derived Noticed label.

## Recruitment and assignment.

We recruited six university participants through a campus forum. The recruitment post described an approximately 50-minute annotation task, and each participant received RMB 50 upon completion. We selected 100 rollouts using stratified sampling: 28 were from the correct condition, 35 from the explicit-error condition, and 37 from the implicit-error condition, with 10 rollouts from each evaluated model. Within each stratum defined by model and condition, rollouts were drawn uniformly at random. Each rollout was independently assigned to three participants, and each participant annotated 50 rollouts, yielding 300 participant–rollout judgments. To balance overlap, each of the 20 possible three-person annotator groups was assigned five rollouts. Participants were instructed to work independently and not discuss individual cases.

## Two-stage annotation protocol.

For each rollout, the interface presented the user task, the correct reference evidence, the complete agent trajectory, any new tool observations, and the final answer. Annotation then proceeded in two stages. In the blind stage, participants answered two binary questions: (i) whether the final answer solved the user task (Result), and (ii) whether the agent explicitly noticed a data anomaly and subsequently invoked a tool to verify it (Noticed). A Noticed label therefore required both an explicit recognition signal in the reasoning and a later verification action. Once submitted, these labels were locked. In the review stage, the interface revealed the two automatic evaluation labels and their rationales. Participants marked each label as agree, disagree, or unsure, with an optional comment. Figure 4 illustrates the two stages. Because the second-stage responses may be influenced by the revealed rationales, we treat the blind-stage comparison as the primary validation and report review-stage agreement only as complementary evidence.

## Appendix E End-to-End Case Studies of Silent-Error Handling

This appendix presents two baseline case studies, not State Checker interventions. In Case 1, the agent successfully refetches the corrupted producer but later overwrites the recovered evidence during reasoning. Case 2 follows an Unnoticed implicit error from a plausible category substitution to a wrong final recommendation.

## How to read the case boxes.

Entries labeled P* summarize inherited prefix events shown to the agent; entries labeled R* are continuation steps generated by the evaluated model. Each step lists the agent action, the observed result, and a diagnostic note. Producer refetch records whether the model re-invokes the producer of the affected value. Observation state describes the latest valid producer observation as Recovered, Residual, or Neither, while final task success separately asks whether the complete answer resolves the user query.

## E.2 Case 2: An Unnoticed Category Error Propagates to the Answer

The second case shows the complementary failure mode: the model never questions or refetches the affected producer, so the polluted value remains the organizing premise throughout the continuation.

Model and condition: GLM-5.2; baseline implicit condition

Workflow: wf06, cross-domain intent and interest modeling

Affected evidence: A content category in the user’s article-reading history

Implicit-prefix category: First level: Pet; second level: Cat

Unchanged context: Article identifier, timestamp, scene, and read_time=115920 remain unchanged; the model sees no competing Finance/Stocks value.

Why the error is silent: Pet/Cat is well formed and locally plausible, and no warning accompanies the article record.

Case 2: Prefix and Rollout

Inherited prefix supplied to the model

P-context

Receive the normal profile and live- and short-video behavior history.
Result: The user is a middle-aged man in a large city; no prior record establishes a pet-domain preference.

P-error

Model-generated continuation

R1

Reported answer

The final answer classifies the user as belonging to the pet domain, cites the Pet/Cat article record with read_time=115920 as its primary justification, and recommends pet-food and cat-supply keywords.

Case 2: Judgment

Noticed: No. No thought questions Pet/Cat or requests verification of the article record.

Producer refetch: No. No continuation step revisits the source of the article category.

Observation state: Residual. The model continues to rely on the inherited Pet/Cat record.

The polluted value shapes every later interpretation.

## Failure mechanism.

The important transition occurs in R2. The additional evidence is non-financial, not positively pet-related, but the inherited category has already established a pet hypothesis. The model therefore interprets absence of finance content as confirmation rather than insufficient evidence. This is the propagation pattern targeted by the benchmark: a locally plausible error becomes an organizing premise, shapes later evidence interpretation, and determines the recommended action.

## Appendix G Limitations

Several limitations qualify our findings. First, each silent-error instance contains a single corrupted value, and re-querying its producer returns the unpolluted response; RITE therefore measures recovery when a trustworthy verification path is available, and faults that persist across re-queries are left to future work. Second, recorded calls are replayed, whereas valid calls absent from the recordings are served by read-only live tools, so continuations that leave the recorded paths may observe current tool behavior. Third, temporal staleness is defined in the taxonomy but not instantiated. Finally, RSR relies on an LLM judge, whose errors may affect absolute scores.
