Abstract.

Code translation converts source code from one programming language to another while preserving its functionality. Although Large Language Models (LLMs) have improved code translation, their outputs still contain hallucinations: generated code that conflicts with the source program, violates target-language facts, or introduces contextually inconsistent dependencies. These failures are especially harmful in translation because small semantic deviations can silently change program behavior. Existing hallucination studies mainly focus on natural-language generation or code generation, leaving the forms, distribution, and mitigation of hallucinations in cross-language code translation insufficiently characterized. This paper presents a systematic empirical study of LLM hallucinations in code translation. Across three benchmark datasets, six language pairs, and seven LLMs, we construct a taxonomy with three major categories: Semantic Consistency Conflicts, Factual Knowledge Conflicts, and Project Context Deviations. We manually annotate 13,919 hallucination cases and analyze how hallucination types vary across models, datasets, and language directions. Guided by the taxonomy, we further propose HaluCodeTran, a mitigation framework that combines BM25-based retrieval of relevant translation examples with taxonomy-aware reflective refinement.
The study provides an execution-tested characterization of code-translation hallucinations and a practical baseline for building more reliable LLM-based code migration tools.

Hallucination, Code Translation, Large Language Models

## 1. Introduction

Code translation, also known as source-to-source compilation or transpilation, involves converting code from one programming language to another while preserving its original functionality. This technique plays a critical role in modern software development.
For example, many industries spend hundreds of millions of dollars to convert code written in older programming languages (e.g., FORTRAN and COBOL) to newer ones (e.g., Java, C++) (Roziere et al., 2020).
By translating code into modern programming languages, organizations can reduce maintenance costs, improve reliability, and enhance non-functional attributes like security and performance (Pan et al., 2024).
Automatic code translation can alleviate the burden of program migration and facilitate the development of software systems, which has drawn sustained attention from neural, LLM-based, and project-scale migration research (Rozière et al., 2020; Ahmad et al., 2023; Du et al., 2024; Pan et al., 2024; Yang et al., 2024b; Macedo et al., 2025).
Recent advancements in Large Language Models (LLMs) have improved code translation and code-generation capabilities, while also raising new concerns about correctness, calibration, and domain-specific reliability (Yang et al., 2024b; Gu et al., 2025; Spiess et al., 2025; Shi et al., 2025).

However, the translation quality of current LLM-driven approaches is still unsatisfactory, partly because generated programs can contain hallucinations: code fragments that conflict with source-program requirements, violate target-language facts, or introduce contextually inconsistent dependencies. These hallucinations can lead to functional errors, incomprehensible code, deprecated or misused APIs, and security vulnerabilities, undermining the reliability of translated codebases (Pan et al., 2024; Tian et al., 2025; Wang et al., 2025b; Wang et al., 2025a; Zhuo et al., 2026).
Most existing hallucination research focuses on Natural Language Generation (NLG) tasks, such as question answering (Sadat et al., 2023) and summarization (Rehman et al., 2024; Ji et al., 2023). Recent software-engineering studies have begun to characterize hallucinations, code-generation errors, and API misuse in LLM-based programming tasks (Liu et al., 2024; Tian et al., 2025; Wang et al., 2025b; Lee et al., 2025; Zhuo et al., 2026), but code translation introduces a different failure surface. Unlike intent-to-code generation, code translation must preserve a structured source program while mapping syntax, types, libraries, APIs, and idioms into a different target language. A generated program may compile and still violate the source semantics, while a superficially small API or data-flow mismatch can completely change behavior. This makes hallucination in code translation a distinct empirical object rather than a direct instance of natural-language or code-generation hallucination.

To address this gap, we conduct an empirical study focused on hallucinations in cross-language code translation. Through open coding and empirical validation, we develop a taxonomy of code translation hallucinations, categorizing errors into three main types:
(1) Semantic Consistency Conflicts (e.g., functional requirement mismatches, data inconsistencies),
(2) Factual Knowledge Conflicts (e.g., syntax errors, incorrect library/API usage),
(3) Project Context Deviations (e.g., dead code, dependency conflicts). We instantiate this taxonomy on outputs from seven LLMs, including GPT-4o (Hurst et al., 2024) and Qwen 2.5-Coder (Yang et al., 2024a), over three widely used code translation datasets: CodeNet (Puri et al., 2021), Avatar (Ahmad et al., 2023), and Transcoder (Rozière et al., 2020). The resulting annotations provide a basis for analyzing which hallucination categories dominate code translation failures and which model/language-pair conditions make them more likely.

Guided by the taxonomy, we propose HaluCodeTran, a mitigation framework that combines retrieval-based contextual grounding with reflective iterative refinement. The retrieval component provides relevant source-target translation examples to reduce factual and idiomatic uncertainty, while the reflection component asks the model to inspect the intermediate translation against the source program and taxonomy categories before producing a revision. On CodeNet, HaluCodeTran improves computational accuracy by up to 23 percentage points and reduces hallucination cases by up to 32% compared with vanilla translation, outperforming Chain-of-Thought, Chain-of-Verification, and Retrieval-Augmentation in average accuracy for the evaluated models.

We summarize our contributions as follows:

• 

We define hallucination in code translation and establish a taxonomy that distinguishes semantic consistency conflicts, factual knowledge conflicts, and project context deviations.

• 

We construct a manually labeled hallucination dataset covering 13,919 cases from seven LLMs, three datasets, and six translation directions, enabling fine-grained analysis across models and language pairs.

• 

We propose HaluCodeTran, a taxonomy-aware mitigation framework that combines retrieval-augmented examples with reflective refinement, and evaluate it against representative prompting and retrieval baselines.

## 2. Related Works

## 2.1. LLM-Powered Code Translation

Automated code translation facilitates the migration of codebases across programming languages and can reduce manual migration effort. Early work focused on rule-based approaches (Alsubhi et al., 2019; An et al., 2018; Pino et al., 2017; Tauda et al., 2021) and phrase-based statistical machine translation techniques (Karaivanov et al., 2014; Nguyen et al., 2015), which laid the groundwork for subsequent neural and LLM-based approaches (Du et al., 2023; Ahmad et al., 2023; Zhu et al., 2022; Du et al., 2024; Macedo et al., 2025).
Recently, large language models (LLMs) with hundreds of billions of parameters have demonstrated impressive capabilities across natural language and code tasks (Hurst et al., 2024; Hui et al., 2024).
General-purpose LLMs (Yang et al., 2024a; Grattafiori et al., 2024; AI, 2023; Abdin et al., 2024) and code-specialized LLMs (Roziere et al., 2023; Team et al., 2024a; Li et al., 2023; Lozhkov et al., 2024) have shown strong performance when trained on large code corpora, such as GPT (Tang et al., 2024), LLaMA (Grattafiori et al., 2024), Qwen (Hui et al., 2024; Yang et al., 2024a), Gemma (Team et al., 2024b), DeepSeek-Coder (Guo et al., 2024; Zhu et al., 2024), etc.

The LLM-powered code translation has achieved significant progress in recent years (Saha et al., 2024; Macedo et al., 2024; Yang et al., 2024b; Shiraishi and Shinagawa, 2024; Tao et al., 2024; Dhruv and Dubey, 2024; Zhang et al., 2024a; Yuan et al., 2024; Jana et al., 2024; Luo et al., 2024; Macedo et al., 2025).
They enhance the code translation performance of large language models through technical approaches such as prompt engineering optimization and domain-specific fine-tuning.
For example, by augmenting generation with in-context learning, the code structure (e.g., Abstract Syntax Tree) knowledge is leveraged into large language models to improve understanding of cross-language semantic alignment (Du et al., 2025). Meanwhile, domain-specific fine-tuning on specialized codebases enables models to better capture niche terminology and idiomatic expressions in specific fields (Dhruv and Dubey, 2024). Additionally, techniques like multi-model ensemble and interactive feedback mechanisms are employed to enhance the accuracy and practicality of code translation (Yang et al., 2024b).

## 2.2. Hallucination of Large Language Models

In the field of natural language processing (NLP), hallucination refers to the phenomenon where a language model generates content that is inconsistent with the input, semantically meaningless, or factually incorrect. With the rapid development of LLMs, research on hallucination has attracted significant attention across various domains (Ji et al., 2023; Huang et al., 2025; Lavrinovics et al., 2025; Lauscher et al., 2025).
In the community of AI for Software Engineering, existing investigations primarily focus on hallucinations, calibration, preference alignment, and error characteristics within code generation and completion (Liu et al., 2024; Tian et al., 2025; Spiess et al., 2025; Wang et al., 2025b; Weyssow et al., 2026; Zhuo et al., 2026).
However, a fundamental distinction exists between code generation and code translation. While code generation requires the model to understand ambiguous natural language intents and write programs, code translation demands a rigorous understanding of structured source code and precise cross-lingual semantic mapping. This shift from “intent-to-code” to “code-to-code” alignment introduces distinct hallucination patterns, such as syntax-level interference, cross-language API mismatches, and subtle source-target semantic divergence. Existing code-hallucination studies provide useful definitions and evaluation ideas, but they do not directly answer which hallucination types dominate execution-tested code translation failures or how these types vary across source-target language pairs. Our study therefore scopes hallucination to cross-language translation and evaluates it through compiler/runtime behavior, source-target comparison, and manual taxonomy annotation.

## 2.3. Hallucination Mitigation via Prompt Engineering

Recent research has extensively explored prompt engineering as a cost-effective paradigm to suppress hallucinations and improve code-generation reliability by optimizing the model’s reasoning paths and grounding its outputs in verifiable contexts (Wei et al., 2022; Khojah et al., 2025).
First, Reasoning-guided Mitigation, exemplified by Chain-of-Thought (CoT) prompting (Wei et al., 2022), encourages LLMs to generate intermediate logical steps, which facilitates the decomposition of complex source code structures. However, CoT is often susceptible to “logical drifting”, where a minor hallucination in the early reasoning stage cascades into a significant functional requirement mismatch in the final translated code.
Second, Self-Verification Mechanisms, such as the Chain-of-Verification (CoVe) framework (Dhuliawala et al., 2024) and recent program-analysis/backtracking strategies (Jiang et al., 2025), introduce a “generate-then-verify” pipeline to rectify factual errors through independent query-answering or code-level analysis. While effective for general knowledge and some code-generation settings, these mechanisms can still fail to recognize subtle API knowledge conflicts across heterogeneous programming languages (Zhuo et al., 2026).
Third, Knowledge-Augmented Approaches, particularly Retrieval-Augmented Generation (RAG) (Lewis et al., 2020; Zhao et al., 2023; Du et al., 2025), mitigate hallucinations by providing external “ground-truth” snippets from documentation or project-specific repositories. Despite its success in reducing project context deviations, RAG remains inherently limited by the quality of the retrieval corpus, and recent TSE evidence shows that code datasets can contain cross-dataset duplication and leakage that complicate LLM evaluation (López et al., 2025).

These lines of work leave two gaps for code translation. First, code translation studies primarily report end-to-end correctness metrics, but they rarely decompose failed translations into hallucination categories that explain what kind of unsupported content the model introduced. Second, hallucination mitigation methods are usually designed as generic prompting or retrieval strategies, while code translation requires feedback that is aligned with source-target semantic preservation, target-language factual knowledge, and project-context consistency. To address these gaps, our work studies hallucination phenomena in code translation and proposes a mitigation approach grounded in the observed taxonomy.

## 3. Taxonomy of Hallucination

We define a code-translation hallucination as a generated target-language program element that is not justified by the source program or target-language semantics and that can affect compilation, execution, maintainability, or dependency consistency. This definition separates hallucination from ordinary translation diversity. A target program is not labeled as hallucinated merely because it differs textually from the reference implementation: semantically equivalent rewrites, idiomatic target-language substitutions, and harmless formatting differences are treated as valid variants. In contrast, we label a generated fragment as hallucinated when test execution, compiler/runtime diagnostics, or manual source-target comparison shows that the fragment introduces unsupported behavior, invalid language/library knowledge, or inconsistent project context.

To construct the taxonomy, two authors first performed open coding on LLM-generated translations from the benchmark setting described in Section 5.1. We employ Qwen 2.5-Coder (Yang et al., 2024a), DeepSeek-Coder-V2 (Zhu et al., 2024), Llama 3.1 (Grattafiori et al., 2024), Gemma 2 (Team et al., 2024b), Mistral (AI, 2023), Phi 4 (Abdin et al., 2024), and GPT-4o (Hurst et al., 2024) on CodeNet (Puri et al., 2021), Avatar (Ahmad et al., 2023), and Transcoder (Rozière et al., 2020), covering C++ $\rightarrow$ Java, C++ $\rightarrow$ Python, Java $\rightarrow$ C++, Java $\rightarrow$ Python, Python $\rightarrow$ C++, and Python $\rightarrow$ Java. Each generated program is compiled or executed in the corresponding target-language environment. The annotators then inspect the generated code, compiler/runtime messages, source program, reference solution, and available test results to identify the concrete erroneous fragment and assign one or more hallucination labels. This process follows open-coding practice and is informed by hallucination taxonomies from natural-language and code-generation studies (Zhang et al., 2024b; Tian et al., 2025).

The annotation protocol is multi-label because a single failed translation can contain more than one hallucinated fragment or one fragment can exhibit multiple failure modes. For example, an undefined function call can simultaneously reflect identifier confusion and dependency conflict if the call is inconsistent with both local scope and required imports. When annotators encounter a case not covered by the current codebook, they record the evidence, propose a provisional label, and discuss whether the case should be merged into an existing category or used to refine the taxonomy. Disagreements are resolved through joint inspection of the source program, generated program, execution result, and category definition.

Figure 1 summarizes the resulting taxonomy. It contains three major categories and eight subcategories. In total, we label 13,919 hallucination cases generated by seven LLMs. The following subsections define each category and provide representative examples from the hallucination dataset.

## 3.1. Semantic Consistency Conflicts

Semantic consistency conflicts occur when the translated code fails to preserve the intended behavior or semantics of the source code.

## 3.1.1. Functional Requirement Mismatch (FRM)

Functional requirement mismatch refers to the generated code diverging from the intended logic or functional requirements.
As shown in Figure 2(2(a)), the source C++ code has a conditional judgment if (time < s[j]), which means that when time is less than s[j], the value of time should be updated to s[j]. However, the generated Python code wrongly writes the condition as if time > s[j]. This incorrect logical condition is a misinterpretation of the original code’s intention, deviating from the correct logic that the source code wants to implement, thus resulting in a logical error.

## 3.1.2. Data Consistency Violation (DCV)

Data consistency violation occurs when variables, inputs, or outputs become inconsistent during translation.
As shown in Figure 2(2(b)), the LLM misuses multiple assignments by incorrectly incorporating the augmented assignment sum += num[i] * m[i] into a multiple-assignment statement. The augmented assignment is not valid as the left-hand side of the multiple assignment must be a legitimate assignable target, and sum += num[i] * m[i] does not meet this requirement.

## 3.2. Factual Knowledge Conflicts

Factual knowledge conflicts arise when the translated code violates the basic syntax or demonstrates misunderstandings of libraries or APIs because of the limitations of the knowledge of the corresponding programming languages.

## 3.2.1. Basic Syntax Conflicts (BSC)

Basic Syntax Conflicts involve syntax-related errors that render the translated code incorrect or uncompileable.
In the Figure 2(2(c)), in Python code, a colon is required at the end of the for loop header to denote the start of the loop body. However, the generated code has for _ in range(n) without the necessary colon, leading to a SyntaxError as the interpreter expects a colon to properly structure the statement.

## 3.2.2. Library Knowledge Conflicts (LKC)

Library knowledge conflicts occur when the translation uses incorrect or non-existent standard or third-party libraries. As shown in Figure 2(2(d)), there is no standard module called vector in Python, yet the code generation wrongly assumes its existence and tries to import it, mimicking the #include <vector> statement from the C++ source code. This is a clear case of the code generation tool generating incorrect code based on a misinterpretation or over-generalization of the source code’s library inclusion mechanism, failing to account for the differences in module availability between C++ and Python.

## 3.2.3. API Knowledge Conflicts (AKC)

API knowledge conflicts involve incorrect usage of APIs, including function names, parameters, or control logic. As shown in Figure 2(2(e)), the generated code attempts to directly pass a numerical result (n - 2) * 180 to sys.stdout.write(), ignoring the fact that this function only accepts strings. This is a misinterpretation of how output operations work in the API of Python.

## 3.3. Project Context Deviations

Project context deviations happen when the generated code fails to align with the broader context of the project, such as naming conventions, dependencies, or logic flow.

## 3.3.1. Repetition & Dead Code (RDC)

Repetition or dead code issues include unnecessary or unreachable code introduced in translation.
In Figure 2(2(g)), since itertools.count(2) creates an infinite list starting from 2, it leads to an infinite loop when iterating over the resulting primes list. The generated code wrongly assumes an infinite sequence is appropriate, resulting in incorrect and non-terminating behavior.

## 3.3.2. Identifier & Function Confusion (IFC)

Identifier & function confusion refers to hallucinations where the generated code misuses variables, functions, or instances that are defined within the local project context (rather than external APIs). These errors often indicate a failure to track or understand in-project definitions, scopes, or naming.
As shown in Figure 2(2(h)), the generated code attempts to call LLI(n) while the function LLI is defined to take no positional arguments. This misinterpretation of the function’s parameter requirements leads to a runtime error stating that “LLI() takes 0 positional arguments but 1 was given”. It shows that the code generation process has an incorrect understanding of how the function should be called, creating an inconsistent and erroneous implementation compared to the intended logic.

## 3.3.3. Dependency Conflicts (DC)

Dependency conflicts occur when the generated code refers to functions, attributes, variables, or APIs that do not exist in the project context. Due to the inability of LLMs to access the entire project context, they often hallucinate dependencies by calling non-existent functions, referencing missing variables or attributes, etc.
As shown in Figure 2(2(f)), in the code generated by Mistral, there is an error of using variables before they are defined. In Python, a variable must be defined and assigned a value before it can be used. In the main function of the generated code, in statements like M = [[0]* N, for _ in range(N)], color = [WHITE]*N, d = [0]*N, f = [0]*N, the non-existing variables N is used within the program.

## 4. Evaluation of Hallucination

## 4.1. Dataset and Studied LLMs

To evaluate the hallucination in code translation, we perform an extensive experiment on three well-known datasets of code translation: CodeNet (Puri et al., 2021), Avatar (Ahmad et al., 2023), and Transcoder (Rozière et al., 2020). The metric to measure the performance of the LLMs in code translation is computational accuracy, proposed by Transcoder (Rozière et al., 2020).

Seven advanced LLMs are evaluated: GPT-4o, four open-source LLMs (Llama 3.1, Gemma 2, Mistral, and Phi 4), and two recent code LLMs (Qwen 2.5-coder, DeepSeek-Coder-V2).

• 

Qwen 2.5-Coder (Hui et al., 2024): is a code-specific model, which is built upon the Qwen2.5 architecture and continues to be pretrained on a vast corpus of over 5.5 trillion tokens. We use the Qwen 2.5-coder-7B model.

• 

DeepSeek-Coder-V2 (Zhu et al., 2024): is an open-source Mixture-of-Experts (MoE) code language model further pre-trained from an intermediate checkpoint of DeepSeek-V2. We use the DeepSeek-Coder-V2-16B model.

• 

Llama 3.1 (Grattafiori et al., 2024): is a new state-of-the-art model from Meta available in 8B, 70B, and 405B parameter sizes that natively support multilinguality, coding, reasoning, and tool usage. We use the Llama-3.1-8B model.

• 

Gemma 2 (Team et al., 2024b): a new addition to the Gemma family of lightweight models, ranging in scale from 2 billion to 27 billion parameters for text and code. We use the Gemma 2-9B model.

• 

Mistral (AI, 2023): is a 7B parameter model released by Mistral AI, which is available in both instruction following and text completion.

• 

Phi 4 (Abdin et al., 2024): is a 14-billion parameter language model developed with a training recipe that is centrally focused on data quality.

• 

GPT-4o (Hurst et al., 2024): is an advanced generative AI model developed by OpenAI. Although not explicitly trained for code translation or code generation, they demonstrate notable performance in this domain.

For each dataset and translation direction, we use the official source programs and available test cases to evaluate generated target programs. A generated program is counted as compilable only when it passes the target-language compilation or syntax-checking stage without manual repair. A generated program is counted as computationally correct only when it produces the same outputs as the reference program on the provided test suite. We do not use test outputs, reference explanations, or ground-truth target code as feedback to the LLM during vanilla translation or reflective refinement; these artifacts are used only for offline evaluation and annotation.

## 4.2. Evaluation Metrics

For translation correctness, we follow most previous studies (Roziere et al., 2020; Rozière et al., 2020; Yang et al., 2024b; Du et al., 2025) to measure two main aspects, including the Compilation Success Rate (CSR) and Computational Accuracy (CA).

Compilation Success Rate (CSR): It computes the ratio of samples that can be successfully compiled after translation.

(1)

 $CSR=\frac{\sum^{N_{x}}_{k=1}cs(\hat{y_{k}})}{N_{x}},\ \textbf{where}\ cs(\hat{y_{k}})=\left\{\begin{matrix}1&Compile(\hat{y_{k}})\to success\\
0&Compile(\hat{y_{k}})\to error\\
\end{matrix}\right.$ 

where $N_{x}$ denotes the total number of samples, $\hat{y_{k}}$ denotes the $k$ -th translated sample via a certain LLM. Compile( $\cdot$ ) denotes compiling samples with their corresponding compilation programs, such as javac for Java while g++ for C++, and its results are either success or error.

Computational Accuracy (CA): It computes the ratio that the translated programs can produce the same execution result as the ground truths, given the same inputs.

(2)

 $CA=\frac{\sum^{N_{x}}_{k=1}ca(y_{k},\hat{y_{k}})}{N_{x}},\ \textbf{where}\ ca(y_{k},\hat{y_{k}})=\left\{\begin{matrix}1&Exec_{k}(y_{k})=Exec_{k}(\hat{y_{k}})\\
0&Exec_{k}(y_{k})\neq Exec_{k}(\hat{y_{k}})\\
\end{matrix}\right.$ 

where
 $N_{x}$ denotes the number of samples for translation,
 $y_{k}$ denotes the ground truth of the $k$ -th
sample, and $\hat{y_{k}}$ denotes the translated program via a certain LLM for the $k$ -th sample. Besides,
 $Exec_{k}(\cdot)$ denotes the execution result of a program with the test suite of the $k$ -th sample.

When interpreting CA, we distinguish absolute percentage-point changes from relative percentage changes. For example, an improvement from 33.58% to 50.33% is reported as a 16.75 percentage-point gain. This convention avoids conflating relative error reduction with absolute translation accuracy improvement.

## 5. Evaluation Results

## 5.1. RQ1: What is the performance of the Vanilla LLMs on code translation?

This RQ establishes the foundational baseline for the entire empirical study, which is essential for objectively measuring the native code translation capabilities of state-of-the-art LLMs via core metrics like CSR and CA. It quantifies performance disparities across models and language pairs, and provides a measurable reference for attributing unsatisfactory translation results to hallucination issues, laying the empirical groundwork for all subsequent hallucination-related analyses.

Table 1 summarizes the computation accuracy of code translation across three datasets (CodeNet, Transcoder, and Avatar) using seven state-of-the-art LLMs.
We report the percentage of successful translations for each source-target language pair, with success measured by functional equivalence.
Overall, GPT-4o (Hurst et al., 2024) demonstrates the strongest performance, achieving the highest average computation accuracy across all datasets: 83.33% on CodeNet, 90.05% on Transcoder, and 72.42% on Avatar. This highlights its robust capability in handling diverse code translation tasks.
DeepSeek-Coder-V2 (Zhu et al., 2024) and Qwen 2.5-coder (Yang et al., 2024a) perform competitively, especially on CodeNet and Transcoder, with DeepSeek-Coder-V2 slightly outperforming Qwen 2.5-coder on average. For example, DeepSeek-Coder-V2 achieves 69.25% on CodeNet and 76.14% on Transcoder, compared to 63.17% and 73.36% respectively for Qwen 2.5-coder.

In contrast, models such as Llama 3.1 (Grattafiori et al., 2024), Gemma 2 (Team et al., 2024b), and Mistral (AI, 2023) show lower computation accuracy, particularly on the Avatar dataset. Mistral, for instance, only achieves 18.90% average on Avatar, indicating its limited ability to generalize to real-world, less-structured codebases.
A closer look at the direction-specific results reveals that translations involving Python as the target language tend to be more challenging. For instance, on CodeNet, the C++ $\rightarrow$ Python and Java $\rightarrow$ Python tasks yield consistently lower computation accuracy across models. Conversely, translations between syntactically similar languages, such as C++ and Java, generally yield higher computation accuracy.
The Transcoder dataset yields overall higher computation accuracy, likely due to its more controlled and balanced nature, while the Avatar dataset proves the most difficult, reflecting the challenges of handling diverse and noisy code from real repositories.
These findings suggest that while recent LLMs show promising translation capabilities, there remains a performance gap between models and datasets. The poor performance is largely due to the hallucinations generated by the model during code translation.
Therefore, in the next section, we conduct an in-depth quantitative and qualitative analysis of hallucination phenomena across different models, datasets, and language pairs, aiming to answer how hallucinations are distributed and which types of hallucinations dominate LLM-based code translation failures.

## 5.4. RQ4: What is the impact of type of programming languages on hallucinations in code translation?

This RQ is pivotal for exploring the scenario-specific characteristics of code translation hallucinations. It analyzes how programming language properties (e.g., static/dynamic typing) and language pairings shape hallucination patterns, and identifies high-risk translation pairs and their typical hallucination subtypes. The results can guide practitioners to predict and avoid hallucination risks in specific translation scenarios, and also provide a basis for tailoring mitigation strategies for different language pairs.

To better understand how hallucinations vary with different programming languages, we analyze the distribution of hallucination types across six translation directions, as shown in Figure 4. The results indicate that hallucination patterns are not uniformly distributed but are influenced by both the source and target languages.

Among all translation directions, hallucinations in the Java to Python, C++ to Python, and C++ to Java tasks are dominated by Data Consistency Violations (DCV), accounting for 44.25%, 44.18% and 46.26%, respectively. These results suggest that LLMs often struggle to preserve input-output behavior and state consistency when translating from statically typed languages into dynamically typed languages. In the case of C++ to Java, although both languages are statically typed, translation errors may stem from differences in how input and output are handled across programming languages, resulting in divergent behavior.

When translating Python to Java and Python to C++, the proportion of hallucinations related to API Knowledge Conflicts (AKC) increases. Specifically, API conflicts account for 12.55% in Python to C++ and 11.13% in Python to Java. This suggests that LLMs face substantial challenges in accurately resolving and translating the flexible, dynamically typed constructs of Python into the more explicit, rigidly defined APIs and dependency structures typical of statically typed target languages.

In the Java to C++ and Python to C++ translations, hallucinations are more evenly distributed across various categories. This implies that while translation to C++ introduces several hallucinations, no single type of hallucination overwhelmingly dominates, likely due to the complexity and strict requirements of the language imposing a wide range of potential failure points.

Finding 4: 
The source and target programming languages influence hallucination patterns in code translation. Translations from statically typed languages (Java, C++) to dynamically typed languages (Python) are mainly affected by Data Consistency Violations (DCV), while translations from dynamically typed languages to statically typed languages exhibit more API Knowledge Conflicts (AKC), reflecting challenges in mapping flexible constructs to rigid target-language APIs.

## 6. Hallucination Mitigation

This section addresses the critical gap in existing literature regarding code translation hallucination mitigation frameworks and serves as the primary application-oriented inquiry of this study. Synthesizing our previous analysis of hallucination taxonomies and the limitations of static methodologies, we investigate the inherent reflection capabilities of LLMs. Specifically, we propose a new approach termed HaluCodeTran, which leverages retrieval-augmentation to supplement LLMs with relevant code translation knowledge and a reflective iterative refinement strategy to identify and correct errors.
In the following sections, we describe the technical details of baseline methods and HaluCodeTran and the quantitative experiments on hallucination mitigation.

## 6.1. HaluCodeTran

HaluCodeTran integrates retrieval-augmented translation with a feedback loop that prompts the model to examine its intermediate outputs against the source logic and the hallucination taxonomy.
The process comprises three primary phases: 1) Knowledge Augmentation, 2) Code Translation, and 3) Recursive Self-Reflection.

1) Knowledge Augmentation via Contextual Grounding. 
The execution begins with the acquisition of the input source code $x$ . To mitigate potential hallucinations arising from cross-language mapping ambiguities, we first perform knowledge augmentation. Specifically, we leverage a demonstrated knowledge base $\mathcal{D}$ , containing high-quality pairs of source and target code. Following established practices (Zhao et al., 2023), we adopt the BM25 algorithm (Robertson et al., 2009) to retrieve a subset of relevant examples $\mathcal{S}$ based on their lexical and structural relevance scores to $x$ . These examples $\mathcal{S}$ act as a repository of implicit knowledge, encompassing target language syntax, library usage, and idiomatic conversion patterns. By providing these grounded references, we effectively narrow the model’s search space and provide a pedagogical basis for the subsequent translation.

2) Initial Code Translation. 
Building upon the augmented context, the Code Translation phase aims to synthesize a functionally equivalent version of $x$ . By conditioning the model on both the original source code $x$ and the retrieved knowledge subset $\mathcal{S}$ , the translator generates an initial translation candidate $\hat{y}^{0}$ :

(3)

 $\hat{y}^{0}=\text{Translate}(x,\mathcal{S})$ 

While $\mathcal{S}$ provides a strong prior, the inherent intricacies of code semantics and latent logic ambiguities mean that $\hat{y}^{0}$ may still harbor semantic inconsistencies, factual errors, or project-specific deviations as identified in our taxonomy.

3) Recursive Self-Reflection and Refinement.
To systematically rectify these hallucinations, HaluCodeTran enters a recursive self-reflection loop. In each iteration $i$ , the model receives four inputs: the source program $x$ , the current translation $\hat{y}^{i}$ , the retrieved examples $\mathcal{S}$ , and the taxonomy definitions in Section 3.1–3.3. It then produces a reflection report $\mathcal{R}^{i}$ that checks whether $\hat{y}^{i}$ preserves source-program behavior, uses valid target-language syntax and APIs, and avoids project-context deviations. Unlike an execution-based repair loop, this reflection step does not observe hidden test results; it relies only on the source code, retrieved examples, and taxonomy-guided inspection.
If the reflection report does not identify any taxonomy category, $\text{IsConsistent}(\mathcal{R}^{i})$ returns true and the process terminates. Otherwise, the model distills a structured critique $\mathcal{T}^{i}$ from the report. Each critique item follows the format <category: location: description: repair hint>, where category is one of the hallucination subtypes, location identifies the suspicious target-code fragment, description explains the mismatch, and repair hint states the required source-aligned revision. This diagnostic feedback directly guides the subsequent refinement step:

(4)

 $\hat{y}^{i+1}=\text{Refine}(\hat{y}^{i},\mathcal{T}^{i},x)$ 

This cycle of reflection, critique, and refinement iterates until the reflection step reports no detected hallucination or the maximum step $M$ is reached. The same $M$ , retrieval size, and prompting budget are used across models in the mitigation study. The pseudo-code of HaluCodeTran is shown in Algorithm 1.

## 6.2. Baseline Methods of Hallucination Mitigation

We perform a series of experiments to validate whether we can guide LLMs to alleviate hallucinations via prompt engineering.

• 

Vanilla: is the standalone LLM without any additional preprocessing modules or external retrievers. Vanilla LLMs represent the original capabilities of LLMs.

• 

Chain-of-Thought(CoT) (Wei et al., 2022): is a prompting technique to encourage multi-step reasoning by explicitly guiding the LLMs to "think" step-by-step before answering.

• 

Chain-of-Verification(CoVe) (Dhuliawala et al., 2024): prompts LLMs to draft the initial response, plan verification questions, answer the question, and generate the final verified response.

• 

Retrieval-Augmentation(RA): following the widely-used setting (Zhao et al., 2023), uses LLMs with the BM25 algorithm (Robertson et al., 2009) to retrieve the most relevant texts as input to vanilla LLMs.

We evaluate hallucination mitigation on CodeNet because it provides balanced language-pair coverage and executable test cases for all six translation directions. For each evaluated model, we construct a retrieval database from source programs and their successfully translated target programs in the model’s successful pool. The evaluation set contains the remaining source programs that were not successfully translated by the same model under the vanilla setting. During retrieval, the query program itself is excluded from the candidate pool, and the model receives only retrieved source-target examples rather than test outputs or reference explanations. This setting evaluates whether a mitigation method can repair cases that are difficult for the original model while avoiding direct test-feedback repair.
For the Retrieval-Augmentation baseline, the 5-shot setting is chosen based on its superior performance in preliminary experiments. To ensure fairness, we also apply the same 5-shot retrieved context in the initial translation phase of HaluCodeTran. CoT, CoVe, RA, and HaluCodeTran are evaluated on the same per-model test split, using the same base model and the same execution-based CA metric.

## 6.4. Extent of Hallucination Mitigation on Different Hallucination Types

This subsection is the key to conducting a fine-grained and in-depth evaluation of hallucination mitigation strategies, which complements the macro performance evaluation of subsection 6.3. It quantifies how different mitigation methods reduce various hallucination subtypes across models, revealing their respective strengths and weaknesses in targeting specific hallucination types. The results provide actionable insights for the further optimization of HaluCodeTran and other mitigation frameworks, and help researchers design more refined strategies for different hallucination subtypes.

To provide a comprehensive understanding of hallucination behaviors, we conduct a fine-grained analysis of how different mitigation strategies affect various types of hallucinations across multiple models on the CodeNet dataset (Table 4 and Figure 5).
Across all models, HaluCodeTran demonstrates the most robust mitigation effect, achieving the largest average reduction in total hallucinations: 29% for Llama 3.1, 32% for Gemma 2, and 32% for Mistral.
Regarding Factual Knowledge Conflicts, especially in subtypes such as API Knowledge Conflicts (AKC) and Library Knowledge Conflicts (LKC), HaluCodeTran leads across all models; e.g., HaluCodeTran achieves a consistent reduction in AKC hallucinations across all three models (11% reduction on Gemma 2, 24% on Llama 3.1, 38% on Mistral), indicating its strength in correcting incorrect or hallucinated API calls and exception handling.
Regarding Project Context Deviations, HaluCodeTran exhibits superior performance in mitigating Identifier & Function Confusion (IFC) hallucinations, with the most significant reduction rates among all methods (49% on Gemma 2, 30% on Llama 3.1, 28% on Mistral), demonstrating its ability to effectively address context deviations and inconsistent logical flow in translated code.

However, during hallucination mitigation by prompt engineering, the biased understanding of LLMs may lead to the emergence of new hallucinations.
For instance, RA increases BSC hallucinations in Mistral, while HaluCodeTran partially alleviates this. This suggests that certain hallucination types, such as syntax-level inaccuracies, may require targeted low-level guidance beyond the general prompting and retrieval-based techniques.

Overall, while each mitigation strategy offers strengths in specific areas, HaluCodeTran consistently delivers balanced improvements across all hallucination categories. This underscores the importance of integrating hallucination-aware constraints during both training and inference to address diverse failure modes in code generation.

Finding 6: 
HaluCodeTran achieves the strongest average hallucination mitigation among the evaluated methods, especially for semantic conflicts and project context deviations. This result indicates that taxonomy-aware feedback is a useful direction for improving robust code translation.

## 7. Threat Analysis

The main internal validity threat comes from manual annotation. Code-translation hallucinations can be multi-faceted, and annotators may disagree about whether an erroneous fragment should be labeled as a semantic conflict, factual conflict, project-context deviation, or multiple categories. To mitigate this threat, two annotators with extensive Java, C++, and Python experience independently inspected the generated program, source program, execution result, compiler/runtime diagnostic, and reference solution before adjudication.
A remaining limitation is that manual labeling still depends on human judgment, especially for semantically equivalent rewrites that differ substantially from the reference implementation.

Another internal validity threat is potential information leakage in retrieval-based mitigation. Because CodeNet, Avatar, and Transcoder contain many structurally similar programming tasks, a retrieval method may obtain examples that are too close to the evaluation query. We reduce this risk by excluding the query program from the retrieval candidate set and by evaluating all mitigation methods on the same per-model test split. Nevertheless, near-duplicate problems or same-family solutions may still inflate retrieval-based methods. We therefore treat the mitigation results as evidence of practical repair capability under the benchmark setting, rather than as proof that the framework fully generalizes to unseen project domains.

Construct validity is affected by the definition of hallucination. This work labels generated fragments as hallucinated when they introduce unsupported semantics, invalid language/library knowledge, or inconsistent project context. This definition is broader than factual hallucination in natural-language generation and overlaps with some categories of code translation error. We adopt the broader definition because code translation failures are often observable only through compilation, execution, and source-target semantic comparison. However, the taxonomy may not cover all edge cases, such as performance-only regressions, security-specific vulnerabilities, or errors that require whole-project context beyond the benchmark snippet.

External validity concerns the choice of languages, datasets, and models. Our study focuses on Java, C++, and Python over CodeNet, Avatar, and Transcoder, which are widely used but still do not represent all migration scenarios. Results may differ for less common languages, domain-specific frameworks, multi-file projects, or tasks requiring build-system migration. Model validity is also time-sensitive: we evaluate seven representative LLMs, including GPT-4o and open-source models, but newer models and specialized code agents may exhibit different hallucination patterns.
Reproducibility is limited by model nondeterminism and closed-model availability. Even with fixed prompts and decoding configurations, proprietary APIs may change over time, and stochastic decoding can alter generated code.

## 8. Conclusion

This paper presents an empirical study of hallucinations in LLM-powered code translation. Through thematic analysis and manual annotation of 13,919 hallucination cases across seven LLMs, three benchmark datasets, and six language pairs, we establish a taxonomy that separates semantic consistency conflicts, factual knowledge conflicts, and project context deviations.
Based on the taxonomy, we propose HaluCodeTran, a mitigation framework that integrates retrieval-augmented examples with iterative reflective refinement. Experiments on CodeNet show that HaluCodeTran improves computational accuracy and reduces hallucination cases compared with representative prompting and retrieval baselines. These findings suggest that code-translation hallucination should be studied not only as a correctness failure, but also as a structured source of semantic, factual, and contextual error signals.
In future work, we plan to extend the taxonomy to multi-file migration scenarios, strengthen automated hallucination detection, and study training or alignment strategies that reduce hallucinations before inference-time repair is needed.
