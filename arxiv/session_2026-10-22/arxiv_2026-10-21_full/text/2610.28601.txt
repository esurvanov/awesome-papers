Abstract

Computer-use agents are limited by the interfaces humans give them. An agent may type a spreadsheet cell by cell when a single line of code would do, or print all two thousand lines of a file through a shell to find one function.
Both the interfaces and the knowledge of when to use each are built by hand, which cannot keep pace with new applications, workflows, and models. We argue that interface design should itself be an agent capability. We introduce Agent S4, an autonomous computer-use scientist that builds Evolving Agent Interfaces from task experience.
A meta-agent examines task agents’ trajectories on synthetic training tasks, without success labels, and constructs and revises interfaces and usage knowledge in a repository.
Population-based evolution then selects which repositories to develop further by their performance on validation tasks the meta-agent never sees, favoring changes that generalize beyond the seen tasks.
On OSWorld V2, Agent S4, with Qwen3.8-27B and the evolved repository of interfaces, sets a new state of the art in open-source computer-use agents, reaching 21.3% binary score, 3.8 times the same model with fixed interfaces. This is above both GPT-5.5 (13.0%) and Claude Opus 4.8 (20.6%), at about 4.3% and 1.5% of their respective costs. On ScienceBoard, the evolved interfaces improve the success rate from 41.4% to 58.6% with the same model. These results suggest that useful interfaces can be evolved from experience, making autonomous interface design a source of improvement complementary to advances in models and harnesses. We open-source our code at https://github.com/simular-ai/agent-s

## 1 Introduction

We want AI agents that can discover like we can, not which contain what we have discovered.

— Richard S. Sutton, The Bitter Lesson

Computer-use agents (CUAs) carry out tasks by observing and acting on digital environments. Their interfaces determine what they can observe and which operations they can request. Current computer-use frameworks focus on GUI interaction, supplemented by dedicated tools (Xie et al., 2024; Zhou et al., 2024; Yang et al., 2024). These interfaces are designed by humans and fixed before task execution. Even though these interfaces are built specifically for agents, they still depend on human judgments about what those agents need.

This practice creates three problems for computer-use.
First, it ties progress to manual labor. Computer use is open-ended, and each new family of tasks or model release exposes new failure modes. A human researcher must read trajectories, diagnose failures, and use them to write new primitives, observation formats, or memory mechanisms, and then release the result as a new agent framework with a new preset interface. This loop does not scale with task diversity.
Second, a static interface often mismatches the task, and current methods compensate with test-time compute instead of a better interface. For example, an agent may complete a shell task by clicking to open a terminal window, typing commands one character at a time, and reading screenshots of a partly occluded terminal for feedback, when a direct shell interface would be faster and more reliable (Yuan et al., 2026; Jia et al., 2026; Lu et al., 2025). Additional sampling can raise benchmark scores under such mismatches, but through wasteful and brittle strategies.
Third, methods that compose test-time experience into reusable skills or routines inherit the same limit (Agashe et al., 2025a; Wang et al., 2025b). Each skill is a composition of the preset observations and actions. Distillation can reorder what the interface allows, but it cannot extend it. These problems arise because the interface is treated as a design decision that humans make before deployment, and not as an object that can be studied and improved from the agent’s own experience.

Instead, computer-use interfaces should evolve from the agent’s own experience.
Therefore, we introduce Agent S411

Its output is a repository of mixed interfaces and knowledge about when and how to use them.
The task agent’s model and harness remain fixed, with the harness governing model invocation, execution, permissions, and task budgets.

The task agent uses candidate repositories of Evolving Agent Interfaces to attempt synthetic tasks, producing trajectories without ground-truth success labels. To limit specialization to the tasks that motivated these changes,
Agent S4 separates the evidence used for construction from that used for selection. The meta-agent receives training trajectories, while validation instructions, trajectories, diagnostics, and scores remain hidden
from it. Validation performance guides parent selection. We evaluate the final selected repository on the full benchmark. The meta-agent never observes any benchmark task while constructing interfaces, and the validation tasks influence only which repositories are selected during evolution.

We evaluate Agent S4 on OSWorld V2 (Yuan et al., 2026) and ScienceBoard (Sun et al., 2025). On the full 108-task OSWorld V2 set, Qwen3.8-27B with the evolved repository reaches $21.3\%$ binary success, above both GPT-5.5 ( $13.0\%$ ) and Claude Opus 4.8 ( $20.6\%$ ) at about $4.3\%$ and $1.5\%$ of their respective costs. interface of Qwen CUA. These results show that agents can evolve their own computer-use interfaces from purely synthetic, verifier-free task experience and outperform human-designed interfaces. We compare our setup against evolutionary baselines such as linear evolution and measure the effect of giving the meta-agent a scratch virtual machine to test its evolved interfaces. Finally, we qualitatively compare agents that act through evolved interfaces with agents that use fixed, human-designed interfaces.

## 2 Problem Formulation

We study how the interfaces of a computer-use agent can be evolved from task experience.
An agent updating a spreadsheet through screenshots must identify visible
cells, enter values, and inspect the display to check the result. A
structured interface can expose the relevant rows and formulas, accept a
bulk edit, and return the changed values. Both interfaces can achieve the
same subgoal (Coutaz et al., 1995), but they require
different decisions and provide different feedback. Their cost and
reliability can also differ. Task experience can reveal which operations
are missing, which observations are difficult to use, and where a different
interface would help.

We call reusable interfaces that are constructed and improved from task
experience Evolving Agent Interfaces.
To make interfaces and knowledge available across tasks, we represent them
in a persistent repository $R$ . It contains executable interfaces and
supporting knowledge such as capability descriptions, reusable workflows,
configuration, and notes about when and how to use them.

Let $\mathcal{D}$ be the target distribution of tasks and $A$ the agent
that uses the repository. Let $J(A,R,x)$ denote the expected task score
when $A$ uses repository $R$ to attempt task $x$ . We seek a
repository constructed from task experience that maximizes this score across
tasks,

 $R^{\star}\in\arg\max_{R}\mathbb{E}_{x\sim\mathcal{D}}\!\left[J(A,R,x)\right].$ 

(1)

This objective concerns performance beyond the experience used to construct
the repository. We next define the agent, interfaces, and interaction
process that determine $J$ .

Computer and task.

A computer $C$ has a state $s\in\mathcal{S}$ comprising its files,
running applications, displays, services, and reachable network endpoints.
A task $x=(g,s_{0},V_{x},B_{x})$ consists of an instruction $g$ , an initial
state $s_{0}$ , an evaluator $V_{x}$ that scores the outcome, and a budget
 $B_{x}$ .

Interface.

An interface
 $I=\langle c_{I},\mathcal{A}_{I},\mathcal{O}_{I}\rangle$ connects an agent to
one or more parts $c_{I}$ of the computer through a language of requests
 $\mathcal{A}_{I}$ and a language of observations $\mathcal{O}_{I}$ .
Executing a request can change the state and returns an observation,
 $(s^{\prime},o)\sim T_{I}(\cdot\mid s,a)$ . A GUI interface, for example, accepts
clicks and keystrokes and returns screenshots. A shell interface accepts
bash commands and returns a string with the requested information, return values or error message.

Model, harness, and agent.

A model $M$ is a language model that generates responses and
requests conditioned on its input context. A harness $H$ 
manages model invocation, request execution, task budgets,
permissions $P_{H}$ , and preparation of the model’s context, including any
context compaction. An agent $A=(M,H)$ is the model operating
through this harness. The agent initially has access to a base set of interfaces
 $\mathcal{I}$ . The harness executes requests through these interfaces and
places the resulting observations in the model’s context.
For example, the harness can execute a spreadsheet helper
under a time limit and permission boundary. The helper defines the requests
for reading or editing cell ranges and the values returned to the agent.
The harness governs execution, while the interface specifies the available
operations and feedback.

Computer use.

Computer use is the process through which an agent observes and acts
on a computer through available interfaces to accomplish a task.
The interaction history $h_{t}$ records the interfaces,
requests, and observations from earlier steps. At step $t$ , the agent
chooses an interface and a request based on the instruction and this history,
with context preparation by $H$ left implicit,

 $(I_{t},a_{t})\sim M(\cdot\mid g,h_{t},\mathcal{I}),\qquad(s_{t+1},o_{t})\sim T_{I_{t}}(\cdot\mid s_{t},a_{t}).$ 

(2)

The available interfaces shape
which operations the agent can request and what evidence it receives about
their effects.

Formally, $R=(\mathcal{I}(R),K(R))$ , where $\mathcal{I}(R)$ contains
its executable interfaces and $K(R)$ its supporting knowledge.
The repository
supplies interfaces $\mathcal{I}_{R}=\mathcal{I}\cup\mathcal{I}(R)$ and
knowledge that informs the agent’s choices,

 $(I_{t},a_{t})\sim M(\cdot\mid g,h_{t},\mathcal{I}_{R},K(R)).$ 

(3)

Each attempt is subject to the task budget $B_{x}$ and harness permissions
 $P_{H}$ . The score $J(A,R,x)$ averages the evaluator’s score over these
interactions.

Interface evolution.

Interfaces implemented as programs can be revised like any other software.
A program can export a material schedule through Blender’s Python API,
extract selected rows from a Calc workbook, or return supplier prices
gathered through a sequence of browser operations. Each defines its own
requests and observations
(Wang et al., 2024; Liang et al., 2023).
Because these interfaces are code, an agent that can read trajectories and
write code can redesign them. It can decide which operations to combine,
what information to return, and how a result can be checked. We call this
process interface evolution. Given a repository $R_{k}$ and the
trajectories $\mathcal{T}_{k}$ of the agent using it, an evolution step
produces a revised repository,

 $R_{k+1}=E\!\left(R_{k},\mathcal{T}_{k}\right).$ 

(4)

Task experience guides each step. Repeated reconstruction of the same
calculation across tasks can motivate a reusable operation, and a repeated
inability to verify a change can motivate a new observation. Trajectories
with the revised repository then provide evidence for further revision.
Section 3 instantiates $E$ with population-based
evolution.

## 3 Agent S4

Figure 3: Agent S4 turns task experience into an evolving repository of interfaces and knowledge.
Starting from parents selected by held-out validation, the meta-agent
studies their task trajectories to identify limitations, then revises one
repository through mutation or combines ideas from two through crossover.
Task agents then use the descendant to produce trajectories on synthetic
tasks and a separate score on held-out validation tasks. Each descendant
joins the population alongside its parents, allowing earlier designs to be
revisited and recombined over successive iterations.

Agent S4 builds Evolving Agent Interfaces and usage knowledge
through population-based evolution of repositories, keeping the task agent’s
model $M$ and harness $H$ fixed. Each iteration selects parents from a population,
constructs a descendant through mutation or crossover, evaluates it, and
adds it to the population while retaining its parents
(Figure 3). Training experience guides the
repository changes, and held-out validation guides subsequent selection.
This optimizes Equation 1 for the fixed task
agent $A$ . Algorithm 1 gives the
procedure.

## 3.1 Population and selection

The population contains repository variants, each with its own interfaces
and knowledge. We initialize $\mathcal{R}_{0}=\{R_{0}\}$ from a seed
repository (Appendix A.2) and evaluate it to obtain training trajectories and a validation
score. These records are retained with each candidate as the population
grows.

At each step, an operator schedule chooses mutation or crossover.
Mutation requires one parent, and crossover requires two distinct parents.
For each parent, binary tournament selection draws two eligible variants
uniformly and chooses the one with the higher validation score. A sole
eligible candidate is selected directly. For crossover, the first selected
parent is excluded from the second selection. The selected repositories
and their saved training trajectories provide the starting point for the
next descendant.

## 3.2 Mutation and crossover

The meta-agent $A_{\mathrm{meta}}=(M_{\mathrm{meta}},H_{\mathrm{meta}})$ 
constructs descendants using a fixed model and harness. Its computer
 $C_{\mathrm{meta}}$ holds the selected parent repositories, their training
trajectories, and a lineage notebook in its filesystem. It studies the
recorded behavior and observations to diagnose apparent failures and
inefficiencies and form hypotheses about useful changes. For example,
repeated cell-by-cell edits can motivate a bulk spreadsheet interface,
while poor use of an existing interface can motivate revised usage
knowledge. It implements these hypotheses through file, shell, and code
interfaces using one of two operators.

Mutation.

Starting from one parent $R_{p}$ , the meta-agent adds, revises, or removes
interfaces and knowledge. Changes can affect operations, returned
observations, and reusable workflows, including capabilities inherited
from the seed.

Crossover.

Given two distinct parents $R_{a}$ and $R_{b}$ , the meta-agent constructs
one coherent descendant by choosing between overlapping interfaces,
porting complementary capabilities, or combining their ideas into new
code and knowledge. The descendant need not contain the union of its parents.

Both operators produce a single descendant repository $R^{\prime}$ . The fixed
base access $\mathcal{I}$ remains unchanged as the repository’s interfaces
 $\mathcal{I}(R)$ and knowledge $K(R)$ evolve.

## 3.3 Evaluation and population update

After construction, we freeze $R^{\prime}$ and run the fixed task agent $A$ 
on synthetic training tasks $\mathcal{T}_{\mathrm{train}}$ and disjoint validation tasks
 $\mathcal{T}_{\mathrm{val}}$ . The repository is available in the task agent’s filesystem, and
a fixed prompt identifies its location and explains how to discover its
capabilities. The agent can consult its documentation and source code and
invoke the interfaces it selects through the harness’s existing
code-execution tool (Appendix A.2). Each rollout
 $\tau\sim\operatorname{Rollout}(A,R^{\prime},C,x)$ starts from task $x$ ’s
initial state within its budget and records the instruction, interfaces,
requests, and observations. The repository remains fixed during execution.
Temporary programs written by the agent do not persist across tasks.

Training experience and validation score.

Training trajectories have no ground-truth success labels. We save them as
evidence for future repository changes and reuse them whenever the
descendant becomes a parent. Validation rollouts provide a separate
selection score for each candidate $R$ ,

 $F_{\mathrm{val}}(R)=\frac{1}{|\mathcal{T}_{\mathrm{val}}|}\sum_{x\in\mathcal{T}_{\mathrm{val}}}V_{x}\!\left(\operatorname{Rollout}(A,R,C,x)\right).$ 

(5)

Asymmetric evaluation.

Only training trajectories are exposed to the meta-agent. Validation tasks,
trajectories, diagnostics, and scores remain inaccessible to it.
Validation therefore influences construction through parent selection,
without supplying direct feedback for repository edits.

Adding the descendant.

We add $R^{\prime}$ to the population alongside its parents regardless of its
validation score. This retains alternative designs for further development
and recombination. Parent links form a directed acyclic graph, with one
parent per mutation and two per crossover. Optional pruning removes
parent eligibility while preserving lineage records. The updated population
supplies candidates for the next iteration. After $N$ steps, we select a
member of $\mathcal{R}_{N}$ by validation performance, using a
benchmark-specific criterion (Section 4), and freeze it for evaluation on
target tasks $\mathcal{T}_{\mathrm{test}}$ . The meta-agent observes none of these tasks during
construction, and validation tasks drawn from the same benchmark affect only
selection.

## 4 Experimental Setup

Benchmarks and task sets.

OSWorld V2 (Yuan et al., 2026) is our primary benchmark, and
ScienceBoard (Sun et al., 2025) tests generalization to niche scientific
computer-use applications and workflows. Repository evolution uses 30
synthetic training tasks for OSWorld V2 and 48 for ScienceBoard, plus 15
official validation tasks for each. Synthetic task attempts yield
trajectories without ground-truth success labels. The meta-agent receives
these training trajectories. Validation scores guide selection, but
validation trajectories and evaluators remain outside its evidence.
Full-benchmark results cover 108 OSWorld V2 and 169 ScienceBoard tasks,
including the 15 validation tasks of each. Benchmark details appear in
Appendix A, and synthetic task
construction is described below and in
Appendix D.

Model and harness.

On both benchmarks, the task agent and meta-agent use Qwen3.8-27B (Qwen Team, 2026) in a
modified Prime Agent harness (Karten et al., 2026) that executes code in a persistent IPython
kernel, with Medium reasoning, a 131,072-token context window, a
32,000-token output limit, and automatic context compaction. The model and
harness remain fixed within each search.
Appendix A gives the harness version,
sampling parameters, and compaction settings;
Appendix C gives implementation
constraints and builder prompts.

A scratch VM with the same AMI as the benchmark tasks lets the meta-agent inspect running applications and try interface code during construction. Without it, the meta-agent works from repository code and saved training trajectories. In all four settings, task agents execute in benchmark VMs. Each meta-agent construction has a two-hour wall-clock budget for OSWorld v2 and 1 hour wall clock budget for ScienceBoard.

Validation and repository selection.

On OSWorld V2, we select the repository that fully solves the most validation tasks and break ties by mean partial validation score, since binary success is the harder metric to improve. On ScienceBoard, whose evaluator reports only success, we select the repository with the highest validation success rate.

In the case of Scienceboard, we also run a Denoise operation after every 5 steps. This picks the top-3 variants in the population and reevaluates them. The repositories validation score is then replaced by the updated running average. We analyze the effect of this denoising step in Section 7.3. We do not run the denoising step for OSWorld-v2 due to much longer time and cost of evolution and repeated evaluations.

Evaluation budgets and cost.

Prime Agent task rollouts have a 300-step budget on both benchmarks, where a
step is one completed assistant response and can contain multiple actions.
New OSWorld V2 training and validation rollouts also have a two-hour
wall-clock limit. The final evaluation keeps the step budget but has no
per-task wall-clock limit. ScienceBoard applies a 60-minute wall-clock limit
to training, validation, validation repeats, and full evaluation.

We report binary success and partial score on OSWorld V2 and success rate on
ScienceBoard. OSWorld V2 task-solving costs are estimated from model-token
usage at Parasail’s input and output rates, assuming an $80\%$ input-cache
hit rate, and exclude repository construction and runtime infrastructure.
Appendix A lists the rates and
remaining runtime settings.

Synthetic task construction.

We constructed 30 synthetic tasks for OSWorld V2 and 50 for ScienceBoard, of which 48 are used (Appendix E),
giving Agent S4 task experience for evolving Agent Interfaces
and usage knowledge without ground-truth success labels. Tasks follow each
benchmark’s methodology but use independently authored scenarios. For
OSWorld V2 (Yuan et al., 2026), we studied its task-construction
principles and challenge-phenomenon taxonomy, and scaled the reported counts
of overlapping phenomena into approximate targets for our 30 tasks. These
targets guided the representation of capabilities such as cross-source
reasoning, visual-spatial precision, and implicit-state inference. For
ScienceBoard (Sun et al., 2025), we followed a planned distribution across
six scientific applications and preserved its compact tasks, usually
centered on one application and one meaningful outcome.

Tasks were created agentically by a coordinator (GPT-6 Astra), authors
(GPT-5.6-Sol), and independent reviewers (GPT-5.6-Sol). The coordinator
tracked accepted tasks against the planned counts and assigned new tasks to
phenomena or applications below target. Each author started from a fresh
context with application documentation, design requirements, and summaries
of accepted synthetic tasks, but without access to official task instances,
evaluators, or task-agent trajectories. Authors produced instructions, input
artifacts, and environment setup specifications, documenting provenance and
capability assumptions.

Reviewers checked originality, coherence, feasibility, and appropriate
complexity. To ensure that no synthetic task overlaps with an existing
benchmark task, they compared each candidate’s purpose, dependencies,
operations, and deliverables against official instruction and setup metadata
and against the accepted synthetic set. Each claimed challenge had to be supported by the
actual materials. The coordinator returned concrete defects for up to two
revision rounds, rejected overlapping designs, and kept official comparisons
out of author feedback. Automated input and setup checks supplemented these
reviews, and only accepted versions entered the training set. No step graded
task-agent attempts or produced reference solutions.

With a repository of interfaces evolved by Agent S4, a 27B open-source model reaches the highest binary success on open-source models at a small fraction of frontier-model cost. Table 2 compares results on the full OSWorld V2 benchmark. We report the best repositories from population evolution with and without a scratch VM, alongside the Qwen CUA baseline and reported open-source and closed-source results from OSWorld V2, which retain the single-action and batched-action settings of the reference evaluations. Binary success measures complete task execution, partial score measures intermediate progress, and cost covers task-solving model calls. Binary gains are the hardest to obtain on OSWorld V2. Strong agents reach similar partial progress, and what separates them is turning that progress into fully completed tasks (Yuan et al., 2026). With the repository evolved without a scratch VM, Qwen3.8-27B achieves $21.30\%$ binary success at $1.10 per task, above the $13.00\%$ of GPT-5.5 and the $20.60\%$ of Claude Opus 4.8 with batched actions, at $4.3\%$ and $1.5\%$ of their $25.50 and $72.40 costs. With the repository evolved with a scratch VM, it reaches a partial score of $51.06\%$ at $1.27 per task.

Evolving interfaces improve the same model. Agents with fixed interfaces already seek programmatic access (Yuan et al., 2026). Terminal commands account for $24.7\%$ of their actions, and GPT-5.5 devotes $78\%$ of its budget to code, API, or file operations (Yuan et al., 2026, Section 4). Under a fixed interface, each such program is typed through the desktop and its result is read from a screenshot. Acting through agent evolved interfaces removes this indirection, and the evolved repository supplies interfaces for the applications and data that recur across tasks. Compared with the Qwen CUA baseline, which runs the same Qwen3.8-27B model with fixed interfaces, this raises binary success from $5.56\%$ to $21.30\%$ and partial score from $20.69\%$ to $46.90\%$ , or to $51.06\%$ with the repository evolved with a scratch VM, while lowering task-solving cost from $1.39to$ 1.10 per task.

## 6 Generalization

The gains are largest on KAlgebra, where success rises from $48\%$ to $68\%$ . ## 7.2 Qualitative Study of Evolved Interfaces

A taxonomy of evolved interfaces.

To compare runs, we label each interface by the part of the computer it
covers and the purpose it serves. The four labels can overlap:

• 

System-wide interfaces cover the desktop and operating
system as a whole, such as inspecting windows or launching and
monitoring background processes.

• 

App-specific interfaces expose the objects of one named
application, such as spreadsheet ranges in LibreOffice, tracks in a
REAPER audio project, or molecules in ChimeraX.

• 

Cross-App interfaces work on data or platforms shared by
many applications, such as reading and rendering PDF files regardless of
which application created them, or reading pages on any website.

• 

Task-specific interfaces package a procedure for a
particular goal together with a check of whether it is achieved, such as
checking a Lean proof, compiling it, updating the editor and reporting
completion.

Interfaces also grow after they are introduced, so we label each added
operation separately. For example, the office-document interface is App-specific
because it edits documents through LibreOffice itself, but an operation added
to it later that edits OpenDocument files directly, without the application,
is Cross-App. Figure 4 counts new interfaces and
these later extensions separately. Table 7 in
Appendix B.3 gives examples of evolved
interfaces, with what each lets the agent observe and do.

so the counts per label can add up to more than the total. Most of its growth therefore deepens interfaces the
agent already has. With a scratch VM, where the meta-agent can open

Cross-App. Seven carry both labels, such as the interfaces for editing musical
scores, audio projects and 3D scenes, which operate one application while reading and writing
file formats that other applications share. Cross-App extensions rise to 129. These
additional application interfaces are a likely explanation for the higher
partial score of the best repository evolved with a scratch VM.

On ScienceBoard, evolution introduces seven new interfaces and 91 extensions.
Six of the new interfaces and 77 of the extensions are App-specific, for
scientific applications such as ChimeraX, KAlgebra, GRASS GIS and Lean. Its
three Task-specific extensions package procedures for displaying a map in
GRASS GIS and completing a proof in Lean.

Across all three runs, evolved interfaces let the agent observe the desktop,
an application’s own objects, data shared across applications, and whether a
goal has been met, and act on each of these in a single call. Evolution
therefore widens the range of software the agent can operate and raises the
level at which it sees, acts and checks its progress.

## 7.3 Repeated Validation during Evolution

Figure 6: Repeated validation separates a high first score from
consistent performance. Red shows the best first-evaluation score on
ScienceBoard and blue the best mean over repeated evaluations.

Long-horizon computer-use tasks show substantial run-to-run variance (Gonzalez-Pumariega et al., 2026), so a single validation run can overrate a repository. On ScienceBoard, we therefore re-evaluate the three highest-scoring repositories every five steps and score each by the mean of its evaluations (Section 4). Figure 6 shows why this matters. Repositories if-003 and if-004 reach the highest first score, $73.33\%$ , at steps 3 and 4. A second evaluation lowers their means to $60.00\%$ and $66.67\%$ . The selected repository, if-016, scores $73.33\%$ , $66.67\%$ , $73.33\%$ and $73.33\%$ across four evaluations, for a mean of $71.67\%$ . A first score alone would have ranked if-003 among the best repositories even though its mean is $60.00\%$ .

## 8 Related Work

Computer-use agents and interaction design.

Computer-use systems differ in how they expose observations and actions, and
SWE-agent showed that this agent-computer interface shapes
performance (Yang et al., 2024). Agent S and Agent S2 organize planning,
perception, and action through engineered agent
components (Agashe et al., 2025a; Agashe et al., 2025b), while UI-TARS learns policies for GUI
interaction (Qin et al., 2025; Wang et al., 2025a). Other systems add programmatic access
beside GUI actions, through application
APIs (Lu et al., 2025; Song et al., 2025b; Zhang et al., 2026a),
code execution (Song et al., 2025a), or tool
calls (Yang et al., 2025; Jia et al., 2026).
Agent S3 and its behavior judge improve task completion by selecting among
multiple rollouts (Gonzalez-Pumariega et al., 2025). In these systems, code and tools, when
available, are one action among a predefined set. Agents that act only by
writing and running code can outperform agents that choose from predefined
actions (Wang et al., 2024; Lu et al., 2026). These
interfaces are designed by people or written within a single task.
Agent S4 instead evolves them across tasks and retains the resulting
operations and usage knowledge in a repository that can be developed beyond
the task that motivated a change.

Skills, memory, and tool construction.

Reflexion stores textual feedback for later attempts (Shinn et al., 2023),
and Agent Workflow Memory induces reusable procedures from
experience (Wang et al., 2025b). Reuse can also take executable form. LLMs as Tool
Makers separates tool construction from subsequent tool
use (Cai et al., 2024), and SkillWeaver discovers and practices
web interactions to build APIs that other agents can
reuse (Zheng et al., 2025). CUA-Skill instead provides an engineered library
of parameterized computer-use skills and composition graphs (Chen et al., 2026).
These methods establish that agents can benefit from persistent knowledge
and executable tools. Our search operates over complete repository versions
containing interfaces, observation routines, configuration, and usage
knowledge. Mutation and crossover can change these components together,
with selection based on their combined effect on task-agent performance.

Automated agent design and evolutionary search.

ADAS searches for agent designs expressed in code (Hu et al., 2025), and the
Darwin Gödel Machine modifies its own coding agent while maintaining an
archive of alternatives (Zhang et al., 2025). Self-Harness studies execution traces,
proposes harness changes, and validates them through regression
tests (Zhang et al., 2026b). AlphaEvolve and ShinkaEvolve combine
model-generated code changes with evolutionary search and executable
evaluation (Novikov et al., 2025; Lange et al., 2025), while GEPA uses trajectory
reflection to evolve prompts and combine complementary
improvements (Agrawal et al., 2025). Validation-based control of overfitting also
predates language-model agents, including evolutionary curtailment in
genetic programming (Fitzgerald and Ryan, 2011).
Agent S4 evolves repositories of interfaces and knowledge through
population-based search with asymmetric access to evaluation evidence.
The meta-agent studies synthetic-task trajectories without ground-truth
success labels and implements changes to application-specific operations,
capability descriptions, and reusable workflows. The fixed harness
retains control of model invocation, execution, permissions, and budgets.
Keeping capabilities in the repository makes them available for revision,
selection, recombination, and reuse with compatible agents and harnesses.
Validation tasks, trajectories, diagnostics, and scores remain with the
controller and are hidden from the meta-agent. Held-out performance
determines which variants become parents, applying selection pressure
beyond the tasks used to construct the software.

## 9 Conclusion

We presented Agent S4, which treats interface design as an agent
capability: a meta-agent studies computer-use trajectories to construct and
evolve reusable interfaces and knowledge about when and how to use them.
The experience used for interface construction comes entirely from synthetic
tasks, without ground-truth success labels or task verifiers; separate
held-out validation guides repository selection. Qwen3.8-27B with a repository of
interfaces evolved by Agent S4 reaches $21.3\%$ binary success on the full 108-task OSWorld V2
benchmark, above both GPT-5.5 and Claude Opus 4.8, at about $4.3\%$ and
 $1.5\%$ of their reported task-solving costs. On the full 169-task ScienceBoard
benchmark, a separate evolution run reaches $58.58\%$ success, compared with
 $41.4\%$ for Qwen CUA. Repository and trajectory analyses show how evolution
constructs application interfaces and refines the operations and observations
available to subsequent task agents. These findings support learning
interfaces from synthetic experience as a way to improve computer use while
keeping the task agent’s model and harness fixed, complementary to advances
in both.

## Appendix A Experimental Design

## A.1 Benchmark Detail

OSWorld V2.
OSWorld V2 (Yuan et al., 2026) evaluates computer-use
agents on 108 long-horizon workflows spanning everyday and professional
activities in real desktop and web applications. Tasks require agents to
combine information across sources, track application state, and adapt to
changes during execution. The benchmark reports both binary task completion
and partial scores, measuring whether agents can complete an entire workflow
and how much of its requirements they satisfy. We use it as our primary
benchmark for evaluating repository evolution on complex computer-use tasks.

ScienceBoard.
ScienceBoard (Sun et al., 2025) evaluates autonomous agents in realistic
scientific workflows involving professional software. It contains 169
human-curated tasks across scientific domains such as biochemistry,
astronomy, and geoinformatics. These tasks combine scientific reasoning with
software operation through graphical and command-line interfaces, testing
whether agents can translate domain-specific instructions into successful
execution in scientific environments. We use ScienceBoard to evaluate
whether repository evolution extends to specialized scientific applications.

Harness.

For our OSWorld V2 and ScienceBoard repository-evolution experiments, we use a modified
harness based on Prime Agent version
0.8.0-beta.546.1.a9b5d88,44

an IPython-backed coding agent. The harness prompts are reproduced in
Appendix C. The model issues tool calls containing
Python code, which the harness executes in a persistent IPython kernel and
returns the execution outputs to the model for the next step. Variables,
imports, and function definitions persist across calls, allowing the agent
to reuse intermediate results and invoke repository interfaces throughout a
task. Prime Agent’s native threshold-based context compaction is enabled
within the 131,072-token context window. The harness reserves 36,096 tokens
for the 32,000-token output budget and a 4,096-token overhead margin.
Compaction is triggered when the last observed token usage plus the estimated
trailing messages exceeds 94,976 tokens. It summarizes older conversation
history while retaining the most recent 20,000 tokens verbatim.
Prime Agent also automatically rescales oversized images to fit within

compression or downscaling as needed to keep the base64-encoded payload
below 4.5 MiB. We disable Prime Agent’s automatic harness refinement. The task agent can still record notes in the harness state during a task, but this state is deleted before every task, so the repository is the only state that carries over between tasks.

Repository access.

For OSWorld V2, each candidate repository is installed at
/home/user/shadow_interface/. A fixed task-agent prompt supplies this
path, directs the agent to inspect the toolkit, and encourages its use as
the primary approach. The agent invokes python3 -m shadow_interface
through the harness’s IPython tool. The capabilities subcommand
lists interfaces with signatures and short descriptions;
doc <module>.<function> displays full documentation, and
call <module>.<function> [args ...] invokes an interface.
The prompt also directs the agent to read the source code when the
documentation is insufficient. These files expose the repository’s
interfaces and usage knowledge without changing the harness’s tool set.

the Chrome DevTools endpoint, and none is specific to a benchmark
application. A setup script installs the tools these interfaces rely on, and
a command-line entry point provides the capabilities, doc

Model Service.

We access Qwen3.8-27B through
Parasail provider.
We set temperature to 1, top- $p$ to 0.9, and thinking effort to Medium,
with a 131,072-token context window and a 32,000-token output limit.
The same model is used for the task agent, GUI grounding, and the interface
builder. We estimate task-solving costs using Parasail’s rates of $0.24 per million
uncached input tokens, $2.20 per million output tokens, and $0.05 per
million cached input tokens. The cost estimates assume an 80% input-cache hit rate.
The Qwen3.8-27B cost estimates in Table 2 use these
rates. These estimates cover task-solving model calls;
repository-evolution and runtime infrastructure costs are excluded.

Cloud infrastructure.

For OSWorld V2, each task episode runs in a freshly initialized virtual
machine on AWS using the same benchmark release image, with a screen
resolution of $1920\times 1080$ pixels. The virtual machine is terminated
after the episode. Model inference is accessed through the API described
above.

Runtime settings.

Our Prime Agent task rollouts use a budget of 300 completed assistant
responses per task, with a timeout of 720 seconds for each model API call.
A response may invoke code that performs multiple GUI or application actions.
New OSWorld V2 training and validation rollouts have a two-hour wall-clock
limit. OSWorld V2 full evaluation retains the API-call timeout and
300-step budget without a per-task wall-clock limit. ScienceBoard uses
a 60-minute wall-clock limit in training, initial validation, validation
re-evaluations, and full evaluation. The meta-agent has a separate
two-hour wall-clock limit for each repository construction. Infrastructure
failures may trigger recovery runs.

## Appendix B Experimental Analysis

## B.1 Evolution Lineage

Figure 7 shows the repository lineage for the
30-step OSWorld V2 population run with a builder scratch VM. Starting
from the seed, construction alternates
between mutation of one parent and crossover of two distinct parents.
Binary tournaments based on mean partial validation score select parents
from the eligible population; after step 10, the five lowest-scoring
variants lose parent eligibility. The resulting graph branches from
earlier repositories and combines branches through crossover, allowing
prior variants to contribute beyond the next construction step.
Validation performance does not improve monotonically. At step 24,
crossover combines repositories from steps 2 and 6 to obtain the highest
mean partial score, $50.2\%$ , compared with $35.8\%$ for the seed. Its
binary success rate is $26.7\%$ , tying steps 5, 25, and 29, compared with
 $6.7\%$ for the seed. Thus, earlier branches remain useful well beyond
their construction step, and the two validation metrics distinguish
different aspects of repository performance.

The aggregate comparison also shows why helper-level improvements need
not shorten every trajectory. Across all tasks, mean call counts remain
nearly unchanged. The full-credit subsets differ, and on the 11 tasks

savings coexist with other sources of task-level variation.

## B.4 Additional Case Study

We examine how a reusable Chrome DevTools Protocol (CDP) interface changes
browser interaction in a client photo-delivery task. The agent must read
instructions in TeamChat, reconcile invoices with payments in VaultBank,
and prepare and email either finished photos or watermarked previews.
We compare the seed repository with evolved variant if-011 on
the same task. The seed provides browser target discovery but lacks a
page-evaluation helper, whereas the evolved repository exposes
browser.page_eval and browser.page_text for executing
JavaScript and retrieving page text through CDP.

These 30 synthetic training tasks (s_001 through s_030) have NO verifiers.

Read the TRAIN trajectories under eval_results/ recursively. Each task folder

Use instructions, actions, tool outputs, screenshots, errors and observed

artifacts to identify repeated work, missing capabilities and fragile workflows.

An agent’s claim that it completed a task is not verified success. Distinguish

observed evidence from hypotheses, and record both in notebook.jsonl. Do not

invent a verifier or labels. Improve the evolving software from trajectories.

## What you can modify

- ‘shadow_interface/‘ — all your code goes here

- ‘shadow_interface/context_compaction.json‘ — evolvable mini-SWE context-window, reserve, keep-recent, and checkpoint-summary policy

- ‘notebook.jsonl‘ — append observations (persists across mutations)

## Constraints

- Python stdlib only — pip is disabled on VMs

- VMs are fresh — no state persists between tasks

- Task agents are autonomous — they may or may not use your tools

- Do NOT modify files outside shadow_interface/ and notebook.jsonl

- Do NOT create or modify SYSTEM_PROMPT.md — the task agent’s system prompt is controlled by the orchestrator

- You do NOT run evals — the orchestrator evaluates after you finish

## Goal

Build general, reusable tools that help agents complete tasks more reliably and efficiently, using trajectory evidence. The orchestrator separately measures each version on the older validation set; synthetic scores remain ungraded.

Two qualities to keep in mind as you build:

- **Generality.** Prefer helpers that work across many tasks. A helper that only addresses one specific task is a sign you stopped one level too early — keep abstracting until the same helper would serve the next, related task.

- **Discoverability.** Write clear signatures and docstrings. Agents find your tools via ‘python -m shadow_interface capabilities‘ and ‘python -m shadow_interface doc <name>‘; helpers without docstrings get passed over for less specialized ones the agent can read.

## Appendix D OSWorld V2 Synthetic Training Tasks

We use 30 synthetic tasks to provide construction experience for
Agent S4. The set contains 21 tasks that use desktop applications and
