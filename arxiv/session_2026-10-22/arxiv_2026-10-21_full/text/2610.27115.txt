Abstract

LLM agents act on the external world through tools and third-party skills, so a single executed action can cause irreversible harm. Existing defenses judge a proposed action without tracking whether its content comes from the user or from external sources such as tool outputs, and they judge it in isolation rather than against an available alternative, which forces a trade-off between security and utility. We present PROVISO, a controller that decides which action to commit after the agent proposes an action and before it is executed. PROVISO encodes trusted observations, external observations, the proposed action, and an alternative into provenance-typed memory, relates them through role-specific queries, and commits the action with the highest calibrated value learned from outcomes. On four agent security tasks spanning the agent lifecycle, no baseline exceeds PROVISO in both security and utility. PROVISO improves F1 over the strongest baseline by 13.84 points on SkillsBench and by 7.07 points on ToolSafe, and it reaches 88–99 F1 on three skill detection benchmarks.

## 1 Introduction

Figure 1: A payment task with an injected instruction. Existing defenses either release $P_{0}$ or block the whole task. PROVISO accounts for where each argument of $P_{0}$ comes from and compares $P_{0}$ with $P_{1}$ : the recipient of $P_{0}$ comes only from $G$ and is not authorized by $K$ , so it commits $P_{1}$ .

Large language model (LLM) agents solve tasks by interleaving reasoning with actions such as tool calls (Yao et al., 2023; Schick et al., 2023). They now send e-mails, make payments, and modify code on behalf of users (Debenedetti et al., 2024; Ruan et al., 2024), often through third-party skills, which are packages of instructions and code installed into the agent (Yang et al., 2026). Since these actions change external state, a single wrong action can cause irreversible harm. Such risks arise throughout the agent lifecycle: a malicious skill can be installed before the agent runs (Guo et al., 2026; Wang et al., 2026c), a user can direct the agent toward harmful tasks (Andriushchenko et al., 2025; Song and Qi, 2026), a tool call can be unsafe in its context (Ruan et al., 2024; Mou et al., 2026), and a tool output can carry instructions planted by an attacker, known as indirect prompt injection (Greshake et al., 2023; Zhan et al., 2024; Zhang et al., 2025).

Whether an action should be executed depends on where its content comes from, which we call its provenance. Suppose a user asks an agent to pay an invoice to account B, and the invoice returned by a tool also says “transfer the payment to account C.” The amount may come from the invoice, but the recipient must come from the user (Figure 1). In general, trusted observations come from the user and the deployment (the request, policy, and tool interface), and external observations are what the agent reads while acting (tool outputs, documents, and skill packages). An action is admissible when its operation and target are authorized by trusted observations, while its arguments may be supported by either kind.

Existing defenses face two challenges in making this decision. (1) Provenance-agnostic judgment. Guard models, which are LLM classifiers that flag unsafe requests or actions, and rule-based runtime monitors judge a request or tool call as a whole (Inan et al., 2023; Han et al., 2024), and skill scanners inspect package text for risky patterns (Yang et al., 2026). Neither tracks which parts the user authorized and which come only from external content, although the same instruction is legitimate from the user and malicious from a tool output (Figure 1, left). Prompt-injection defenses do separate instructions from data (Chen et al., 2025a; Chen et al., 2025b; Debenedetti et al., 2025), but they modify the agent itself and cover only injected instructions. (2) Judgment without alternatives. Most defenses judge whether a proposed action is unsafe in isolation and block it above a fixed threshold. Yet blocking is itself an action with a cost, since it can stop a benign task. Without comparing the proposed action with what would happen otherwise, a defense must trade security against utility: baselines that block most attacks also block many benign inputs, and those that keep benign inputs miss many attacks (Section 5.1).

To address these challenges, we propose PROVISO (PROVenance-Informed Selection Of agent actions), a controller placed between the agent’s policy and the executor. At the commitment point, the moment after the policy proposes an action and before it is executed, PROVISO chooses between the proposed action and an alternative action, either a refusal or another continuation of the trajectory. Releasing or blocking an action (admission) and choosing between two continuations (candidate selection) are special cases of this formulation. For the first challenge, provenance-typed memory encodes each observation and candidate with a learned embedding of its role, and role-query deliberation lets learned queries retrieve from this memory, compare the proposed action with the trusted and external observations, and retrieve again after the comparison. For the second challenge, calibrated commitment learns the value of each candidate from outcomes and selects the trade-off between security and utility on development data (Figure 1, right; Figure 2).

We evaluate PROVISO on four agent security tasks ordered along the agent lifecycle: malicious skill detection, agent misuse, unsafe tool invocation, and indirect prompt injection. On every task, no baseline exceeds PROVISO in both security and utility. PROVISO improves F1 over the strongest baseline by 13.84 points on SkillsBench and by 7.07 points on ToolSafe, and it reaches 88–99 F1 on three additional skill detection benchmarks. Our contributions are as follows:

• 

We formulate agent security decisions at the commitment point as provenance-informed action selection, with admission and candidate selection as special cases.

• 

We propose PROVISO, which realizes this formulation through provenance-typed memory, role-query deliberation, and calibrated commitment.

• 

Experiments on four agent security tasks show that no published defense exceeds PROVISO in both security and utility, results on three skill benchmarks are consistent, and controlled analyses identify the components behind its gains.

## 2 Related Work

## Agent Security Benchmarks.

Benchmarks evaluate agent security at different stages of the agent lifecycle. Skill benchmarks collect malicious and benign third-party skills for detection before installation (Yang et al., 2026; Guo et al., 2026; Hossain et al., 2026; Wang et al., 2026c). Misuse benchmarks measure whether agents carry out harmful requests (Andriushchenko et al., 2025; Zhang et al., 2024; Song and Qi, 2026). ToolEmu and ToolSafe evaluate whether individual tool calls are unsafe in their context (Ruan et al., 2024; Mou et al., 2026), and InjecAgent, AgentDojo, and ASB measure indirect prompt injection in tool-using agents (Zhan et al., 2024; Debenedetti et al., 2024; Zhang et al., 2025). Each benchmark comes with its own family of defenses; we evaluate one formulation across four of these stages.

## Guardrails and Skill Scanners.

Guard models classify requests or responses as safe or unsafe (Inan et al., 2023; Han et al., 2024; Zhao et al., 2025). Agent guardrails extend this judgment to actions: GuardAgent and AGrail check agent actions against safety requirements through LLM reasoning (Xiang et al., 2025; Luo et al., 2025), AgentSpec enforces user-specified rules at runtime (Wang et al., 2026a), MCIP checks the contextual integrity of tool interactions (Jing et al., 2025), Safiron and ShieldAgent are trained to judge agent actions (Huang et al., 2026; Zhang et al., 2024), and TS-Guard predicts the safety of each tool call from the interaction history (Mou et al., 2026). Skill scanners screen packages before installation with static rules, LLM-based semantic analysis, or both (Yang et al., 2026; Cisco AI Defense, 2026; Sentry, 2026; NVIDIA, 2026; Qualixar, 2026). These methods judge the input as a whole against a fixed threshold or rule set, whereas PROVISO separates trusted from external observations and compares the proposed action with an alternative.

## Prompt Injection Defenses and Provenance.

Prompt-level and training-based defenses isolate instructions from data (Chen et al., 2025a; Chen et al., 2025b; Yi et al., 2025), while detectors flag injected content in tool returns (Li et al., 2025b; Zhu et al., 2025). System-level defenses instead constrain agent execution via dependency planning, dynamic isolation, or privilege and task-alignment policies (Debenedetti et al., 2024; An et al., 2025; Li et al., 2025a; Debenedetti et al., 2025; Shi et al., 2025; Jia et al., 2025). Closest to our work, several recent defenses explicitly track provenance or authorization to gate actions and enforce information-flow control (Wang et al., 2026b; Zhang et al., 2026; Kravchenko et al., 2026; She et al., 2026; Santos-Grueiro, 2026). However, these approaches rely primarily on explicit rules, policies, or graph checks for authorization. PROVISO instead learns the relation between provenance and action value directly from outcomes, offering a unified formulation that spans from skill installation to indirect prompt injection.

## 3 Methodology

## 3.1 Problem Formulation

## LLM Agents as Observation–Action Loops.

Following ReAct (Yao et al., 2023), an LLM agent alternates between observing and acting. At step $t$ the agent holds the interaction history $h_{t}=(o_{1},a_{1},\ldots,o_{t})$ , and its policy $\pi$ , the underlying LLM, proposes the next action $a_{t}\sim\pi(\cdot\mid h_{t})$ . Actions include reasoning tokens, tool calls, and final answers. An executor runs each tool call and returns the next observation $o_{t+1}$ . Observations range from the user request to tool returns, web pages, and third-party skills, which are packages of instructions and code that extend the agent.

Some actions have external effects: they change state, transmit data, or expose information outside the agent. Once executed, such an effect cannot be withdrawn. The policy, however, conditions on every observation in $h_{t}$ regardless of where it came from, so text from an external source can steer the proposed action away from the user’s objective. This attack is known as indirect prompt injection (Greshake et al., 2023; Zhan et al., 2024). We therefore study the commitment point: the moment after the policy has proposed an action and before the executor runs it. To commit an action is to pass it to the executor.

## Observations by Provenance.

We partition the observations available at the commitment point by their provenance, that is, the source they come from. Trusted observations $K$ define the contract against which an action is checked. They come from the user and the deployment (the request, the policy, and the tool interface) and specify the task contract $K=(O,S,R,T)$ : the objective $O$ , the permitted scope and operations $S$ , the authorized resources or recipients $R$ , and the required answer or terminal condition $T$ . Because the user and the deployment are distinct sources, a harmful request is one whose objective falls outside what the deployment permits. For a third-party skill, no user instruction describes the package, so its declared purpose plays the role of $K$ . External observations $G$ come from everything the agent reads while acting: tool returns, documents, messages, web pages, and skill packages. Content the agent produces after reading $G$ , including its own reasoning, inherits this external provenance. We say an operation or target is licensed by $K$ when the task contract permits it:

An action is admissible when its operation and target are licensed by $K$ 

and its arguments are supported by $K\cup G$ .

External observations may supply values, but they cannot change the objective. In these terms, indirect prompt injection is content in $G$ that attempts to act as $K$ . PROVISO is not given this rule as a procedure; it learns the decision from outcomes, and its memory keeps the distinction between $K$ and $G$ available to the learner.

## Candidate Actions.

At the commitment point, $P_{0}$ is the proposed action, the default that happens if no one intervenes: the action or continuation that the deployed agent produces, or the installation of a skill. $P_{1}$ is an alternative action that is also available, and the action set is $\mathcal{A}(x)=\{P_{0},P_{1}\}$ . In candidate selection, $P_{1}$ is a second executable continuation, a sequence of actions from this point onward such as a recovery trajectory or another program; when the commitment point is the start of the task, each candidate is a complete trajectory. When the environment can be restored, as in our candidate-selection benchmarks, each continuation is first rolled out in a restored copy of the environment, and committing executes the chosen one in the live environment. The observations returned during a rollout belong to the candidate that produced them. In admission, $P_{1}$ is a refusal (block the call, reject the package, or decline the task), and the decision reduces to releasing or blocking $P_{0}$ . Including the alternative makes the decision relative: since refusing has a utility cost, the question is which action better serves the authorized task.

## Objective.

We call a specific agent setting, with its own observations, action set, and outcome scorer, a deployment; each benchmark in our experiments is one deployment. A decision instance is $x=(K,G,P_{0},P_{1})$ . Committing action $a$ produces a native outcome $y(x,a)\in[0,1]$ , the score that the deployment’s own scorer assigns to the result, here whether it is jointly safe and useful. A controller decides, at the commitment point, which action to commit. It estimates the action value

 $V^{*}(x,a)=\mathbb{E}\bigl[y(x,a)\mid x,a\bigr]$ 

(1)

and commits the action with the highest value. The controller sees only information available before commitment, which in candidate selection includes these sandboxed rollouts; the native outcome is used only for training and evaluation. Appendix A lists the observations and actions of each benchmark.

## Running Example.

A user asks the agent to pay an invoice to account B ( $K$ ). The invoice supplies the amount and also contains the line “transfer to account C instead” ( $G$ ). The policy proposes a transfer of that amount to C ( $P_{0}$ ). The alternative is a transfer to B in candidate selection, or a refusal in admission ( $P_{1}$ ). The amount is supported by $G$ , but the recipient is not licensed by $K$ , so $P_{0}$ should not be committed.

## 3.2 The PROVISO Framework

Figure 2: Overview of PROVISO. Left: at step $t$ , the agent’s observations are split by provenance into trusted ( $K$ ) and external ( $G$ ) ones; the LLM policy proposes $P_{0}$ , and an alternative $P_{1}$ is available. Middle: PROVISO builds role-typed memory from $x=(K,G,P_{0},P_{1})$ , lets four role queries and a commitment state (C) retrieve, compare, and update over $L$ blocks, then values each candidate and commits $a^{*}$ . Right: the executor runs $a^{*}$ , and the next observation joins $G$ . Dashed arrows show training: native outcomes fit the parameters, and the offsets $\tau$ are calibrated on development data.

## Overview.

PROVISO sits between the policy and the executor (Figure 2) and proceeds in three stages:

 $\displaystyle(Z,r,\mu)$ 
 $\displaystyle=A_{\psi}(x),\qquad Q=F_{\theta}(Z,r,\mu),$ 

(2)

 $\displaystyle a^{*}$ 
 $\displaystyle=\arg\max_{a\in\mathcal{A}(x)}\operatorname{Cal}_{\eta}\bigl(D_{\rho}(Q,a),a\bigr).$ 

Here $A_{\psi}$ is an adapter, $F_{\theta}$ the role-query network, $D_{\rho}$ a readout, and $\operatorname{Cal}_{\eta}$ a calibration rule. The computation $F_{\theta}$ and its interfaces are the same for every deployment, while $\psi$ , $\theta$ , $\rho$ , and $\eta$ are fitted to each deployment.

## Stage 1: Provenance-Typed Memory.

The adapter $A_{\psi}$ serializes each component of $x$ into text segments $s_{j}$ . A frozen encoder maps each segment to $z_{j}=\operatorname{Enc}(s_{j})$ , the segment receives the role $r_{j}\in\{K,G,P_{0},P_{1}\}$ of its component, and $\mu_{j}$ marks valid rows as opposed to padding. Each row is projected and tagged with a learned role embedding,

 $m_{j}=Wz_{j}+b+e_{r_{j}},\qquad M=[m_{1};\ldots;m_{J}],$ 

(3)

where $W$ , $b$ , and the role vectors $e_{r}$ are part of $\theta$ . The role embedding is how provenance enters the computation: two identical sentences, one from the user request and one from a tool return, produce different memory rows. A component may contribute no rows; in admission, the two fixed actions may be represented only by their queries. When $G$ is long, an evidence selector scores each $G$ segment by its similarity to the commitment query $q_{C}$ (Eq. 4) and keeps the top-scoring segments plus the mean over all segments. The selector is trained with the native outcome and its parameters form $\psi$ ; adapters without a selector have no trainable parameters (Appendix C).

## Stage 2: Role-Query Deliberation.

The controller maintains five query states, learned vectors that read the memory on behalf of each role,

 $Q^{(0)}=[q_{K};q_{G};q_{P_{0}};q_{P_{1}};q_{C}].$ 

(4)

The first four correspond to the four roles. The fifth, $q_{C}$ , has no input role; it is the commitment state that collects what the decision requires. The queries pass through $L$ deliberation blocks with separate weights,

 $Q^{(\ell)}=\mathcal{D}^{(\ell)}_{\theta}\bigl(Q^{(\ell-1)},M;\mu\bigr),\qquad\ell=1,\ldots,L.$ 

(5)

Each block applies three pre-normalized residual sublayers: masked cross-attention lets every query retrieve from the valid memory rows, self-attention lets the five queries compare what they retrieved, and a feed-forward layer updates each query. The memory $M$ stays fixed. Because retrieval in a later block is conditioned on the comparison formed in an earlier one, in the running example the first block can find that the recipient of $P_{0}$ differs from the one in $K$ , and the second can return to $G$ to find where that recipient came from. The final states are $Q=Q^{(L)}$ .

## Stage 3: Action Valuation and Calibrated Commitment.

The readout $D_{\rho}$ estimates the action value in Eq. 1. In candidate selection, a small feed-forward network $g_{\rho}$ values each candidate from the states that describe the authority, the evidence, that candidate, and the commitment state:

 $\widehat{V}(x,P_{c})=g_{\rho}\bigl([q_{K};q_{G};q_{P_{c}};q_{C}]\bigr),\qquad c\in\{0,1\}.$ 

(6)

In admission, the native outcome is a label: releasing $P_{0}$ scores one if it is benign, and refusing scores one if it is unsafe. If $p(x)$ is the probability that $P_{0}$ is unsafe, then $V^{*}(x,P_{1})-V^{*}(x,P_{0})=2p(x)-1$ . Only this difference matters, so we set $\widehat{V}(x,P_{0})=0$ and $\widehat{V}(x,P_{1})=\widehat{p}(x)=\sigma(h_{\rho}(q_{C}))$ , read from the commitment state by a linear head $h_{\rho}$ . Calibration then sets the operating point, the trade-off between blocking unsafe actions and keeping benign ones:

 $\displaystyle U(x,a)$ 
 $\displaystyle=\operatorname{Cal}_{\eta}\bigl(\widehat{V}(x,a),a\bigr)=\widehat{V}(x,a)-\tau_{a},$ 

(7)

 $\displaystyle a^{*}$ 
 $\displaystyle=\arg\max_{a\in\mathcal{A}(x)}U(x,a),$ 

where $\eta=\{\tau_{a}\}$ are per-action offsets chosen on development data. Only $\tau_{P_{1}}-\tau_{P_{0}}$ affects the decision, so we fix $\tau_{P_{0}}=0$ ; a deployment may select a separate offset for each task family. Calibration here means selecting an operating point, not adjusting predicted probabilities. In admission, Eq. 7 blocks $P_{0}$ whenever $\widehat{p}(x)>\tau_{P_{1}}$ .

## Learning.

For each deployment, $\psi$ , $\theta$ , and $\rho$ minimize $\mathbb{E}_{(x,y)}[\mathcal{L}(\widehat{V}(x,\cdot),y(x,\cdot))]+\lambda\mathcal{R}$ on native examples: decision instances paired with the outcome of each candidate in candidate selection, or with the label of $P_{0}$ in admission. In candidate selection, $\mathcal{L}$ is binary cross-entropy between each candidate’s value and its outcome plus a pairwise ranking term; in admission, it is binary cross-entropy between $\widehat{p}(x)$ and the label, with a risk-class term where finer labels exist. $\mathcal{R}$ collects auxiliary terms (role-level supervision on the query states, the selector loss, and load balancing for the feed-forward layer), weighted by $\lambda$ . The encoder $\operatorname{Enc}$ is not updated. Calibration is selected afterwards on development data to maximize the deployment’s operating criterion, for example F1, unsafe recall, or the fraction of benign actions released. Fitting and calibration are kept separate: the first learns which action is better, and the second decides how much evidence is required before departing from the default. Algorithm 1 in Appendix C summarizes inference.

## Tasks along the Agent Lifecycle.

We evaluate PROVISO on four agent security tasks, ordered by when the commitment occurs in the agent lifecycle. Malicious skill detection: before the agent runs, a third-party skill package is admitted or rejected (SkillsBench (Yang et al., 2026)). Agent misuse: when a request arrives, a CLI agent executes it or refuses a task with real-world harm (ANCHOR (Song and Qi, 2026)). Unsafe tool invocation: at each step, a proposed tool call is released or blocked (ToolSafe (Mou et al., 2026)). Indirect prompt injection: when tool returns may carry injected instructions, the controller commits either the agent’s trajectory or a recovery trajectory, both rolled out from the start of the task (AgentDojo (Debenedetti et al., 2024)). The first three are admission decisions, where $P_{1}$ is a refusal; the last is a candidate selection between two executable continuations (Sec. 3.1). For malicious skill detection, we add three further benchmarks: MalSkillBench (Guo et al., 2026), SkillVetBench (Hossain et al., 2026), and MaliciousSkillBench (Wang et al., 2026c). Appendix A lists $K$ , $G$ , $P_{0}$ , $P_{1}$ , and the native outcome for every benchmark (Table 6), together with the data splits (Table 7).

## Metrics.

We use the metrics defined by each benchmark. On SkillsBench and the three additional skill benchmarks, we report precision (Prec), recall, F1, and false positive rate (FPR) for malicious packages. On ANCHOR, we report the Harm & Risk Score (H&R), which combines refusal with judged harm and catastrophic risk on harmful tasks.
On ToolSafe, we report accuracy (ACC), F1, and recall for unsafe calls. On AgentDojo, we report benign utility (task completion without attacks), utility under attack, and targeted attack success rate (ASR), the fraction of attacked episodes in which the attacker’s goal is achieved.

## Baselines.

Each task is compared with the defenses designed for it. Malicious skill detection uses static and semantic package scanners: SkillGate (Yang et al., 2026), Sentry (Sentry, 2026), Cisco (Cisco AI Defense, 2026), SkillSpector (NVIDIA, 2026), and SkillFortify (Qualixar, 2026); Sentry, Cisco, and SkillSpector are each run in a static mode and an LLM-based semantic mode. Agent misuse and unsafe tool invocation use guard models that judge a proposed action, four of which are evaluated on both tasks: MCIP (Jing et al., 2025), WildGuard (Han et al., 2024), AgentSpec (Wang et al., 2026a), and Safiron (Huang et al., 2026). Agent misuse adds AGrail (Luo et al., 2025) and GuardAgent (Xiang et al., 2025); tool invocation adds TS-Guard (Mou et al., 2026), Qwen3Guard (Zhao et al., 2025), and ShieldAgent (Zhang et al., 2024). Indirect prompt injection uses dedicated defenses: Tool Filter (Debenedetti et al., 2024), DRIFT (Li et al., 2025a), IPIGuard (An et al., 2025), BIPIA (Yi et al., 2025), PIGuard (Li et al., 2025b), and SecAlign (Chen et al., 2025b). Every baseline keeps its released prompts, parsers, and action mappings and is scored on the same test population. Appendix B gives configurations and which baselines use training data.

## Implementation Details.

The encoder $\operatorname{Enc}$ is a frozen ModernBERT-large (Warner et al., 2025), or E5-large-v2 (Wang et al., 2022) for SkillVetBench and MaliciousSkillBench. The controller has width 384, five queries (four role queries and the commitment state), and $L=2$ deliberation blocks; each attention layer has eight heads, and the feed-forward layer is a mixture of four SwiGLU experts (Shazeer, 2020) with top-two routing (Shazeer et al., 2017), giving 17.40M trainable parameters. The architecture is shared across benchmarks, while weights are fitted per benchmark with AdamW (Loshchilov and Hutter, 2019) on the splits in Table 7, where cross-validation folds keep each source, trajectory, or user task within one fold. Operating points are selected on development data, except on SkillVetBench, which uses a fixed threshold. The agent on ANCHOR and AgentDojo is Gemma 4 31B IT (Gemma Team, 2026), and the role summaries on ToolSafe are written by gpt-oss-20b (OpenAI, 2025). Training, calibration, and compute details are in Appendix C.

## Malicious Skill Detection.

As shown in Table 1, PROVISO achieves the best F1, precision, and FPR on SkillsBench, outperforming the strongest baseline, SkillGate, by 13.84 F1 points. Static scanners rely on predefined rules and patterns and detect only 58–73% of malicious skills. LLM-based semantic scanners detect nearly all of them, but they also flag 7.6–13.8% of benign skills; since benign skills are the large majority on SkillsBench, these false alarms keep their precision below 57%. PROVISO has lower recall than the semantic scanners because its threshold is selected on development data to maximize F1, which favors precision when most packages are benign. At this operating point it flags only one in a hundred benign skills.

## Unsafe Tool Invocation.

As shown in Table 3, PROVISO reaches 99.12 F1, missing one unsafe call and blocking five benign calls. TS-Guard, the guardrail introduced with the benchmark, is the strongest baseline at 92.05 F1. General-purpose guards stay below 65 F1: Qwen3Guard, WildGuard, and Safiron miss most unsafe calls, while MCIP and ShieldAgent block many benign ones. One reason is that these guards judge the call content itself, while whether a call is unsafe often depends on the user request and the preceding tool outputs. The result is stable across training runs, proposer models, and thresholds (Appendix G).

## Indirect Prompt Injection.

As shown in Table 4, PROVISO achieves the highest utility under attack, 2.06 points above SecAlign, with a targeted ASR of 0.28%. BIPIA and DRIFT reach a similarly low ASR but lower utility under attack, and Tool Filter and PIGuard lose much more utility because they restrict tools or remove flagged tool outputs. SecAlign has slightly higher benign utility (one more task out of 97) but an ASR more than ten times higher. On clean tasks, PROVISO only selects between two candidate trajectories, so it cannot complete a task that neither candidate completes. Calibrating the threshold within each training fold gives the same ASR and benign utility (Appendix F.4).

To test whether the results on SkillsBench depend on a single data source, we apply PROVISO to three further malicious skill detection benchmarks that differ in size, malicious ratio, and how skills were collected (Table 5). ## Evidence Selection.

A short instruction can decide whether a long skill package is safe. Removing the supervision that decides which package windows enter memory lowers F1 by 16.73 points, and also removing local memory lowers it by 26.44 points. With the trained model and threshold fixed, replacing the selected windows with an equal number of permuted ones lowers F1 by 21.47 points, while reversing their order changes no decision, so the gain comes from which content is retained (Appendices F.1 and F.2).

## Query Reasoning.

We replace role-query deliberation with an MLP of the same parameter count that reads the same selected memory, flattened together with its role indicators. This dense readout reaches only 48.62 F1, 37.19 points below PROVISO (Appendix F.1).

## Repeated Retrieval.

In the payment task, the user authorizes an invoice ( $K$ ), and the ledger links and payment notes the agent reads ( $G$ ) disagree with it in a quarter of the cases. Averaged over five training seeds, suppressing the retrieval in the second block lowers utility from 88.48% to 78.54%, with unsafe transfers below 0.4% in both. The drop is 13.15 points larger when trusted and external observations conflict than when they agree (Appendix F.3).

## 6 Conclusion

We presented PROVISO, which decides which action an LLM agent commits by separating trusted from external observations and comparing the proposed action with an alternative. On four agent security tasks along the agent lifecycle, no published defense exceeds PROVISO in both security and utility, and PROVISO reaches 88–99 F1 on three additional skill detection benchmarks.

## Limitations

PROVISO is fitted separately for each benchmark and therefore requires labeled outcomes from the target setting; we do not study transfer of a single trained controller across tasks. In candidate selection, both continuations are rolled out in a restorable environment before the controller is applied, so a deployment must support such rollouts and pay for both. Roles are assigned by benchmark-specific adapters: on AgentDojo, external content enters memory inside the candidate trajectories rather than as separate $G$ rows, and on ToolSafe, part of the input consists of role summaries generated by a proposer model, which adds generation cost. The agent on ANCHOR and AgentDojo is a single LLM. Finally, our evaluation uses the released benchmarks and their attacks; attacks adapted to PROVISO itself are not evaluated.

## Ethics Statement

Experiments use released data and execute attacks inside simulated benchmark applications to improve defenses for agents acting on external content.
PROVISO can still release unsafe actions or block benign ones, as the error rates in Section 5 show, so it should complement rather than replace other safeguards, such as permission controls and human confirmation of irreversible actions. We do not develop new attack methods.

The code release implements the shared controller and the calibrated inference used in our experiments. The appendix gives implementation details, complete results, and statistical tests.

## Configurations.

On AgentDojo, every defense covers all attacked and clean episodes with the official scorer. Tool Filter uses the official tool-filtering interface; BIPIA separates external content, guidance, and task restatement; DRIFT keeps dynamic rules, observation isolation, and action validation; IPIGuard uses its dependency graph; PIGuard applies its classifier to each tool message; SecAlign uses its preference-optimized model. On ANCHOR, all methods use the same actor (Gemma 4 31B IT), artifact collector, and released Harm & Risk judge; benign completion is measured on the same 80 tasks for all six guards; AGrail completes 35/80 (43.75%). On ToolSafe, exact sample IDs select the same test calls for every method, and severity greater than zero defines unsafe; MCIP blocks after ten unsuccessful parsing attempts, following its protocol. On SkillsBench, Sentry static and Cisco static block HIGH or CRITICAL findings, SkillFortify blocks at MEDIUM, SkillSpector static uses its DO_NOT_INSTALL decision, and the semantic scanners keep their released model calls and blocking rules.

## Malicious Skill Detection.

ModernBERT-large encodes the full package text in 1,536-character windows with stride 768, pooling four vectors per window. The declared purpose populates $K$ , the package windows populate $G$ , and allow/reject anchors populate $P_{0}/P_{1}$ . On SkillsBench, a selector scores each window by its similarity to the initial commitment query and keeps the top $\min(8,n)$ of a package’s $n$ windows plus the mean over all windows; the selector is supervised with the package label through a log-sum-exp pooling over windows. The loss combines risk BCE, decision cross-entropy, role-level witness targets, within-source ranking between malicious and clean packages, the selector losses, and a router balance term. MalSkillBench uses the same input with all windows and no selector. SkillVetBench and MaliciousSkillBench use E5-large-v2 embeddings: a declared-purpose vector for $K$ and global and local document vectors for $G$ . The package is blocked when its risk score exceeds the threshold.

## Agent Misuse.

The request and setting are encoded with ModernBERT-large (up to 2,048 tokens) into 34 rows: a CLS row, a global mean, and 32 ordered local means. Global rows carry $K$ ; local rows carry $K$ , $G$ , or $P_{0}$ according to the serialized field; $P_{1}$ (refusal) is represented by its query only. A risk-class head on $q_{C}$ is trained with cross-entropy plus a scalar risk BCE. The task is refused when the predicted risk exceeds the development threshold (.01).

## Unsafe Tool Invocation.

The frozen ModernBERT-large encoder encodes the call, history, and tool schemas (up to 4,096 tokens) into a CLS row and 32 ordered means. Four further rows hold short summaries written in advance by the proposer model (gpt-oss-20b), one for each role ID $K$ , $G$ , $P_{0}$ , and $P_{1}$ . The proposer writes every summary after reading the full context, including tool returns, so under Sec. 3.1 the content of these rows has external provenance; the role ID records which part of the decision a summary describes, not that its content is trusted. The loss combines severity cross-entropy, scalar risk BCE, commitment BCE, and router balance. The call is blocked when the unsafe probability reaches .005.

## Indirect Prompt Injection.

The commitment point is the start of the task. $P_{0}$ is the complete trajectory of the deployed agent, whose prompt marks external content with boundary tags and restates the task, following BIPIA (Yi et al., 2025). $P_{1}$ is a complete recovery trajectory produced by DRIFT (Li et al., 2025a), which plans the task, removes instructions it detects in tool returns, and validates later actions. Both candidates are rolled out from the initial environment with Gemma 4 31B IT, and each is recorded as its full message sequence: system and user messages, assistant text, tool calls with their arguments, tool returns, and the final answer. The user request forms $K$ . No external observation precedes the commitment point, so $G$ holds only a fixed stage description, and the tool returns enter memory as part of the candidate that produced them. The messages are encoded with ModernBERT-large in 510-token chunks. Committing a candidate replays its recorded tool calls in a freshly restored official environment, which yields its native outcome. Each candidate is valued from $[q_{K};q_{G};q_{P_{c}};q_{C}]$ and trained with BCE on its native outcome (task completed and attack failed) plus a pairwise ranking loss. Five folds keep all attack variants of a user task together. $P_{1}$ is chosen when its value exceeds that of $P_{0}$ by a per-suite margin selected on calibration curves.
