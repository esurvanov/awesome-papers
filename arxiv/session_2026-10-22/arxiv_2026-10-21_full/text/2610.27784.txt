Abstract.

Vulnerability benchmarks and software engineering research depend on rebuilding historical software. Yet builds rely on external resources, such as base images and packages, that change independently of the source code. In this study, we examine this environment decay on 14,159 OSS-Fuzz cases. We find that 69.7% no longer complete reconstruction and verification, and that most failures share a small number of recurring failure symptoms. A recurring failure can therefore be diagnosed once and its repair reused. We present Relay, a hybrid framework that uses an LLM to derive and validate deterministic repair rules from representative failures, reuses them without model calls, and escalates cases unresolved by rules to a per-case agent. We evaluate Relay in human-guided and fully automated rule-derivation campaigns and compare it with a per-case agent approach. We find that rule derivation can be fully automated, and that reusable rules restore as many builds as per-case agents with fewer build executions. However, agents restore cases that the rules cannot. Our results show that a hybrid approach that applies rules first and escalates the remaining cases to an agent restores more builds than either approach alone and at a lower cost than using agents alone.

Keywords: 
Build repair, environment decay, build reproducibility, software benchmarks, LLM agents, AI for software engineering (AI4SE), OSS-Fuzz

## 1. Introduction

Rebuilding an earlier version of a software system is necessary for
reproducing reported bugs, bisecting regressions, and evaluating tools on
historical defects. This need is especially visible in vulnerability research.
For instance, ARVO reconstructs vulnerable and fixed versions of OSS-Fuzz
projects (Mei et al., 2026) and benchmarks such as CyberGym and SEC-bench depend on
executable historical software (Wang et al., 2026; Lee et al., 2025). If a case no longer
builds, its vulnerability and any proposed repair cannot be evaluated through
execution. Researchers must instead exclude the case or rely on indirect
measures such as code similarity, which may not reflect whether a patch
actually fixes the vulnerability (Zhang et al., 2026).

Rebuilding historical software is often much harder than checking out its
source code. Build instructions may remain available, but they depend on
resources that change independently of the target project. Base images are
retired, package repositories remove old versions, toolchain installers move,
and third-party download URLs disappear (Nourry et al., 2025; Mei et al., 2026; Malka et al., 2026). A build can
therefore fail years later even though its target source revision has not
changed. We refer to failures caused by such changes as environment
decay. Developers generally maintain the current version of a project rather
than restore every historical release, leaving this work to the researchers and
benchmark maintainers who depend on those releases.

Existing approaches repair build environments through reusable operations,
such as Shipwright’s Dockerfile repairs (Henkel et al., 2021), or through
per-case language-model agents (Hu et al., 2025b; Bouzenia and Pradel, 2025). Per-case agents are flexible, but they repeat the diagnosis, patch generation,
and validation process for every build. This is inefficient when the same
environment failure affects many builds, since each case requires new model
calls and one or more build executions. Moreover, external dependencies
continue to change, so a restored build may fail again later. A scalable
approach should therefore reuse previously validated repairs where possible,
while retaining per-case reasoning for failures that cannot be handled by
existing rules.

In this study, we use historical OSS-Fuzz cases to examine whether reusable
rules and per-case agent escalation can restore build environments efficiently
at scale. These cases cover different projects, languages, dependency managers,
and toolchains. Their recorded crashing inputs also let us evaluate whether a
repaired environment preserves the expected historical behavior, rather than
measuring build completion alone.

We investigate a hybrid approach to historical build restoration. We implement
Relay, a framework built around ARVO’s historical reconstruction pipeline.
Relay converts build logs into normalized failure observations, groups related
failures, and selects representative cases. An LLM uses evidence from these
cases to propose a repair rule. The framework checks the permitted repair
scope, applies the rule, and validates it by rebuilding the affected cases.
Validated rules are stored in a registry and reused whenever their conditions
hold. When a repair exposes a different failure, Relay records the new
evidence and continues from the updated build state. Cases that remain
unresolved are escalated to a per-case agent.

We aim to produce rules that recognize recurring failures and express repairs that can
apply across cases. A rule may pin a stable version when that version addresses
a recurring compatibility or availability problem, but it should not simply
encode a one-off change for a single project. The model proposes both the
conditions under which a rule applies and the changes it makes. For example,
several builds may fail because they refer to a retired source archive. A rule
should recognize the relevant download failure and redirect the request to a
supported mirror or archive without reasoning about every affected case
separately.

Our study separates the prevalence of environment decay from the evaluation of
repair. We first examine 14,159 historical OSS-Fuzz cases with recorded
execution outcomes and find that 9,868 do not complete reconstruction
and verification. We characterize the failures using the 4,513 cases
for which we collected detailed failure logs. We then evaluate whether rules derived from representative failures transfer to
other cases and whether their derivation can be automated. We compare rules,
per-case agents, and their rule-first combination on the same failures.
Finally, we test agent escalation on a separate set of cases where deterministic
repair had stopped.

This paper makes the following contributions:

• 

We conduct a large-scale investigation of environment decay in 14,159 historical OSS-Fuzz cases and show that build decay is widespread and that failure causes tend to recur across unrelated cases.

• 

We present Relay, a scalable framework that derives reusable deterministic
repair rules from representative failures, validates them through execution,
and escalates unresolved cases to a per-case agent. It also extends historical
build verification beyond C and C++.

• 

We show that the framework can derive and validate reusable repair rules without human intervention and use them to restore historical builds.

• 

We compare rule-based and per-case agentic build repair and show that a hybrid strategy combining the cost-efficiency of reusable rules with the flexibility of per-case agentic repairs is effective for large-scale build restoration.

• 

We provide a replication package with the rule registry, failure observations, repair records, prompts and model responses, and analysis scripts. We provide a partial version for review and will release the full package upon publication.

## 2. Background

## 2.1. OSS-Fuzz and Historical Builds

OSS-Fuzz is a continuous fuzzing platform that fuzzes open-source software to detect crashes and other
incorrect behavior (Serebryany, 2017). When it confirms a failure, it creates a report identifying the affected project,
fuzz target, sanitizer configuration, and input that triggered the
failure (Mei et al., 2026). A reported failure shows that the project built and that its fuzz target executed successfully when the issue was discovered.

Projects integrated with OSS-Fuzz share a common configuration structure. Each
project supplies a project.yaml file containing project metadata, a
Dockerfile defining its build environment, and a build.sh script
that compiles the project and its fuzz targets inside that
environment (Google, ). This common structure provides a consistent
interface for executing builds, but it does not make those builds
self-contained. A Dockerfile may download base images, install system packages,
or retrieve source archives, while the build script may resolve language
packages, invoke code generators, and select a compiler or toolchain. These
external resources can change or disappear even when the project files and
target source revision remain unchanged.

## 2.2. Executable Vulnerability Datasets and ARVO

Executable historical software is increasingly used to evaluate vulnerability
discovery and repair systems. CyberGym evaluates vulnerability
reproduction, while SEC-bench evaluates both proof-of-concept generation and
vulnerability patching (Wang et al., 2026; Lee et al., 2025). These benchmarks
require more than a source snapshot: the project must build, the
relevant target must execute, and the recorded input must still exercise the
expected behavior.

ARVO reconstructs vulnerable and fixed versions of vulnerabilities reported by
OSS-Fuzz (Mei et al., 2026). It combines information from the OSS-Fuzz report with
historical project and dependency revisions, the OSS-Fuzz integration files,
and the recorded crashing input. ARVO also addresses several recurring
obstacles to historical reconstruction, including dependency revision
selection, base-environment changes, and unavailable external resources. ARVO’s published dataset and evaluation focus on C and C++ memory-safety
vulnerabilities. While its reconstruction approach can be extended to other
ecosystems, doing so requires language-specific handling of dependencies,
build outputs, and crash behavior. We extend the workflow to Rust, Go, Python,
and JVM projects and add the necessary logging and validation needed to distinguish build
completion from successful reproduction of the historical vulnerability. The
repairs studied in this paper begin with the failures that remain after ARVO’s
existing reconstruction mechanisms have run.

## 2.3. Build and Environment Repair

Build failures can arise from source errors, dependency changes, unavailable
resources, incompatible tools, or faults in build and container
configuration. Existing repair systems often address one part of this space.
For example, Shipwright groups Dockerfile failures and develops reusable
repairs through a human-in-the-loop process (Henkel et al., 2021).
Other approaches repair dependency-related build failures or restore
language-specific environments (Macho et al., 2018; Mukherjee et al., 2021). More recent work includes language-model agents that
configure and execute repositories individually (Hu et al., 2025b; Bouzenia and Pradel, 2025), as well as EnvBench, a benchmark for automated environment
setup (Eliseeva et al., 2025).

Prior work on OSS-Fuzz build failures found 25 causes of fuzzing build
failures across project source, build scripts, dependencies, toolchains,
external resources, and execution infrastructure (Nourry et al., 2025). These
failures can occur in sequence; repairing a Docker image may expose a dependency
error, and repairing that dependency may expose a compiler incompatibility.
Success in progressing past one build error therefore does not establish that the complete historical build has been restored.

Relay combines the cost-efficiency of reusable rules with the flexibility of per-case agentic repair. It uses an LLM to
derive deterministic rules from representative failures and applies validated
rules to matching cases without further model calls. Cases that remain
unresolved are escalated to a per-case agent. Both repair paths (rule and agentic) may modify
files at different stages of the build, but they must preserve the historical
target revision and recorded crashing input.

## 3. Relay Framework

Figure 1. The Relay repair pipeline. (1) Each historical OSS-Fuzz case is
built in an ARVO container; target source and the crashing input are
protected. (2) The build log is normalized into a signature and placed in a
failure tree whose high-yield branches supply representative cases. (3) If an existing
rule matches, it is reused without a model call; otherwise a bounded evidence
packet enters the rule-authoring process, where a model is invoked automatically
or under researcher guidance. The proposed rule enters the registry only after
it rebuilds the representative cases. (4) Rules are applied deterministically to build-environment files. A changed
failure is rebuilt with the repair chain carried forward. Eligible cases that
remain unresolved are escalated to a separately budgeted per-case agent, while
cases blocked by unavailable resources or execution infrastructure are
deferred.

Figure 1 shows how Relay combines deterministic repair, LLM-assisted rule derivation, and per-case agent escalation. The framework
reconstructs builds, normalizes and groups failures, selects representative
cases, prepares evidence, matches and applies rules, executes builds, and
records outcomes. A rule-authoring LLM operates on groups of related failures
and proposes deterministic rules intended for reuse. A per-case repair agent is
invoked only after deterministic repair stops. It may inspect and modify one
case iteratively, but remains subject to the same protected-file policy and to
explicit limits on turns, builds, and tokens.

## 3.1. ARVO Integration and Repair Scope

Relay uses ARVO as its execution mechanism for reconstructing a project at a
specific historical revision. ARVO already controls parts of the base
environment, dependency revisions, and resource retrieval, and attempts its own
environment fixes during reconstruction (Mei et al., 2026). Our repair loop therefore begins with
the failures that remain after those mechanisms have run. It surrounds ARVO
with evidence collection, reusable rule derivation and application, repair
state management, and agent escalation. Relay does not replace ARVO’s
reconstruction workflow but rather invokes that workflow repeatedly to observe and validate environment repairs.

The original ARVO workflow used as our starting point selects C/C++ cases. We
extend selection and verification to non-C/C++ projects, including language-aware
handling of Rust, Python, and JVM crash signals and target wrappers. The
Dockerfile/build-script interface made much of the existing build machinery reusable
across ecosystems, while crash verification required separate handling.
We also add an interface for applying repair rules and record which repairs were attempted, whether they were applied, and how each execution ended. These records let us distinguish project build failures, repairs that could not be applied, and failures in the execution infrastructure.

To reduce the risk of modifying program behavior, we permit repairs only to the
build environment: Dockerfiles, build scripts, package-manager configuration,
dependency metadata, resource locations, and toolchain setup. The target source
revision, program source, crashing input, fuzz target, and sanitizer
configuration are protected. An attempted change to a protected input, whether
produced by a rule or a repair agent, is rejected before execution.

## 3.2. Observations, Grouping, and Evidence

Each execution produces a run directory containing output streams, status
records, available log metadata, and a normalized case observation. Relay classifies the failure, estimates the execution phase reached at which it occurred, and derives a signature from the relevant log excerpt. Relay selects excerpts using generic and ecosystem-specific failure markers and the evidence requirements of existing rules. It then normalizes dynamic
content such as paths, identifiers, hashes, version numbers, line numbers, and
repeated whitespace. The grouping key combines failure class, phase, and
signature hash. Including the phase prevents a similar message during image
creation and target execution from being treated as the same blocker.

Relay groups similar failures to select cases for rule derivation, but the same error message can have different causes. For example, removing version numbers during normalization can group failures involving different dependency versions. We therefore keep the original logs for rule derivation and test each rule by rebuilding every case to which it is applied.

Relay then organizes observations in a tree from coarse categories to exact signatures:
failure class, phase, cluster family, ecosystem, error pattern, abstract
template, and normalized signature. This hierarchy lets the framework
prioritize high-yield branches, where one reusable repair may affect many
builds, as well as branches that have not yet been examined. We refer to a case
selected from a branch for rule authoring and initial validation as a
representative. Representatives provide concrete evidence for the
branch, but do not eliminate the need to validate other matching cases.

Rather than provide complete logs to the rule-authoring model, Relay
constructs bounded evidence packets. A packet contains relevant excerpts, the
failure class, phase and signature, case metadata, and repair history. The
history records previously applied rules and how the observed failure changed
after each rebuild. Excerpt selection uses generic and ecosystem-specific
failure markers, the evidence requirements of existing rules, and removes repeated or redundant log content. Relay records packet sizes and token counts to bound the
cost of each proposal, with the trade-off that a packet may omit useful
context. When the available evidence is insufficient, the framework schedules
a fresh execution or a targeted diagnostic execution and constructs a new packet before requesting
another proposal.

## 3.3. LLM-Assisted Rule Derivation

Figure 2. Difference between a case-specific patch and a reusable rule. The
patch hard-codes one toolchain for one project. The rule reads the missing
toolchain from the failing path and installs it with its source component,
recovering 22 cases across 7 projects with different toolchains.

Before requesting a new rule, Relay checks the current observation against the
validated rules in its registry. If a rule matches, the framework applies it
without invoking a model. Rule derivation begins only when the registry contains
no eligible rule for the observed failure.

For a selected branch, the rule-authoring LLM receives evidence packets from
its representatives, relevant repair history, and descriptions of existing
rules. It returns a structured candidate containing a failure precondition,
parameters to extract from the evidence, permitted repair operations, evidence
requirements, and allowed file scope. We instruct the model to express repairs
in terms of the observed failure rather than project names, case identifiers,
or constants copied from one case. For example, Figure 2
shows a toolchain rule that reads the name of the missing Rust toolchain from
the failing path and installs it, instead of hard-coding one toolchain. A version may be pinned when the evidence establishes a
compatibility requirement, but the rule must also state when that pin applies.

In the human-guided campaign, one of the authors selected branches, reviewed the
evidence, and guided or revised model proposals. In the fully automated
campaign, the framework selected branches, constructed prompts, invoked the
model, materialized its proposal, and scheduled validation without human
intervention. In both settings, the model proposed a repair, but execution
determined whether it worked.

A proposal is not immediately added to the rule registry. The framework checks
its scope, applies its operations against the historical build files, and
rebuilds representative cases. Before adding a proposal to the registry, the framework checks its scope, applies its operations to the historical build files, and rebuilds representative cases. It accepts the rule only if the execution restores a build or exposes a different failure. Once a rule is adopted, later applications require no further model calls.

## 3.4. Rule Matching and Deterministic Application

A rule pairs a failure precondition with a repair specification. Preconditions
describe the observation and relevant context. Repair specifications use
bounded operations such as rewriting a URL, pinning a dependency, installing a
package, selecting a toolchain, replacing a base image, or editing a build
script. The rule applicator applies these operations against the
historical build files.

Three decisions remain separate. First, the matcher determines whether the
current observation satisfies a rule’s preconditions. Second, the applicator
determines whether the requested operations can be carried out on the available
files without violating the repair scope. Third, a new ARVO execution determines
whether the applied repair recovers the build, exposes a different failure, or
leaves the original failure unchanged. We record all three outcomes so that a
matching error, an application failure, and an ineffective repair are not
treated as the same event.

Each rule targets a specific breakage step: an identifiable operation that
fails during reconstruction, such as retrieving a retired archive, installing
a missing package, or invoking an incompatible toolchain. The same rule can repair a failure across several versions or projects if it recognizes the failure and can apply the required change to their build files.

A build may fail again after its first error is fixed. For example, an unavailable base image prevents compilation from starting, while a failed source download can hide a later dependency error. Relay therefore keeps edits that resolve an intermediate failure and rebuilds after each applied rule. These edits form a repair chain. After each rebuild, Relay uses the latest failure to select the next rule. Cases that initially failed for different reasons may then encounter the same failure and reuse the same rule.

Relay determines whether a repair restored the build or exposed a different failure by rebuilding the case. It records a change in failure class or signature as a progression, rather than a recovery. When this happens, the framework keeps the repair chain and continues from the newly observed failure.

## 3.5. Stopping and Agent Escalation

Relay stops deterministic repair when the build recovers, no eligible rule remains, two consecutive attempts return the same failure state, or the required action exceeds the permitted scope. It records why it stopped, including whether a case needs a new rule, an unavailable resource, case-specific reasoning, or an edit that the applicator could not apply. It records infrastructure failures and provenance problems separately from repair outcomes.

Relay escalates cases with a repairable build failure when no applicable rule remains. It defers cases blocked by infrastructure failures or a confirmed unavailable resource. The agent receives the case’s current failure, complete repair history, and build files. It can inspect logs and files, probe the environment, make edits, and invoke ARVO. It keeps earlier edits as it works on subsequent failures.

The agent aims to repair one case. Its patch does not need to generalize, and Relay does not automatically add it to the rule registry. The agent can make case-specific edits that the deterministic rule operations cannot express, but it cannot change the protected source revision, program source, fuzz target, crashing input, or sanitizer configuration. Relay limits the model turns, build executions, and tokens available for each case and counts a recovery only when a new execution confirms that the build has been restored.

## 4. Study Setup

We answer four research questions using different subsets of the OSS-Fuzz cases
described below. RQ1 measures the prevalence and distribution of historical
reconstruction failures. RQ2 evaluates reusable repair rules and whether their
derivation can be automated. RQ3 compares reusable rules, per-case agents, and
their rule-first combination on the same failures. RQ4 examines why
deterministic repair stops and what per-case agents recover after it does.

## 4.1. Dataset and Study Subsets

We constructed the dataset from an OSS-Fuzz issue-tracker snapshot collected on January 27, 2026. Each eligible issue contributes at most one case containing the project, fuzz target, crashing input, sanitizer, and historical source revisions required by ARVO. Issues without sufficient reconstruction metadata are excluded.

Historical reconstruction is computationally expensive: each execution attempts
to restore the build environment, build the relevant project revisions, and run
the recorded crashing input. Across the cases in our dataset, the recorded
execution times total approximately 1,894 hours, and
174 cases took at least one hour. We therefore evaluated a
broad subset of the collected issues rather than attempting every issue in the
tracker.

C and C++ account for 83.5% of the 51,408 issues in our
metadata. To include failures from other ecosystems, we executed the available
cases from projects identified as using other languages and then sampled C/C++
cases in random order. After removing repeated case identifiers, the dataset
contains 14,159 distinct historical cases. Table 1
summarizes the dataset and the subsets used in each evaluation.

Our pipeline first invokes ARVO’s existing reconstruction mechanisms, including its handling of historical dependencies, base environments, and unavailable resources. The failures studied here are therefore cases that remain unresolved after this initial reconstruction. Of the 14,159 cases in the dataset, 9,868 did not complete reconstruction and verification, giving a failure rate of 69.7%. ARVO’s published reproduction rate (Mei et al., 2026) and the failure rate reported in this paper come from different case selections and execution periods and should not be compared directly.

## 4.2. Repair Selection and Budgets

Relay does not try to repair every case separately. It groups similar failures and selects representatives from promising groups. It then derives and validates rules on those representatives. A case is executed when it is chosen as a representative or when an accepted rule matches its failure. This gives priority to recurring failures for which one rule may repair several cases.

Across the RQ1 and RQ2 campaigns, Relay attempted to repair 2,451 distinct cases. It rebuilt each case after applying a
repair, sometimes exposing another failure that required a further change. Relay stopped deterministic repair when the build recovered or when two consecutive repair
attempts returned the same failure state without exposing a new one. We set limits on build executions, model turns, tokens, and cost for agent runs, as summarized in
Table 2. Note that an unresolved case may still be repairable with a larger budget.

## 4.3. Per-Case Agent Configuration

All models use the same agent harness. Each agent receives the case evidence,
complete build logs, and historical build files. It can inspect files, run
read-only shell commands, edit the permitted build-environment files, and
rebuild the case. The harness disables web access, and prevents changes to the protected source revision,
program source, fuzz target, crashing input, and sanitizer configuration. After each rebuild, the agent
receives the latest failure and can address the newly exposed blocker without
discarding earlier changes. If the harness cannot apply a patch, it returns
the error to the agent so that it can propose a correction.

## 4.4. Outcome and Cost Measures

Our primary outcome is build recovery (i.e., the build completes
successfully). We also check whether the repaired environment preserves the historical crash behavior. We count the vulnerability as reproduced when the recorded input triggers a crash at the vulnerable revision. We classify a case as benchmark-ready when the input triggers the crash at the vulnerable
revision and runs without a crash at the designated fixed revision.

We measure repair effort through build executions. For each approach, we
divide the total number of build executions across all evaluated cases by
the number of recovered cases. This includes executions spent on cases
that remain unresolved. Proposed edits that the harness cannot apply do
not launch a build and do not contribute to this count. For agent runs,
we also report model calls, token use, and hosted-model charges.

We inspect execution errors before classifying outcomes. We count patches
that fail to apply, attempts to edit protected files, and decisions by the
model to stop as agent outcomes. We report results for all selected cases.
For each paired comparison, we also report results after excluding cases
where either approach encountered a harness failure that prevented a
reliable outcome.

## 5. RQ1: How prevalent is build decay, and how are historical build failures distributed?

## 5.1. Motivation

Before developing a repair framework, we first need to establish whether historical build failures are common and whether the same failures affect multiple cases. Reusable rules are useful only when failures repeat. RQ1 therefore measures how often historical reconstruction fails, how strongly the failures are concentrated, and whether repair outcomes vary by age or project.

## 5.2. Approach

We calculated the overall failure rate across the 14,159 cases we executed. We used the 4,513 cases in the failure-analysis dataset to examine how often the same failure occurred across multiple cases.

We assigned each case to the first failure observed before any repair was
attempted. As described in Section 3, we represented each
failure by its class, execution phase, and normalized signature. Cases sharing
all three values formed a baseline failure group. We report the number and
size of these groups, along with the share of cases in groups of at least five
and the share that occurred alone. We chose five as the threshold because it
left enough cases to inspect representatives and test whether a repair
transferred to other cases. We kept this initial grouping fixed throughout the
analysis. Failures exposed by later repair attempts did not change a case’s
baseline group.

We also measured how often a failed case later built without a repair. Among
the 2,451 cases included in the repair campaigns, we classified a
case as a no-patch recovery when a later execution succeeded without a repair
chain. This showed that re-execution was sufficient, but not why the initial
execution failed. For the age and project analyses, we used outcomes from the
deterministic repair campaigns evaluated in RQ2. We classified a case as recovered
if any campaign execution succeeded, with or without a repair. Of the 1,320 attempted cases with a known vulnerable revision
date, we included those from projects with at least ten such cases
spanning at least two historical years.
These criteria left 884 cases from 23
projects and gave each half of the within-project comparison at least five
cases. Within each project, we ordered cases by their vulnerable revision date
and split them at the median. We then compared the unresolved rates of the
older and newer halves. We used an exact two-sided sign test, excluding ties,
to determine whether the differences consistently pointed in either direction.
Finally, we report project-level unresolved rates only for projects with at least
twenty attempted cases to avoid comparisons based on only a few cases.

## 6. RQ2: Can deterministic repair rules repair decayed builds, and can their derivation be automated?

## 6.1. Motivation

Reusable rules are useful only if they repair recurring failures and can be
derived with limited human effort. RQ2 examines how many builds these rules
restore, whether rule derivation can run without human intervention, and
whether the applied repairs were needed for recovery.

## 6.2. Approach

We evaluated two consecutive phases of rule derivation. The first phase lasted
approximately three months. One of the authors selected failure groups,
reviewed the evidence and rules produced by the LLM, and revised the proposals
when needed. During the second phase, Relay selected groups, prepared the
evidence, generated candidate rules, and validated them without human
intervention. This phase started with the registry produced during the
human-guided work. We ran this phase until it reached approximately the same number of rule-associated recoveries as the human-guided phase. This took two weeks.

For each failure group selected during the automated phase, Relay prepared
evidence from two or three representative cases and asked GPT-5.6 Terra to
propose a rule. The proposal specified both the conditions under which the rule
should apply and the change it should make. Relay checked the repair scope, applied the candidate rule, and rebuilt the representative cases. If the rule restored a build or exposed a different failure, the framework added the rule to the registry and applied it to other matching cases. Relay recorded when each rule entered the registry and which successful repair chains used the rule.

We report the human-guided and automated phases separately. We count a
recovery as rule-associated when the successful execution used at least one repair rule. We count cases that built successfully without a repair as
no-patch recoveries. For the automated phase, we also report recovery rates by ecosystem. We calculate each rate by dividing
rule-associated recoveries by the number of cases attempted in that
ecosystem during the automated phase.

The two phases took place at different times, attempted different cases,
and shared an expanding rule registry. The human-guided phase also
included development of the framework. We report how long each phase
took to reach a similar number of recoveries, but these differences
prevent a direct comparison of their speed.

Early in the campaign, we prioritized failure groups that appeared likely to
produce reusable rules. We consequently explored some ecosystems more
than others. We later focused on underrepresented ecosystems, primarily
those outside C and C++, until we had examined approximately half of the
failure groups in each major ecosystem. Within these ecosystems, we
continued to choose groups based on their repair potential.

Some cases built successfully on a retry without a repair, so we checked
whether the rules were needed for recovery. First, we identified cases
that had failed without a repair before succeeding with one. We then
conducted a paired control using cases with a saved repair chain from
the successful execution. We selected 50 of these cases using a fixed seed and stratified the sample by language and failure class. We executed
each case once with the saved repair and once without it. We used separate data
directories and alternated which version ran first.

Finally, we examined whether repaired builds preserved the behavior needed by a
vulnerability benchmark. A successful build does not guarantee that the
recorded input will reproduce the historical crash. ARVO encountered the same
problem, including cases where the input did not trigger the crash on an
archived vulnerable binary (Mei et al., 2026). We therefore compared crash-reproduction rates
between rule-associated and no-patch recoveries to
check whether applying rules made the historical crash less likely to
reproduce. We report the difference between these rates with its 95%
confidence interval. We also report how many recoveries met the
benchmark-ready criteria defined in Section 4.4.

## 7. RQ3: How do reusable rules and per-case agents compare in recovery, cost, and the cases they restore?

## 7.1. Motivation

Per-case agents can inspect one repository and adapt its environment to the
failures they encounter (Hu et al., 2025b; Bouzenia and Pradel, 2025). This raises the question of why reusable rules are needed at all. RQ3 compares rules
and agents on the same failing cases and examines whether combining them
improves recovery and reduces repair effort. We measure build executions,
model usage, and which cases each approach restores. We also examine
how widely the rules are reused and whether they repair cases outside
those used during development.

## 7.2. Approach

We first measured how often the same repair rule helped restore different
cases, projects, and failure groups. Because a successful repair chain could contain more than one rule, we reported both recovered cases and rule credits. We gave a
rule one credit each time it appeared in a successful repair chain. The number
of credits can therefore exceed the number of recovered cases. We also report how many projects and baseline failure groups used each rule in a successful repair.

We reserved 400 previously unattempted cases to test whether the
registry could repair cases outside those used during rule development. We sampled by language and failure class using a fixed seed. We excluded Swift
because too few cases were available. We kept these cases out of rule derivation, validation, and subsequent repair campaigns.

After freezing the registry, Relay rebuilt each reserved case and
checked whether an existing rule matched the observed failure. These cases came from those that remained untouched after the campaign had examined many promising failure groups. This let us test the registry on the remaining failure families rather than on additional cases from groups where the rules had already succeeded.

Next, we compared the rules with per-case agents using cases that rules had restored during either campaign phase. We excluded the held-out sample and the RQ4 cases, leaving 227 candidates whose recorded failures matched a rule in the current registry. We grouped these cases by language, failure class, and
failure-group size. We randomly ordered the cases within each group using a
fixed seed and sampled from the groups in turn.

Relay rebuilt candidates without a repair in the sampling order. We retained the first 50 cases that still failed. This ensured that every case
presented an active repair problem when the comparison began. We used these initial executions to select the cases and excluded them from the reported build counts.

We ran the rule registry, Qwen3.8-27B, and GPT-5.6 Terra once on each retained
case. Qwen3.8 and Terra operated as per-case agents. Relay selected rules using the failure observed during the new execution. We ran the rule evaluation within one day of the agent runs to reduce changes in the external environment. We report recovered cases and build executions per recovery. For agents, we
also report model calls, tokens, and hosted-model charges. We report the
earlier cost of deriving the registry separately.

We report 95% Wilson confidence intervals for the recovery rates.
Because we evaluated all three approaches on the same cases, we compared their
recovery outcomes using two-sided exact McNemar tests. We adjusted the three
pairwise $p$ -values using the Holm-Bonferroni method.

Finally, we estimated the result of running the rules first and sending only the
remaining cases to an agent. For each case the rules did not restore, we used
the agent result and resource usage already observed for that case. Each agent started from the initial failure and did not inherit edits made by the rules. RQ4 evaluates agent escalation after deterministic repair stops.

first identify why rule-based repair stops and whether per-case agents

## 9. Discussion

## 9.1. Why Not Use an Agent for Every Build?

Rules and per-case agents both use model reasoning to decide how to repair
a build. A per-case agent repeats that reasoning for every build. Relay uses evidence from representative failures to derive a rule that specifies when a
repair applies and what to change. Once validated, the rule can be inspected and applied to
other matching cases without further model calls.

Our paired evaluation supports using rules before agents. The rules
restored similar numbers of cases with fewer build executions, while
agents restored additional cases that the rules missed. Combining
the recorded outcomes gave 37 to
39 recoveries out of 50 cases,
using fewer builds and less than half the agent tokens of an agent
alone. Rules handled recurring failures efficiently, while agent escalation
provided flexibility on the remaining cases.

Building the registry also takes work. Each new rule requires model
calls and validation builds, and some repairs require extending the
applicator with new editing operations. We paid these costs during
framework development and rule derivation. Reuse becomes worthwhile
when enough cases share a failure to justify that initial effort.
A larger registry can reduce repeated diagnosis, but it still needs
maintenance as build tools and external resources change.

The held-out evaluation showed where the registry needed further work:
no rule matched 376 of the 400 cases.
Deriving another rule is most useful when several cases share a failure.
For a failure affecting only one case, an agent may repair the build
with less effort than deriving and validating a reusable rule.
These limits motivate the division of work in Relay: apply validated rules wherever they match, then escalate what remains.

## 9.2. Improving the Repair Process

Our application audit showed that rules sometimes recognized a failure
but could not find the text they needed to change. Parsers for package manifests and build instructions could help the applicator make the
same edit across different file layouts. The resulting repair would still
need to be validated through execution, since a more portable edit could also
spread an incorrect change more widely.

The derivation loop sometimes proposed several versions of the same
unsuccessful repair. Keeping a record of the strategies already tried
and their execution results could help the model choose a different
approach. The framework could also use this history to stop rule
derivation or send the case to an agent when repeated proposals
fail to restore the build.

Per-case agents remained useful after the registered rules stopped. They
restored 17.5 to 28.1% of the remaining cases.
However, more model reasoning cannot recover a missing external resource or
correct a failure in the execution infrastructure. The models reported an
infrastructure or resource problem in 28 cases, but another
model restored 3 of them. The framework should therefore validate the model’s explanation for stopping using the execution logs before deferring a case.

Improving the agent harness or using stronger models may increase
recovery. Many unsuccessful runs reached the token limit, so better
evidence selection, conversation management, and tool use could help
agents spend their budgets more effectively. Sol did not improve
recovery on our small diagnostic subset. Further experiments could
test harness changes with the same model and compare models using
the same harness.

## 9.3. Preserving Executable Benchmarks

Benchmark maintainers can reduce future repair work by preserving
the resources needed to rebuild each case. Alongside the source
revision, they should record base-image digests, dependency revisions,
toolchain versions, and build instructions. Where redistribution
permits, archiving installers and source packages would also protect
against downloads becoming unavailable.

Benchmark maintainers should also preserve build logs, repair chains,
and the results of running the recorded input at both revisions.
These records let researchers inspect earlier repairs and check
whether a restored build still reproduces the historical vulnerability
and meets the benchmark-ready criteria.

## 10. Threats to Validity

## 10.1. Internal Validity

Attribution. Some cases built successfully on retries without a repair. We therefore report no-patch recoveries separately and use a paired control to check whether repairs were needed. For this reason, we also describe recoveries as rule-associated rather than claiming that every applied rule caused the observed recoveries.

Campaign comparison. The automated campaign started with the registry developed during
the human-guided phase. The phases attempted different cases at
different times, and the human-guided work also included framework
development. Early selection prioritized promising failure groups,
while later selection focused more on underrepresented ecosystems.
These differences limit conclusions about how much automation
reduced repair time.

Changes between executions. External resources continued
to change during the study. Some previously failing cases built successfully without a repair when we re-executed them before RQ3 and RQ4. We excluded these cases because they no longer presented a repair problem. In RQ3, we ran the rule and agent evaluations within one day of each other. These steps reduce, but do not eliminate, differences caused by changes in
package repositories, mirrors, and other external services.

Harness errors. We inspected failed runs to distinguish repair failures from errors in the experimental harness. We report results for all selected cases and additional comparisons excluding runs affected by harness
errors. We count patches that fail to apply as repair outcomes.
Some errors require judgment to classify, so we may have
misclassified cases despite inspecting their logs.

## 10.2. Construct Validity

Failure and success measures. We count a case as failed
when it does not complete the full reconstruction and verification process.
This definition includes build failures, unavailable resources, and failures
in the execution infrastructure. Some failures may be temporary or have
causes unrelated to environment decay. Conversely, a successful build does
not by itself restore a vulnerability benchmark. We therefore report crash reproduction and the stricter benchmark-ready outcome separately. These checks do not prove that every behavior of the rebuilt program is unchanged.

Grouping and rule credit. Normalized signatures can merge distinct
causes or separate variants of one cause. Shared groups motivate investigation
but do not guarantee a common repair. Rule credits can overlap within a chain,
so we distinguish them from distinct cases. Several rule identifiers may also describe the same repair strategy. Models may misidentify why they stopped, so we check their explanations against the execution evidence.

Manual audits. We classified repair operations and repair limits using the available logs and repair specifications. Some earlier records contained less detail, and different rule identifiers sometimes described similar
repair strategies. These classifications required judgment, and
another researcher might group some operations differently.

Costs and budgets. Build executions vary in duration and resource use. Some fail early, while others compile large projects. Token totals count conversation history again each time the harness sends it to the model, and
different tokenizers may count the same text differently. Reported
model charges exclude hardware and human effort. We report rule
derivation costs separately from the cost of applying existing rules.
Our cost comparisons therefore cover only part of the total effort
needed to develop and run the framework.

## 10.3. External Validity and Repeatability

Dataset scope. All cases use OSS-Fuzz build recipes and our extended ARVO workflow. Their shared base images and build conventions may make rules easier to reuse than in other build systems. We also deliberately increased the
representation of non-C/C++ projects. The 69.7%
reconstruction-failure rate therefore describes our dataset and may
differ from the rate across the full OSS-Fuzz issue tracker.

Failure and repair selection. The failure-analysis
dataset contains cases for which Relay produced a normalized observation. We assembled it first by including failures from non-C/C++ projects and then
adding C/C++ cases. The repair campaigns prioritized recurring groups
that appeared likely to support reusable rules. These choices affect the failure groups and ecosystem recovery rates we report.
We selected the held-out cases from those the campaigns had not
attempted. This limits how well the evaluation represents rule reuse
across the wider dataset.

Evaluation cohorts. RQ3 used cases that had previously
been repaired by rules and still failed when re-executed. Most selected cases were C or C++ builds, and selecting previously repaired cases may favor the rule-based approach. RQ4 used cases where the rules had stopped or could not express the required repair. Recovery rates may differ on other
samples. We also did not compare Relay with reconstruction using
archived distribution snapshots.

Model repeatability. We ran each model once per case.
The local models used temperature 1.0, so repeated runs could produce different results. Both Qwen releases use the same serving settings, but
their weights and templates differ. Hosted models may also
change over time. We selected the small Sol subset using earlier Qwen outcomes, and many Sol runs reached the token limit. A larger evaluation is needed
to assess how model capability affects repair success. Models may
also have encountered the public projects and issue reports during
training, which could influence their repairs.

## 11. Related Work

## 11.1. Historical Build Reproducibility

Prior work has studied how to preserve software builds and reproduce
their outputs. Reproducible-build research has examined whether
rebuilding the same source produces bit-for-bit identical
artifacts (Lamb and Zacchiroli, 2022; Fourné et al., 2023; Malka et al., 2025). Studies of container reproducibility have
shown that rebuilding can still depend on changing image tags,
package repositories, and external downloads (Malka et al., 2026).
Researchers have addressed environment preservation through
functional package managers (Malka et al., 2024) and
developed systems to reconstruct dependencies for Python programs
and notebooks (Horton and Parnin, 2019; Ye et al., 2022; Wang et al., 2021). We examined how to restore historical builds
across several ecosystems after their environments had stopped
working.

Research on executable defect datasets has highlighted the need to
preserve historical build environments. Defects4J, BugSwarm, and
Vul4J provided historical failures for controlled
experimentation (Just et al., 2014; Tomassi et al., 2019; Bui et al., 2022), while Zhu and Rubio-González showed that dataset
artifacts could lose reproducibility over
time (Zhu and Rubio-González, 2023). ARVO addressed this problem for
OSS-Fuzz vulnerabilities by reconstructing vulnerable and fixed
revisions (Mei et al., 2026). CyberGym and SEC-bench subsequently used
executable historical software to evaluate security
agents (Wang et al., 2026; Lee et al., 2025). We extended ARVO to repair the
environment failures that remained after its reconstruction
mechanisms ran. This also distinguished our work from systems
such as CodeRover-S, which repaired vulnerabilities by changing
the target source (Zhang et al., 2026) whereas we preserved that source and
repaired the environment needed to build and execute it.

## 11.2. Build Repair and Reusable Fixes

Several studies have investigated build failures and their repair across
continuous integration, Docker, and other build
systems (Rausch et al., 2017; Vassallo et al., 2017; Wu et al., 2020; Lou et al., 2020). A prior study by Nourry et al. also studied active OSS-Fuzz projects and identified failure causes across project source, build scripts, dependencies, toolchains, external resources, and execution
infrastructure (Nourry et al., 2025). These findings motivated us to
examine repairs across several stages of a build. We focused on
historical revisions, where changing the target source could alter
the benchmark case, and investigated whether environment repairs
could be reused across versions and projects.

Researchers have also developed tools to automate build repair using project history, dependency fixes, and reusable editing operations. HireBuild used
earlier changes to repair build scripts (Hassan and Wang, 2018),
while later work examined the limits of relying on history and
proposed repairs that did not require it (Lou et al., 2019).
Dependency-focused systems included BuildMedic for Maven
builds (Macho et al., 2018) and PyDFix for Python dependency
errors (Mukherjee et al., 2021). Reusable operations have also
supported Dockerfile repair through human-guided
derivation (Henkel et al., 2021) and mined
patterns (Sakamoto and Ohira, 2026). Other work has addressed
flaky Docker builds and equipped agents with operations for Android
build repair (Shabani et al., 2025; Son et al., 2026). These approaches
have developed repair mechanisms for specific build technologies
and ecosystems. Alternatively, we examined how to derive and reuse repairs across the containers, dependencies, resources, toolchains, and scripts
involved in historical reconstruction.

Program-repair research has also investigated how to reuse fixes.
Refazer learned syntactic transformations from
examples (Rolim et al., 2017), and Getafix learned fix patterns
from human-written changes (Bader et al., 2019). These systems
showed how examples could guide repairs beyond the original case.
We applied this idea to build environments by asking an LLM to
derive rules from representative failures. We tested each candidate
by rebuilding cases, then reused accepted rules without further
model calls.

## 11.3. Agents for Environment Setup and Compatibility Repair

Recent studies have used language-model agents to automate repository
setup, compilation, and test execution (Hu et al., 2025b; Bouzenia and Pradel, 2025; Milliken et al., 2025; Hu et al., 2025a; Yu et al., 2025). EnvBench has provided tasks for evaluating
environment setup in Python and JVM
projects (Eliseeva et al., 2025). Much of this work has focused on
preparing repositories for execution. RepoRescue examined a setting
closer to ours: older Python and Java repositories that no longer
worked in modern environments (Lin et al., 2026). It allowed
source changes and evaluated success through historical tests.
We preserved the target source revision and used the recorded
crashing input to check historical behavior. Other studies have
used agents or LLM-generated patches to repair dependency-related
build failures (Macho et al., 2026; Reyes et al., 2026).

Recent work has explored how agents could reuse knowledge from
earlier setup tasks. SetupX transferred structured experience between
repositories, while BootstrapAgent recorded verified setup knowledge
for later agents (Zhou et al., 2026; Fu et al., 2026). We pursued
reuse through executable repair rules. Once a rule passed validation,
the framework could apply it to matching failures without another
model call. Per-case agents handled cases that remained unresolved.

These studies have advanced reusable repair and per-case environment
setup. We brought the two approaches together for historical build
restoration and evaluated where each helped. Our comparison examined
their recovery, build effort, model use, and the cases they restored.
Combining the recorded outcomes let us assess the benefit of
applying existing rules before spending agent effort on unresolved
cases.

## 12. Conclusion

We examined 14,159 historical OSS-Fuzz cases and found that
69.7% failed to complete reconstruction and verification
despite pinned source revisions. The failures were concentrated:
161 groups covered 71.0% of the failure-analysis
dataset. These recurring failures created opportunities to reuse
repairs across cases.

We developed Relay to derive reusable repair rules and escalate
unresolved cases to per-case agents. Across the campaigns,
52 rules contributed to 469 recoveries.
On the 50 cases in our paired evaluation, agents restored
similar numbers of builds but required 2.3 to
3.6 times as many build executions per recovery.
Combining the recorded outcomes gave 37 to
39 recoveries with fewer builds and less than
half the agent tokens of an agent alone. Agents also restored
17.5 to 28.1% of the cases left unresolved
by deterministic repair. These findings support applying reusable
rules first and using agents for the remaining cases.

Further work could improve how rules edit different build-file
layouts and how agents use their execution and token budgets.
Experiments could also vary the execution evidence given to
rule-authoring models and repair agents to determine which logs,
error excerpts, and repair history help them make better repairs.
Evaluating stronger models with the same harness would help identify
where model capability improves recovery. Throughout restoration,
checking the recorded historical behavior remains essential to
preserving the cases used by vulnerability benchmarks.
