## Certifying Repeatable Entry-Replay Witnesses

for COBOL-to-Java Migration

Andras L. Ferenczi ,
Mariya Bessonov, Allwyn Ponnudurai

Chandrakanth R. Mamillapalli, Krishna K. Maddula, Krishna K. Lingamneni

Affiliation: American Express

Abstract

Producing synthetic data for comparison testing a migrated COBOL application is a major challenge that agentic migrations face today. Our prior paper, the Agentic Method for Deterministic Validation of Legacy Code Migration, presents a deterministic oracle to facilitate such migrations, the Locksmith Loop. We now propose a novel method for achieving high branch and paragraph coverage through generated synthetic end-to-end test cases, by means of entry-replay test-case certification by observing the code execution trace on a surrogate COBOL program that mocks external interactions via a chronological external-operation tape.
We applied our method to a very large COBOL program with 33,429 lines of code to generate 849 synthetic end-to-end test cases covering 2,973/3,806 source branches (78.1%) and 989/1,033 main-AST paragraphs (95.7%).
Using the Locksmith Loop’s projected-agreement validation, the generated Java code matched the COBOL surrogate on the specified observations across all 849 certified synthetic end-to-end test cases.
During the campaign we detected 61 defects and fixed the Java generator accordingly. To test whether the coding agent could silently introduce business logic bugs, we seeded 450 defects into the Java code, such as deleted writes, deleted paragraph calls, and altered rounding, to verify how many of these would be detected by the gating methodology. The gate detected 47.6%, including all deleted writes and paragraph calls in executed code, but was unable to detect the rounding and precision defects.

Index Terms: 
legacy migration, COBOL, differential testing, test generation, deterministic replay, translation validation

## I Introduction

Agentic legacy migration projects need deterministic methods for validating migrated behavior. Frequently, lack of documentation and test data makes it difficult to validate parity between the legacy code (COBOL, in our case) and the new migrated Java code. Unit tests go only so far as to validate local functionality, and integration tests can go only so far as to minimally validate functionality. Even with comprehensive quality assurance user testing, there is a limited guarantee that the system will work as expected with the COBOL code being the ground truth.

The Locksmith Loop [1] provides two methods for generating witnesses (synthetic end-to-end test cases): the Witness Search (input-space exploration) and the Mutation (parity-preserving code mutation).
The Locksmith Loop provided a witness generation method demonstrated on a 4,114-line, 142-paragraph COBOL codebase. This paper evaluates a methodological successor to the Locksmith Loop on a 33,429-line, 1,033-paragraph program.

We focus in this research on a novel approach for witness discovery while reusing the Locksmith Loop agentic method for checking projected agreement between the migrated Java code and the surrogate COBOL codebase on certified witnesses. It is important to clarify that the method does not guarantee production functional parity. It is nevertheless helpful for discovering behavioral differences that might otherwise not be identified.

We ask:
RQ1: can our method grow the coverage of the COBOL surrogate, and how does coverage accumulate as the certified catalog grows?
RQ2: how does the source-outcome set of the final certified catalog differ from that of the retained local-search corpus?
RQ3: how many seeded translation defects does the certified gate detect under the observation projection $\Phi_{H}$ (Section III), and where does detection fail?
RQ4: what kinds of COBOL-to-Java migration bugs did the repeatable certification method expose, and how many repairs did each kind require?
RQ5: what are the guarantees and the limits of our witness certification process?

## II Related Work

At a high level, we reuse the Locksmith Loop [1] approach for validation against a deterministic oracle, including mocked interactions with external systems such as databases, message queues, and other programs, but not its method for proposing witnesses. The local-state adaptation is related to testability transformation [2] and to DART, Driller, and T-Fuzz [3, 4, 5] (see [6] for a survey). We use agentic functionality for this task and count only end-to-end source replay as coverage. Elbaum et al. [7] and Saff et al. [8] extract intermediate program states from an execution and use those to replay a subcomponent of the program in isolation; we do exactly the opposite, proposing witnesses in isolation and walking our way upstream to the conditions that satisfy execution of the subcomponent.
Kumar et al. [9] and Hans et al. [10] use symbolic execution on the COBOL source code to generate JUnit test cases, which are then run against the Java code. Similarly to the Locksmith Loop, this method implies like-for-like migration rather than object-oriented refactoring. However, their method is performed strictly at the unit test level, with the known limitation of path explosion, thus making it intractable for very large programs. Etemadi et al. [11] begin with functioning test inputs that produce matched behavior in two programs, then use an LLM iteratively to generate new inputs until it identifies different behavior between these (disagreement as an oracle). A disagreement shows that the two programs differ, but not which one is correct. As an alternative for settings lacking a deterministic ground truth, Chen et al. [12] use metamorphic testing, a method that verifies relations that must exist between multiple execution outputs. While this can indeed identify discrepancies between original and migrated code, it only detects violations of the chosen relations, and so does not offer a comprehensive solution. Pnueli et al. [13] prove translation accuracy by establishing a formal correspondence between the source and target programs and verifying it for each translation run. In contrast, our method uses an empirical approach, which we demonstrate to be feasible at the scale of a 33,429-line program using agentic coding methods. Our method addresses the frequently most realistic scenarios where suitable from-entry source tests are unavailable.
Dijkstra’s 1975 paper [14] presents a formal method for defining the weakest execution precondition for a guarded command in order for the execution to result in expected behavior. By decomposing the program into such guarded commands one can better derive the end-to-end execution preconditions. In contrast, our method works on an already existing COBOL program, computes the requirements empirically and produces a precondition sufficient for a specific witness to work. Chvátal [15] is a foundational method for a greedy subset (witness) search by repeatedly picking the subset with the lowest cost per newly covered element in every iteration and is repeated until all elements are found, a technique also applied to test-suite minimization [16] and directly applicable to reducing our own certified witness catalog.

## IV Evaluation

## IV-A Setup

As in the Locksmith Loop [1], we used a production-like COBOL program, here eight times larger (33,429 lines). We instrumented the source’s decision constructs and mocked all external interactions (mediated files, database operations, subprograms), correctly handling binary, packed-decimal, redefined, and repeated record layouts along the way. We compiled it using GnuCOBOL 3.2.0 on an Arm workstation, targeting OpenJDK 17. Unlike the Locksmith Loop, we did not leverage any test data, but instead generated inputs based on the COPYBOOK structures used by the program.11
 1

 No customer data were used in any experiment during the campaign.

 $F$ holds the final contents of the output files generated by each run in the certified runtime. The remaining output files are served by the mocked I/O layer, so $J$ and $O$ check their operations but not their payloads.

Agent governance. We used commercial LLM-based coding agents to propose witnesses and repairs. The models and agent harnesses were upgraded several times as new versions became available during the campaign. Certification, replay, tape matching, and the $\Phi_{H}$ comparison are deterministic code that every agent output must pass. An author reviewed the repairs in the surrogate, mock, and capture oracle and accepted them only after the full catalog re-certified.

Sections IV-B–IV-E answer RQ1–RQ4, Section IV-F reports cost, and Section V answers RQ5.

## IV-B Coverage (RQ1)

In the end we covered 2,973/3,806 source branches (78.1%), and 989/1,033
main-AST paragraphs (95.7%). This does not mean that either of the
uncovered paragraphs or branches is unreachable, but rather reflects
the fact that we intentionally stopped construction once main-AST paragraph coverage passed a 95% target. Even with a “perfect” deterministic match under the declared observation projection, there could exist undetected subtle defects hiding in the code, as quantified in Section IV-D and Table II. For example, the Java code might write the wrong value somewhere in the middle of the program run but then overwrite it with the correct value. Table III reports the full
case measurements.

Certified branch and paragraph coverage reached 47.8% and 73.5% after 50 witnesses, which represent only 6% of the catalog. We attribute this to shared validation paragraphs and common error handling routines. Coverage rose to 68.3% branch and 89.9% paragraph after 400 witnesses, and to 78.1% and 95.7% after 849 (Fig. 4). Figures 6 and 7 show how the final paragraph coverage is distributed across the recovered graph and its depth ranks.

Of the 44 unentered main-AST paragraphs, 27 occur at condensation rank zero, making this the largest remaining structural concentration.

The other 17 unentered paragraphs are sparsely distributed through ranks 1–20, rather than forming a shallow coverage cutoff.

## IV-D Fault Detection (RQ3)

To verify our method’s ability to detect unwanted silent business logic changes the agent could potentially introduce, we derived ten mutation operators based on Fig. 9, limited to ten by the cost of finding reliable locations where these operators reside. Our coding agent then created a site search function that looks up the generated Java code to list where every operator can apply (a total of 27,218 candidate sites). We then used a fixed seed to pick 45 sites per operator, a total of 450 sites. Each version of the compiled Java code contained a single mutation. We then replayed the witnesses that reach each mutated line, while $\Phi_{H}$ stayed fixed. Mutants were killed if disagreement was found under $\Phi_{H}$ . REDEFINES layout mutants have no executable line: they replay all 849 witnesses and count as reached if a witness enters a paragraph that names the overlaid field or its group, so this rule affects only the reached/unreached split. The gate killed 214 of 450 mutants (Table IV), 206 of them in code the witnesses reach. No rounding or precision mutant was killed. Of 32 sampled survivors, 6 were equivalent and 26 needed inputs that no witness reaching the site carries.

## IV-E Repair Ledger (RQ4)

We maintained a ledger to keep track of a filtered set of defects encountered
and repaired, in the Java or, when a disagreement traced back to them, in the surrogate, mock, or capture oracle, including deterministic disagreements that
were consistently recurring rather than one-offs, bugs that occurred
in shared code and thus affected multiple witnesses/branches, and
defects that were clearly identifiable rather than a collection of
small scattered tweaks. The final results can be seen in
Fig. 9. Excluding transient bugs, the ledger holds 69 durable repairs: 61 in the Java and 8 in the surrogate, mock, or capture oracle, none of which touched the program’s logic. The ledger was filtered and classified retrospectively, so its counts show which kinds of defects the method exposed, not a defect rate.

## IV-F Validation Loop and Cost

The Java replay used the chronological tape matcher in
Fig. 3 and the normalization contract in
Eq. (1). As soon as $\Phi_{H}(E_{J})$ diverged from
 $\Phi_{H}(E_{S})$ at any point, the agent would repair, recompile,
re-deploy the Java code and re-run the same witnesses until
 $\Phi_{H}(E_{J})=\Phi_{H}(E_{S})$ . Figure 8 shows the
dependency of progress on full catalog repairs, as previously passing
witnesses may fail post-repair. Table I reports the runtime of the final gate: about 12 minutes for all 849 witnesses.
Although we tracked the spend of 203 million tokens across 1,067 agent requests, these benchmarks cannot directly be attributed to algorithmic per-witness spend. The resources allocated included fixes to the reusable Java code generator that made it progressively better over time; it also included tape, runtime, COBOL mock, and parity repairs. Additionally, as the experiment spun across several weeks, the agent models were also uplifted, and hence the token consumption and caching methodologies, as well as costs, changed accordingly.

## V Discussion and Threats to Validity

Certification guarantees repeatable source replay and target agreement under $\Phi_{H}$ only (RQ5). It does not guarantee production equivalence or any behavior outside $\Phi_{H}$ .
As we only certified successful runs, error scenarios were excluded. Transient storage was also not tracked. To assess the risk of the coding agent introducing unintended business logic changes, we performed a mutation study (Section IV-D) that showed 47.6% fault detection. Our normalization process may also miss genuine parity failures. The GnuCOBOL compiler may not be 100% identical to the original mainframe compiler; for example, ASCII versus EBCDIC mismatches or compiler defects may go unnoticed. For branching we used a limited set of probes: IF, EVALUATE, PERFORM UNTIL, SEARCH, and conditional handlers, which may not be a comprehensive list of inflection points. Future enhancements include a more comprehensive set of branching instrumentation, boundary-directed witness construction, and field-level payload comparison. Although our method does not guarantee 100% code compatibility, we expect it to substantially reduce the number of defects prior to an integration testing phase.

As an engineering campaign that was carried out over time, it leveraged evolving agentic functionality that, in the course of the processing, fixed Java generator bugs, the mock layer, and the certification tools. As a result, it was impossible to establish a “like-for-like” equivalence with the Locksmith Loop witness method. Accordingly, we make no claim of a quantified improvement over the Locksmith Loop witness-generation approach; we report only the coverage achieved on this subject.

Entry-replay certification establishes that the COBOL surrogate and migrated Java agree for the certified witnesses under $\Phi_{H}$ ; it does not establish identical internal behavior.

## VI Conclusion

We describe in this paper entry-replay certification, a novel method for gradually discovering repeatable entry witnesses starting with local isolated discovery and backward lifting. We were able to generate 849 certified witnesses covering 2,973/3,806, or 78.1% of all source branches, and 989/1,033, or 95.7% of the paragraphs, of a 33,429-line production-like COBOL program. A repair ledger supplied useful information about challenges encountered in this migration.
The gate exposed 61 Java defects during the campaign and detected 47.6% of seeded mutants, but no rounding or precision defects, since the witnesses rarely exercise value boundaries.
We verified feasibility of the solution by creating repeatable source certification and reached COBOL-to-Java agreement for the certified witnesses under the declared observation projection.
