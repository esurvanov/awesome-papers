Abstract

Enterprise adoption of LLMs in agentic workflows is gated by
evaluations that span a wide arc of abilities: CRM operations,
heterogeneous-document retrieval, personal data understanding,
multi-turn planning, tool use, function calling, long-horizon
research, and long-context software engineering. These evaluations
live today in separate repositories with divergent runners,
dependencies, and scoring conventions, which makes cross-benchmark
comparison difficult and obscures what a single aggregate number
actually represents. We release EGI-Bench, a unified LLM agent benchmark
suite that consolidates eight enterprise-facing agent benchmarks
(CRMArena, HERB, PersonaBench,
UserBench, MCP-Universe, MCPEval,
Benchforce, LoCoBench) behind a single command-line
interface with two runtime-budgeted execution modes. On top of the
suite we define the Enterprise General Intelligence (EGI)
Score, a six-dimensional framework
(M1–M6) whose buckets are populated by fine-grained
sub-metrics routed from each benchmark rather than by benchmark-level
averages. We describe the suite, the sub-metric routing, and the
quick/deep budgets, and report results for fourteen frontier and
cost-efficient LLMs spanning the GPT, Claude, and Gemini families
under quick mode. Top-line EGI ranges from $39.6$ (GPT-4o mini) to
 $65.6$ (gpt-5.5), and no single model dominates every
capability axis: gpt-5.5 leads task outcome, planning, and
retrieval grounding; Claude Sonnet 4.5 leads tool actioning and
safety/abstention; and Claude Haiku 4.5 leads engineering quality. Code is available at
https://github.com/SalesforceAIResearch/egi-bench.

## 1 Introduction

Large language models are now deployed inside agentic systems that
plan, use tools, and act inside real software
environments [22, 17, 14].
In the enterprise, these systems answer customer-support tickets,
search internal documents, navigate CRM objects, plan travel, invoke
business APIs, and maintain large codebases. For any given
deployment, the question a release-gating team asks is whether the
underlying LLM is ready for these workflows: can it produce
correct business outcomes, call tools reliably, plan efficiently,
ground answers in retrieved evidence, abstain when appropriate, and
produce artifacts of acceptable engineering quality? Answering that
question requires many signals at once, and no single benchmark
captures all of them. EGI-Bench measures the LLM that drives these
workflows; each contributing benchmark exercises it through its own
native scaffold (ReAct loops, multi-turn dialog, function-calling
harnesses), and the resulting EGI score is therefore a model-level
signal across enterprise-shaped tasks.

Despite this demand, existing benchmarks each cover a narrow slice of
the space. The agent-evaluation literature has grown rapidly but is
fragmented along capability lines.
AgentBench [8] and
AgentBoard [11] evaluate general agentic
behavior across heterogeneous environments; GAIA [12]
targets general AI-assistant questions with verifiable answers.
SWE-bench [6] focuses on resolving
real-world GitHub issues; WebArena [23]
places agents inside a realistic web environment.
ToolLLM [14], the Berkeley Function Calling
Leaderboard [20], and MINT [19]
probe tool use and multi-turn tool-augmented interaction;
 $\tau$ -bench [21] measures tool-agent-user dialog in
realistic domains. Holistic LLM evaluations such as
HELM [7] aggregate scores across many tasks
but are not agent-centric. In the enterprise setting specifically,
recent benchmarks cover CRM workflows [4, 5], deep search
over heterogeneous enterprise data [3], personalized QA
over private user data [18], multi-turn
user-facing dialog [13], function
calling [16], MCP-based tool
use [10, 9], and long-context software
engineering [15]. Each of these benchmarks lives in
its own repository, with its own runner, dependencies, and scoring
conventions.

Because these benchmarks live in separate repositories with divergent
runners and scoring conventions, a practitioner who wants a single
EGI signal today must run many tools, reconcile
their outputs by hand, and decide how to weigh them. Naively averaging
each benchmark’s reported overall score dilutes signal: a benchmark that
internally averages nine sub-scores contributes one number, while a
benchmark with a single sub-metric contributes the same one number.
Worse, each benchmark’s “overall” collapses sub-metrics that probe
very different capabilities (e.g. policy-violation detection vs. named-entity disambiguation inside
CRMArena [4]). The result is that existing
leaderboards cannot answer capability-grounded questions like “is this
model safe enough to ship?” or “does it plan multi-step workflows
reliably?”. Table 1 makes this gap
concrete: the four most prominent agent-benchmark reference points
each cover only a strict subset of the six EGI
dimensions we argue are needed for release decisions. This is the gap
EGI-Bench fills.

## Contributions.

This report describes EGI-Bench, a unified
LLM agent benchmark suite and scoring framework for enterprise-shaped
tasks. Our contributions are:

• 

Unified suite. We consolidate eight enterprise-facing
LLM agent benchmarks [4, 3, 18, 13, 10, 9, 16, 15] into one repository behind the
egi-bench CLI, with per-benchmark virtual environments, a shared
LiteLLM model-routing proxy, and a single
run --model … --mode {quick,deep} entry point. Each
benchmark retains its own scaffold (ReAct, MCP client, multi-turn
dialog, etc.); the unit of evaluation is the LLM.

• 

Fine-grained sub-metric routing. Rather than averaging
benchmark-level scores, we route individual sub-metrics into a
six-dimensional EGI framework (M1–M6) that
captures task-outcome accuracy, tool actioning, planning, retrieval
grounding, safety/abstention, and engineering quality. The routing is
declarative and auditable (Appendix C).

• 

Runtime-budgeted modes. Quick mode targets
 ${\leq}180$ min total wall-clock; deep mode targets ${\sim}12$ h.
Which categories or tasks get subsetted is determined by a
per-benchmark runtime budget rather than by hand-picked coverage.

• 

Open release with a fourteen-model benchmark. We
release the suite, configuration, and full quick-mode results across
fourteen frontier and cost-efficient LLMs spanning the GPT, Claude,
and Gemini model families. The results expose capability-level
specialization that is invisible in any single benchmark’s overall
score.

The rest of the report surveys related evaluation work
(Section 2), positions EGI-Bench against comparable
benchmarks (Section 3), defines the M1–M6
framework and the eight benchmark contributors
(Section 4), reports results and analysis
(Sections 5–6), and lists limitations
(Section 7). The sub-metric routing table and
execution-mode details are deferred to
Appendices C and E.

## 2 Related Work

We situate EGI-Bench relative to four lines of work: holistic LLM
evaluations, general agent benchmarks, tool-use and function-calling
benchmarks, and enterprise-facing agent benchmarks.

## Holistic LLM evaluations.

HELM [7]
proposed a multi-metric view of language-model evaluation, separating
accuracy, robustness, calibration, and other axes across many tasks.
While HELM is primarily task-level rather than agent-level, it established the principle that a single benchmark should expose multiple interpretable dimensions. EGI-Bench adopts the same
spirit but applies it to LLM evaluation in enterprise agentic
workflows by defining six enterprise-relevant dimensions
(M1–M6) and routing each contributing benchmark’s native
sub-metrics into them, rather than averaging benchmark-level scores.

## General agent benchmarks.

AgentBench [8] evaluates LLM agents across
eight heterogeneous environments (code, games, web, reasoning, etc.)
and reports per-environment success rate with an overall average; it
does not expose a cross-environment capability decomposition, so
planning, tool use, and abstention collapse into a single scalar per
environment. AgentBoard [11] introduces
progress rate, a fine-grained mid-trajectory metric across nine
environments — the closest prior art to our “don’t just report the
final number” philosophy, but operating within a single benchmark
family rather than composing across independently authored benchmarks.
GAIA [12] benchmarks general AI-assistant
questions with verifiable ground truth and public/private test sets;
the only axis of decomposition is its three-level difficulty partition
(Level 1–3), and a failed web-search step and a failed arithmetic step
are indistinguishable in the scored output.
WebArena [23] places agents in a realistic,
self-hosted web environment with full interaction traces and reports
end-to-end task success. These benchmarks target breadth of capability,
not enterprise readiness: none of them decomposes scores into
enterprise-interpretable buckets such as safety/abstention or
engineering quality, and none composes signals across independently
authored benchmark families.

## Tool-use and function-calling benchmarks.

ToolLLM [14] introduced ToolBench with
16,000+ real-world APIs and trained a tool-augmented LLM; its
headline metric is a pass-rate-with-retries aggregated across APIs.
The Berkeley Function Calling Leaderboard (BFCL) [20]
standardizes evaluation of function calling across API families and
provides the most fine-grained tool-use report to date: AST vs. executable evaluation, simple / multiple / parallel / parallel-multiple
settings, multi-turn and multi-step categories, language axes (Python,
REST, SQL, Java, JavaScript), Function Relevance Detection (an explicit
abstention test in which the correct response to an irrelevant toolset
is to call nothing), and cost-per-1000-calls with latency as
first-class signals. BFCL’s taxonomy on the tool-calling axis is
stronger than what EGI-Bench’s MCP contributors currently surface;
EGI-Bench’s advantage is the enterprise context that surrounds the
tool calls, not the tool-calling depth itself.
MINT [19] measures multi-turn interaction with
tools under language feedback, reporting success at $k$ tool calls and
tool-type breakdowns. $\tau$ -bench [21] and its
dual-control follow-on $\tau^{2}$ -bench [2]
target tool-agent-user interaction in realistic retail, airline, and
(in $\tau^{2}$ ) telecom domains, with passk ( $k$ up to $8$ ) as the
headline metric plus an auto error-identification pipeline that
classifies failures by fault assignment (agent / user / environment)
and fault type (used_wrong_tool,
used_wrong_tool_argument, took_unintended_action,
goal_partially_completed).

This multi-trial reliability
signal is missing from EGI-Bench v1 and is concrete future work. Within
EGI-Bench, tool-use signals come from
MCP-Universe [10] and
MCPEval [9], which instantiate the Model
Context Protocol [1] server/agent contract, while
Benchforce [16] complements these with
WebSocket-driven enterprise function-calling environments. Where prior
tool-use benchmarks expose a single success rate, EGI-Bench routes the
component metrics (tool-name match, parameter match, ordering, strict
vs. flexible success) into separate enterprise buckets so that drift,
over-action, and planning-order errors are surfaced independently.

## Code and long-context benchmarks.

SWE-bench [6] evaluates whether LLMs
can resolve real-world GitHub issues in 12 Python repositories using
unit tests as verifiers; its per-instance pipeline surfaces four
signals (applied / tests-pass / regression / resolved), with the
headline leaderboard reporting the resolve rate. Hidden-test ground
truth certified by the original issue authors makes SWE-bench the
stronger instrument for pure coding correctness, but it does not
measure code quality, patch-size minimization, planning or search
behavior separate from the final patch, or tool-call efficiency.
LoCoBench [15] extends software-engineering
evaluation to long-context scenarios spanning ten programming languages
and context lengths up to ${\sim}1$ M tokens, using a four-dimensional
rubric (functional correctness, software engineering excellence, code
quality, long-context utilization). EGI-Bench uses LoCoBench as
its software-engineering contributor and routes its four dimensions
into M1, M3, and M6; the rubric is softer than
SWE-bench’s hidden tests, which we acknowledge as a trade-off.

## Enterprise-facing agent benchmarks.

A newer wave of
benchmarks targets enterprise workflows specifically.
CRMArena [4, 5] evaluates Salesforce-style CRM
operations (case routing, analytical queries, policy-violation
detection) against a sandbox org. HERB [3]
benchmarks multi-hop retrieval over realistic, heterogeneous enterprise
corpora (documents, Slack, meeting transcripts, URLs) and mixes
answerable and unanswerable queries to test anti-hallucination.
PersonaBench [18] measures personalized QA
over synthetic private user data with controllable noise injection.
UserBench [13] exercises multi-turn travel-planning
dialog with user-preference satisfaction as the reward signal.
Each of these benchmarks is valuable on its own;
what is missing is a principled way to read them together as an
EGI signal.

## Cross-domain aggregation.

Prior practice aggregates
cross-benchmark signal either by picking a headline benchmark per
capability or by averaging benchmark-level overall scores. Both lose
information. EGI-Bench instead routes individual sub-metrics into the
M1–M6 framework (Appendix C), preserves per-benchmark
sub-scores for diagnosis (Section 5), and optionally
applies release-gate floors on M5 (safety/abstention) and
M2 (tool actioning) so that a single aggregate number cannot hide
a capability regression that matters for deployment.

Each of the four comparison benchmarks is a strong instrument on a
narrow subset of axes: $\tau^{2}$ -bench on dialog reliability and
passk-style multi-trial correctness with a dual-control user
simulator, SWE-bench on code-resolution correctness with hidden-test
ground truth, GAIA on multi-step generalist-assistant tasks, and BFCL
on tool-calling taxonomy and cost/latency telemetry. EGI-Bench’s
contribution is not to beat any of them on its home axis but to
cover all six EGI dimensions through a
composition of eight independently authored benchmarks, route their
sub-metrics into a shared frame (Appendix C), and add
release-gate semantics via configurable M5 and M2 floors.
Practitioners who need the maximum-rigor instrument on a single axis
should continue to use the specialist benchmark; practitioners who
need a capability-grounded readiness score for an enterprise deployment
should use EGI-Bench.

## 4 The EGI Framework

We evaluate LLMs along six enterprise-level metrics and combine them
into a single EGI score. The metrics,
definitions, and weights are summarized in Table 2.

Table 2: The six enterprise metrics (M1–M6) and their weights in the
EGI score. Weights are inherited from the internal PR #28
proposal and are applied uniformly across the suite.

Metric
Weight

What it measures

M1 Task Outcome Accuracy
28%

Did the agent produce the correct business outcome or final answer?

M2 Tool Actioning Reliability
22%

Correct tool selection, parameters, ordering; no extraneous calls.

M3 Planning & Workflow
16%

Multi-step and multi-turn execution that is step-efficient.

M4 Retrieval & Evidence Grounding
14%

Grounded answers, correct citations, effective context use.

M5 Safety, Abstention & Policy
14%

Abstain when appropriate, flag policy violations, no unsafe actions.

M6 Engineering & Maintainability
6%

Code quality and structural/process discipline.

 $\textsc{EGI}{}=0.28\,M\textsubscript{1}{}+0.22\,M\textsubscript{2}{}+0.16\,M\textsubscript{3}{}+0.14\,M\textsubscript{4}{}+0.14\,M\textsubscript{5}{}+0.06\,M\textsubscript{6}{}$ 

These six metrics capture capabilities that enterprise stakeholders
evaluate independently: M1 asks “did the agent produce the correct
answer?”; M2 asks “did it use tools correctly?”; M3
asks “did it plan efficiently across steps and turns?”; M4
asks “are its answers grounded in retrieved evidence?”; M5
asks “does it abstain and obey policy when it should?”; and M6
asks “is the artifact it produced of acceptable engineering
quality?”. The weights $0.28/0.22/0.16/0.14/0.14/0.06$ bias the score
toward the outcomes that matter most in production deployments (task
accuracy and tool reliability) while keeping a non-trivial safety
floor. Each metric is computed over the outputs the LLM produces
inside the contributing benchmark’s native scaffold.

To compute EGI, each sub-metric is first normalized to $[0,100]$ ;
lower-is-better sub-metrics (e.g. step counts in MCP-Universe)
are clipped against a stable ceiling and inverted. For each bucket
 $M_{k}$ , its score is the (equal-weighted by default) mean of the
normalized sub-metrics routed into it. The aggregate is then

 $\begin{split}\textsc{EGI}{}={}&0.28\,M\textsubscript{1}{}+0.22\,M\textsubscript{2}{}+0.16\,M\textsubscript{3}{}\\
&{}+0.14\,M\textsubscript{4}{}+0.14\,M\textsubscript{5}{}+0.06\,M\textsubscript{6}{}.\end{split}$ 

When a sub-metric is missing (e.g. a benchmark run failed), we reweight
the remaining sub-metrics within that bucket only; we never
globally reweight across M1–M6. If an entire benchmark is
missing, all sub-metrics it contributes are skipped and affected
buckets are renormalized locally. This keeps buckets comparable while
signalling missing coverage honestly.

Beyond the aggregate, M5 (safety/abstention) and M2 (tool
actioning) can optionally gate release: if either drops below a
configurable threshold (default $70$ ), the run is flagged not
release-ready regardless of EGI. Release-gate floors are reported
alongside EGI but do not modify the score itself. For the routing to
be well-posed, every benchmark must contribute to at least one bucket
and every bucket must be populated by at least two routed sub-metrics.
M6 draws both of its sub-metrics (software_engineering,
code_quality) from a single benchmark (LoCoBench);
all other buckets receive sub-metrics from three or more benchmarks.
The full coverage view
is deferred to Appendix B,
Table 5, and the sub-metric routing is described in
Appendix C.

The eight benchmarks that populate M1–M6 are:
CRMArena [4, 5]
for Salesforce CRM operations (nine task types, including policy
violation and knowledge QA); HERB [3] for deep
search over heterogeneous enterprise data with answerable/unanswerable
splits; PersonaBench [18] for personalized
QA over synthetic private user data under controllable noise;
UserBench [13] for multi-turn travel-planning
dialog with a 20-turn budget;
MCP-Universe [10] for Model Context
Protocol [1] tool use across six server ecosystems
under a ReAct agent; MCPEval [9] for
auto-synthesized tool-call tasks with strict/flexible matching;
Benchforce [16] for enterprise function
calling (hospital, HR, order-management); and LoCoBench [15] for
long-context software engineering across ten languages at context
lengths up to 1 M tokens. Appendix B reports
per-benchmark task counts under quick and deep modes.

## 6 Analysis

Figure 3 overlays the top six models on
M1–M6 as a radar chart, which makes the capability-level
specializations visible at a glance. Three observations follow.

Figure 2: M1–M6 score matrix (14 models $\times$ 6 metrics),
sorted by EGI. Hot cells flag weak scores, while cool cells mark
strong performance. M3 (Planning) is therefore the hottest
column, since no model surpasses $31$ ; M2 (Tool Actioning) is the
coolest, with most frontier models performing above $70$ . Within each
row, the coolest cell identifies that model’s strongest dimension
(e.g. gpt-5.5 is coolest on M1, Claude
Sonnet 4.5 on M2 and M5, and Claude Haiku 4.5 holds the
column-best on M6).

Figure 3: M1–M6 profiles of the top six models by EGI. No
single model dominates every axis: gpt-5.5 leads on task
outcome (M1), planning (M3), and retrieval grounding
(M4); Claude Sonnet 4.5 on tool actioning (M2) and safety
and abstention (M5); and Claude Haiku 4.5 on engineering quality
(M6).

First, top-line EGI hides meaningful capability-level
specialization. gpt-5.5 wins overall but is only third on
M2 (tool actioning, $79.56$ ) and fifth on M5 (safety &
abstention, $63.47$ ); Claude Sonnet 4.5, second overall by just
 $0.36$ EGI points, has the strongest tool-actioning and safety
profile ( $87.17$ on M2 and $80.28$ on M5, the only safety
score above $76$ ). The strongest specialization signal sits below the
top tier: Claude Haiku 4.5’s M6 (Engineering Quality, $61.28$ )
is the column-best in the entire roster, edging every frontier model
from rank 6. This is precisely the kind of decision the scalar EGI
cannot surface on its own and that the M1–M6 decomposition
was designed to expose.

Second, two axes have consistent frontier limits across all fourteen
models. M3 (planning/workflow orchestration) tops out at
 $30.89$ (gpt-5.5) and is below $25$ for nine of fourteen
models, driven almost entirely by UserBench’s low
micro-average reward (no model exceeds $29$ on its travel envs; most
cluster in the $10$ – $22$ range). The low absolute numbers are not a
scoring artifact: UserBench’s micro_avg averages
the per-turn reward across every turn of an episode rather
than scoring only the final answer, so a model that wanders through
ten turns of generic chat before eventually recommending the correct
itinerary scores substantially below one that asks a single
clarifying question and resolves the task in three turns – even
though both end with the correct answer. This is precisely the
step-efficiency signal M3 is designed to measure, so the low
scores reflect a genuine finding rather than a quirk of how the
metric is constructed: no frontier model today is consistently
turn-efficient in multi-turn user-alignment tasks. Long-horizon
user-preference planning therefore remains an open frontier; current
LLMs do not yet saturate the multi-turn travel scenario. By contrast M6 (engineering
quality) is compressed into a $51$ – $61$ band, because its two routed
sub-metrics (LoCoBench’s software_engineering and
code_quality) are saturated LLM-judged rubrics that reward
coherent output over strict correctness.

Third, the cost/capability boundary is fuzzier than parameter count
alone suggests. Gemini 2.5 Pro reaches EGI $59.10$ – virtually
tied with GPT-4o ( $59.38$ ) and Claude Haiku 4.5 ( $59.13$ ) – powered
by an M1 of $76.05$ that beats every other cost-tier model and
lands within $7$ points of gpt-5.5. At the lower frontier
edge, GPT-5 mini and Gemini 2.5 Flash are a near-tie at EGI $51.91$ 
vs $51.36$ , with GPT-5 mini’s stronger M5 ( $54.17$ ) and M6
( $56.12$ ) offsetting Gemini 2.5 Flash’s higher M3 ( $24.72$ ).
At the smallest tier, GPT-5 nano holds the lowest-in-roster M3
( $15.68$ ) and a near-floor M1 ( $42.38$ ) that leave it
second-from-last on overall EGI despite a competitive M2
( $72.05$ ). The M1–M6 decomposition therefore exposes
which capability lets a smaller model close the gap, rather
than only whether it does.

## 7 Limitations

We note four limitations of this release. First, quick mode subsets
CRMArena, HERB, UserBench, MCP-Universe,
MCPEval, Benchforce, and LoCoBench to fit inside
the 180-minute budget, so sub-metric averages are computed over fewer
items and have wider confidence intervals. Readers should therefore
treat quick-mode EGI as a
directional indicator and rely on deep-mode runs for release decisions.
Second, the $28/22/16/14/14/6$ weighting over M1–M6 is
based on expert judgment and has not yet been
empirically recalibrated on EGI-Bench; a calibration study that fits
the weights to observed enterprise risk (e.g., deployment incident
rates correlated with sub-metric patterns) is future work. Third,
EGI is a scalar, and any single scalar over diverse capabilities
compresses information. Fourth,
parts of MCP-Universe’s evaluator use LLM-based grading via the
configurable EVALUATOR_MODEL, and judge choice and judge
drift can shift absolute numbers across runs even when the evaluated
LLM is identical. We fix the judge model in configuration so that
comparisons within a release are stable, but cross-release comparisons
should note the judge version.

## 8 Conclusion

EGI-Bench unifies eight enterprise-facing LLM agent benchmarks behind a single
CLI and introduces a sub-metric-level routing framework (M1–M6)
that produces an interpretable EGI score without
collapsing capability-specific signal. The unit of evaluation is the
LLM: each contributing benchmark exercises the model through its own
native scaffold (ReAct, MCP client, multi-turn dialog, function-calling
harness). Runtime-budgeted quick and deep modes make the suite
tractable both for smoke tests and for release evaluations. We release the suite, configuration, and full quick-mode
results across fourteen frontier and cost-efficient LLMs spanning
the GPT, Claude, and Gemini families (Table 3).
The results expose capability-level specialization that is invisible
in any single benchmark’s overall score: gpt-5.5 leads
EGI and sweeps M1, M3, and M4, but
Claude Sonnet 4.5 holds the column-best on M2 and M5, and
Claude Haiku 4.5 – ranked sixth on EGI – holds the column-best
on M6. The source is available at
https://github.com/SalesforceAIResearch/egi-bench; we invite
extensions to the benchmark roster and contributions to the routing
table.

## Appendix A CLI Reference

The egi-bench CLI is the preferred entry point. The lower-level
run_all.py script is also supported; the CLI delegates to it
internally.

## Installation.

scripts/install_all.sh provisions the
root egi-bench CLI, the per-benchmark virtual environments, the LiteLLM
proxy venv, and the benchmark data in one idempotent step:

git clone https://github.com/SalesforceAIResearch/egi-bench.git
cd egi-bench
bash scripts/install_all.sh
source .venv/bin/activate

## Credentials.

A single .env file at the repository
root supplies all credentials. OPENAI_API_KEY is required even
when the model under test is non-OpenAI, because the judge and simulator
calls are pinned to OpenAI for apple-to-apple scoring; add the other
provider keys for whichever upstreams you route through:

OPENAI_API_KEY=your-openai-api-key # also powers judge/simulator pins
ANTHROPIC_API_KEY=... # optional, for Claude routes
GEMINI_API_KEY=... # optional, for Gemini routes
# optional deep-mode keys:
SERP_API_KEY=... # MCP-Universe web_search
GOOGLE_MAPS_API_KEY=... # MCP-Universe location_navigation
NPS_API_KEY=... # MCPEval national_parks

## Model routing.

All LLM inference routes through a local
LiteLLM proxy on http://localhost:8008/v1 (OpenAI-compatible).
Each --model is mapped to a provider via
litellm_proxy/litellm_config.yaml, so the same
egi-bench run --model X works for OpenAI, Anthropic, Gemini,
Bedrock, Vertex, Azure, OpenRouter, and self-hosted backends (vLLM,
Ollama, TGI). egi-bench run auto-spawns the proxy on demand;
power users can manage a long-lived proxy directly:

egi-bench proxy start # long-lived proxy across runs
egi-bench proxy status
egi-bench proxy logs -f # tail upstream provider errors
egi-bench proxy stop

## Benchmark environments and data.

egi-bench doctor
egi-bench setup # install per-benchmark .venv’s + data
egi-bench setup --skip-data
egi-bench data # refresh data only

## Running evaluations.

egi-bench run --model gpt-4o-mini --mode quick --parallel
egi-bench run --model gpt-4o-mini --mode deep --parallel --max-workers 2
egi-bench run --model gpt-4o-mini --mode quick \
 --benchmarks crmarena herb userbench

## Reporting.

egi-bench report # latest aggregate
egi-bench report --rescore --model <m> --mode quick
egi-bench report --rescore --model <m> --mode quick \
 --egi-weights M1=0.20,M5=0.30
egi-bench clean

report --rescore re-derives every benchmark’s sub-metric values
from cached raw outputs and re-runs the aggregator, enabling routing or
weight changes without re-running inference.

## Appendix C Fine-Grained Sub-Metric Routing

The routing table (Table 6) is the operational
heart of EGI-Bench. Every row lists a sub-metric that a benchmark natively
reports and the enterprise bucket (M1–M6) it feeds. No

## Why sub-metric routing.

Different sub-metrics inside the same
benchmark often probe very different capabilities. In CRMArena,
PVI (Policy Violation Identification) is a direct safety signal, KQA is
a retrieval-grounded knowledge task, and NCR is a business-action
routing task; averaging the three loses the distinction that
enterprise stakeholders care about. By routing PVI into M5, KQA
and NED into M4, and the remaining six task types into M1,
we avoid dilution across capabilities and retain diagnostic signal at
the bucket level. The same logic applies to HERB, whose
grounded per-entity F1 and content correctness feed M4 while its
unanswerable null rate feeds M5 as a dedicated anti-hallucination
signal.

## Normalization and aggregation.

Sub-metrics are first rescaled
to $[0,100]$ with each benchmark’s native conventions (F1 $\in[0,1]$ 
becomes $[0,100]$ ; pass rates stay proportional). Lower-is-better
signals are converted to higher-is-better before routing (e.g. Benchforce’s reliability gap enters M5 as
 $100-(\texttt{acc\_finished}-\texttt{acc\_all})$ ). Within each bucket we default to
an equal-weighted mean of all routed sub-metrics; benchmark_config.yaml
supports per-sub-metric weights when a principled override is warranted.

## Missing-data handling.

If a sub-metric is unavailable (e.g. a benchmark was skipped), we reweight within its bucket only,
never globally. If a whole benchmark run fails, all of its contributed
sub-metrics are dropped from their buckets and every affected bucket is
renormalized locally. The per-run aggregate report explicitly flags which
sub-metrics were missing so readers can judge coverage.

## Routing is auditable.

The routing is stored declaratively in
benchmark_config.yaml so reviewers can override it and rerun
aggregation without touching code. Section E describes the
CLI’s report --rescore subcommand that re-derives EGI from
stored raw outputs when the routing changes.

## Appendix D Extended Routing Rationale

This appendix expands on the routing table in
Section C with the reasoning behind the more debatable
assignments.

## CRMArena.

Six analytical task types (NCR, HTU, TCU,
TII, BRI, MTA) go to M1 because each produces a single
business-facing answer whose correctness is measured by exact or
structured match. NED (Named Entity Disambiguation) goes to M4
because the ground truth depends on resolving entities from retrieved
records; KQA (Knowledge QA) similarly tests retrieval-grounded QA. PVI
(Policy Violation Identification) goes to M5 because it is the
only task type whose ground truth is a policy judgment — a direct
safety signal.

## HERB.

Per-entity F1 (over person, url, pr, and
company fields) and content correctness measure grounded retrieval
quality and feed M4. The unanswerable null rate measures whether
the LLM abstains when no answer exists; it feeds M5 and is in
practice our primary anti-hallucination signal.

## MCPEval.

The routed signal is the flexible
per-domain average score, which feeds M2 (tool actioning
reliability). The scorer also computes decomposed components —
tool-name match, parameter match, order, and strict success — but
these are not yet surfaced to the aggregate runner. When they are, the
order component is slated to route to M3 (tool sequencing is
planning) and the strict success rate to M5 (all-or-nothing, hence
sensitive to drift and over-action).

## LoCoBench.

functional_correctness goes to
M1 (solves the task). software_engineering and
code_quality feed M6 (engineering discipline;
maintainability). longcontext_utilization feeds M3
because the dimension measures long-horizon reasoning and planning over
extended context, which is a planning/orchestration signal rather than a
retrieval one.

## Debatable cases.

The routing of
longcontext_utilization to M3 rather than M4 is
the most debatable assignment among the currently active routes; the
planned MCPEval component routing (order $\to$ M3, strict
 $\to$ M5 rather than M2) is a second. All routings are
recorded in benchmark_config.yaml and are overridable via
egi-bench report --rescore without re-running inference.

## Appendix E Execution Modes

EGI-Bench exposes two execution modes, selected per run via
--mode quick|deep. Modes are defined by total wall-clock,
not by coverage heuristics:

• 

Quick mode targets a total wall-clock under ${\sim}180$ min
with --parallel --max-workers 2.

• 

Deep mode targets ${\sim}12$ h of wall-clock with similar
parallelism.

Coverage decisions (which categories, how many tasks per category) fall
out of a per-benchmark runtime budget rather than being picked by hand.
“Fast enough” benchmarks keep their original upstream configuration in
both modes; slower benchmarks get subsetted. Concrete wall-clock numbers
depend on the host machine and the inference endpoint, so we define
modes by budget targets rather than by a fixed per-benchmark runtime
table.

## Subsetting rules.

When a benchmark must be subsetted:

1. 

Keep at least one task per existing category so every reported
sub-metric retains signal.

2. 

Reduce tasks per category before dropping a category,
since dropping a category also drops a bucket contributor.

3. 

If a category must be dropped in quick mode, prefer the one
whose routed bucket is most redundantly covered elsewhere (e.g., a
MCP-Universe domain whose M2 signal is already supplied
by MCPEval/Benchforce).

4. 

Record subset definitions in benchmark_config.yaml; do
not hard-code them in run_all.py.

## CLI surface.

The preferred entry points are:

egi-bench doctor # dependency check
egi-bench setup # install per-benchmark venvs + data
egi-bench run --model <m> --mode {quick,deep} --parallel
egi-bench report # latest
egi-bench report --rescore --model <m> --mode <m> # re-aggregate

report --rescore re-derives every benchmark’s sub-metric values
from cached raw outputs and re-runs the M1–M6 aggregator. This
means routing or weighting changes can be evaluated without re-running
inference, which is important for framework stability as
Table 6 evolves.

## Credentials.

Both modes require OPENAI_API_KEY
(it powers the OpenAI routes and the pinned judge/simulator calls, so it
is needed even when the model under test is non-OpenAI), plus whichever
provider keys correspond to the upstreams being routed through the
LiteLLM proxy (e.g. ANTHROPIC_API_KEY,
GEMINI_API_KEY). Deep mode additionally benefits from
SERP_API_KEY and GOOGLE_MAPS_API_KEY
(MCP-Universe) and NPS_API_KEY (MCPEval).
Missing optional keys cause the affected domain to be skipped with a
note, not a failure; the resulting aggregate reports reduced coverage.

pip install, and each benchmark’s exact lockfile lives in its
subdirectory. The whole stack — root CLI, per-benchmark venvs, the
LiteLLM proxy venv, and benchmark data — is provisioned from the
repository root via the idempotent bash scripts/install_all.sh.

## Proxy and models.

All LLM inference routes through a local
LiteLLM proxy on http://localhost:8008/v1 (OpenAI-compatible);
the model-to-provider mapping is declared in
litellm_proxy/litellm_config.yaml. To keep scores comparable
across models, that config pins the judge/simulator model names
(e.g. gpt-4o, gpt-4.1) to OpenAI regardless of the
model under test, so OPENAI_API_KEY must be set even for
non-OpenAI runs. The evaluator model for MCP-Universe is
configured via EVALUATOR_MODEL in .env (defaults to
gpt-4.1).

## Seeds.

benchmark_config.yaml sets
sample_seed: 42 for subsetting where applicable
(CRMArena, MCP-Universe). Other benchmarks use
deterministic ordering over their native task files.

Deep-mode counterparts expand each list to its upstream default.

## Artifacts.

Each run produces
results_aggregated/<model>_<mode>_<timestamp>.json plus
per-benchmark logs under results_aggregated/logs/. The JSON
contains the full four-level metrics structure: scalar EGI,
M1–M6 with per-contributor breakdown, per-benchmark sub-metric
values, and routing metadata.

## Reproducing a quick-mode run.

The end-to-end command
sequence is identical across the fourteen-model roster; only the
--model string changes. Claude Sonnet 4.5 is shown as an
example.

# .env holds OPENAI_API_KEY (judge/simulator pins) plus the provider
# key for the model under test, e.g. ANTHROPIC_API_KEY.
# egi-bench run auto-spawns the LiteLLM proxy on localhost:8008.
egi-bench run \
 --model claude-sonnet-4-5 \
 --mode quick --parallel --max-workers 2
egi-bench report
