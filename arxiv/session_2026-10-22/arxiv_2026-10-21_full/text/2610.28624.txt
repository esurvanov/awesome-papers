Abstract

Warehouse robot fleets continuously observe operational conditions, but preserving these observations as reusable semantic memory incurs substantial computation, communication, and storage costs. For example, explaining recurring aisle blockages can require reviewing video from multiple robots across several shifts. We present Industrial ReMEmbR, a shared spatiotemporal memory system that extends NVIDIA ReMEmbR to robot fleets and reduces server-side computation by generating scene descriptions only on demand. On each robot, an NVIDIA Jetson encodes video clips into retrieval embeddings with Cosmos-Embed1, vision tokens with Cosmos3-Edge, and reconstruction latents with the Wan2.2 VAE, without uploading raw camera frames. The encoding models are re-used to detect people in image patches, zeroing them out to support PII abstraction for GDPR-compliant deployments. We split Cosmos3-Edge at its vision–language boundary, placing the vision encoder on the robot and the language decoder on an on-premises server. A Nemotron agent retrieves memories by content, position, and time and queries the decoder using cached vision tokens. This design eliminates caption generation at write time, while cached-token decoding reproduces the unsplit model’s output in all 450 tested decodes. On the NaVQA benchmark, the updated model stack achieves comparable retrieval recall while reducing unparsable answers from 4.5% to 1.9% with an agent half the parameter size. We further demonstrate a live semantic traffic map that classifies aisle conditions directly from retrieval embeddings. Across 914 simulated warehouse frames, this method exceeds the best caption-based alternative by 6.0 percentage points. By decoupling memory encoding from description, Industrial ReMEmbR transforms a fleet’s collective experience into an extensible foundation for spatial and temporal reasoning, including faithful scene reconstruction, context-guided elaboration, and semantic mapping of dynamic warehouse conditions as they unfold.

## 1 Introduction

An embodied memory lets a robot recall what it has seen, where, and when, long after the moment has passed. NVIDIA’s ReMEmbR (Anwar et al., 2025), a spatiotemporal memory system designed for long-horizon visual question answering for robot navigation, showed that a single robot can build such a memory from its own camera stream. On a warehouse floor, however, that robot is only one of many. A fleet management system, or fleet manager, continuously tracks dozens of autonomous mobile robots (AMRs) and other integrated devices in a modern warehouse, assigning them orders and planning their routes over VDA5050, the standard interface between mobile robots and fleet management systems. Obstacles outside the tracking system are left to each robot’s intelligent navigation system to recognize and avoid. What a passing robot sees is rarely kept, because continuously uploading and storing raw video from every robot is expensive, so the rich semantic context of each scene never reaches the rest of the fleet.

To illustrate, consider the case of a fleet management system that keeps routing AMRs through an aisle partially blocked by a clutter of untracked obstacles. Each robot independently maneuvers around the clutter, losing time before carrying on with its scheduled tasks. A few days later, a human operator reviewing the daily logs notices that task completion times slipped that day, but has no record of the scene from which to trace its root cause. Neither the fleet manager nor the operator has the semantic context that could have prevented the congestion, by adaptively routing later robots away from the aisle, or its recurrence, by revealing what caused it.

Closing this contextual blind spot requires scaling embodied memory from a single robot to the entire fleet, with every connected robot acting as a live reporter from the warehouse floor that continuously contributes its observations, tagged with location and time, to a shared fleet memory. In the scenario above, the first robot to encounter the clutter would report it on a live semantic map, letting the fleet manager route subsequent robots around the blocked aisle. Days later, the operator could ask the fleet’s shared semantic memory what caused the reroutes and receive an answer grounded in direct visual observation: when and where the clutter appeared, and what it consisted of. The same record can supply the world state of a centralized planner such as RobotFleet (Gupta et al., 2025), which schedules heterogeneous robots from declarative statements about the site and replans when a robot reports a discovery.

To this end, we build on ReMEmbR, which captions each short video clip, stores the caption along with the robot’s time and location and a corresponding caption embedding, and lets an agentic model perform semantic retrieval over the vector database to answer arbitrary questions. Scaling this design from one robot to a fleet breaks three of its assumptions, and each break motivates one principle of our design. First, ReMEmbR generates a caption for every clip as it is written, so its cost grows with every robot added and every hour it operates, and continuously uploading raw video from every robot is costly to begin with. We therefore encode once, compressing each clip on the robot’s own edge compute into compact representations that every later step reuses. Second, ReMEmbR answers occasional questions, whereas the fleet manager also needs a continuously updated view of the site. We therefore interpret continuously, reading that state directly from each memory as it arrives, without generating any text. Third, the questions a memory must answer are not known when it is first encoded. We therefore elaborate on demand, deferring any description of a scene until a question about it arrives. In the blocked aisle example, the clutter is encoded once by the first robot that passes it, flagged on the live map as soon as its memory arrives, and described in detail only when the operator asks about it days later.

We present Industrial ReMEmbR (Fig. 1), a shared memory system built around these three principles. It encodes clips on edge compute across the fleet, continuously aggregates and interprets them on server compute for live semantic mapping, and elaborates on any of them on demand. Each robot’s onboard Jetson edge-compute device runs iw.encode, the edge component for efficient multi-purpose encoding. This deployed service continuously generates video-text embedding vectors for memory retrieval derived from Cosmos-Embed1 (NVIDIA, 2025), vision tokens for optional scene description derived from the detached vision encoder of Cosmos3-Edge (NVIDIA, 2026a), and compressed latent frames for optional scene inspection generated by the Wan2.2 VAE (Team Wan, 2025b; Team Wan, 2025a) encoder. Only the aforementioned multi-purpose scene representations, robot pose and memory timestamp are uploaded into a shared fleet memory, whose vector index is accelerated with NVIDIA cuVS (RAPIDS Team, 2024).

Our contributions are:

• 

Video-native agentic memory. We rebuild ReMEmbR on an efficient NVIDIA model stack and move its index key from the caption to the video itself. Retrieval is no longer bottlenecked by what a captioner chose to mention, and a smaller, tool-calling agent returns more reliable structured answers (Section 3).

• 

Encode once, distributed across the fleet. Every robot acts as a distributed sensor, and a modular set of parallel encoder services on its Jetson turns each clip, in a single pass, into multi-purpose representations for memory retrieval, description and reconstruction. Per-clip compute is offloaded to the edge and scales out with the fleet, and raw camera frames never leave the robot (Section 4.1).

• 

Disaggregated vision-language inference for describe-on-demand. Cosmos3-Edge is split at its vision–language boundary, with the vision encoder on the robot and the language decoder on the server. Cached vision tokens are encoded once and queried many times, so description cost scales with the questions asked rather than with the video recorded (Sections 4.2 and 4.3).

• 

A zero-shot, multi-purpose live semantic map. The retrieval embedding the robot already computes doubles as a training-free semantic classifier, in this case reused for traffic classification, interpreted continuously and fed to the fleet manager over its existing VDA5050 interface. An agent sits between the map and the memory as a natural-language interface, so a new site-level insight requires only a new question, with no new model to train (Section 5).

• 

A modular, scale-out service architecture. Encoders, a GPU-accelerated vector index, a tiered object store, NIM-served agents and on-demand decoders run as independent, versioned services that can each be scaled or upgraded in isolation. We profile the edge encoders on Jetson and model how server compute, bandwidth and storage scale from a single robot to a full fleet (Sections 4.3 and 6.3).

## 2 Preliminaries

Industrial ReMEmbR builds on three main lines of research: large language model (LLM) agents that support versatile tool use, retrieval-augmented generation from semantic embeddings, and the ReMEmbR system, which combines the two to encode and query a robot’s memories over long horizons.

Agents. In this context, an agent is an LLM that runs in an interactive loop with access to predefined tools. At each step in the loop, the model reads the task and its own running history, and then either calls any of the available tools or provides its final answer. ReAct (Yao et al., 2023) features the model writing out its intermediate reasoning between tool calls, so that the result of one call guides the next. Practically, every tool call must be well-formatted to allow for deterministic parsing and automated execution. The loop also needs a limit on the allowed number of steps, so that it always ends with a concrete answer. Industrial ReMEmbR follows this loop, and adds a tool that lets the agent ask a vision–language decoder its own question about any memory it retrieves.

Retrieval-augmented generation. Retrieval-augmented generation (RAG) (Lewis et al., 2020) allows a model to derive answers from a corpus even if it is too large to directly fit in context. The corpus is chunked and indexed in advance, and for each question the $k$ most relevant chunks are retrieved and incorporated in the model’s context window. Retrieval is usually done with a bi-encoder, which embeds queries and documents separately so that search involves a fast vector comparison (Karpukhin et al., 2020). The trade-off is that every document vector is computed before any query is known. A cross-encoder, by contrast, reads a query and a document together, which tends to be more accurate but often too slow to apply to a whole corpus, so it normally only re-ranks a shortlist already retrieved (Nogueira and Cho, 2019) by the bi-encoder. Agentic RAG (Singh et al., 2025) exposes retrieval as a tool for the agent. The agent writes its own retrieval queries, retries upon search misses, and decides when it has sufficient evidence to return with a contextually grounded response. Industrial ReMEmbR uses agentic RAG over video instead of text, with a video–text bi-encoder as the index and a decoder that reads the question and the retrieved memory together.

ReMEmbR. ReMEmbR (Anwar et al., 2025) lets a user ask a mobile robot where something is, when something happened, or what it saw over hours of operation, and returns answers the robot can act on, such as an $(x,y,z)$ position to navigate toward. Because a question rarely needs the whole history $H$ , ReMEmbR answers from a small retrieved subset $R\subseteq H$ , approximating $p(A\mid H,Q)$ with $p(A\mid R,Q)$ for a question $Q$ and answer $A$ .

It works in two phases. In the memory-building phase, VILA (Lin et al., 2024) captions each 3 s video segment, MxBai (Lee et al., 2024) embeds the caption, and Milvus (Wang et al., 2021) stores the embedding with the segment’s mean position and time.11
 1

 Position and orientation are stored in separate columns. In the querying phase, an LLM agent searches this memory by text, position or time for up to three rounds, and then returns a structured JSON answer that holds text, a yes/no value, a time, a duration or a goal position. The accompanying NaVQA benchmark contains 210 questions over seven CODa sequences (Zhang et al., 2024) of 15 to 30 minutes each. A position answer counts as correct within 15 m, and a time answer within 2 min.

The memory is built before any question is asked, so it has to be general enough to serve whichever question comes later. However, ReMEmbR captions every clip when it is recorded. The memory can answer only what the captioner chose to mention, and generating a caption for every clip is the main cost of writing a memory.

Upgraded ReMEmbR keeps its pipeline and updates its models (Section 3). Industrial ReMEmbR keeps the two-phase design but stores no caption, and describes a memory only once a question asks about it (Section 4).

## 3 Upgraded ReMEmbR: Updated Models and Video-Based Retrieval

In ReMEmbR, a caption does two jobs. It serves as the index key, since its text embedding decides which questions can find the clip, and it serves as the context, since it is all the agent reads once the memory is retrieved. Both jobs depend on what the captioner chose to mention when first encoding. “A forklift in a warehouse” may be accurate but still leave out whether the forklift blocks the aisle, in which case a question about blocked aisles becomes less likely to align with the caption’s embedding. Captioning is therefore an information bottleneck for retrieval, since a scene detail has to survive both the captioner’s limited attention and the embedding step to play any role in the search. To build toward Industrial ReMEmbR, we first introduce Upgraded ReMEmbR. It keeps ReMEmbR’s pipeline, updates its underlying models, and moves the index key from the caption to the video itself, circumventing the retrieval bottleneck.

Upgraded ReMEmbR retains ReMEmbR’s three-second segments, its position and time metadata, and its search by content, position and time, so that any change on NaVQA can be attributed to the models. Two of the three model updates are direct replacements. Cosmos3-Edge (NVIDIA, 2026a) takes over captioning from VILA-1.5-13B (Lin et al., 2024). It is roughly one-third the size, and its emphasis on physical-world and spatial understanding suits questions about how a scene is arranged. Nemotron-3-Nano-4B (NVIDIA, 2026b; NVIDIA et al., 2025) takes over the agent role from Llama-3.1-8B (Grattafiori and others, 2024), ReMEmbR’s locally hosted agent. It is a hybrid Mamba-Transformer model with half the parameters, post-trained for tool use and structured output, and it has access to the same search tools as before.

The third update changes what the index is built from. ReMEmbR embeds the caption text with MxBai (Lee et al., 2024). Upgraded ReMEmbR embeds the clip itself with Cosmos-Embed1 (NVIDIA, 2025), which maps video and text into a shared semantic space, so a natural-language query is matched against the content of the video (Fig. 2). The caption still accompanies each retrieved memory as context, but it no longer limits what the search can find.

Upgraded ReMEmbR leaves the caption in place as context, so generating it remains the bulk of the cost of writing a memory. Section 6 evaluates each of the three replacements on NaVQA, changing one component at a time.

## 4 Industrial ReMEmbR: Encode Once, Interpret Continuously, Elaborate on Demand

Upgraded ReMEmbR showed that a memory can be found without its caption, yet it still generates one for every clip before any question is known. Industrial ReMEmbR goes further and eliminates that step. Each robot stores the inputs that a server-side model would need to describe a memory, and the description itself is generated only when a question calls for one (Fig. 3).

Three principles guide the design. The first is to encode once. Each clip passes through the robot’s encoders a single time and comes out as the representations that later steps read: an embedding for retrieval, vision tokens for description, and a video latent for inspection. No later step has to return to the camera frames, which never need to leave the robot. Per-clip work therefore runs on the robot, and its cost grows with the length of the footage. The second is to interpret continuously. The server scores each incoming embedding as it arrives, which keeps the live semantic map current without generating any text. The third is to elaborate on demand. Text is generated once a question is known, so it can address that question, and the same memory can be described again for the next one. Per-question work therefore runs on the server, and its cost grows with the number of questions asked rather than with the amount of video recorded. The following subsections follow these principles in turn: encode once on the robot (Section 4.1), interpret continuously on the memory the robots feed (Section 4.2), and elaborate on demand on the server (Section 4.3).

## 4.1 On the Robot: One Pass, Three Representations

Each robot runs iw.encode, a set of three encoder services on its Jetson AGX Xavier, on every three-second segment. Each encoder produces the input for a later application, and none of them needs the camera frames again.

Cosmos-Embed1 maps the segment to a single 768-dimensional vector in a shared video–text space, which takes 3 kB. This vector is the memory’s index key, and the agent’s content search reads it (Section 4.3). As in Upgraded ReMEmbR, it replaces ReMEmbR’s MxBai embedding of the caption, so retrieval no longer depends on what a caption mentions. Text prompts map into the same space, so the server can score the same vector for the traffic verdict of Section 5 and can support other prompt-based checks, each at the cost of a dot product.

The vision encoder of Cosmos3-Edge produces 60 projected vision tokens of width 2048, which the model’s language decoder would normally receive from it directly. The robot stores these tokens with the metadata the decoder needs to read them, 247 kB in total. The language decoder on the server reads them when the agent asks about a retrieved memory (Section 4.3). They replace the caption that ReMEmbR generates for every clip, so the robot never runs the expensive step of generating text on edge.

The Wan2.2 VAE (Team Wan, 2025b; Team Wan, 2025a) encoder compresses the segment into a $48\times 2\times 30\times 52$ video latent of 300 kB, one-twentieth of the size of its uncompressed frames. The Wan2.2 decoder on the server reads this latent when an operator wants to revisit a memory, and reconstructs the scene for inspection. ReMEmbR has no counterpart to it, since its memory keeps the caption’s embedding and not a compression of the scene itself.

The three encoders run in parallel as independent services, and their outputs are the only data that leave the robot (Fig. 1). Each memory covers three seconds in our configuration, and how often a robot writes one is a deployment setting. NaVQA uses contiguous segments; fleet resource projections assume one write every 12 s, while the live map polls every 10 s. Encoder timing and memory on Xavier are reported in Tab. 7, Tab. 8 and Appendix D.1.

## 4.2 Fleet Memory

Fleet memory has two parts, matched to how each kind of data is used. Every segment adds one row to a shared Milvus collection (Wang et al., 2021), containing its Cosmos-Embed1 vector, the robot’s pose, the capture time and any verdict the server computes as the row arrives, which is what lets the server interpret continuously without reading the larger data. Indexes over the vector, the position and the time support search by content, place and time, and NVIDIA cuVS (RAPIDS Team, 2024) builds and searches the vector index on the GPU. The vision tokens and the latent are much larger and are read only when a memory is retrieved, so they are kept in an object store, and the row holds a reference to them.

ReMEmbR’s reference deployment runs Milvus on the robot (Anwar et al., 2025). Here, we centralize it on the on-premises server to offload database and index-serving work from robots, avoid duplicated fleet indexes and per-robot reconciliation, and provide the fleet a shared live database of memories to independently contribute to and query from.

## 4.3 On the Server: Answering Questions

Questions are answered on an on-premises server by a Nemotron-3-Nano-4B agent. As in ReMEmbR, the agent searches the index by content, position and time, and the entries it retrieves accumulate in its working memory. Each retrieved entry now holds a reference to its cached vision tokens in place of a caption, and a fourth tool lets the agent put a question of its own to the Cosmos3-Edge language decoder about any entry. The agent therefore decides both which moments to look at and what to ask about them.

This is where the server elaborates on demand. The decoder answers from the cached tokens alone (Fig. 4). It builds its usual prompt from the chat template and the question, and it places the stored vision tokens in the slot where freshly encoded video would normally go. This split turns an intermediate model output into a lasting memory. Edge–server partitioning such as Neurosurgeon (Kang et al., 2017) chooses a split layer per request to reduce its latency or energy, and the intermediate output is discarded once that request is served. Here, the boundary sits at the model’s vision–language interface, and the robot’s tokens persist in fleet memory long after they are encoded. One set of tokens can answer any number of questions.

After one or more rounds of search, the agent returns a structured answer with text, yes/no, position, time and duration fields that downstream systems can consume directly. An operator can query the agent interactively, and a service can call it on a schedule, as the live map does in Section 5. When an operator wants to see a scene, the Wan2.2 decoder reconstructs it from the stored latent. New typed tools can expose site-specific tasks to the agent without any change to how memories are encoded.

Every component runs as a versioned service on the local network. Our reference setup places fleet memory, cuVS, both decoders and the NIM-served agent on one on-premises server with NVIDIA RTX PRO 6000 Blackwell Server Edition GPUs. Larger sites can distribute the agent and the decoders across dedicated GPUs and provision Milvus, the object store and the map service separately, and each modular service can be scaled or upgraded in isolation (Appendix A.2).

## 5 A First Application: The Live Semantic Traffic Map

We return to the blocked aisle example from the introduction. The first robot to pass the clutter stores a memory of it like any other clip, and whether the aisle ahead is occupied is already implicit in that memory’s embedding. When the live semantic map next refreshes, it finds that this embedding vector aligns more closely with those of descriptions of an occupied aisle than those of a clear one, and the aisle’s zone turns orange. The fleet manager can then take the blocked aisle into account when planning routes in that area. Further, an operator who wants to know what exactly is in the way can click the robot and read a description of what it saw, generated on the spot from the memory’s cached vision tokens. None of this changes the robots, which run the same iw.encode pipeline as in Section 4.1. The server adds two cached text prototypes and a map service that queries the agent on a fixed clock, and the rest is Industrial ReMEmbR (Fig. 5).

The report adds no robot-side computation, as it reuses the Cosmos-Embed1 vector $\mathbf{v}$ generated for retrieval as part of the deployed iw.encode pipeline. Cosmos-Embed1 projects video and text onto a shared embedding space, so a written description can be directly compared with a recorded video. We describe each of the two outcomes with a handful of concise text prompts, such as “a warehouse aisle blocked by a pallet” for an occupied aisle and “an empty warehouse aisle” for a clear one (Appendix F). Averaging the embeddings of each set and rescaling the result to unit length gives one prototype per outcome, $\mathbf{p}_{\mathrm{occ}}$ and $\mathbf{p}_{\mathrm{clr}}$ , following the prompt ensembling that CLIP introduced for zero-shot classification (Radford et al., 2021). The server caches both prototypes, so the prompt ensembles can be maintained and updated. Unlike CLIP’s evaluation, where each image is embedded solely to be classified, the verdict reuses the vector the robot already uploads as the memory’s index key, so it requires no separate classification pass. As each vector arrives, the server’s verdict on the clip is traffic when the clip is closer to the occupied prototype,

and clear otherwise. The traffic verdict is thus derived on the server straight from the embedding the robot already computes at encoding time, at the cost of two dot products, without a detector, captioner or any other trained model dedicated to traffic classification.

A single similarity score is a weak signal. A clip’s embedding describes the whole scene, including its background, colors and lighting, so its similarity to any short prompt is low, and the scores for the two outcomes end up close together. This score attenuation is a direct consequence of the average pooling applied to the Q-Former tokens in the Cosmos-Embed1 architecture. Because this pooling operation collapses all visual tokens into a single global vector, v encodes the entire scene thereby diluting the specific signals. By contrasting v against the two opposing, generalized prototypes, we isolate the relevant semantic axis and bypass the dilution caused by the global visual pooling. A fixed threshold on either score would be fragile, so the verdict compares the two directly. Their difference, $\mathbf{v}^{\top}(\mathbf{p}_{\mathrm{occ}}-\mathbf{p}_{\mathrm{clr}})$ , cancels whatever the prototypes have in common, such as the aisle itself, and keeps only how much more the clip looks like an occupied aisle than a clear one.

The server stores the verdict in the same memory row as the embedding, its pose, its timestamp and the reference to the clip’s cached vision tokens. Next to the verdict, the row holds a short sentence such as “In the aisle straight ahead there is traffic,” filled in from a fixed template. The agent can read this sentence directly, and writing the memory still generates no text.

The map combines this memory with what the fleet manager already knows. Under VDA5050, each AMR regularly sends the fleet manager a state message whose agvPosition field reports the robot’s pose, its position $(x,y)$ and heading $\theta$ . Fleet memory adds what each robot sees. The map service divides the floor plan into zones, polygons that each cover an aisle segment or a crossing, and keeps one traffic state per zone.

To minimize redundancy, the map service does not react to every memory a robot writes. It polls on a fixed period of $\Delta t$ seconds (10 s by default). The request rate follows the robot count and the poll interval. The compute each request takes also depends on the agent’s work and the length of its answer. On each tick it takes the latest pose of every robot that reported since the last one and looks up which zone the robot is in. Robots outside all zones are skipped. For the rest, it asks the agent a question that carries the robot’s time and position:

“The time now is HH:MM:SS. You are a robot at position $[x,y,z]$ in a warehouse. … Is there any other vehicle or agent in the zone directly ahead of you right now? Answer with only one word yes or no.” (full text in Appendix F.2)

The agent answers it the way it answers an operator, by searching memory with its text, position and time tools. Each query runs with a fresh agent state, so no memories carry over from the previous robot and the tool-call budget is reset. A yes labels the zone as traffic and a no relabels it as clear. Any other output triggers a re-query (Fig. 6).

We see traffic as the first layer of a multi-purpose semantic map of industrial sites, whose zones could eventually record whether a charging station is free, whether a dock is filling up, or whether a recognizable landmark is still where a navigation policy expects it. Each new model improves a different measure (Tab. 2). Nemotron is the one that makes answers reliable. Swapping it in alone cuts first-attempt parse failures from 20.7% to 16.2% and unscorable answers from 4.5% to 0.9%, whereas swapping in the captioner or the index instead raises first-attempt failures to 22.4% and 23.5%. The effect does not depend on what the agent reads. Across all four captioner–index pairs of Tab. 5, Nemotron stays within 12.2–16.2% first-attempt failures against 20.7–23.5% for Llama, and within 0.9–1.9% unscorable answers against 3.6–5.5%. Nemotron has half the parameters of Llama, so this gain likely reflects its post-training for tool use and structured output rather than its size.

Recall, in contrast, follows the index. Replacing the caption-text index with Cosmos-Embed1 alone raises recall from 22.9% to 29.7%, the largest gain of any single swap, and the video index matches or improves recall for every agent–captioner pair. With Nemotron as the agent, it adds 8.5 points over caption-text indexing with VILA captions and 3.8 points with Cosmos3-Edge captions. This is the bottleneck of Section 3. A caption-text index can find only what the captioner chose to mention, while the video index matches a question against the clip itself, and so it needs neither a caption nor a caption-text embedding stage. Industrial ReMEmbR relies on this property when it stops writing captions altogether.

Combined, the three models improve on original ReMEmbR in both reliability and recall. First-attempt parse failures fall from 20.7% to 13.8% and unscorable answers from 4.5% to 1.9%, relative reductions of about 33% and 58%, and median position error falls from 69.1 to 66.6 m. Recall rises from 22.9% to 24.6%, less than the index swap alone achieves. Because recall also depends on the agent’s queries, Nemotron lowers it by 2.3–5.9 points relative to Llama in every pair, and the full stack keeps only part of the index’s gain. In exchange, Nemotron lowers median position error by 7.7–11.9 m relative to Llama whenever it is paired with either new component.

Upgraded ReMEmbR therefore finds more evidence and answers more reliably, yet it still captions every clip as it is written. The next question is whether Industrial ReMEmbR can drop that step without losing what the caption provided.

## 6.3 Does the Cost Scale to a Fleet?

Industrial ReMEmbR moves encoding onto the robots and generation onto the questions, so its cost has an edge side and a server side, which we measure separately. Edge timings use warmed TensorRT 8.5.2 engines on a Jetson AGX Xavier with the inputs of Tab. 4, and they include transfers between host and device (Appendix D.1). Server measurements use one RTX PRO 6000 Blackwell Server Edition GPU unless stated otherwise. Where we extrapolate to a fleet, we assume one memory per robot every 12 s over an eight-hour day and mark the result as modeled (Appendix D.3). The live map’s 10 s poll interval is a separate setting (Section 5).

On the robot. Robots run only encoders, and the language decoder stays on the server. The Cosmos3-Edge vision encoder takes 196 ms per frame, the Wan2.2 VAE 6.46 s for five frames in FP32, and Cosmos-Embed1 11.76 s for six frames (Tab. 7). Cosmos-Embed1 dominates encoding time and is the first target for engine optimization (Section 7). GPU memory is less of a constraint. The three encoder services together hold 6.55 GiB, about a quarter of the 26.3 GiB peak of the original VILA captioner (Fig. 10).

On the server. Original ReMEmbR’s write-time captioning takes a mean of 4.35 s per memory, whereas a description in Industrial ReMEmbR costs 1.25 s from cached tokens and is generated only when requested. We measure server load in GPU equivalents, the GPU time requested per second, so one equivalent keeps one GPU fully busy. At the modeled write interval of 12 s, captioning every memory represents 36.25 GPU equivalents for 100 robots. If 10% of memories are each described once, the serialized demand is 1.04 GPU equivalents; at 1%, it is 0.10. At a fixed write interval and description fraction, both loads scale linearly with fleet size. Describing 10% of memories once yields a 34.8-fold reduction. This combines the move from VILA captioning to Cosmos3-Edge decoding with deferral. Deferral costs less than captioning unless memories are described more than 3.48 times each on average. These are serialized single-GPU service-demand estimates before provisioning headroom, modeled from measured per-memory costs (Fig. 11). Appendix D.3 adds the live map’s agent load, sized below, and scene inspection as a symbolic term.

The agent must also keep up as the map polls more robots at once. Original ReMEmbR serves its agent through Ollama, whose throughput in our deployment barely grows with concurrency. At an 8k context, Ollama with Q8_0 grows from 203 to 235 output tokens/s as concurrent requests rise from one to eight, while NIM in FP8 grows from 236 to 1,217 tokens/s, about five times Ollama’s throughput at eight requests (Fig. 13). Ollama’s scheduler serves the Nemotron architecture families, including Nemotron-3-Nano-4B, one request at a time (Morgan, 2026). We measure how many robots the agent can serve under load. With one GPU serving the agent, 95% of map updates finish within 20 s for 24 robots polling every 10 s, and two GPUs serve at least 48 (Appendix D.2). The map therefore costs about 0.042 GPU equivalents per robot, or 4.2 for 100 robots. With 10% of memories described, the server’s generation load for 100 robots is about 5.2 GPU equivalents, still below the 36.25 of captioning alone, although captioning is costed unbatched here and batching it would narrow the gap. Because most of this load comes from map polling, the poll interval outweighs the description fraction as the main lever on server cost at fleet scale.

## 6.4 Can the Memory Keep a Live Traffic Map?

The live map of Section 5 reads a traffic verdict directly from each memory’s Cosmos-Embed1 vector, without a detector or a captioner. The map is only useful if this verdict is accurate and if the agent passes it on unchanged, so we compare it with caption-based memories under the same agent. The test set is a deterministic, contiguous warehouse simulation of 914 frames, each stored as a single-frame memory with its pose and time and paired with one yes/no question about traffic ahead. Labels come from the simulator’s record of other agents in the zone ahead of the robot, giving 607 traffic frames and 307 clear ones. Traffic is the majority class, so always answering “traffic” already scores 66.4% accuracy. We therefore report balanced accuracy, the mean of traffic recall and clear recall, on which that baseline scores 50.0%.

The three memories differ only in what each frame writes. The embedding verdict scores the frame’s Cosmos-Embed1 vector against the occupied and clear prototypes of Section 5, with no tuned threshold. For detection, Cosmos3-Edge lists the obstacles in the forward path as labeled bounding boxes, and for description it writes a free-text description of the scene, both with reasoning enabled. Before answering, the agent must search memory by the frame’s position, so it reads every representation from the same memory row. A frame counts toward a representation’s coverage when that representation produced usable content for it. Prompts and prototypes are listed in Appendix F, and protocols in Appendix E.

The embedding verdict reaches 71.3% balanced accuracy, 6.0 points above detection, the best caption-based memory, and it is the only representation that covers all 914 frames, against 844 for detection and 902 for description (Fig. 12). The caption arms are scored only on the frames they cover, so counting dropped frames as errors would only widen this margin. The two caption-based memories fail in opposite directions. Detection finds traffic in 88.4% of traffic frames but recognizes only 42.3% of clear frames, so its 72.7% accuracy, slightly above the verdict’s 72.1%, mostly reflects the majority class. Description errs the other way, with 91.1% clear recall and only 27.1% traffic recall. The verdict balances the two classes, with 73.8% traffic recall and 68.7% clear recall (Tab. 13).

Routing the verdict through the agent barely changes its classification. Nemotron agrees with the raw embedding verdict on 913 of 914 frames, scoring 659/914 against the direct classifier’s 660/914. It retrieves the target memory in 99.6% of cases and produces no unparseable answers. The map can keep the agent as its interface, which lets it ask new questions of the same memory.

## 7 Road Ahead

The traffic map is the first application built on fleet memory. The directions below reuse the same encoding and storage, and several of them require only new tools on the server.

New uses of the same memory. The agent can already locate any landmark that any robot has seen, yet it uses that knowledge only to answer questions. Recast as semantic subgoals, such as “pass the blue loading bay, then turn left at the marked crossing,” that knowledge could guide a robot along routes it has never driven, drawing on what other robots have already observed. The live map’s zone verdicts can play the same role for fleet scheduling. RobotFleet (Gupta et al., 2025) allocates subtasks across a heterogeneous fleet from a shared world state of declarative statements and replans when a robot reports something new. An occupied zone can update that state as soon as its memory arrives, and the agent can be asked what is blocking the zone before the next allocation.

Fleet memory as training data. Each robot already encodes its clips into the vision tokens and video latents that compatible Cosmos3 models consume (NVIDIA, 2026a), so routine fleet operation doubles as distributed preprocessing for training. This costly visual encoding is offloaded to edge devices across the fleet, paid once per memory, and amortized over every epoch and every compatible model trained from the cached representations, without transferring raw video or re-running the encoders (Appendix G). A world model trained on these latents could become a learned simulator of the site, replaying recorded scenes under alternative robot behaviors to show what would have happened had a robot taken another aisle, therefore translating failed rollouts into successful ones and distilling back to deployed policies and closing the flywheel. Fine-tuning the language decoder on the cached vision tokens could teach it the site’s own objects and terminology. Fine-tuning Cosmos-Embed1 with location-aware captioning objectives, as in LocCa (Wan et al., 2024) and SigLIP 2 (Tschannen et al., 2025), could also strengthen the spatial awareness that physical AI tasks require, thereby improving the balanced accuracy on traffic verdicts.

A cheaper memory at every stage. On the robot, the general-purpose video–text embedder answers the traffic question with two dot products but dominates encoding time. An embedder specialized for industrial scenes and distilled into a compact backbone such as SigLIP 2 (Tschannen et al., 2025) could encode faster on the edge and sharpen every prompt-based check on factory and warehouse vocabulary. On the server, the edge deployment expertise behind our encoders could yield a leaner agent, pruned, quantized and distilled from open models, that answers map polls with fewer calls and tokens. In storage, every memory is kept in full, so the store grows linearly, reaching 3.9 TB per month for 100 robots at the modeled write interval (Tab. 12). Much like human episodic memory, fleet memory could consolidate routine observations of the same place while keeping surprises in full, so that storage grows with the site’s rate of change rather than with fleet operating hours.

The physical world as an attack surface. Text that the decoder reads from a scene enters the agent’s context like any other content, so a sign or a screen in view of a camera becomes an input the agent might obey, a physical form of prompt injection. As the agent gains authority over the fleet, perception must be treated as untrusted data. iw.shield, a protection layer under development, is our first step toward agents that can read the world without taking malicious orders from it.

## 8 Conclusion

We present Industrial ReMEmbR, a shared fleet memory that decouples observation encoding from on-demand interpretation. Each robot encodes a clip once into a retrieval embedding, vision tokens, and a video latent while retaining raw camera frames onboard. These representations support semantic retrieval, live traffic mapping, scene description, and reconstruction. We derive traffic classifications directly from retrieval embeddings at encoding time and generate scene descriptions and reconstructions only when needed.
Encoding, storage, mapping, and interpretation operate as independent services, allowing multiple applications to reuse each observation and individual models to be replaced independently.

Our evaluation demonstrates the benefits of deferred description and validates key components of the architecture. Deferring caption generation removes text generation from the memory-write path.
Video-based indexing matches or improves retrieval recall in every matched comparison, and cached-token decoding reproduces the unsplit Cosmos3-Edge output in all 450 tests. On full NaVQA, the updated model stack reduces first-attempt parse failures from 20.7% to 13.8% and unparsable answers from 4.5% to 1.9% with an agent half the parameter size. At a modeled 12 s write interval, description demand for 100 robots is 1.04 GPU equivalents when 10% of memories are described, compared with 36.25 GPU equivalents for captioning every memory. Across 914 simulated warehouse frames, embedding-based traffic classification achieves 71.3% balanced accuracy, exceeding the best reasoning-enabled caption-based alternative by 6.0 percentage points.

Further engineering is required for production deployment. Cosmos-Embed1, the slowest encoder on Jetson AGX Xavier, is our first target for TensorRT optimization and fine-tuning, while agent provisioning must account for the map-update workload and polling cadence. We plan to extend the system to congestion-aware fleet planning, semantic guidance for navigation policies, and continuous curation of deployment data for model fine-tuning. We will also investigate deploying agents on robot edge devices, reorganizing encoding components on the robot to obfuscate people from memories directly on the robots’ volatile memory, and developing iw.shield to protect the system against cyberattacks. The broader contribution is a reusable memory architecture through which a fleet’s collective experience can support an expanding range of applications as models, tasks, and warehouse conditions evolve.

## A.2 Agent, Tools and Services

Agent loop. Nemotron-3-Nano-4B may call tools for up to three rounds, with several calls per round, before a final step writes a structured JSON answer with text, yes/no, position, time and duration fields. Each search returns the $k$ nearest memories ( $k=5$ in the NaVQA runs). An answer that fails to parse is regenerated, up to three attempts in total. In deployment, NVIDIA NIM serves the agent in FP8 with a 16k-token context and a 4,096-token output limit, and removes the reasoning trace before tool calls are parsed. The describe tool decodes greedily from the cached tokens with at most 512 new tokens. Tool signatures and the answer fields are listed in Appendix F.3.

Services. Each model service holds one loaded instance and returns HTTP 503 when the model stays busy for more than one second or runs out of GPU memory, rather than queueing without bound.

Live semantic map. Zones are directed floor-plan polygons at 0.05 m per pixel. Every 10 s, the map asks the agent, once for each robot it has seen, whether there is traffic at that robot’s position and colors the zone as traffic or clear. The agent runs with reasoning enabled.

## Appendix C Describe-on-Demand and Reconstruction

Describe-on-demand run. In a separate 150-frame run, each frame is encoded once by the Cosmos3-Edge vision encoder, and its cached tokens are decoded with three prompts: the detection prompt of Appendix F.1 (at most 256 new tokens), a general scene-description request (512) and a one-word yes/no question (16). Decoding is greedy with reasoning disabled, and each prompt gets a single attempt. The same frame and prompt are also run through the unsplit model. Two outputs match when the decoded strings are equal after trimming surrounding whitespace; all 450 frame–prompt pairs match. Times are wall-clock after one warm-up and include tokenization and image preprocessing.

Reconstruction run. Each of the 150 traffic frames is repeated five times into a $5\times 480\times 832$ input, encoded, and reconstructed from its stored BF16 latent; reconstruction time is a median over frames.

## D.3 Fleet Model

Notation. Let $N$ be the number of robots and $r=1/12$ s-1 the write rate of one robot, one memory every 12 s. An operating day is $h_{\mathrm{op}}=28{,}800$ s (8 h), so a robot writes 2,400 memories per day. Service times are $t_{\mathrm{cap}}=4.35$ s for original captioning and $t_{\mathrm{desc}}=1.25$ s for describing a memory from cached tokens, both means, and $t_{\mathrm{insp}}$ for scene inspection, kept symbolic. Per new memory, $p$ is the mean number of descriptions and $q$ the mean number of inspections; $p=0.1$ and $p=0.01$ mean one description for 10% and 1% of memories. The live map polls every $\tau$ s (10 s by default), and $u_{a}$ is the rate of map updates one GPU completes while answering 95% of them within two polling periods, 20 s. One GPU serves at least 24 robots within this limit (Tab. 10), so $u_{a}\approx 2.4$ updates/s. Unlike the serialized description terms, $u_{a}$ is a batched serving rate. A memory keeps $b=546.1$ kB of objects and a 3.2 kB index row, and $D$ is the retention in days. A GPU equivalent is the serialized service time offered per second, so one equivalent is one fully busy GPU.

## Appendix E Traffic Evaluation

Dataset. The evaluation set is 914 consecutive RGB frames of one warehouse simulation run from a single ego robot. Of the 607 traffic frames, 289 are low severity and 318 are high; 307 frames are clear.

Embedding verdict. Each class has an ensemble of short text prompts (Appendix F.1). Their Cosmos-Embed1 text embeddings are mean-pooled and renormalized into one vector per class, and a clip is labeled by whichever class vector its video embedding is closer to. The verdict is written to memory as one sentence.

Caption arms. The Cosmos3-Edge detection and description arms run at temperature 0 with reasoning enabled and 2,048 output tokens each. Detection returns one JSON array of {label, bbox_2d} objects in normalized 0 to 1000 coordinates. A response that does not parse, or has the wrong keys, a generic label or an out-of-range or misordered box, is re-asked with the shorter correction prompt, for up to three attempts in total, and the frame is dropped if all three fail. Severity follows from the number of validated boxes: none is clear, one is low and two or more is high. Description asks for one sentence of at most 40 words. A description whose reasoning was cut off, or that exceeds the length limit, is dropped. The prompts are in Appendix F.1.

## Appendix G Training on Cached Representations

Fleet operation already performs the preprocessing that Cosmos3 training needs. Each memory stores the Cosmos3-Edge vision tokens $\mathbf{H}=f_{\phi}(\mathbf{x})$ and the Wan2.2 video latents $\mathbf{z}_{0}=\mathrm{VAE}(\mathbf{x})$ (NVIDIA, 2026a), so training reads both from the object store without moving or re-encoding video (Fig. 15). Cosmos-Embed1 queries select relevant events and diverse scenes for the training set. Over $E$ epochs on $M$ memories, the cache saves $EM$ forward passes of each encoder, and training compute goes only to the components being adapted: the language decoder, diffusion components or action heads.

Conditions.

• 

Frozen cache boundary. The learnable parameters of everything upstream of a cached tensor remain frozen through finetuning.

• 

Pinned encoders. Each artifact records its encoder version, preprocessing and tensor layout, and the consumer must match the Cosmos3 variant and vision interface that produced it.

• 

Shared latent space. The world model trains in the Wan2.2 VAE latent space. Another tokenizer needs re-encoding or a learned latent adapter.

• 

Targets. Recorded latents are self-supervised targets for the world model. Language training uses operator-validated answers attached to selected memories, and action adaptation needs synchronized, embodiment-compatible action targets.
