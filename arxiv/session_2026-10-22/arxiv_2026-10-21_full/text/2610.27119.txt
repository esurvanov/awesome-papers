Abstract

LLM agents perform tasks over multiple steps and revise their actions based on feedback. As the total reasoning budget is often limited and must support future steps, the agent must choose between short and long reasoning before each action.
Longer reasoning may improve the final task outcome by preventing later errors, but it also uses budget capacity that may be needed for future decisions.
This creates two challenges: estimating the downstream value of long reasoning and deciding when that value is worth using the remaining budget.
We propose Paired Outcome-guided Reasoning Allocation (PORA), which learns this decision by comparing short and long reasoning from the same interaction state. During training, PORA completes the task twice from each selected state, once with a short reasoning allowance and once with a long allowance, and compares their final quality and total processing to estimate when longer reasoning is valuable. During inference, a controller weighs this estimate against learned prices on remaining-budget pressure and chooses either short or long reasoning without running both alternatives.
We evaluate PORA across application, memory, code, retail, and mathematics tasks, achieving strong results across all settings. On BFCL memory, it exceeds the strongest existing method by 17.4–32.9 percentage points. Within the same agent, it matches or exceeds always using long reasoning on code and mathematics with 50.6% fewer actor tokens and 31.2% fewer model requests, respectively.

## 1 Introduction

LLM agents solve tasks by using tools, maintaining memory, and revising their actions in response to execution feedback (Yao et al., 2023; Shinn et al., 2023; Trivedi et al., 2024; Berkeley Function Calling Leaderboard, 2026). Under a finite episode budget, an agent must balance how much computation to allocate before each action. Specifically, a short reasoning allowance saves computation for later steps, while a longer allowance may help the agent resolve uncertainty before acting (Wei et al., 2022; Snell et al., 2025). For example, when updating a calendar with conflicting records, additional reasoning may prevent an incorrect write and the repairs that follow (Figure 1). However, the extra computation also consumes a finite episode budget that may be needed for later evidence acquisition and verification. The value of reasoning therefore depends on its effect on the rest of the task, not only on the current action. This raises an important question: given the current interaction state and the remaining budget, when is it worth using a longer reasoning allowance?

Figure 1: Deciding how long to reason at one step (illustrative). ❶ From the same state, short reasoning leads to a wrong write and two repairs, while long reasoning writes correctly; which is better is known only after the task ends. ❷ Long reasoning uses budget that later steps also need, so the same choice can help with ample budget and hurt with a tight one.

Since long reasoning is often wasted on easy inputs (Chen et al., 2025; Sui et al., 2025), existing methods choose reasoning budgets based on task complexity, plans, or confidence (Fang et al., 2025; Han et al., 2025; Lin et al., 2026; Fu et al., 2025; Lee et al., 2026). For agents, ARES estimates the effort needed for successful step completion (Yang et al., 2026), and TAB learns turn-level budgets from trajectory rewards under a global token constraint (Jali et al., 2026). Re-FORC estimates the reward available from additional thinking (Zabounidis et al., 2026).
These signals describe step difficulty, the payoff of further thinking, or the return of a whole trajectory, but none measures how the rest of an interaction changes when only the current allowance changes, with the interaction state and the subsequent policy held fixed.
Closing this gap raises two challenges.
❶ Quantifying the Benefit of Long Reasoning.
A longer allowance at the current state can change subsequent actions and observations. It may improve terminal quality by preventing downstream errors, or reduce total processing by avoiding later corrective work. Local step success and current-step token counts therefore cannot supervise this value, which has to be measured through the completed interaction.
❷ Choosing Long Reasoning Under a Shared Budget.
Even when longer reasoning helps, it uses capacity that later steps may need. The interaction state can therefore warrant different allowances depending on the remaining budget and the number of future decision rounds. An allocation rule must weigh the expected benefit of longer reasoning against this capacity pressure.

We propose Paired Outcome-guided Reasoning Allocation (PORA), which learns when to use short or long reasoning by comparing their outcomes from the same interaction state. To address ❶, during training we start two separate task executions from each selected state: one uses a short reasoning allowance (Preserve), and the other uses a long allowance (Spend). Both executions follow the same subsequent policy until the task ends, and we record their final quality and total processing. A small controller learns to predict the paired differences from the visible interaction history.
To address ❷, the controller turns the remaining budget and future decision rounds into two capacity-pressure terms and weighs them, with learned positive prices, against the predicted benefit. At inference, it makes a single choice at each step and does not run both alternatives. Pairs can be recollected under the updated controller, since it determines how preserved capacity is later used.
Overall, PORA enables an interactive agent to spend more reasoning when it is useful and save capacity when it is not.

We evaluate PORA across application, memory, code, retail, and mathematics tasks, achieving strong results across all settings. On three BFCL memory settings, PORA exceeds the strongest existing method by 17.4–32.9 percentage points. Within the same agent, PORA improves over always using the short allowance in all six settings with complete fixed-allowance runs, and on code and mathematics it matches or exceeds always using the long allowance while using 50.6% fewer actor tokens and 31.2% fewer model requests, respectively. Refitting the controller with targets shuffled across states lowers code success by 7.9 points, showing the value of learning from paired outcomes.
Our contributions are as follows:

• 

Problem. We formulate reasoning allocation in interactive LLM agents as a same-state comparison: a longer allowance is valued by its effect on final quality and later processing, under the same subsequent policy.

• 

Method. We propose PORA, which learns this value from paired executions and selects the allowance by weighing the predicted benefit against learned prices on remaining budget.

• 

Experiments. We evaluate PORA across application, memory, code, retail, and mathematics tasks, showing that it improves task success and processing efficiency over existing methods and fixed allowances, and we analyze the value of paired outcomes and capacity prices.

## 2 Methodology

## 2.1 Problem Formulation

An interactive LLM agent reasons before taking each task action. At decision $t$ , a controller observes the visible history $s_{t}$ , the remaining episode budget $b_{t}$ out of a total bank $B$ , and the remaining decision rounds $N_{t}$ . It chooses between a short reasoning allowance $\kappa_{s}$ (Preserve) and a long allowance $\kappa_{l}>\kappa_{s}$ (Spend). An allocation policy $\rho$ maps these inputs to a binary proposal and its allowance:

 $\displaystyle\widetilde{a}_{t}$ 
 $\displaystyle=\rho(s_{t},b_{t},N_{t})\in\{0,1\},$ 

(1)

 $\displaystyle\widetilde{\kappa}_{t}$ 
 $\displaystyle=(1-\widetilde{a}_{t})\kappa_{s}+\widetilde{a}_{t}\kappa_{l}.$ 

Here $0$ denotes Preserve and $1$ denotes Spend. Native phase and budget rules $\mathcal{F}$ map the proposal to a feasible grant $\kappa_{t}=\mathcal{F}(\widetilde{a}_{t},s_{t},b_{t},N_{t})$ , which may differ from $\widetilde{\kappa}_{t}$ . A fixed LLM actor acts under $\kappa_{t}$ , the observation extends the history, and $b_{t+1}=b_{t}-c_{t}$ , where the charge $c_{t}$ is the granted allowance or the realized use, depending on the interface.

Our goal is to allocate reasoning where it improves the completed task while preserving capacity for later steps. The task’s evaluator supplies terminal quality $Y$ , and we measure complete processing $C$ , in a declared unit such as tokens, from the current decision to termination. $C$ includes subsequent work such as retrievals, repairs, and failed requests, differing from the charges. The controller uses only information available before allocation.

## 2.2 Paired Outcome-guided Reasoning Allocation

## Overview.

Figure 2 shows PORA in three stages. Paired rollouts (\raisebox{-0.9pt}{\footnotesize1}⃝) measure how short and long allowances differ in terminal quality and complete processing, addressing ❶. A controller (\raisebox{-0.9pt}{\footnotesize2}⃝) learns to predict these differences and to price remaining-budget pressure. At inference (\raisebox{-0.9pt}{\footnotesize3}⃝), it weighs its predictions against the priced pressure, addressing ❷. Collection and training can be repeated as the policy changes.

Figure 2: Overview of PORA. \raisebox{-0.9pt}{\footnotesize1}⃝ From one checkpoint $(s_{i},b_{i},N_{i})$ , a Preserve branch and a Spend branch continue under the same policy $\rho_{k}$ ; their differences in terminal quality and complete processing give the paired targets $(q_{i},g_{i})$ . \raisebox{-0.9pt}{\footnotesize2}⃝ The controller learns to predict these targets from the visible history and learns the prices on the pressure terms $(O_{i},H_{i})$ through the direction label $d_{i}$ . \raisebox{-0.9pt}{\footnotesize3}⃝ At inference, the predicted gain is weighed against the priced pressure, and native rules map the proposal to a feasible grant $\kappa_{t}$ . The dashed arrow repeats collection and training under the updated policy. The calendar case is illustrative.

## Paired Supervision Collection.

The benefit of additional reasoning may appear several steps later. In the calendar example, a short allowance may leave a record conflict that causes later repairs, while a long allowance may resolve it before a write. We thus construct supervision from completed trajectories rather than local step success.

At training iteration $k$ , we collect decision checkpoints under an allocation policy $\rho_{k}$ , starting from an initial policy $\rho_{0}$ . For checkpoint $i$ , we restore the same history, environment, memory, budget, and random state into two isolated branches. One receives the short allowance (Preserve), and the other receives the long allowance (Spend). Both then follow $\rho_{k}$ until termination, so the branches differ only in the allowance at the checkpoint, and their later actions and observations can diverge as a consequence. The memory instances draw their checkpoints from synthetic fixtures under the native memory interfaces (Appendix A.3).

Let $(Y_{s,i},C_{s,i})$ and $(Y_{l,i},C_{l,i})$ be the terminal quality and complete processing of the short and long branches. They provide two regression labels and a training set:

 $\displaystyle q_{i}$ 
 $\displaystyle=Y_{l,i}-Y_{s,i},$ 

(2)

 $\displaystyle g_{i}$ 
 $\displaystyle=(C_{s,i}-C_{l,i})/Z_{i},$ 

 $\displaystyle\mathcal{D}_{k}$ 
 $\displaystyle=\bigl\{((s_{i},b_{i},N_{i}),(q_{i},g_{i}))\bigr\}_{i=1}^{M_{k}}.$ 

 $M_{k}$ denotes the number of pairs and $Z_{i}=\max(C_{s,i},C_{l,i},z_{\min})$ , with $z_{\min}>0$ , normalizes processing. Positive $q_{i}$ means that long allowance improves terminal quality; positive $g_{i}$ means that it saves complete processing despite allowing more reasoning now. For a tradeoff $\lambda\geq 0$ , $q_{i}+\lambda g_{i}$ equals the difference between the branch utilities $Y-\lambda C/Z_{i}$ of the long and short branches. Each branch runs once, so $(q_{i},g_{i})$ is a single-sample estimate of the expected paired difference under $\rho_{k}$ , whose conditional mean is estimated below.

## Controller Training.

The controller needs to recognize relevant evidence and unfinished work from the visible history. Let $u^{\mathrm{task}}$ be the task text and $u^{\mathrm{plan}}$ a textual evidence plan describing the evidence the task requires; both are visible from the first decision. A frozen pretrained encoder $E_{\psi}$ embeds these texts and the observations already returned by tools. We construct a compact controller representation as

 $\displaystyle e^{\mathrm{task}}$ 
 $\displaystyle=\operatorname{norm}\!\left(E_{\psi}(u^{\mathrm{task}})\right),$ 

(3)

 $\displaystyle e^{\mathrm{plan}}$ 
 $\displaystyle=\operatorname{norm}\!\left(E_{\psi}(u^{\mathrm{plan}})\right),$ 

 $\displaystyle x_{\phi}(s)$ 
 $\displaystyle=[r(s);\,f(s);$ 

 $\displaystyle\operatorname{proj}_{\phi}(e^{\mathrm{task}},e^{\mathrm{plan}});\,\omega(s)].$ 

Here $\operatorname{norm}$ denotes L2 normalization, also applied to observation embeddings, and the brackets denote concatenation. The features $r(s)$ summarize cosine similarities between the task, plan, and accumulated or recent observations, capturing evidence relevance. The feedback features $f(s)$ summarize interaction progress and tool successes or failures. The function $\operatorname{proj}_{\phi}$ concatenates learned affine projections of the task and plan embeddings, providing semantic context beyond their similarity summaries. Finally, $\omega(s)$ records visible obligations, such as missing evidence, pending writes, or repair needs. The budget quantities do not enter $x_{\phi}(s)$ ; they affect the decision only through the capacity terms in Eq. 6. Exact features, dimensions, and encoder configurations are specified in Appendix A.1 and the native recipes.

Two independent MLP heads read $x_{i}=x_{\phi}(s_{i})$ and predict the paired consequences:

 $\displaystyle\widehat{Q}_{i}$ 
 $\displaystyle=\widehat{Q}_{\phi}(x_{i})=\operatorname{MLP}_{Q}(x_{i};\phi_{Q}),$ 

(4)

 $\displaystyle\widehat{G}_{i}$ 
 $\displaystyle=\widehat{G}_{\phi}(x_{i})=\operatorname{MLP}_{G}(x_{i};\phi_{G}).$ 

The quality head estimates the terminal-quality gain $q_{i}$ , and the processing head estimates normalized complete-processing savings $g_{i}$ , both for the long allowance relative to the short one. Their parameter blocks $\phi_{Q}$ and $\phi_{G}$ are independent. Separate outputs keep quality and processing interpretable and allow an explicit tradeoff when choosing an allowance. The trainable parameters $\phi$ comprise the semantic projections, the two heads, and the capacity prices introduced below; through Eq. 7, they define the allocation policy $\rho_{\phi}$ .

To train both consequence estimates and allowance selection, we combine two regression losses with an allocation-direction loss. Let $U_{i}=U_{\phi}(s_{i},b_{i},N_{i})$ be the capacity-priced allocation score of Eq. 6, with pressure terms $O_{i}$ and $H_{i}$ computed from $(b_{i},N_{i})$ . The shared per-example loss is

 $\displaystyle\mathcal{L}_{i}(\phi)={}$ 
 $\displaystyle w_{Q}\ell_{Q}(\widehat{Q}_{i},q_{i})+w_{G}\ell_{G}(\widehat{G}_{i},g_{i})$ 

(5)

 $\displaystyle+w_{D}\ell_{D}(U_{i}/\tau,d_{i}).$ 

We minimize the mean of these losses over $\mathcal{D}_{k}$ . The first two terms fit the observed quality and processing differences. The third is binary cross-entropy with logits on the direction label $d_{i}=\mathbf{1}[q_{i}+\lambda g_{i}>\delta]$ , which indicates whether the observed utility difference favors the long allowance by more than a margin $\delta\geq 0$ ; $\tau>0$ scales the score, and the weights $w_{Q},w_{G},w_{D}$ control the loss contributions. The direction loss back-propagates through the projections, both heads, and the prices, and it is the only term that trains the prices. Since $d_{i}$ already reflects downstream budget effects under $\rho_{k}$ , the prices act as a learned correction, fitted to the extent that $O_{i}$ and $H_{i}$ explain direction errors left by $\widehat{Q}_{i}+\lambda\widehat{G}_{i}$ . Actor and encoder weights remain frozen. Appendix A.3 specifies regression choices, label margins, tie handling, sample weighting, and additional task-specific loss terms.

After fitting, we select parameters $\phi_{k+1}$ with an instance-specific rule and set $\rho_{k+1}=\rho_{\phi_{k+1}}$ . We can then collect new checkpoints and paired continuations on training tasks under $\rho_{k+1}$ . This refresh matters because changing the continuation changes how preserved capacity is later used, and hence the labels to be predicted. Choosing Spend exactly when the expected paired utility difference under $\rho_{k}$ is nonnegative is the improvement step of rollout-based policy iteration (Lagoudakis and Parr, 2003); the controller approximates this step from visible inputs, and the capacity terms calibrate it to current budget pressure. Algorithm 1 and Appendix A.4 specify the loop; the application instance uses one recollection round.

## Online Inference with Capacity Pricing.

At inference, we encode the current visible history and construct $x_{t}=x_{\phi}(s_{t})$ using the same representation as in training. Relative to a short allowance, the two heads estimate the long allowance’s terminal-quality gain, $\widehat{Q}_{\phi}(x_{t})$ , and normalized complete-processing savings, $\widehat{G}_{\phi}(x_{t})$ . These are predictions of the paired consequences; inference does not execute either paired rollout.

A predicted benefit must also justify using capacity needed by later steps. In the calendar example, resolving a conflict now must leave budget for subsequent evidence acquisition and verification. We therefore derive two pressure terms in $[0,1]$ from the remaining budget and rounds (Eq. 10). $O_{t}$ measures the extra commitment $\kappa_{l}-\kappa_{s}$ relative to $b_{t}$ , scaled by the share of rounds still to come. $H_{t}$ measures how far the budget left after a long grant falls short of funding short allowances in all future rounds, relative to $B$ . Both vanish at the final decision. The allocation score is

 $\displaystyle U_{\phi}(s_{t},b_{t},N_{t})={}$ 
 $\displaystyle\widehat{Q}_{\phi}(x_{t})+\lambda\widehat{G}_{\phi}(x_{t})$ 

(6)

 $\displaystyle-p_{O}O_{t}-p_{H}H_{t}.$ 

The first two terms combine predicted quality gain and processing savings using the tradeoff $\lambda$ . The learned positive prices $p_{O}=\operatorname{softplus}(\alpha)$ and $p_{H}=\operatorname{softplus}(\eta)$ scale the capacity penalties.
Writing $U_{t}=U_{\phi}(s_{t},b_{t},N_{t})$ , the controller proposes

 $\widetilde{a}_{t}=\begin{cases}1\ (\textsc{Spend}{}),&U_{t}\geq 0,\\
0\ (\textsc{Preserve}{}),&U_{t}<0.\end{cases}$ 

(7)

The native rules then give the feasible grant $\kappa_{t}=\mathcal{F}(\widetilde{a}_{t},s_{t},b_{t},N_{t})$ . The actor executes under $\kappa_{t}$ . The returned observation and the charge $c_{t}$ update the inputs for the next decision. This cycle repeats until termination with all parameters fitted (details in Appendix A.2).

## 3 Experimental Setup

The experiments address three questions. Q1: how does PORA compare with existing reasoning-budget and search methods in task success and processing cost? Q2: does state-dependent allocation improve over granting the same allowance at every step? Q3: how do the paired targets and the capacity prices contribute?

## Benchmarks and metrics.

We evaluate on five benchmarks covering seven settings. AppWorld (Trivedi et al., 2024) provides 417 application tasks scored by AppWorld.evaluate. BFCL memory (Berkeley Function Calling Leaderboard, 2026) provides 155 questions for each of three memory backends (key–value, vector, and recursive summary), scored by official validity. LiveCodeBench (LCB) (Jain et al., 2024) provides 126 programming problems with public and private tests. The retail domain of $\tau$ -bench (Yao et al., 2024) provides 40 customer-service conversations scored by the task evaluator and its assertion judge. MATH500 (Hendrycks et al., 2021) provides 500 problems with exact answer checking. We report the task success rate.

## Models and budgets.

The AppWorld actor is OpenAI gpt-oss-120b with a BGE-M3 encoder. All other settings use Google Gemma 4 31B IT with a MiniLM encoder. On AppWorld and BFCL, an episode has a bank of 8,192 reasoning tokens, a short allowance of 128, a long allowance of 1,024, and at most twenty rounds. The code, retail, and mathematics settings adapt the bank and allowances to their interfaces (Appendix C.3).

## Controller training.

Every setting uses the same controller architecture, with 2,400 to 4,960 trainable parameters, and fits its own weights. Paired rollouts come from public AppWorld training tasks, synthetic memory fixtures for BFCL, and earlier programming problems for LCB. The AppWorld and memory controllers are each fitted on no more than two dozen pairs; AppWorld uses one recollection round (Appendix A.3).

## Baselines.

Reasoning-budget methods decide how much the model reasons: Plan and Budget (Lin et al., 2026) and Certaindex (Fu et al., 2025). Search and rollout methods spend additional rollouts, branches, or tool calls: DORA (Wang et al., 2025), BATS (Liu et al., 2026), LATS (Zhou et al., 2024), and Forest-of-Thought (Bi et al., 2025). Each baseline keeps its own procedure and runs with the same actor model inside the benchmark’s tool interface (Appendix B).

## Controlled comparisons.

For Q2, we run the PORA agent with a fixed allowance: fixed Preserve always grants the short allowance, and fixed Spend grants the long allowance whenever the budget rules permit. These controls are complete for the three memory backends, LCB, $\tau$ -bench retail, and MATH500; on LCB and MATH500, all policies start from the same initial programs or solutions, and the LCB rerun of PORA from these programs again solves 93 of 126 problems. For Q3, we refit the controller with jointly shuffled targets, with absolute per-branch utilities in place of paired differences, with current-turn targets, and without the obligation features. We rescale the learned prices on vector memory, rescale the processing coefficient of a frozen MATH500 controller, and replay the 6,245 recorded AppWorld decision states with one term of Eq. 6 removed at a time.

## Cost.

Cost is the total number of model tokens, prompt plus completion, and the number of model requests. AppWorld totals count actor and encoder tokens on evaluated trajectories, and memory totals include memory preparation. Some recorded totals are lower bounds (Appendix C).

## 4 Results and Analysis

## 4.1 Comparative Results (Q1)

## Task success.

In Table 1, PORA reaches the highest success rate on AppWorld, key–value memory, vector memory, and LCB, and shares the highest rate on $\tau$ -bench retail. The margin is largest on BFCL memory, where PORA reaches 77.4%, 81.3%, and 81.3% on the three backends. These rates are 32.9, 31.6, and 17.4 points above the strongest external method in each setting. On AppWorld, PORA completes 129 of 417 tasks against 114 for Plan and Budget, a 3.6-point difference. On LCB and MATH500, PORA and the strongest external method are within one point of each other. MATH500 is close to saturation for this actor: even fixed Preserve solves 91.8% of the problems.

## Processing cost.

Figure 3 plots success against total tokens for the five settings in which several methods have recorded totals. In all five, the recorded total of PORA is below that of every search and rollout method. Plan and Budget records fewer tokens than PORA on key–value memory, recursive-summary memory, and LCB, as does Certaindex on LCB, with lower success in each case. On $\tau$ -bench retail, PORA, Certaindex, and Forest-of-Thought reach 72.5% with recorded totals of 3.3M, at least 10.5M, and 98.4M tokens. On AppWorld, where totals are recorded for PORA and Plan and Budget, PORA processes 67.3M actor and encoder tokens against 122.8M, a 45.2% reduction.

## Backbone generalization.

Across additional LLM backbones evaluated on BFCL memory (Appendix D), PORA consistently sustains its advantage over fixed allocations, demonstrating that the learned capacity trade-offs generalize beyond a single base model.

## 4.2 Effect of State-dependent Allocation (Q2)

Figure 4: Fixed and learned allocation in the same agent where all three token totals are recorded. Shading marks the region cheaper and more accurate than fixed Spend; hollow markers are lower bounds.

The fixed-allowance rows separate the allocation decision from the rest of the agent. Figure 4 places the three policies by success and actor tokens. On key–value memory, PORA reaches 77.4% with 6.76M tokens, against 73.5% for fixed Spend with at least 9.59M. On vector memory, it is 10.3 points above fixed Preserve and 6.5 above fixed Spend, with a token total between the two. On LCB, it solves 93 of 126 problems against 86 and 92 and uses 50.6% fewer actor tokens than fixed Spend. On MATH500, it solves 477 of 500 problems against 459 and 475 with 31.2% fewer requests than fixed Spend. In these four settings, PORA matches or exceeds fixed Spend at a lower recorded cost. Table 2 summarizes these results.

On $\tau$ -bench retail, the three policies complete 29, 28, and 28 of 40 tasks with nearly equal token totals (3.33M, 3.38M, and 3.30M), so the lower total relative to Forest-of-Thought is shared by the fixed-allowance agent.

## 4.3 Effect of Paired Supervision and Capacity Pricing (Q3)

## Supervision target.

On LCB, all supervision variants share the fitting problems, the initial programs, and the executor (Appendix C.4). As summarized in Table 2, jointly shuffling the quality and processing targets across states lowers the solved count from 93 to 83, a 7.9-point difference. Absolute per-branch utilities give 92. On recursive-summary memory, a 24-pair refit with shuffled or current-turn targets scores 2.6 and 1.3 points below the terminal-target refit. In a separate LCB refit, removing the obligation features lowers the solved count from 90 to 82, a 6.3-point difference.

## Capacity prices and processing coefficient.

Scaling both learned prices by 0.5 or by 2 on vector memory lowers success from 81.3% to 72.9% and 76.1% (Table 2). With a frozen MATH500 controller, scaling the processing coefficient by 0.5, 1, and 2 gives 475, 476, and 474 correct answers with 712, 689, and 655 requests (Table 3). A larger coefficient lowers the number of requests while correctness stays within two problems, so the processing term mainly adjusts cost.

## 5 Related Work

## Sequential computation allocation.

TAB treats multi-turn reasoning as a sequential budget problem, explicitly considers downstream dependencies and delayed feedback, and trains a budgeter with GRPO using accuracy and global token constraints (Jali et al., 2026). Its trajectory-level reward supplies a shared advantage to the turn-level allocation decisions. ARES predicts the minimum suitable reasoning effort from interaction history using labels for successful step completion (Yang et al., 2026). PORA instead compares two allowances from the same state under a common continuation policy.

## Predicting the value of reasoning.

Re-FORC predicts expected future reward as a function of additional thinking tokens and uses it for stopping and resource selection (Zabounidis et al., 2026). PORA instead predicts how two allowances change the rest of an interaction. Thinkless learns to select short or long reasoning, and Token-Budget-Aware Reasoning adjusts budgets according to problem complexity (Fang et al., 2025; Han et al., 2025). Budget forcing and length-controlled reinforcement learning set the length of a single reasoning trace (Muennighoff et al., 2025; Aggarwal and Welleck, 2025). Certaindex uses confidence signals to adapt computation, Plan and Budget allocates effort through a plan, and DART uses draft agreement and entropy to route thinking (Fu et al., 2025; Lin et al., 2026; Lee et al., 2026). PORA also prices the remaining episode budget.

## Tool use and search.

ReAct interleaves reasoning with actions (Yao et al., 2023); AppWorld and $\tau$ -bench evaluate longer tool-mediated tasks (Trivedi et al., 2024; Yao et al., 2024). LATS, DORA, BATS, and Forest-of-Thought allocate search, rollouts, or tool effort (Zhou et al., 2024; Wang et al., 2025; Liu et al., 2026; Bi et al., 2025). We compare with them as complete systems.

## Metareasoning.

Valuing computation by its expected downstream benefit has a long history (Russell and Wefald, 1991; Hay et al., 2012; Callaway et al., 2018). Rational Metareasoning for LLMs uses a value-of-computation reward with Expert Iteration to learn selective reasoning (De Sabbata et al., 2025). Rollout-based approximate policy iteration evaluates alternative actions from sampled states under a common continuation policy and learns an updated policy (Lagoudakis and Parr, 2003). PORA applies these principles to reasoning allowances in interactive tasks.

## 6 Conclusion

We presented PORA, which learns when an interactive LLM agent should use short or long reasoning by comparing the two allowances from the same interaction state. Paired executions measure how a longer allowance changes final quality and total processing, a compact controller learns to predict these differences, and learned prices on remaining-budget pressure turn the predictions into a feasible allowance. Pairs are recollected as the controller changes, since it determines how preserved capacity is later used. Across five benchmarks, PORA achieves strong task success; within the same agent, it matches or exceeds always using long reasoning on code and mathematics at lower cost, and shuffled paired targets lower code success.

## Limitations

Each task family uses its own fitted controller and native phase and budget rules, which are specified per interface. Paired collection requires restoring the environment, memory, and budget into two isolated branches and running both to termination, which adds training cost and is not available for every environment; the memory instances therefore draw their checkpoints from synthetic fixtures. Each branch is executed once, and some controllers are fitted on a few dozen pairs or fewer, so the paired targets are noisy estimates. The controller chooses between two allowances and does not consider finer-grained budgets. Most results use one actor per setting; with the additional actors in Appendix D, the differences between allocation policies are smaller.

## A.1 Feature construction and parameter accounting

## A.3 Fitting recipes

## Application fitting.

The initial collection has twelve paired checkpoints at steps zero and seven from six public-training tasks. Recollection visits six different tasks from the same scenario families and supplies ten decision-observable pairs. The selected updated checkpoint has two quality-informative pairs and eight quality ties. Both fits use 300 full-batch AdamW epochs, learning rate 0.001, weight decay 0.001, and gradient-norm clipping at one; the update initializes from the earlier controller.

The application quality label is the Spend-minus-Preserve difference in terminal success plus 0.25 times the difference in requirement completion. Because both heads end in $\tanh$ , labels whose magnitude exceeds one are fitted toward the saturated output. Processing is normalized by the maximum complete branch cost. The objective combines smooth-L1 quality loss, smooth-L1 processing loss, binary direction loss, and smooth-L1 utility loss with weights 1, 0.25, 0.25, and 0.25. Quality ties have quality-fit weight 0.25; their direction and utility paths detach the quality prediction so processing can receive the cost signal. Direction logits use temperature 0.25. These weights concentrate fitting on the paired quality contrast and the continuation-processing signal.

## A.5 Application instance

## State and encoder.

AppWorld uses normalized 1,024-dimensional BGE-M3 embeddings. The six obligation slots contain required-source coverage, required-source count divided by eight and clipped at one, pending-write status, execution-failure fraction, last-execution failure, and successful-state-change status. Returned records update these fields before the next allowance.

## Native execution.

The bank is 8,192 committed reasoning tokens; short and long allowances are 128 and 1,024, with at most twenty rounds. Actor temperature is 0.6, top- $p$ is 0.95, context is 32,768, and each decision allows at most 2,048 additional answer tokens. The observation view takes the first 2,500 characters of each normalized response.

The phase becomes repair after an evidence-check rejection, two consecutive recovery-trigger events, or an acquisition with unchanged source coverage below $3/7$ . A pending write, a successful state change, complete source coverage, or at most three remaining rounds selects commit. Other states acquire evidence. Six prior Spend decisions enforce later Preserve decisions. One eligible repair may receive recovery Spend; ordinary spending requires coverage at least $3/7$ . Allowances are constrained by the remaining bank and charged in full.

The evidence-aware executor checks API names, fields, parameters, and the observed support of values. When a generated program has a valid read prefix, it can execute the longest qualifying top-level prefix to obtain evidence for a subsequent revision. The prefix contains an API call and passes the same support checks. AppWorld 0.1.3.post1 and AppWorld.evaluate define the final 417-task population and scorer.

## A.6 Memory instances

## Preparation and state.

Each method completes native prerequisite conversations before answering the mode-specific 155 questions. Key–value memory uses explicit records; vector memory uses bounded topic updates and similarity retrieval; recursive summaries use the official 10,000-character cap. The controller encoder is MiniLM with attention-mask mean pooling, a 512-position tokenizer limit, and embedding dimension 384.

The two anchors are the question and the plan to recover the requested fact through native memory tools. The adapter includes the most recent eighteen visible events. Tool returns have observation role 3; other dynamic events have role 2. The six obligation fields represent observed successful evidence, a source-load value of $1/8$ , a zero pending-write slot, tool-failure fraction, last-tool-failure status, and a zero state-change slot. These local fields feed the common graph in the same order.

## Action and scorer.

The native phase policy permits at most six ordinary Spend decisions and one eligible recovery Spend. Its source-coverage threshold is zero for the memory interface. The common bank is 8,192 with short and long allowances of 128 and 1,024 and at most twenty rounds. The core proposal is translated to the local short or long allowance. If the remaining bank cannot fund the long allowance, the executor attempts a complete short allowance; an insufficient short bank terminates. Granted allowances are charged in full. The official validity field scores every terminal answer. Shared-history scenario sizes are 30, 25, 25, 25, and 50.

## Code.
